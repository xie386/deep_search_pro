### Q1:**先读「大脑」**。主 Agent 和子 Agent 的 `system_prompt` 写在这里。理解：一个 Agent 的「人设」和「能力边界」是怎么用 YAML 描述出来的？为什么要把提示词放在配置里而不是写死在代码里？

A1:
YAML通过几个关键字段来塑造Agent：

name 和 description：定义了 Agent 的身份和专长。主 Agent 根据子 Agent 的 description 来决定将任务交给谁。

system_prompt：这是定义“人设”的核心。它详细描述了 Agent 的角色、职责、工作原则和限制，以此约束其行为和思考方式。

tools：明确列出了 Agent 可以使用的工具，这定义了它的“能力边界”。一个没有绑定“数据库工具”的 Agent，就无法执行查询。

🤔 为什么要把提示词放在 YAML 配置里？
将提示词外置到 YAML 配置文件，而非硬编码在代码中，主要有以下好处：

降低维护成本，方便迭代：修改 Prompt 是 Agent 开发中最频繁的操作之一。如果 Prompt 写在代码里，每次调整都需要修改代码文件，增加了出错风险和发布成本。而放在 YAML 中，修改提示词就像编辑文档一样简单，无需触碰核心代码，大大降低了维护成本。

实现关注点分离，让代码更干净：这是一种优秀的工程实践。YAML 文件专门负责定义 Agent 的“个性与知识”（system_prompt）和“配置”（tools），而 Python 代码则专注于实现“能力”（工具的具体逻辑）和“流程”（如何调度）。这使得项目结构清晰，易于理解和分工。

便于复用和组合，构建复杂系统：你可以为不同的场景（如客服、编程助手）编写不同的 YAML 配置文件，而复用同一套调度代码。在 deep-search-pro 中，正是通过这种方式，用一套代码框架搭配不同的 YAML 配置，就组合出了主 Agent 和三个各具功能的子 Agent。

对非技术人员更友好：YAML 文件易于阅读和编写。产品经理、运营人员或提示词工程师可以直接修改 YAML 文件来调整 Agent 的表现，无需了解背后的代码逻辑，从而促进了团队协作。


### Q2:配置是怎么被代码读进来的？注意 `yaml.safe_load` 比 `load` 安全（防执行注入）。输出 `main_agent_content` / `sub_agents_content` 两个字典。
A2:
获取配置文件:
yaml.load() (不安全)：它的设计初衷是强大的对象重构。为了能还原YAML文件中的自定义Python对象，它允许在解析时创建并执行任意的Python对象和方法。这等同于赋予了YAML数据“编程”的能力。

yaml.safe_load() (安全)：它的设计初衷是安全地解析数据。它将解析能力限制在一个安全的子集，只允许创建基本的Python数据类型，如字符串、整数、列表和字典。任何尝试创建函数、类或执行代码的操作都会被阻止。
再通过基本的字段提取得到主 Agent 和子 Agent 的配置。

### F2 deepagent
`deepagents` 是 LangChain 官方推出的一个“**开箱即用**”的 Agent 开发包。它和 LangChain 的关系不是替代，而是**分层**的：LangChain 是底层的“**框架**”，而 `deepagents` 是基于它构建的一个“**高级封装**”或“**智能体套件**”。

你可以把 LangChain 提供的 Agent 看作是**基础的“引擎”**，而 `deepagents` 则是基于这个引擎，为你**预先装备好了一切**的一辆“**整车**”。

### 🆚 核心区别对比

| 维度 | LangChain Agent (`create_agent`) | `deepagents` (`create_deep_agent`) |
| :--- | :--- | :--- |
| **定位** | **Agent 开发框架** | **Agent 套件 (Harness)** |
| **核心理念** | **极简、不预设 (Un-opinionated)**。提供最基础的 Agent 循环（LLM调用工具），把最大的灵活性和控制权交给开发者。 | **有主见、最佳实践 (Opinionated)**。内置了官方团队总结的上下文管理、任务规划等最佳实践。 |
| **内置功能** | **极少**。只提供最核心的抽象。 | **丰富**。开箱即用地集成了以下关键能力：<br>- **文件系统**：用于管理上下文，避免对话窗口过载。<br>- **子智能体**：可委派子任务，在隔离的上下文中运行。<br>- **记忆系统**：让 Agent 能在多次运行间学习和改进。<br>- **技能 (Skills)**：可按需加载的指令和脚本。<br>- **任务规划**：提供规划工具来处理复杂任务。 |
| **代码量与上手难度** | **代码量大，门槛高**。需要开发者自行实现文件系统、子Agent调度等配套功能。 | **代码量少，上手快**。通过 `create_deep_agent` 一行代码即可创建，大幅减少样板代码。 |
| **灵活性** | **高**。你可以完全自定义 Agent 的每一个环节。 | **中等**。封装了最佳实践，但依然保留了通过`tools`、`middleware`等方式进行深度定制的入口。 |
| **适用场景** | 需要**高度定制化**、对 Agent 行为有**精细控制**的复杂项目。 | 希望**快速构建**一个能处理真实、复杂任务的 Agent，而不想从零搭建所有基础设施。 |

### 🏗️ 技术架构：三层结构

为了更好地理解，可以看下 LangChain 生态中这三者的关系：

*   **底层 (LangGraph)**：**Agent 运行时 (Runtime)**。负责 Agent 的底层执行、状态管理和持久化。
*   **中层 (LangChain)**：**Agent 框架 (Framework)**。提供模型、工具、Agent 循环等核心抽象与集成。
*   **顶层 (Deep Agents)**：**Agent 套件 (Harness)**。基于中层的 `create_agent` 构建，打包了文件系统、子智能体等最佳实践，提供一个可直接用于生产的“成品”。

### 💡 如何选择？

*   用 **LangChain Agent**：当你需要从零开始，精细控制 Agent 的每一个细节，或者你的应用场景非常独特，不适合套用通用方案时。
*   用 **Deep Agents**：当你希望快速搭建一个功能强大的 Agent，并且信任 LangChain 团队总结的最佳实践时。它特别适合构建“深度研究”、代码编写等复杂任务型 Agent。

简单来说，**Deep Agents 让构建强大 Agent 的门槛变得更低，让你能更专注于应用本身的业务逻辑**。三者之间也可以灵活组合使用。
