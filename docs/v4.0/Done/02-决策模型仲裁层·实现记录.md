## 一、问题（现象 + 证据）

**现象**：工具路由的召回已经够好，但"**定下第一个**"这一步会错——尤其是多步链题，失败姿势高度一致：都选了链条的**首步**。

**证据**（2026-10-12 两期实验，`research/02-Jev仲裁层.md` §十八 / §二十）：

- 第二期真机池轨道：top3 里含正解 23/23（召回满分），但 `precision@1` 只有 0.826；
- 4 道失分题里 3 道是"自信题"（路由器自己认为很确定），说明阈值机制救不了它们；
- 链题失手姿势一致：`trip-tickets` 应选 `get-tickets` 却选 `get-current-date`、`trip-transfer` 应选 `get-interline-tickets` 却候选咬死在首步。
- 另有一条结构性证据：决策模型对同一输入是**确定函数**（重复调用概率差 1e-9），所以"同一句问题重复付费"是纯浪费 → 缓存有明确收益。

## 二、功能（做成什么样）

候选互相咬住时，**多问一次决策模型**来定顺序；其余一切照旧。

- 默认关闭；开启后只影响"工具怎么被想起"，**不参与能不能执行**（铁律）。
- 只在**近并列**时触发（融合分间距 < 门限），因此绝大多数请求零成本、零延迟。
- 同一句问题 24 小时内只问一次（缓存），过期作废并删除。
- 开关在**前端 AI 对话区**，按账号生效；`.env` 只留模型与凭据。
- **03 路由质量测评期间强制关闭**，与开关状态无关（否则测评数字与历史基线不可比）。

## 三、方案（首批四件 + 三处运行约束）

来源：`../v4.0规划文档.md` §02 ③ 段第 1~14 条 · 裁定 1~6。

1. **精排**：`near_tie` 触发（门限 `0.0005`）→ 只改写候选顺序，渲染路径原样复用；
2. **缓存**：键 = 账号 + 归一化问题 + 池版本 + 素材指纹 + 模板版本 + 模型；**时效 24 小时**；
3. **计量**：每次精排落一条审计（选择、概率、间距、耗时、是否命中缓存、池版本）；缓存命中单独计数；calls_today 供预算闸门；
4. **fail-safe**：未启用 / 未触发 / 不可用（超时、无额度、形状错、限流、预算用尽、任何异常）一律返回 None，调用方行为逐字等于现状；
5. **开关**（裁定 6 同批）：账号级字段 `accounts.decision_router` + 前端按钮，不走 `.env`；
6. **测评隔离**：`/api/chat?probe=1` → `allow_decision=False` → 不参与、不读不写缓存。

### 5.4 缓存时效与断服（临时把 TTL 压到 2 分钟实测）

| 步骤 | 时刻 | 观测 |
|---|---|---|
| 写入（服务在跑） | 01:19:57~58 | 清掉旧记录 → 真调（`cached=false`）→ 落缓存 `ts=01:19:58`；紧接着同句再问命中（`cache_hit`，309 ms） |
| 对照组：换新进程、时效内 | 01:20:08 | 命中（`cached=true`），缓存记录未被重写 |
| 断服 2 分 41 秒 | 01:20:14 → 01:22:55 | 端口全程无监听；缓存文件与审计条数原封不动 |
| 重启服务 | 01:23:09 | 重启那一刻过期记录仍在文件里（启动不碰缓存） |
| 重启后同句再问 | 01:23:18~19 | `cache_compact dropped=1 kept=0` → 未命中 → 真调（975 ms）→ 新缓存 `ts=01:23:19` |

结论：有效期**不依赖内存、只依赖文件里的 `ts`**；断服本身不影响"跨重启仍然有效"（对照组已证），超时后过期记录被**真删**并重新决策。

## 六、踩坑与偏差（现象 → 证据 → 根因 → 验证）

1. **选项键写成路由器内部键 → 决策模型判断漂移。** 内部键对 ref 自带前缀的条目会变成 `mcp:mcp:12306-mcp/...` 双层，与调研期实测/题库形态不一致（真机审计里能看到 v1/v2 两批 choice 形态不同）。根因：选项键直接用了映射键。改法：选项键改用显示键 `e.ref`、回填时映射回内部键，并把 `STATE_TEMPLATE_VERSION` 从 v1 升到 v2。
2. **审计记录缺 `ts` → 每日预算闸门恒判 0。** 现象：审计已 30 条而 `calls_today=0`。根因：`audit()` 没补时间戳，而 `calls_today()` 靠"本行含今日日期串"计数（还有"问题文本里带日期就误计"的隐患）。改法：`audit()` 自动补 `ts`，`calls_today()` 严格解析 JSON 且只认 `event=="call"`；补两个回归用例。
3. **离线脚本污染真机审计。** 现象：审计里 30 条"真机记录"其实全是脚本跑的，导致一度把脚本数据当成用户真机数据来解读。根因：脚本与服务的审计/缓存路径相同。改法：审计/缓存路径支持环境变量覆盖，脚本写自己的文件；并把这条写进脚本注释。
4. **"调用了但没触发"在审计里不可区分。** 现象：用户提问后审计文件一条没变，无法判断是"没走到"还是"走了没触发"。改法：开关一开就落一条 `seen`（含 `fired` 与不触发原因、间距），可用 `DECISION_AUDIT_SEEN=0` 关掉。
5. **对账脚本没跟上开关改版（静默失效）。** 现象：开关改成账号字段后，对账跑出"什么都没改"（19/23 → 19/23，`enabled=false`）。根因：脚本仍按 `.env` 变量判断开关。改法：脚本在进程内强制打开（不写库）；重跑回到 19/23 → 22/23。
6. **`probe` 用在错的作用域（最危险的一个）。** 现象：`probe` 被写在 `_run_agent()` 里，而它是 `/api/chat` 的参数 → `NameError` 会被外层 `try/except` 吞掉，后果是**工具简报整个不注入**（比"不生效"更糟）。改法：`_run_agent(..., probe=False)` 形参 + `asyncio.to_thread` 传参；CLI `cli/cmd_chat.py` 与调试脚本走默认值，行为不变。
7. **`tool_calls.jsonl` 半截行（非本大点引入）。** 现象：81 条里 1 条孤立 `'}}'`。根因：`api/monitor.py::report_tool` 用裸 `open(...,"a")` 追加，主对话线程与测评线程同时写会交错。改法：加进程内互斥锁 + 一次写整行；实测 20 线程 × 5 次 = 100 行、0 半截。已清掉历史半截行（82 → 81，备份在侧；被截断那条的头部已丢失，无法找回）。
8. **灰区不精排（实现期新增的省调用规则）。** 灰区题本就走全量简报（所有工具都给了模型），候选顺序不参与渲染，精排无增量，还会白花一次调用（实测：`trip-transfer` 的门限落点若触发就会"弄坏"，跳过它之后净收益多 1）。已写进代码与规划文档。
9. **缓存时效实验第一次白等 3 分钟。** 现象：`taskkill //F` 在该环境被当成字面量拒绝，服务其实没关。验证与改法：改用单斜杠 `/F`；重做实验，并把"服务是否真停"作为前置断言（`netstat` 查监听）。
10. **前端开关"点了没反应 / 徽标永远是已关"（根因：漏了 setup 的暴露列表）。** 现象：先表现为"轨道变绿、徽标仍写已关"，改成单向驱动后又变成"点击毫无反应"。根因：`front/index.html` 是 **in-HTML 模板**的 Vue 应用，模板只能看见 `setup()` **return 列表**里的名字；我加了 `decRouter` / `loadDecRouter` / `setDecRouter` 的状态、模板与初始化调用，**却没加进 return** → 模板拿到的是 undefined：三元表达式悄悄走 falsy 分支（徽标恒为"已关"）、事件处理器变成空操作（点了没反应）。证据：`grep` 显示 `digestAuto` 三处齐（模板 / setup 体 / 第 8572 行 return），而 `decRouter` 只在模板与 setup 体、return 里没有。验证：补进 return 后，用脚本核对"块内模板引用的标识符是否都已暴露"（结果：已暴露），harness 76/76。同类规矩本项目在 return 处自带注释（"模板里用到的每个标识符都要在这儿出现，否则静默失效"）。
11. **诊断时我自己给出的一个错误结论（已纠正）。** 现象：开关写入没落库时，我先断言"用户的进程是旧的、接口 404"。事实：直接打那个接口，GET 返回 401、POST 返回 422，说明**接口在**（是认证与参数校验），服务是新代码。改法：把"接口是否存在"作为**先验一次**的探测（curl 看 401 还是 404），别靠推断。

**当前实测暴露的真实失分面（第二批下一步的靶子）**：**灰区题选错**。样本 `city-basic`（"查一下广州这个城市的基本信息" → 被选成 `12306-mcp/get-stations-code-in-city`）：路由不确定 → 回退全量简报 → 决策层被"灰区跳过"规则挡下 → 失分发生在主模型从全量里选错。

**两条链路事实**（决定了杠杆在哪；★ 均经 2026-10-13 带自检复测确认，前一版结论是勘误）：

1. **`abilities_user` 本来就进向量**。它是数据库列，在**建条目时**并进 `e.abilities`（`capability_pool.py:358-361`：工具级用户描述顶掉自动摘要，来源级用户描述一起并入），而 `_entry_text()` 取 `name + keywords + abilities + 参数摘要`。上一轮"用户侧说明不进向量"是**错的**：`CapabilityEntry` 上根本没有 `abilities_user` 字段，当时那段核心代码改动是空操作（已撤回）。
2. **`keywords` 也进向量**（同上）。上一轮"关键词无效"同样是**缺自检的静默空跑**。带命中自检重测：给 `city` 的 `keywords` / `abilities` 各追加一句后，z 分从 `0.978` 动到 `0.995` / `0.972`，**名次不变** —— 两条杠杆都只有 ±0.02 的位移，**不足以翻转判定**，这才是"素材微调无效"的真实原因。

**灰区排名实测（2026-10-13，入库口径）**：`city-basic` 的期望工具 `mcp:city/search_city` 排 **第 2**（fused 0.0313 vs 站码工具 0.0315，**仅差 0.0002**）；`trip-transfer` 的两个期望工具排 **1 与 4**。两题都因 z 不达自信线（0.978 / 2.259 < 3.8）落灰区 → 按设计回退全量、由主模型定夺。**结论：这批失分是「0.0002 之差的邻位选择」＋「分数不达自信线」叠合**，灰区本就全给工具、精排无增量，所以决策层救不到；而在灰区裁剪工具池已被裁定 8 否决 → **唯一被允许的杠杆只剩素材层**（实测能翻转，但首版改法带坏 2 道）。口径提醒：去掉来源级描述另测时该工具会升到第 1 —— 两个口径不可混用。
