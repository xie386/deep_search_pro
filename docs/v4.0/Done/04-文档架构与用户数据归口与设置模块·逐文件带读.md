## 二、逐文件

### 1. `utils/paths.py`（路径唯一事实源，152 行）

- **关键行**：`47 ACCOUNT_DIRS`（7 个账号级根，三份互不一致的清单在这里合一）· `51 PROBE_ARTIFACT_DIRS`（测评水位线子集，**故意不含 `tts_ref` / `RAG_DB`**）· `64-96` 各路径函数（`memory_path` / `soul_path` …）。
- **位置**：所有账号级落盘的第一跳；`tools/probe_runner.py`、`api/*`、`tools/chat_images.py` 等 17 个生产文件都改问它。
- **检查要点**：`PROBE_ARTIFACT_DIRS` 少一项 → 清理测评水位线时会**误删音色素材或向量库**；`ACCOUNT_DIRS` 少一项 → `purge_account` 会漏清（历史事故：`tts_ref` 曾漏过）。
- **思考题**：为什么清单要「合一」而不是各模块自己列？三份不一致时，故障会以什么形态出现（提示：不是报错，是**静默漏清**）？

### 2. `scripts/migrate_user_data.py`（一次性迁移，259 行）

- **关键行**：`47 MOVES`（7 处 旧→新 映射）· `97 dry_run()` · `121 backup()` · `--apply` / `--restore`。
- **位置**：只跑一次的历史脚本，留在库里作**可复跑的回滚器**（不是日常工具）。
- **检查要点**：备份目录必须先落 `docs/v4.0/backups/user_data_move_<时间戳>/` 再搬；库内相对路径 `digest_reports.md_path`（34 行）要同步改前缀，否则周报证据链解析会断。
- **思考题**：为什么迁移脚本要自带 `--restore`，而不是「出问题就 `git checkout`」？（提示：`git` 不管 33.72MB 的用户数据）

### 3. `tools/schema_personal.py`（库结构）

- **关键行**：`298 CREATE TABLE app_settings`（键值对）· `305 CREATE TABLE verify_codes`（只存 `code_hash`）· `317 idx_verify_codes_acct` · `73 purge_account`（库行 + 文件侧 + 会话一次清）。
- **位置**：设置与验证码的落点；`purge_account` 是「一键注销」的地基。
- **检查要点**：`verify_codes` **不许出现明文码**；`purge_account` 的文件侧必须走 `ACCOUNT_DIRS`（否则新增目录会自动漏清）；`app_settings` 的 upsert 用 `ON CONFLICT(key)`。
- **思考题**：为什么验证码存哈希而不是加密？「5 次试错」写在库里的意义是什么（对比只在前端计数）？

### 4. `utils/settings.py`（设置读写，~340 行）

- **关键行**：`39 SPECS`（登记表＝前端表单的唯一事实源）· `150 get()`（库 → `.env` → 默认）· `262 save()`（**开关/参数进库**）· `301 apply_runtime_hooks()`（导入期常量热更）· `318 GROUP_LABELS`。
- **位置**：设置页的表单、读取、校验全从这里长出来；`decision_router._env()` 也从这里取。
- **检查要点**：① `get()` 的兜底顺序决定了「`.env` 能不能压住库」——**库值优先**，所以单测要显式隔离库（见第 9 条）；② 密钥类**不登记**（登记了就会出现在表单里）；③ `apply_runtime_hooks` 只对「导入期读取」的键有效（如 `ZX_ASSEMBLY_SOURCES`），其余改完即生效。
- **思考题**：为什么「开关落库、密钥留 `.env`」比「全落库」更安全？如果哪天要把密钥也落库，`all_values()` 的掩码逻辑够不够？

### 5. `utils/mailer.py`（邮件通道，~215 行）

- **关键行**：`38 USER_KEYS = ("QQMAIL", "SMTP_USER")`（QQ 键优先、老键兼容）· `55 _cfg()`（解析 + 冲突警告）· `127 quota_problem()`（24 小时滑窗）· `141 _friendly()`（异常归一 + **兜底抹掉授权码**）· `180 send()`。
- **位置**：`account_sec` 的发码、设置页的「发测试邮件」都只经过 `send()` / `send_code()`。
- **检查要点**：① `QQMAIL`/`QQMSTP` **只在 `.env`**，不进前端/库/回传/日志；② `_friendly` 里那句 `msg = msg.replace(code, "***")` 是**最后一道防线**（服务商回显也不许透传）；③ 配额按 `verify_codes` 的 24 小时行数统计，**0 = 不限**。
- **思考题**：为什么错误归一化要**认异常类型**而不是把 `str(e)` 直接甩给用户？（提示：用户看不懂 `SMTPDataError 550`，但看得懂「当日发信量超限」）

### 6. `api/settings_api.py`（三个动作，72 行）

- **关键行**：`31 _who()` · `36 get_all()` · `41 save()` · `59 test_mail()`（收件留空 = 发到项目发件箱自己）。
- **位置**：设置页的唯一 HTTP 入口。
- **检查要点**：审计只记**改了哪些键**，绝不记值（密钥可能在其中）；`test_mail` 的提示要能区分「未配置」与「调试模式」两种不发信原因。
- **思考题**：为什么「留空发给自己」比「必填收件人」更适合做通道自检？

### 7. `api/account_sec.py`（账号安全，348 行）

- **关键行**：`127 _issue_code()`（先查 60 秒重发，再过**发信配额**）· `157 _verify_code()`（未用/未过期/未超试错/匹配，通过即作废）· `215 send_bind_code()` · `301 _snapshot_account()` · `326 delete_confirm()`（密码 + 邮箱 + 确认词三闸）。
- **位置**：绑定/解绑/注销三条写路径，全部走临时账号验证。
- **检查要点**：① 配额检查的**位置**在重发检查之后（否则同一用途的第二次请求会先被 60 秒挡住、测不到配额）；② 注销**先快照再清除**，快照落 `docs/v4.0/backups/account_delete_<账号>_<时间戳>/`；③ 邮箱**全局唯一**（一邮箱一账号）。
- **思考题**：为什么换绑要「先解绑再绑定」，而不是双向验证一次到位？（提示：少一条「同时持有两个邮箱」的攻击面）

### 8. `tools/decision_router.py` · `utils/audit.py`（收口）

- **关键行**：`decision_router.py:39 _env()`（一处改问 `utils.settings`，覆盖该模块全部开关与参数）· `audit.py:19 write_event()`。
- **位置**：决策层的配置入口 + 全项目审计落点。
- **检查要点**：`_env` 是**唯一读取口**，别在别处再直接 `os.getenv` 决策参数；审计事件名要能按 `stream` 过滤（`data/audit/*.jsonl`）。
- **思考题**：为什么「一处收口」比「逐个改成 settings.get」更不容易漏？

### 9. `front/index.html`（设置页：样式块 + JS 段）

- **关键行**：`1988 .set-view .set-item`（条目描边盒）· `2018 .set-pix input`（018 像素开关）· `2039 .set-radio`（020 滑动单选）· `2067 .cust-card.danger`（深红危险区）· `4933 pickVal()`（单选写值，**必须进 `setup()` 的 return 列表**）。
- **位置**：设置页是**数据驱动**的——卡片与条目都来自 `/api/settings` 的 `groups`，前端不写死分组 id。
- **检查要点**：① **样式块必须在 `<head>`**：写在 `<div id="app">` 内会被挂载时连根替换掉，且**不报错**（本项目实际踩过，验法 `getComputedStyle('.set-item').borderTopWidth` ≠ `0px`）；② 单选各格要**等宽**（`flex:1 1 0`），否则滑块半格错位；③ 新增的状态写入函数一律要进 return 列表。
- **思考题**：为什么「删除登记项」就能让前端卡片消失，比在前端加一个 `v-if` 更好？

### 10. `tests/unit/test_mailer_config.py` · `tests/testclient/settings_account_e2e.py`

- **关键行**：单测 `12` 项（QQ 键生效 / 优先级 / 老键兼容 / 覆盖主机端口 / 未配回落调试 / 调试开关强制 / **报错不泄露授权码** / 配额 / 三用途文案）；e2e `32` 项（绑定 → 唯一性 → 分组与非法值 → 开关落库 → 测试发信 → 注销三闸 → 快照 → 会话失效 → 零残留）。
- **位置**：口径的看守者；e2e 全程用临时账号（`t_sec_*`）并 `atexit` 兜底自清。
- **检查要点**：① 单测**不能依赖 `app_settings` 为空**（真机库里可能有用户保存值 —— 本轮为此给 4 个文件加了「隐藏库值」隔离）；② e2e 的自清要**按本轮 STAMP 前缀扫全部临时账号**（只清主账号会在异常退出时漏掉第二个账号，实测漏过一次）；③ **客户端测试必须先快照设置再强制调试模式**，收尾**只回滚本次改动**——整表 `DELETE` 会抹掉用户的真实配置。
- **思考题**：为什么「测试自己清干净」要写成硬约束？（提示：调研 D6 —— 不清的话，清理会被单测反复重新污染）
