## 二、逐文件

### 1. `tools/web_workflows.py`（236 行）—— 本点的核心

- **关键行**：`71 budget_gate`（两道代码闸）· `121 pick_sites`（挑站点纯函数）· `146 web_search_only` · `180 browse_only` · `199 search_then_browse` · `50-53` 闸门状态与 `_TURN_KEEP`（只留最近 24 轮）· `109 _emit`（统一记账 + 进度上报）。
- **位置**：子 Agent 的**全部工具面**；两个底层 util 的唯一调用方。
- **检查要点**：
  - `web_search_only` 的签名里**没有 `urls`**、`browse_only` 的签名里**没有 `query`** —— 这是「情况②不许检索」的实现方式（不是提示词纪律）。改动签名时先想清楚这一点。
  - `budget_gate` 在**被挡回时不发起任何外部调用**（省钱也不浪费时间），且计数键是 `(账号, 会话, 轮次)` —— 计数挂在「轮次」上，所以下一轮自动清零；`_prune()` 防长跑进程内存膨胀。
  - 两个工作流各自在**检索那半段**调 `budget_gate`：`browse_only` 不调（它本来就不检索）。
- **思考题**：为什么把「去重 + 上限」放代码而不写进提示词？（提示：本点审计实测一轮 2 分钟发了约 30 次，提示词里明明写着 ≤5 —— **纪律写在对手看不到的地方就等于没写**）如果闸门改成「按天限额」，计数键该挂在哪一层？挂错会出什么故障？

### 2. `tools/browser_tool.py`（199 行）

- **关键行**：`36-38` 三个路径（`browser_venv` 解释器 / 跑手脚本）· `46 _active_llm`（模型解析）· `100 _proxy`（系统代理透传）· `106 browse_pages`（**util，不再有 `@tool`**）。
- **位置**：工作流 → 本文件 → 子进程跑手。
- **检查要点**：模型解析走的是**聊天侧同一处**判定（`api.customize.get_active_provider` / `get_provider_by_ref`）—— 曾经它自己查 `llm_providers` 把未启用的配置当生效配置，对没有自配的账号会直接拒绝。改这里时对齐「聊天侧用什么模型，浏览器侧就跟什么」。
- **思考题**：为什么密钥走 stdin 而不是命令行参数？（提示：命令行在进程列表与日志里可见）如果浏览器侧改用主 venv 的 Python 会怎样？（提示：browser-use 要替换 `pydantic_core`，而那份文件正被运行中的后端占用）

### 3. `scripts/browser_runner.py`（283 行）

- **关键行**：`93 _run_once`（一次浏览的完整编排）· `252 run`（收请求 / 归一化）· `270 main`（stdin 收 JSON、stdout 末行回 JSON）· `69 _profile_base` / `81 _cleanup_profile`（profile 归位与清理）。
- **位置**：独立进程内的执行体；被 `browser_tool.browse_pages` 以子进程调用。
- **检查要点**：三处本机特有的硬约束**不能删**——`--headless=new`（Chrome 155 已移除旧式 `--headless`）、`--no-sandbox`（受限令牌下建不了子进程，表现为 0.2s 静默崩溃）、`NO_PROXY=127.0.0.1,localhost,::1`（否则 CDP 被系统代理劫持）。`compat_json` 是「原生优先、上游明确拒时降级」的开关。
- **思考题**：为什么浏览器跑手要**独立 venv + 独立进程**，而不是「想办法把依赖塞进主 venv」？（提示：本点真实事故——装了它会让主 venv 卸掉 14 个包，而其中一个关键 `.pyd` 正在被运行中的后端占用）子进程方案为此付出了什么代价？

### 4. `agent/subagents/network_search_agent.py`（23 行）+ `prompt/prompts.yml`

- **关键行**：装配 12-14 行（`_TOOLS = [web_search_only]`，开关开则追加另两个）· `web_search_only` 分类映射见 `agent/usage_counter.py:53-55`。
- **位置**：主 Agent 用 **task** 调度本子 Agent；工具面在这里固定。
- **检查要点**：开关（`BROWSER_USE_ENABLED`）**在 import 期判定**——因为子 Agent 的工具列表是装配期固定的；关掉后子 Agent 只剩「只全网检索」，与升级前**等价**（这是可安全回滚的设计）。提示词侧：主 Agent 是**判别口径**（要一批网站的清单→①／要某个具体站的网址且要站内内容→③／已给地址或库里有的→②，另有「涉及具体网址必须经助手取证、禁止凭记忆」），子 Agent 只有一条铁律「只调点名的那一个工作流」。
- **思考题**：为什么判别口径写在**主 Agent** 而不写在子 Agent？（提示：本点踩过——把「整轮最多 2 次」写在子 Agent 的 system_prompt，可是反复重试的是**主 Agent**；写在被调度方，管不住调度方）如果把三个工作流拆成三个严格子 Agent，主 Agent 的提示词要怎么改？

### 5. `utils/settings.py`（384 行）

- **关键行**：`105 WEB_SEARCH_MAX_PER_TURN`（每轮检索上限，默认 15，0=不限）· `109 BROWSER_MODEL_REF`（浏览器侧模型引用，留空=跟随聊天侧）· `120 BROWSER_USE_ENABLED`（总开关，标了 `restart=True`）· `124/127/130/132`（步数 / 单次超时 / 最多站点 / 无头）。
- **位置**：设置页「🌐 浏览器抓取」组；前端表单与读值的唯一事实源。
- **检查要点**：总开关改动**需重启后端**（装配期生效），其余即时生效。`BROWSER_MODEL_REF` 的口径是「**全机同名**」——填的是模型配置里的名字，跨账号取同名配置。
- **思考题**：为什么「每轮检索上限」要做成设置项而不是写死 15？（提示：这个数是**防失控**的门限，不同任务类型下「合理上限」不同；写死会让调不动的人去改代码）

### 6. `agent/usage_counter.py`（422 行）

- **关键行**：`246 context()`（公开的上下文读取，供工作流取 `(账号, 会话, 轮次)`）· `53-55` 三个工作流名 → `KIND_INTERNAL`。
- **位置**：M4 的用量计数中间件；工作流内部对底层调用**显式** `record(...)`。
- **检查要点**：**不许出现双记**——工作流自身由中间件记成「内部工具」，底层真正花额度的调用（Tavily / 浏览器）由工作流显式记成「外部检索」。改动工作流时保持这个分工，否则用量页会把一次检索算成两次。
- **思考题**：为什么「内部工具」这个分类存在？（提示：M4 的口径是「要能回答这次为什么烧了额度」——如果不区分，工作流这层会把底层的账遮住）如果将来工作流内部串了三种外部调用，记账该怎么设计？

### 7. `agent/turn_ledger.py`（135 行）+ `api/server.py`

- **关键行**：`30 PLACEHOLDER`（中断占位文案）· `62 begin` / `76 end` / `88 recover`（台账三动作）· `api/server.py:510-518`（`_run_agent` 记台账）· `611-612`（启动时 `recover()`）· `1435`（开关变更落审计）。
- **位置**：`_run_agent` 里与 `agent_cancel.begin/end` **同一处**；`recover()` 在 startup 钩子。
- **检查要点**：`recover()` 必须**幂等**（处理完删文件）；`begin/end` 里的写盘**都有兜底**——台账写不进去也绝不能影响问答主流程（这条是单测逼出来的：早先 `begin()` 漏了兜底）。为什么需要台账：用户点中断走 `AgentCancelled` 能落占位，**进程被 kill 时走不到那条路**（详见 §三 故障史）。
- **思考题**：为什么「启动时补偿」比「关服时写占位」可靠？（提示：进程被强杀时关服钩子根本不执行）这个方案的代价是什么（提示：一轮开始到结束之间，台账文件每个进程都可能看到同一份残留）

### 8. `tools/decision_router.py`（含本点新增）

- **关键行**：`56 switch_on`（账号级开关，默认关；读库失败一律当关）· `419 maybe_refine`（`435` 是门禁：**开关关着直接 return，不会碰模型**）· `520 _FATAL_ERR_MARKS` · `525 _maybe_auto_off`。
- **位置**：工具池路由之后、候选近并列时的一次复核（大点 02 的层）。
- **检查要点**：`_maybe_auto_off` 只对**重试也不会好**的错误（402 无额度 / 鉴权 / 模型不存在）动手；普通错误（超时、形状不对）**不降级**——那些是瞬时的，关了反而白降级。审计写失败也**不许阻断**关闭动作（审计是记录，不是前置条件）。改特征表时别把 `http_402` 漏掉（有回归钉子）。
- **思考题**：为什么这条「自动关开关」要写在这个模块里，而不是在 API 层？（提示：只有这里知道失败是**什么原因**——API 层只看到「这一轮走完了」）自动降级与「用户手动关」在行为上等价吗？有没有用户会觉得被夺权？

### 9. 测试

- **关键行**：`tests/unit/test_web_workflows.py`（9 项：签名结构约束 / `pick_sites` 规则 / 记账不被遮蔽 / 降级）· `test_web_budget_gate.py`（7 项：去重 / 上限 / 换轮清零 / 跨会话独立 / 0=不限 / 被挡回不碰引擎）· `test_browser_tool.py`（20 项）· `test_web_prompt_modes.py`（4 项：提示词口径断言）· `test_turn_ledger.py`（6 项）· `test_decision_auto_off.py`（7 项）。
- **位置**：`tests/unit/`（全离线，不触网、不碰真库）。
- **检查要点**：本点新增的测试里有三条是**回归钉子**，改代码时别拆：① 「被挡回时不发起任何外部调用」；② 「台账写盘异常不抛」；③ 「特征表必须含真实遇到过的错误串」。另外 `test_decision_router.py::test_maybe_refine_error_is_fail_safe` 里加了**假库连接**——因为它的错误串正是 `http_402`，会走到自动降级，而单测不许碰真库。
- **思考题**：为什么「签名约束」要靠测试钉，而不是靠代码注释说明？（提示：签名是唯一不会随重构消失的约束；注释会被下一版的人当成过时说明删掉）

## 三、故障史（读代码时的背景）

真机会话「网搜测试」里，有一轮用户看到 Agent 说「准备开始查」然后**对话直接结束**。审计加上 `failure_events` 给出的结论是：后端在那一轮运行中**被重启**（两次 `BACKEND_PORT_TAKEN`），在跑的轮次没有任何回执就消失。这与用户是否手动中断无关，也与 Agent 逻辑无关 —— 现在由 §二 7 的台账 + 启动补偿兜住。同一批排查还发现「决策模型报余额不足，而开关在界面上是关的」：结论是那一刻库里开关**是 1**（门禁是硬的、全仓只有开关端点能改该字段），而开关的改动作当时没有任何留痕 —— 现在由 §二 8 的审计与自动降级覆盖。
