### 裁定 1：大点定位与「两条腿」的归属

| 项 | 内容 |
|---|---|
| **分叉点** | 路由改进经验怎么从「只对一个账号的池有效」变成可迁移；算法侧与词法侧各归谁 |
| **可选方案** | A 全做成用户端工具；B 全由开发者固化进代码；C **按性质分家** |

### 裁定 11（2026-10-10 实现期）：执行与判分之间的「临时原始记录」落 `data/sandbox/{用户名}/`

| 项 | 内容 |
|---|---|
| **分叉点** | 「执行」与「判分」是两个按钮、可能相隔很久（用户要去打分），中间的**原始记录**（逐题调用序列）存哪？执行完就清理掉的话，判分时无据可依 |
| **可选方案** | A 新建 `data/probe_runs/` 目录；B 存 `tests/test_out/`（开发目录，产品不该依赖）；C 存**已有的** `data/sandbox/{用户名}/`（该目录本来就在清理清单 `ARTIFACT_DIRS` 里 ✓）；D 判分前不清理（违背用户「其余产物删除」） |
| **裁定结果** | **C**：`run_cases()` 把原始记录写 `data/sandbox/{username}/probe_run_YYYYmmdd_HHMMSS.json`，**随即按水位线协议清理本轮会话/用量**；判分消费该文件；「写入大屏」时产出正式打分表 → 该临时文件随下一轮清理/水位线消失 |

### 裁定 12（2026-10-10 实现期）：打分表内附**机器可读 JSON 块**

| 项 | 内容 |
|---|---|
| **分叉点** | 判分/大屏/版本对比要从打分表读结构化数据；若只存 md，就得**解析 md**（脆弱）。而用户要求「其余产物删除」→ 不能另存一份 JSON 产物 |
| **裁定结果** | 打分表 md **末尾**附一段 ```` ```json ```` 块（本轮 run 元信息 + 判定 + 指标 + 逐题调用），并注明「机器可读（判分 / 大屏 / 版本对比用；请勿手改）」 |
