## 裁定 1（2026-10-16）：工作目录只做“外部真实目录”

| 项 | 内容 |
|---|---|
| **日期** | 2026-10-16 |
| **分叉点** | 工作目录要不要支持“项目托管的新目录”（即项目在某处统一创建并管理的一批目录） |
| **可选方案** | ① 只支持用户在磁盘上自己挑的外部真实目录 + 默认条目（账号沙箱）；② 同时支持项目托管目录（自动挂进清理链、备份与权限体系） |
| **裁定** | **①** —— 只做外部真实目录 + 默认条目（前端名「主页」） |
| **依据** | 用户 2026-10-16 拍板。托管目录会把“注销清理链 / 备份 / 权限”一并拖进来，而本步的目的是让 Agent 的工作位置**可见可控**，不是做文件托管 |
| **代价/备注** | 外部目录不进账号清理链 —— 创建 UI 明示风险三条（§06 ①） |

## 裁定 3（2026-10-16）：保护名单 fail-closed，且名单自身硬保护、所有写工具都过守卫

| 项 | 内容 |
|---|---|
| **日期** | 2026-10-16 |
| **分叉点** | `_保护名单.md` 读不到或解析失败时怎么办；名单文件自身可否被 Agent 删除；守卫只挂在删除上还是全部写操作上 |
| **可选方案** | ① 读不到就当无保护（放行）；② 读不到一律拒绝写；③ 守卫只挂 `delete_file`；④ 守卫挂**全部**写工具（含 `edit_file` 与 `mkdir`） |
| **裁定** | **②+④** —— fail-closed；名单自身**硬编码不可写不可删**；5 个新写工具与 `run_shell_command` 的 `mkdir` **都过守卫** |
| **依据** | 03 清理链的“水位线读不到就一行不删”教训；保护名单若能绕开等于没有保护 |
| **代价/备注** | 保护名单缺失属异常态（工作目录创建时即播种），拒绝写不会误伤正常使用 |

## 裁定 4（2026-10-16）：`edit_file` 增删改查合一；受保护文件上退化为只读定位

| 项 | 内容 |
|---|---|
| **日期** | 2026-10-16 |
| **分叉点** | “查”要不要单独做一个工具；`edit_file` 触到受保护文件时怎么处理 |
| **可选方案** | ① `edit_file` 只做改，另设 `read`；② `edit_file` 一工具承担读 / 改 / 加 / 删四种；③ 受保护文件可被 `edit_file` 修改 |
| **裁定** | **②** —— 一工具承担 `op=read|replace|append|delete`（整份读取仍由 `read_file` 负责）；触及受保护文件时**退化为只能读和定位**，其余 op 拒绝并说明原因 |
| **依据** | 用户 2026-10-16 拍板 |
| **代价/备注** | 工具数控制住（Agent 工具面越小越稳），同时权限不松 |

## 裁定 6（2026-10-16）：池归属只看“用户确认后的有效 `read_only`”（回归红线）

| 项 | 内容 |
|---|---|
| **日期** | 2026-10-16 |
| **分叉点** | 自配工具（CLI/API/MCP）初始识别为写、用户**强制确认为只读**后，改造成“只读池/写池”时它们还算不算只读 |
| **可选方案** | ① 按初始识别结果归属；② 按用户确认后的有效 `read_only` 标记归属 |
| **裁定** | **②** —— 只看用户确认后的有效标记。已被确认为只读的（原识别为写）工具**必须继续留在路由池**、能被纯对话唤起；以后新配的同理 |
| **依据** | 用户 2026-10-16 明确点名：尼古喵喵当前 4 个 MCP 服务器就是“初始判写 → 用户强制确认只读 → 进路由池”，本次改动不得把它们拽出路由池 |
| **代价/备注** | 实现期在 `tests/unit/test_capability_pool.py` 配专门用例钉住 |
