# 06 Agent工作目录前端可编辑可视化与写能力开发 · 裁定记录

> 本大点的分叉与纪律裁定汇总。技术方案见 `../v4.0规划文档.md` §06 ③；调研与取证见 `../research/06-Agent工作目录前端可编辑可视化与写能力开发.md`。
> 用词规定：本文不出现 `v1`/`v2`、`第一批`/`第二批`；分期一律表述为「本次实现」与「bug 维护与优化期」。

## 裁定 1：工作目录只做"外部真实目录"

**背景**：工作目录要不要支持"项目托管的新目录"（即项目在某处统一创建并管理的一批目录）。
**裁定**：不做。只支持用户在磁盘上自己挑的**外部真实目录** + 默认条目（账号沙箱，前端名「主页」）。
**依据**：用户 2026-10-16 拍板。托管目录会把"账号注销清理链 / 备份 / 权限"一并拖进来，而这一步的目的是"让 Agent 的工作位置可见可控"，不是做文件托管的网盘。
**代价**：外部目录不进账号清理链 —— 已在创建 UI 里明示风险。

## 裁定 2：默认条目命名「主页」

**背景**：默认工作目录（沙箱）在前端叫什么。
**裁定**：叫「**主页**」，不叫"默认工作目录"。
**依据**：用户 2026-10-16 拍板 —— 面向纯体验向用户，"默认工作目录"是开发者语言。

## 裁定 3：保护名单 fail-closed，且名单自身硬保护、所有写工具都过守卫

**背景**：`_保护名单.md` 读不到或解析失败时怎么办；名单文件自身是否可被 Agent 删除；守卫只挂在删除上还是全部写操作上。
**裁定**：① 读不到或解析失败 → **一律拒绝写**（fail-closed）；② 名单文件自身**硬编码不可写、不可删**；③ **所有写工具**（不只是 `delete_file`）以及 `run_shell_command` 的 `mkdir` 都过守卫。
**依据**：03 清理链的"水位线读不到就一行不删"教训；把保护名单设计成"可被写工具绕过"等于没有保护。

## 裁定 4：`edit_file` 增删改查合一；受保护文件上退化为只读定位

**背景**："查"要不要单独做一个工具；`edit_file` 触到受保护文件时怎么处理。
**裁定**：① `edit_file` 一个工具承担**读内容 / 改内容 / 加内容 / 删减内容**四种能力（`op=read|replace|append|delete`），整份读取仍由 `read_file` 负责；② 触及受保护文件时**退化为只能读和定位**，其余 op 拒绝并说明原因。
**依据**：用户 2026-10-16 拍板。

## 裁定 5：`agents_docs/` 是画像目录专属，其他写工具不得越界

**背景**：`user_data/agents_docs/` 里的文件在前端不可见（"Agent 看得见、用户看不见"的真正位置），要不要一并白盒化。
**裁定**：不。该目录仍由 `readtofile` / `writetofile`（`read_agent_doc` / `write_agent_doc`）**专属管理**；新写工具与自配写工具**一律不得读写**该目录；工作目录面板**不暴露**该目录。药喵账号下的 3 个 office 文件**移入沙箱**（已执行）。
**依据**：用户 2026-10-16 拍板 —— 画像目录是既定的专用文件夹，边界一旦开口就失守。

## 裁定 6：池归属只看"用户确认后的有效 read_only"（回归红线）

**背景**：自配工具（CLI / API / MCP）初始识别为写、但用户**强制确认为只读**后，新版本改造成"只读池 / 写池"时，这些工具还算不算只读。
**裁定**：算。池归属判定**只看用户确认后的有效 `read_only` 标记**，**不看**初始识别结果。已被确认为只读的（原识别为写）工具**必须继续留在路由池**、能被纯对话唤起；以后新配的同理。
**依据**：用户 2026-10-16 明确点名 —— 尼古喵喵当前 4 个 MCP 服务器就是"初始判写 → 用户强制确认只读 → 进路由池"，本次改动不得把它们拽出路由池。实现期配专门测试钉住。

## 裁定 7：写工具"始终挂载 + 运行期闸"，不按轮装配

**背景**：写工具是否只在「/」选中时才装进 Agent。
**裁定**：**始终挂载**，靠**运行期闸**（中间件）在调用时判断"本轮是否经「/」选中"，未选中直接中文拒绝、不执行。
**依据**：`api/server.py:247-254` 的 `AGENT` 是**模块级单例**，工具面在导入期固定（§十 10.2 取证）；按轮装配需要改框架结构，代价远大于一道中间件闸。

## 裁定 8：workflows 用"代码逐步驱动"的编排器；本次只做只读型

**背景**：workflow 的步骤由谁驱动 —— 写进提示词让 Agent 自行安排，还是代码逐步驱动。
**裁定**：**代码逐步驱动**（照周报引擎的编排器形态与测评跑手的签名形态）：一步做完、校验该步产出、再放下一步；Agent 只执行每一步。任一步失败**停在该步**、如实报错、不自动跳步。本次只做**只读型** workflow；写型 workflow 放到 **bug 维护与优化期**。
**依据**：周报引擎的既有成功形态；步骤写进提示词等于"又把推断权交回模型"。

## 裁定 9：03 测评产物搬出沙箱，与代码改动同批执行

**背景**：沙箱里混住着 03 测评的原始记录（`probe_run_*.json`）与画像快照（`profile_backup_*`），"沙箱白盒化"后这些会对用户可见。
**裁定**：搬到 `user_data/probe_artifacts/{账号}/`，**与实现期的代码改动同批**执行（先备份后搬移、跑完自检）；不单独提前搬（现在搬会打断判分与画像还原）。
**依据**：路径级取证见 §十 10.7（`utils/paths.py` / `tools/probe_runner.py` 五处同步点）。

## 裁定 10：本大点用词纪律

**背景**：方案与文档里出现"v1 / v2 范围""第一批 / 第二批"这类分期字眼。
**裁定**：**不出现**。分期一律表述为「**本次实现**」与「**bug 维护与优化期**」（写工作流在 bug 维护与优化期做）。历史版本号 `v2.0` 属事实陈述，正常使用。
**依据**：用户 2026-10-16 明确要求，且对本大点全部文档与代码注释生效。
