## 一、用户的初衷与构想（原话要点，逐条落）

1. **痛点**：路由质量的测评与修复，**相当一部分（尤其真机测评）只覆盖「尼古喵喵」一个账号当前的工具池**。换账号、或同一账号增减工具后，**没有可比性**，此前的结论不可直接迁移。
2. **要做的事分两条腿，性质不同**（这条是本次议题的**骨架**）：

   | 腿 | 内容 | 归属 | 谁来做 |
   |---|---|---|---|
   | **硬编码侧**（路由算法） | 把往期在「尼古喵喵」池上验证出来的**算法/阈值/表征经验**，直接改进**项目路由代码** | **项目代码**（全账号受益） | 开发者（我们）一次改到位 |
   | **词法侧**（工具素材） | 每个工具的「应用场景 + 方法介绍词段」（`keywords` / `abilities_user` / `name`） | **账号数据**（每账号不同） | **用户自维护**，工具负责测评与给建议 |

3. **词法侧要做成一个前端小模块**：在「🧩 技能与工具」里**平级于 CLI 面板 / 第三方 CLI / MCP / API** 增加一个**工具池测评模块**，模块内：
 - 记录**该账号自配置的全部工具**；
 - 记录**该账号当前的路由质量数据**（数据大屏）；
 - 按钮流程：**生成真机题目 → 测评 → 判分 → 入库（写回数据大屏）**；
 - **额度提前声明**：真机测评要消耗网络搜索额度，按钮上/弹窗里必须提前讲清；
 - 真机测评**只产出「工具调用记录表单」**，对错**由人工或 Agent 判分**（沿用 v3.1 的「脚本只记录、对错人工打分」制度）。
4. **后端多一个独立 Agent**：针对**当前账号工具池**的测评 Agent，**独立于主 Agent 体系**（不纳入 `main_agent` / 子 Agent 编排），职责与前端按钮一一对应：
 1. **生成题目**：了解当前账号工具池 → 生成适当数量题目（**覆盖所有工具的单工具题 + 适量多工具题 + 少量噪声题**）；
 2. **执行测试**（这一步 Agent 可以完全不参加，**可完全硬编码**）；
 3. **判分**：读真机测试表单 → 判分（方法与技巧**沿用 v3.1 对尼古喵喵池的人工 + Agent 判分过程与脚本设计**）；
 4. **给词法改进建议**：判分出结果后由**人类二次打分**，Agent 再给出**词法上的改进建议**（需给 Agent 灌入既往**词法修复经验**）；
 5. **归档到数据大屏**，等用户改完词法后**指导下一轮测试**，直到用户满意 / 达到项目建议指标。
5. **目的**：让「不同账号、不同工具池、以及同账号工具池变化」引起的路由质量波动，成为**用户可自维护**的事。

> **注（写调研文件时补的现状认知）**：算法侧这条腿**已有部分落地**——大点 01 的「度量口径收口」（指标口径 / 结构上限自算 / 灰区分栏）与 `Z_STRONG` 两轮重标定，本身就是「把尼古喵喵池上验证出的经验固化进项目代码」。所以大点 03 的算法侧工作 = **盘点「还有哪些算法侧经验尚未固化」**（例如：`precision@1` 剩余 3 个失分点背后的表征问题、同源工具互相挤占的通用规律、噪声假阳性对池内方差的敏感度），逐条评估能否做成与账号无关的项目级改动。

## 三、要解决的「波动」有三类（定验收时要分开）

| # | 波动来源 | 例子 | 期望手段 |
|---|---|---|---|
| 1 | **换账号** | 另一个账号的池与尼古喵喵完全不同 | 模块能对新账号**从零出题 → 测评 → 给建议** |
| 2 | **同账号增减工具** | 尼古喵喵新接了 1 个 MCP 来源 | 重跑测评得到**新的基线**，与上一轮**按题对齐**对比 |
| 3 | **同账号改词法/阈值** | 用户按建议改了 `keywords` | 同一批题目**复测**，看指标是否改善（这是自维护的闭环） |

## 四、前端交互构想（5 个动作 + 一块大屏）

```text
┌ 工具池测评（新 tab，平级于 CLI 面板 / MCP / API）────────────────┐
│ ① 本账号工具池：N 条（来源分组 · 每条：name / 有无 keywords / 有无描述 / 体检灯）│
│ ② 按钮：[🧪 生成真机题目] → 生成 N 题（单工具题 × 覆盖全部工具 + 多工具题 + 噪声题）│
│ [▶ 开始测评] → ⚠️ 先声明额度消耗；产出「工具调用记录表单」 │
│ [🧮 判分] → Agent 判分（+ 人类二次打分入口） │
│ [💡 词法建议] → Agent 给出逐条改进建议（含静态体检的硬规则结论） │
│ [📥 写入大屏] → 本轮数据入档，形成趋势 │
│ ③ 数据大屏：轮次 × 指标（命中 / 判分分布 / 噪声假阳性 / 注入量 / 额度消耗） │
│ ④ 历史轮次：可对比、可回看调用表单、可回滚词法（对接已有素材 A/B 与备份约定） │
└──────────────────────────────────────────────────────────────┘
```

## 五、测评 Agent 的职责拆分（对应按钮）

| # | 职责 | Agent 参与度 | 关键约束 |
|---|---|---|---|
| 1 | 了解池子并**出题** | **要**（LLM 生成 + 硬规则约束） | 覆盖全部工具的**单工具题**（一工具至少 1 题）、**适量**多工具题、**少量**噪声题；题面必须**自足**（新会话里没有先行词） |
| 2 | **执行测试** | **可完全不参加**（硬编码脚本） | 沿用既有探针记录器形态：**只记录、不判对错**；每轮**额度声明** |
| 3 | **判分** | **要**（可先 Agent 后人工） | 沿用 v3.1 的判分口径与技巧；**真值从库里 `messages.tool_calls` 读**，不采信模型自述 |
| 4 | **词法建议** | **要**（需灌经验） | 建议要落到 `keywords` / `abilities_user` / `name` 三个字段与「替代路径」写法上；**不得**建议改路由代码（那是开发者的腿） |
| 5 | **归档 + 指导下一轮** | 半个（数据由代码写） | 指标趋势 + 「这轮先改哪几条」的排序 |

## 六、难点清单（调研期要逐个定价）

1. ** 用户点名的那个**：「怎么根据不同账号的不同题目去单测？」——即**题集随账号变**，而执行器/判分器不能写死 43 条。分解成三问：① 题目的**标识**怎么稳定（题目 id？问句 hash？）；② 执行器怎么**消费任意题集**（参数化：题集 JSON → 逐题新会话 → 记录）；③ 判分怎么**对得上**（`expect` 从哪来：出题时一并产出，还是判分时现推？出题自产 `expect` 会有「自己出题自己判」的闭环风险）。
2. **判分口径**：v3.1 的制度是「脚本只记录序列、对错人工打分」。本议题要加 Agent 判分 → 需要明确 **Agent 判分的定位**（建议/预填 vs 终判）与**人类二次打分**的留痕方式（沿用评分表形态？）。
3. **额度声明**：「消耗网络搜索额度」的**量化口径**要提前写清（每轮预计多少次外部检索 / 什么情况下会更多）；Tavily 额度每月 1 日重置。
4. **独立 Agent 的边界**：不纳入主 Agent 体系，但**复用**同一套能力池、执行网关、模型配置与用量计数；它的产出**不得**直接改素材（只出建议，人确认后落库——与既有「AI 预写只填表单不落库」一致）。
5. **指标口径**：账号级测评的指标要不要与项目级基准（`precision@1` 等 12 项）**同名**？账号级用「真机判分分布」（ / / / 未测）更贴真实；两者别混成一张表。
6. **数据与隐私**：测评会写真机会话与 `usage_events` —— 沿用既有「真实账号按水位线清理」的约定，还是给测评单独开口子？（**必须**在方案里定，否则跑一轮就污染账号数据）
7. **可复跑的稳定性**：真机结果受模型概率性与限流影响（v3.1 已确认），所以**不能**把单轮数字当能力结论——大屏要能标「未测」并允许人工判定有效性。

## 八、待回答的问题（调研期逐个定价）

1. 出题**由谁来出**：纯 LLM？LLM + 硬规则（一工具至少 1 题、题面自足、噪声题上限）？题量公式是什么（按池规模）？
2. 出题时是否**同时产出 `expect`**？若是，如何避免「自出题自判分」的闭环？（候选：`expect` 由**独立第二次调用**产出 / 由能力卡结构硬推 / 人工抽检）
3. 判分**Agent 的定位**：预填 + 人工确认（推荐）还是终判？置信不足怎么办？
4. 账号级测评要不要**也跑离线**（零额度）作为前置闸门？顺序是「离线先绿 → 再真机」还是直接真机？
5. **额度声明**具体写什么（预计检索次数 / 预计模型 token / 失败重试策略）？
6. 数据大屏存哪：新表（按账号）还是复用 `usage_events` + 现有报告？（倾向新表，但需定 schema）
7. 测评产生的会话与用量**怎么收尾**（水位线清理 / 标记保留 / 不清理）？
8. 这套能不能**反过来喂项目级改进**：账号级测评发现的算法侧问题，如何**结构化回流**给开发者（即「硬编码侧」那条腿的输入端）？

## 九、明确不做（预判，方案期再定稿）

- **不**让测评 Agent 直接改素材或改路由代码（只出建议，人工确认）。
- **不**把真机测评做成自动判定（沿用「只记录 + 人工/人工校订的 Agent 判分」）。
- **不**把账号级测评的指标与项目级离线路由基准混成一张表。
- **不**在测评流程里改项目默认阈值（阈值是项目级、要单独立项）。

### 10.2 「独立 Agent」在项目里**已有 6 个先例**（这条推翻了「要新造一种东西」的假设）

**markdown 渲染器的两条路线**（**关键约束：项目是本地离线应用，不能靠 CDN 拉 `marked.js`——用户断网/被墙就白屏**；这也是本项目前端一直单文件自足的原因）：

- **路线甲（推荐）**：**自写极简渲染器**（≈60 行，只支持 `#/##/###`、表格、有序/无序列表、`**粗体**`、`` `代码` ``、行分隔）。理由：**打分表的格式是我们自己产出的**，渲染子集完全可控——不需要通用 markdown 兼容。
- **路线乙**：把 `marked.min.js` **放本地**（`front/vendor/`）随页面加载。代价：引入一个第三方文件（项目至今前端零外部依赖）。
