## 一、用户需求与目的（2026-10-16 用户草案，逐字）

### 现状

当前项目Agent是一个完全只读式的Agent智能体,虽然有沙箱和写工具(writetofile)的存在,但其实1.Agent并没有在沙箱里面创建或删除任何东西(早期预想是存放CLI,API,MCP工具使用后的产物,但本身是伪命题,因为设计上这三类只接受只读命令,现在沙箱只是Agent在后台敲CLI命令的cmd目录所在地),用户(该文档中"用户"默认为不懂开发,只使用桌面端使用项目的纯体验向用户)也不知道有所谓沙箱存在("尼古喵喵"账号沙箱存放的是题集和快照画像,算是其他模块中间产物暂时存放地,"药喵"的沙箱中存放着几份word和csv文档,但那是hermes在开发阶段主动放进去的,Agent能看到,但用户在前端完全意识不到它们的存在,所以在"药喵"的工具池测评中的"帮我看看那几份文件是什么"这个问题实际上合理有明确对象的,但纯体验用户看起来就很莫名其妙.可能直接误删该题目);2至于写工具,更简单,它是一个有明确限制的工具,其实更适合叫MEMORY.md编辑工具

### 功能

1. 沙箱白盒化,沙箱在前端需要可以见,需要可以点击查看和编辑沙箱的任意子文件夹和文件
2. 除了沙箱这一个工作地址,用户可以编辑选择一个工具目录作为工作地址
3. 写工具的扩展与进化:不再只是wiritetofile可以编辑 `deep_search_pro\user_data\agents_docs\<user>\MEMORY.md` 画像文件；还有一个新的tool: edittofile 可以编辑沙箱 `deep_search_pro\user_data\sandbox\<user>` 或者指定工作目录内的授权文件
4. 承接沙箱事实上没有做好存放CLI,API,MCP产物的历史问题,"技能与工具"模块开放具有"写"性质套装工具进入Agent进入写工具池(与当前只读工具池区分)
5. "技能与模块"中"skill"小板块升级为"skill与workflows"

### 调研

应对以上功能需求,请先进行以下想法的可行性与实现细节的调研,或者阅读完后补充你认为需要加、裁决的缺漏的地方:

1. 想要实现沙箱白盒化(可视化与内含文件可打开可看可编辑),对当前AI聊天助手的前端布局是一个挑战(当前是左栏:开关、便捷快速消息、会话选择、兴趣、关注;中间窗口:会话消息;右栏:监控,思考可视化、台账)。我的想法是,1.在当前会话的左栏和右栏增加一个可收起的小按钮;2.左侧栏添加一个工作目录列表,每个账号初始默认有沙箱的工作目录,每个工作目录可以点击然后展开看到工作目录的目录结构,再点击工作目录的子文夹进入下一级子文夹目录结构展示,点击某个文件跳出某文件内容的弹窗,用户可以手动增删改查文件,或者这个工作目录的子文件夹(类似一个微型的文件资源管理器),工作目录列表的每个目录项右侧有一个启用/停用按钮,通过选择,Agent的命令输入位置和写行为产物位置为该工作目录
2. Agent的写能力之一内置写工具:内置写工具的进化:原来的writetofile保持专职MEMORY文件编写的功能,新建新的edittofile专门用于编写沙箱或者自配工作目录内的文件的文件内容增删改查
3. 承接2. 配套内置写工具集的tool:listfile(列出当前选中工作目录的目录结构)、createfile(在工作目录内创建文件)、deletefile(工作目录内删除文件)供Agent使用,其中deletefile需要有一套适合但不过于死板的管制制度(我的想法是在每个工作目录,包括沙箱和自定义工作目录创建时放置一个保护名单文件,用户自由编辑,Agent无编辑权限,delete不能影响保护名文件本身和文件内提到的子文件夹和文件)
4. Agent的写能力之二自配写工具:"技能与工具模块"的CLI,MCP,API,工具池测评四个子模块,再每个再分成两个子模块,一个子模块就是当前的样式;另一个就是"写CLI","写MCP","写API","写工具池",前面三个它们的配置方式与政策和原来的只读工具配置方法是一样的,只是去除了写能力的拦截与限制,以后用户想配置一个套装工具,可以选择是配置进只读式(筛掉写功能)池或者写式(全量导入)池,"写工具池"只汇总配置了什么工具,没有路由测评更不进路由,它们不靠路由唤醒调用
5. 承接4. 自配写工具怎么唤起?不再是通过用户纯问题提问路由找,而是在聊天框的第一字打"/"建,打开自配写工具集列表(当前/只打开skill列表,把这个功能扩展,以后这个"/"可以唤起skill,自配写工具集,workflows三大列表),通过选定的自配写工具集(可以多选)加用户的提问引导完成任务
6. Agent的写能力之三工作流:本项目的工作流即一套不要Agent推断而直接有明确步骤规定展示的流程,工作流当然不只是写类工作的特权,其实也可以设计类似全只读式的信息收取方案的工作流,写工作流即有各种工具集(包括内置只读工具集,自配只读工具集,内置写工具集,自配只读工具集)参加,有完整流程步骤规定,不靠Agent自定制的工作,在"skill和workflows"配置好后,在AI助手模块"/"唤起列表中选中,Agent根据工作流要求执行工具调用步骤

## 二、P1：现状取证与「工作目录 vs 沙箱」边界（2026-10-16 完成）

### 2.1 沙箱现状：四类东西混住

| 沙箱里的东西 | 谁写的（出处） | 谁在读 | 性质 |
|---|---|---|---|
| `README.md`（每账号一份 277B） | `tools/_runtime/shell_runtime.py:75-85` 建目录时**自动播种** | 人 | 目录自述，唯一的"用户可见"善意设计 |
| `.wechat-cli/`、`.weread-cli/`（尼古喵喵） | **v2.0 旧设计遗留**（见 2.4） | 无 | **废弃**，含凭据副本 ⚠️ |
| `probe_run_2026*.json`（112KB / 122KB / 50KB） | 03 测评：`tools/probe_runner.py:18`（判分/建议/写大屏都读它） | 测评链 | 临时产物，`_prune_raw()` 只留最近 1 份 |
| `profile_backup_2026*/`（画像快照；**药喵那三份 office 文件就在其中**） | 03 测评（测试前快照，用于还原） | 测评还原 | 中间产物，`probe_runner.py:404` 注明"**永远跳过**清理" |
| `.git/`、`~/`、`mkdir/`（尼古喵喵） | CLI 实验与 Agent 的 shell 命令 | 无 | 遗留垃圾（已于 2.6 清理） |

### 2.2 根因（代码自己写着的）

测评之所以往沙箱里落盘，理由只是"**该目录本来就在清理清单里（不新建目录）**"（`tools/probe_runner.py:18-20`）—— 图方便，不是设计。沙箱因此同时承担了两个角色：

1. **合法角色**：`run_shell_command` 的 **cwd**（命令执行位置）；
2. **越界角色**：被 03 测评当成临时产物与快照的堆放处。

### 2.3 【重要发现】"Agent 看得见、用户看不见"的真正位置是**画像目录**

药喵那三份 office 文件的**原始位置**是 `user_data/agents_docs/药喵/`（画像目录，实测：`组会数据_GLP1随访.csv` 1018B · `.xlsx` 5348B · `组会汇报稿.docx` 5501B，均为 10-12 01:48），沙箱里那份只是 03 测评**画像快照**里的副本。

**含义**：用户草案里观察到的痛点（"题集问'帮我看看那几份文件是什么'，纯体验用户完全莫名其妙，可能误删该题"）**不是沙箱白盒化能解决的** —— 那些文件在**画像目录**，Agent 通过 `read_agent_doc` 能读，而前端目前看不到 `agents_docs/{账号}/`。**06 的可见范围需要把画像目录一并纳入考虑**（或确认题集自包含，二者至少取其一）。这条留到 P4 定。

### 2.4 【已澄清】沙箱内的 CLI 配置是 v2.0 设计错误的遗留

用户 2026-10-16 指出：自配 CLI 设计要求**使用全局环境**（"你在自己终端配置一次即可"），v2.0 曾误做成"一个沙箱一个环境"，现已改回全局，沙箱内那两份是**改之前的遗留**。取证证实：

| 文件 | 全局（真正在用） | 沙箱内（遗留） |
|---|---|---|
| `.wechat-cli/all_keys.json` | `C:\Users\ZQK\.wechat-cli\` · 5331B · 09-14 16:36 | 5331B · 09-14 16:36（同一时刻副本） |
| `.wechat-cli/config.json` | 84B · 09-14 16:36 | 84B · 09-14 17:50 |
| `.weread-cli/config.json` | 47B · 09-15 18:28 | 47B · 09-15 18:30 |

代码原文即口径：`tools/_runtime/shell_runtime.py:369-373` 写明"第三方 CLI 的登录态与配置都存在**真实用户目录**……把 `~` 改指沙箱会让它们找不到凭据、误报未登录……沙箱的写入边界由 **cwd** + **参数级路径校验**负责，不靠篡改用户目录"；`:378-382` 把 `USERPROFILE/HOME/APPDATA/LOCALAPPDATA` **继承**给子进程。旁证：`user_clis` 表里 4 个 CLI（weread / wechat-cli / bili / agently-cli）**没有任何"沙箱环境"字段**；04 迁移脚本只整包搬了目录（`scripts/migrate_user_data.py:52`），未做内容级清理。

**结论**：**切换工作目录不会影响 CLI 认证**（它们读全局 `~`，与 cwd 无关）。功能 2 因此少了一个大堵点，工作目录的定义可以很干净。

### 2.5 边界定义（2026-10-16 用户确认）

- **工作目录**＝用户可见、可增删改查的那一层；`user_data/sandbox/{账号}/` 保留为**默认工作目录**（前端显示「默认工作目录」，不叫"沙箱"）。
- **用户可见范围红线**：文本类（.md/.txt/.csv/.json 等）可看可编；**凭据类一律不放行**（`*key*`/`*token*`/`*secret*` 命名与点开头目录在前端显示"受保护、不可预览"）。

## 五、P3：内置写工具集与保护名单（2026-10-16 完成）

### 5.1 底料：现有 22 个内置工具里只有 2 个有写能力

| 类别 | 工具 |
|---|---|
| 只读 / 查询 | `query_kb` · `read_agent_doc` · `list_agent_docs` · `invoke_tool`（网关，只读能力直调）· `db_tools`×3 · `personal_tools`×3 · `company_read_tools`×3 · `price_tool` · 三个网搜工作流 |
| **有写能力（2 个）** | `write_agent_doc`（`tools/writetofile.py`：写 `agents_docs/{账号}/` 下 `.md`/`.txt`，禁 `../`）· `update_user_profile`（`tools/profile_update.py`：写画像 MEMORY.md）|
| 半写（须一并守卫） | `run_shell_command` —— 白名单含 `mkdir`，今天就能在工作目录里建目录 |

**口径纠正**：草案里"写工具更适合叫 MEMORY.md 编辑工具"精确对应 `update_user_profile`（MEMORY.md 由它写）；`write_agent_doc` 是**画像目录通用写**（人格、技能也走它）。用户 2026-10-16 确认"草案里是我理解漏了说错了"。

### 5.2 定案（用户 2026-10-16 拍板）

| 项 | 结论 |
|---|---|
| A1 工具集与命名 | `list_file` · `read_file` · `create_file` · `edit_file` · `delete_file`（跟随 `read_agent_doc` / `list_agent_docs` 风格）。**`edit_file` 为"增删改查"合一的编辑工具**：兼具读一份文件的内容、修改内容、增加内容、删减内容（用户澄清原作者意图）；`read_file` 负责整份读取 |
| A2 `write_agent_doc` | 保持现状（画像目录通用写，**不收窄**）|
| A3 用量分类 | 新增 `write` kind（写工具单独归类，否则用量页与审计对不上账）|
| B1 保护名单 | 每个工作目录根一份 **`_保护名单.md`**（建目录时播种）；一行一条 + 支持 `#` 注释；支持**文件名 / 目录前缀 / glob** 三种写法 |
| B2 生效范围 | **所有写工具都过守卫**；**名单文件自身永远受保护**（硬编码）；`run_shell_command` 的 `mkdir` 同样过守卫；**`edit_file` 接触受保护文件时退化为"只读 + 定位内容"**（其余写工具直接拒绝）|
| B3 fail-closed | 名单**读不到或解析失败 → 一律拒绝写**（照 03 清理"水位线读不到就一行不删"的教训）|
| B4 前端侧 | 用户可在前端删除受保护文件，但**二次确认 + 明示"这是 Agent 的保护项"** |
| C1 回收站 | 删除移入该工作目录下 `.回收站/{时间戳}_{原名}`；前端可查看 / 还原 / 清空；**过期天数在设置模块可调（单位：天，默认 7）** |
| C2 体积闸 | 单次写入上限 **1MB 默认，设置模块可调（单位：MB）**；外部目录另加"体积不受项目管控"提示 |
| C3 审计 | 每次写/删落审计（账号 / 工作目录 / 工具 / 目标路径 / 结果），**不留文件内容**（内容在回收站里）|

### 5.3 新增设置项（落 `app_settings` 全局层 —— 该表无 `account_id`，见 §4.2）

| 键 | 默认 | 说明 |
|---|---|---|
| `WORKDIR_TRASH_TTL_DAYS` | 7 | 工作目录回收站的自动过期天数 |
| `WORKDIR_MAX_WRITE_MB` | 1 | 单次写入体积上限（MB）|

### 5.4 留给 P4 的问题（本轮提出，未定）

B2 允许 `edit_file` 对受保护文件"只读 + 定位"。若用户把**凭据类文件**放进保护名单，按此规则 Agent 仍能**读**它。是否对 `*key*` / `*token*` / `*secret*` 这类再加一层"**连读都拒绝**"？与 P4 的"前端不放行凭据"一并定。

## 六、P4：前端文件管理器与「谁来管画像目录」（2026-10-16 完成）

### 6.1 定案（用户 2026-10-16 拍板）

| 项 | 结论 |
|---|---|
| A1 布局 | 采用用户方案：左栏「工作目录」列表（逐级展开目录树）+ 点文件开弹窗。三条细化获同意：① 弹窗加宽/可拉（编辑用，约 70vw）；② 目录树懒加载 + 搜索框；③ 弹窗区分三模式：**可编辑**（.md/.txt/.csv/.json…）/ **只读预览**（.docx/.xlsx）/ **仅下载**（PDF 及未知类型）|
| A2 冲突处理 | 保存前比对修改时间；若文件已被 Agent 改过 → 弹「文件已被修改，仍要覆盖吗」|

## 四、P2：工作目录模型（2026-10-16 完成）

### 4.1 已定案（用户 2026-10-16 拍板）

| 项 | 事项 | 结论 |
|---|---|---|
| A1 | 模型 | **可定义多个工作目录，同一时刻只有一个"启用"**（对应草案里"列表 + 每项右侧启用/停用"）；默认条目＝该账号的沙箱路径；用户可再配置其他自定义目录 |
| A2 | 存储 | **新表 `account_workdirs(account_id, name, path, is_active)`**；**不放** `app_settings`（那张表是全局的、无 `account_id` 列） |
| A3 | 默认条目的前端名称 | 叫 **「主页」**（不叫「默认工作目录」）；路径仍是 `user_data/sandbox/{账号}/` |
| B | 新目录来源 | **只做"外部真实目录"**（不做项目托管的新目录）：用户在磁盘上挑任意目录；**创建时明示风险**（二次确认） |
| C1 | "写行为产物"的边界 | 仅指 **Agent 的内置写工具**（`writetofile` 除外）与**自配写工具套装**留下的产物；`output/{账号}/` 里的周报 / 导出 / 打分表等**模块产出永远留在原地** |
| C2 | CLI 面板 | 其 cwd **跟着**当前启用的工作目录变（面板与 Agent 共用同一执行器，规则不漂移） |
| C3 | 轮次留痕 | **新建专门的审计文件**存放这类数据（记录"哪一轮用的哪个工作目录"），不混进既有审计流 |

### 4.2 取证（支撑上面各条）

- **设置分两层**：`app_settings` 只有 `key/value/updated_at/updated_by`（**全局**、无 `account_id`）；账号级开关走 `accounts` 表列（`decision_router`、`digest_auto` 即此例）→ 故 A2 落新表。
- **"cwd 可换"的影响面小**（3 个文件，且核心函数已把根目录当参数收）：
  `tools/_runtime/shell_runtime.py`（`43` 导入 · `75-78 sandbox_dir` · `104 _resolve_in_sandbox(tok, sandbox)` 在 `144/241/271/302/342` 六处调用 · 三个入口 `425/551/566`）·

- **B 条"风险"要写进 UI 文案（本节即定稿口径）**：
  1. 启用外部目录后，命令的**路径守卫根**变为该目录（沙箱不再是边界）；
