**字段说明（每个指标是什么、怎么算、从哪来）**：

| 指标 | 含义（一句话） | 公式（`tests/live/m5c_router_bench.py` 内的真实实现） | 数据来源 |
|---|---|---|---|
| precision@3 | 只注入 top3 时，**注入的东西里有多少是这题真该用的** —— 衡量「别乱塞」 | `Σp / n_conf`，每题 `p = \|top3 ∩ expect\| / max(1, min(3, \|top3\|))` | 题库 `tests/fixtures/router_bench.json` + 冻结池 `tests/fixtures/router_pool_snapshot.json` |
| recall@3 | 这题该用的工具里，**有多少被 top3 覆盖**了 —— 衡量「别漏」（可接受集合按 3 封顶） | `Σr / n_conf`，每题 `r = \|top3 ∩ expect\| / max(1, min(3, \|expect\|))` | 同上 |
| hit@3 | **至少命中 1 个**的题占比 —— 最粗的「有没有想起来」 | `n_hit / n_conf` | 同上 |
| 灰区比例 | 判成「没有明确目标」→ 回退全量简报的题占比（**fail-safe，不是错误**；噪声题里本该回退的那种也算灰区，属正确行为） | `n_gray / n_qs`，`n_gray` = 路由结果 `confident=False` 的题数 | 同上 |
| 噪声假阳性 | **噪声题（本就不该路由）里被「自信路由」的比例** —— 越低越好，是 Jev 的主要理由之一 | `n_noise_fp / max(1, n_noise)`，`n_noise` = 类别为「噪声」的题数（6） | 题库里 `cat == "噪声"` 的 6 题 |

- `top3` = `tools/tool_router.py` 的 `decide()` 返回 `order` 的前 3 个（剥掉 `source:` 前缀后的真 ref）；`expect` = 该题在题库里的可接受 ref 集合。
- `n_conf` = **非噪声题数**（30 − 6 = 24）—— precision@3 / recall@3 / hit@3 的分母都是它，**噪声题不计入这三项**。
- 题集构成：30 题 = 明确 18 / 跨工具 6 / 噪声 6；冻结池 28 条 = cli 3 / api 4 / mcp 21（一次性导出后冻结，**不受账号增删工具影响**，这是可复现的前提）。
- 「自信路由」的判定：`confident = lex_top ≥ LEX_MIN(2) 或 z_top ≥ Z_STRONG(2.4)`（`tools/tool_router.py:41,48`）。`2.4` 是 2026-09-27 用本基准在 28 条池上标定出来的，**预研原文写的 2.0 已过时**。
- 判据口径：**软判据**（能力目标，仅记录不告警）= `precision@3 ≥ 0.7`、`噪声假阳性 ≤ 0.1`、`灰区 ≤ 0.3`；**硬判据**（告警依据）= 与 `tests/fixtures/router_bench_baseline.json` 逐项比**任一指标不得下降**。两条都印在脚本输出里。

## 二、v4.0 头号议题：决策模型仲裁层（旧称 Jev 仲裁层 · M5c-4）

> **状态：方案已定（2026-10-12）** —— 形态改为**两段式决策精排**（不再沿用"只在灰色区间"的旧设想）：现有快路召回 top-k → 决策模型精排；触发用**近并列**（融合分间距 < 0.0005 起步，配置项）；**噪声归路由器、决策模型只管选**；首批 = 精排 + 缓存 + 计量 + fail-safe，链题专项作第二批。
> **要读的两份**：`v4.0规划文档.md` §02 的 **③ 段**（唯一权威的方案，含来源标注与验收判据）+ `Verdict/02-决策模型仲裁层.md`（5 条裁定）。
> **本节以下文字是调研前的历史描述**，口径与结论均可能不同（例如"只在灰色区间"已被实测否掉），**勿直接照用**。

**它是什么**：路由现在是「词法 + 本地向量」两路免费判定，判不准的一律回退全量简报（fail-safe）。Jev 是**只在灰色区间**加一层 LLM 仲裁，把「该进 top3 的没进」捞回来，并新增一个岗位治「『你是谁』也被自信路由」。占位代码在 `tools/tool_router.py` 的 `_route_provider()` 与 `route_tools` 的灰区分支注释。

**现状判定（照原文字面推）**：三条触发线里 **precision@3 = 0.389 < 0.7 这一条已越线**，另两条（灰区 0.267、噪声假阳性 0.000）在安全区。预研的反向条件「若 precision@3 已 ≥0.7 且噪声假阳性 ≤10% 则继续搁置」**不成立**。

**但这个结论开工前必须请你拍板**，理由两条（都是口径问题，不是数字问题）：

1. **`precision@3 ≥ 0.7` 在本项目里从未当过闸门**。权威口径在 `tests/fixtures/router_bench_regressions.json` 的 `verdict_rule`：「软判据 precision@3≥0.7 **仅记录**；硬判据 = 相对 `baseline_metrics` **不得下降**，下降才告警」。也就是说日常开发只守「不退化」，0.7 是 09-19 调研时定的**期望水位**。它作为「立项触发线」是否仍然有效，需要你确认。
2. **前置硬条件要复核**。预研写明「步骤一、二必须先落地，否则是把糊在一起的文本喂给更聪明的判断器，脏进脏出」。步骤一（来源级只读声明 M5c-1）已落地；步骤二（向量文本卫生 M5c-2）实测**负收益已回退**，改由「M5c-2' 词法卫生」顶替（hit@3 +19%、噪声假阳性 −50%）——**这是否算「步骤二已落地」，要你拍板**，新会话不要自行认定。

## 四、环境与纪律硬约束（新会话最容易踩的）

### 4.1 环境

1. **禁跑 `uv add` / `uv sync`**（实测踩过：会整批卸掉不在 lock 里的手动包 —— torch cu121 / sentence-transformers / chromadb / pywebview / pystray / pillow 等 24 个）。装包一律 `uv pip install`，装完 `uv pip check` 核对。事故复盘见 `docs/v3.1/语音转文字-逐文件带读.md`。
2. **`.venv` 必须 Python 3.11.15**，`pyvenv.cfg` 不可指向 `C:\python`（3.12）—— site-packages 是 cp311 编译，`.pyd` 会全崩。
3. **跑本项目脚本前 `unset PYTHONPATH`** —— 否则 Hermes 自己的 venv 泄漏进来，pydantic / pydantic_core 版本错配报 `ModuleNotFoundError: _pydantic_core`（已踩两次）。
4. **本机代理 127.0.0.1:7897**：localhost 请求要加 `--noproxy '*'`（不加会被代理挡成 502）；`.env` 里的 API key 不看不碰。
5. **服务测试约定**：默认**直接用用户已开着的服务**做真机测试，不要自己另起。识别陷阱：`netstat -ano` 里 LISTENING 的 PID ≠ 自己启动的 PID，说明那是用户的服务（可能是旧代码）→ 此时**换端口**验证（`--port 8124`），**不要 kill 用户的进程**，也不要断言「代码没生效」。
6. **涉及数据修改/删除**（清理 session、UPDATE、kill 进程）：给**用户手动分步执行指南**，不要自己直接跑（他要先看清每一步的风险点）。例外：用户当次显式授权。
7. **额度纪律**：Tavily 额度每月 1 日重置，测试会话尽量别触发网搜。**测试默认在网页端**（要测桌面壳他会明说）。
8. **桌面版跑测隔离**：外壳自检自带临时目录（`ZX_DESKTOP_LOGDIR`、`--storage-path`）；**检测到用户桌面实例在跑会自动跳过 `[16]` 真机重启段**（114 → 107 项）。不要让测试碰用户的实例与 WebView2 存储。

### 4.2 文档与代码纪律（用户明确要求过的）

1. **符号只作数据不作标点**：`✓` / `✗` / `△` 只许出现在①评分与判据的表格单元格 ②行内代码 ③紧邻数字的统计串；正文一律中文写清。约定全文在 `docs/README.md` §一 顶部。
2. **责任判据**：先证明**工具本身有没有那个能力**——没有 → 只改工具（不是 agent 的锅）；确有而 agent 不用 → 才修调用纪律。
3. **探针制度 v3**：脚本**只记录**「调用了哪些工具、什么顺序」，**对错由用户人工打分**；真值从 `messages.tool_calls` 按会话读回，**不采信模型自述**。
4. **固化原则**：接入新工具时，防坑必须**改进到 tool 层 / agent 层 / prompt 层的代码里**（对「不会跑测试脚本的用户」自动生效），不能靠装完再用测试脚本复跑发现。
5. **文件存放**：新增文件前读 `docs/文件存放规则.md`；**新建子文件夹必须先经用户同意**；前端一律 `front/`；基准与夹具放 `tests/fixtures/`（**不能放 `data/`**，会被 `.gitignore` 吞掉）。
6. **测试不许动用户数据**：流程类断言用**既有账号**并断言**账号总数跑前跑后不变**；测试自建的账号/会话/文件自己回收。
7. **一版做完再传**：不要边做边提交；一轮工作收尾时再 commit + push。commit message 讲清「更新了哪些功能 / 修了哪些 bug / 系统设计优化」。
8. **批注与暂停点**：用户会在交付文档上直接打批注（形式为六级标题或 `<......>` 尖括号），**先复述确认再改**；遇设计分叉、约束冲突、需求歧义、**纯前端任务里需要后端配合** → 都要先暂停报告、等用户拍板，不擅自决定。
