## 01 度量口径收口工程

### ① 应对什么问题

路由质量的度量体系本身有三类**结构性缺陷**，导致「该不该上更强的机制（Jev 仲裁层）」这类判断建立在一个错误的读数上：

1. **目标不可达**：`precision@3 ≥ 0.7` 这条立项/软判据在现题库上**结构上限只有 0.536**——24 道非噪声题里 13 道只有 1 个可接受工具，而 top3 恒 3 条 → 这些题单题封顶 1/3。这条线**恒真**，等于没有触发条件（「只要去看就一定有问题」）。
2. **指标把正确行为算进坏账**：灰区比例把「噪声题的正确回退」也计入（7/30 道噪声题本该回退、实测也确实全部正确回退），于是灰区**天然 ≥ 0.233**；读数 0.267 看起来像 26.7% 的路由失败，实为「6 道噪声正确回退 + 2 道真没把握」。
3. **答案键与工具能力不符**：唯一未命中题 `city-climate`（气候知识问答）期望的 `mcp:city/search_city` 只返回地名/行政区/经纬度/人口/地点类型，**答不了气候问题**；这既拿错期望扣路由的分，又掩盖了「它其实是被自信路由到了错工具（z = 3.22）」这个真问题。

**证据（本机可复现，2026-10-09 实跑）**：`.venv/Scripts/python.exe tests/live/m5c_router_bench.py` 复现交接基线 `0.292 / 0.674 / 0.792 / 0.500 / 0.000` 与 `router_bench_baseline.json` **逐项一致**；三类缺陷的推导、逐题拆解与阈值扫描原始数据见 `research/01-度量口径收口工程.md` §二 / §四。

### ② 功能

把尺子先校准，让后续所有路由工作有**可达**的判据：

- 新增 **`precision@1`**（top1 是否可接受；**可达**，作为主力信号）与 **`precision@3_ceiling`**（结构上限，**脚本自算**，改题库自动跟着变，不会再漂）；
- 灰区**分两栏**：`gray_ratio`（全题，含正确的噪声回退）+ `gray_ratio_nonnoise`（非噪声题里的灰区，真信号）；
- 注入量按**实际注入形态**统计（完整卡数 + 注入字符，整池全量为参考）；
- 判据与 **Jev 立项线**重写为可触发的两条：软判据 = `precision@1 ≥ 0.7` ｜ `hit@3 ≥ 0.9` ｜ 噪声假阳性 ≤ 0.1 ｜ 非噪声灰区 ≤ 0.2；立项线 = **非噪声灰区题 ≥ 5 道 或 噪声假阳性 > 0.1**（原 `precision@3 < 0.7` 作废）；
- 题库 `city-climate` 按工具实际能力改判；阈值 `Z_STRONG` 依扫描重标定 2.4 → 3.3（噪声假阳性归零，四个质量指标不变）。

## 02 决策模型仲裁层（旧称 Jev 仲裁层）

> **状态：已完成(2026-10-13)

### ① 应对什么问题

素材层落地后，路由的**召回**这一侧已经打通（top3 含正解 **23/23**），但**「从候选里定下第一个」这一步仍是短板**：同一次运行里 23 道非噪声题有 **4 道 top1 选错**（`pdd-search`、`trip-route`、`compare-price`、`city-basic`），而现有机制**没有任何纠错手段**——快路的 `confident` 衡量的是"有没有明确目标"（z / 词法分数），**不是"第一个选得对不对"**，所以选错的 4 道里有 3 道是"自信题"，连灰区回退都拦不到。

同一批候选上，**决策模型（不吃文本、只给概率的一类新模型）的精排能力足够用**：第一期在"候选含正解"的 18 道上**全对**（18/18）；第二期召回已覆盖 23/23，它仍有 **2 道失手，且都是多步链题**（见下）——两轨实测把 `precision@1` 从 **19/23（0.826）抬到 21/23（0.913）**，噪声假阳性保持 **0.000**，单次决策调用的 state 只有 420~470 字符。另有一类失分**本批不治**：多步链题的单选退化（`trip-tickets` / `trip-transfer` 等失败姿势一致——都选了链条第一步 `get-current-date`），留作第二批。

**证据（可复现）**：
- 指标与逐题：`research/02-Jev仲裁层-demo/jev_track_metrics.json`（同仪器基线）· `jev_ag2_result.json`（两轨方案指标）· `jev_ag_items.jsonl` / `jev_ag2_items.jsonl`（逐题原始）
- 复跑：`unset PYTHONPATH && .venv/Scripts/python.exe docs/v4.0/research/02-Jev仲裁层-demo/jev_tracks_baseline.py`（三轨基线对账）、`…/jev_ag2_tracks.py`（两轨 B/C/D 复测）
- 分析与复盘：`research/02-Jev仲裁层.md` §十八（第一期 A~G 对比）· §二十（第二期两轨实测，含链题清单 §20.3）· §二十二（主路三条决定与噪声假阳性的单变量实验）
- 口径警示：素材层会漂移，`Done/01` §7.5 记的 0.870 属 10-09 那版素材、今日不可复现（§十九 / §二十一）；故本大点验收一律用**同仪器同期基线**（见 `Verdict/02-决策模型仲裁层.md` 裁定 5）

### ② 功能

**一句话**：当路由给回的两个候选咬得很近时，系统会请决策模型**复核一次**再定夺——做完之后，**在候选互相咬住的那些题上，Agent 第一次就选对工具的概率提高**（同口径实测 19/23 → 21/23），而现有能力与失败行为**一字不改**。

具体多了三样东西：

1. **一次「第二意见」**：只在触发条件下发生（近并列；默认关），选中结果被当作新的候选顺序；不改变 prompt 的注入量，也不改变「要不要用工具」的判定（噪声仍由路由器负责）。
2. **一条可配、可回退的生产接口**：不可用（超时 / 无额度 / 形状错 / 限流）时行为**逐字等于现状**；配置项全开（模型、门限、top-k、state 模板、预算、缓存开关）。
3. **一套可观测与可复算的工程件**：决策缓存（同池版本 + 同问题直接复用）、计量（token 走 `usage_events`、失败分类走 `failure_events`、缓存命中单独计数）、审计（每次精排的选择、概率、间距、耗时），为第二批链题专项留好位置。

### ③ 实现功能的技术方案

**形态：两段式决策精排**（主路；裁定 1）。不替换任何现有环节，只在"选"这一步加一层。

```text
用户消息
 └─ 现有快路（词法 + 向量 + 阈值；本地毫秒级，不动它）
 → 候选 top-k + fused / z / lexical 分数 + confident
 ├─ 触发条件命中（融合分间距 fused[top1] − fused[top2] < 门限）
 │ → 决策精排：候选卡片 + 用户消息 → 决策模型 choice → 采用其选择
 │ └─ 失败（超时 / 402 / 400 形状 / 限流）→ 逐字回退现状
 └─ 未命中 → 现状直通
```

1. **触发**：`decision_trigger = near_tie | always | gray`（默认 `near_tie`）；`decision_tie_threshold` 起点 **0.0005**；每次触发把间距写进审计日志，供后续在更大题集上复标。来源：`Verdict/02-决策模型仲裁层.md` 裁定 2 · `research/02-Jev仲裁层.md` §22.1 · 标定数据 `research/02-Jev仲裁层-demo/jev_near_tie_calibration.json`。
2. **state 构造**：`候选工具卡片（名称 / 关键词 / 能力说明，取**素材层之后**的字段）+ 本轮用户消息`；**选项键用 `e.ref`（显示键，与题库/实测同形）**，回填时映射回路由器内部键 `source:ref`；模板版本 `decision_state_template = v2` 计入缓存键（改 state 构造必须 +1）；**默认不含**对话历史、人格、画像（留开关）。来源：§十八（state 与选项粒度决定成败）· §二十（卡片必须用素材层之后的文本）。
3. **问法**：`choice`；`instructions = 从候选里选出最合适的一个工具`；`criteria = {候选 ref: 该工具的能力说明}`。**首批不把"要不要用工具"交给决策模型**（噪声归路由器）。来源：§二十（模板实测）· 裁定 3。
4. **候选集**：`decision_top_k = 3`（可配 3~8），取快路 `order` 的前 k 条；**决策调用的 state 约 420~470 字符**——这是发给决策模型的上下文大小，**不是**给主模型的 prompt 注入；本层不改变 prompt 注入量。来源：§二十。
5. **模型与凭据**：读项目 `.env` 的 `DECISION_MODEL_BASE_URL` / `DECISION_MODEL_NAME` / `DECISION_MODEL_API_KEY`；请求地址 = `base_url` 去掉 `/api/v1` 后接 `/api/alpha/decisions`。**总开关**（2026-10-13 用户裁定）：**账号级字段 `accounts.decision_router`，由前端 AI 对话区的开关切换**——开不开**不写进 `.env`**（`.env` 只留模型与凭据），默认关。**不硬编码厂商**。来源：§十七 Q5 / Q6 · §十一 · 2026-10-13 用户裁定。
6. **缓存**：键 = `账号 + 归一化问题文本 + pool_version + 素材指纹（source/ref/name/keywords/abilities/abilities_user —— 素材层改措辞即失效）+ state 模板版本 + 模型 ref`；**时效 24 小时**（`decision_cache_ttl_h`，2026-10-13 用户裁定：过期作废**并从缓存文件里删掉**）；命中直接复用上次选择与概率。来源：§十七 Q8 · §九·F · 2026-10-13 用户裁定。
7. **计量**：模型 token → `usage_events`（输出 token 免费）；失败按类型（超时 / 402 / 400 形状 / 限流）→ `failure_events`；缓存命中单独计数；每次精排落一条审计（选择、概率、间距、耗时、是否命中缓存）。来源：§九·F · §十二。
8. **fail-safe**：任何异常**逐字回退**现状（现有全量注入）；本层只影响"工具怎么被想起"，**不参与能不能执行**。来源：§十二。
9. **代码落点**：启用 `tools/tool_router.py` 的 `_route_provider()` 缝隙；新增模块（决策客户端 + 精排判定）的**位置按 `docs/文件存放规则.md` 第三节判据定，新增文件前先查该文件**。来源：预研 §3.4 · §九。
10. **配置项清单**（全部可配、默认关）：**开关 = `accounts.decision_router`（前端按钮，不走 `.env`）** · `decision_base_url` · `decision_model` · `decision_api_key` · `decision_trigger` · `decision_tie_threshold` · `decision_top_k` · `decision_state_template` · `decision_timeout_s` · `decision_max_retries` · `decision_cache_enabled` · `decision_cache_ttl_h`（**默认 24 小时，过期作废并从缓存文件里删除**） · `decision_budget_per_day` · `decision_budget_per_session`。
11. **明确不做**：不替换词法/向量快路；不做关键词黑名单式补丁；不在没有基准的情况下调阈值；不改 `card_text` 结构；不把"要不要用工具"交给决策模型；首批**不做**链题选项粒度改造（第二批）。
12. **验收判据**（裁定 5）：① `precision@1` ≥ 同一次运行路由器基线的 90%；② 噪声假阳性不得高于路由器；③ 附报 `hit@3` / 平均注入字符 / 调用次数 / 延迟。参考读数：第二期两轨基线 0.826 → 目标 ≥ 0.743，精排实测 0.913。跑基准时**连素材快照一起记录**（`pool_version` + 草稿文件哈希）。
13. **验证方式**：离线（同一次运行跑"路由器基线 / 精排"两遍比指标）+ 专项（4 道链题单列）+ 真机（网页端，含链题与噪声题的会话）；脚本自测与客户端测试**两步都不跳**。来源：§二十 · 项目「bug 修复」阶段纪律。

### ① 应对什么问题

- **测评面太窄**：路由质量的测评与修复（尤其**真机**测评）目前只覆盖「尼古喵喵」**一个账号当前的工具池**——换账号、或同一账号增减工具后，结论**不可迁移、也没有可比基线**。
- **词法经验没有落点**：往期改「工具的应用场景 + 方法介绍词段」（`keywords` / `abilities_user` / `name`）的经验散在文档与本机脚本里；用户自己改完**无从验证「到底变好了没有」**。
- **两条腿性质不同、此前混着走**：算法侧的经验（阈值、表征、判据）属**项目代码**（一次改到位、全账号受益）；词法侧属**账号数据**（每账号不同，只能由用户维护）。混着走的结果是两头都没沉淀。

**证据**：现状盘点见 `research/03-….md` §二（离线路由基准是项目级尺子、真机探针是脚本且题集绑账号）；三类波动见 §三；试点与既往可复用资产见 §七。

### ② 功能

分两条腿给出**明确归属**：

1. **算法侧（项目级）**：把往期在「尼古喵喵」池上验证出的算法/判据经验**直接改进项目路由代码**——全账号受益，不由用户端碰。
2. **词法侧（账号级，用户自维护）**：在「🧩 技能与工具」里**平级于 CLI 面板 / 第三方 CLI / MCP / API** 新增一个**工具池测评**模块：
 - 列出**本账号全部工具**与其**路由质量数据大屏**；
 - 动作流程：**生成真机题目**（覆盖全部工具的单工具题 + 适量多工具题 + 少量噪声题）→ **测评**（**提前声明网络搜索额度消耗**；只产出「工具调用记录表单」，不判对错）→ **判分**（Agent 判分 + **人类二次打分**）→ **词法改进建议**（Agent 带既往词法经验）+ 静态体检的硬规则结论 → **写入大屏**，并给出下一轮要改哪几条的排序；
 - 后端配一个**针对当前账号工具池的独立测评 Agent**（**不纳入主 Agent 体系**），职责与按钮一一对应（出题 / 执行 / 判分 / 建议 / 归档）。

#### D. 出题规则（题量公式定稿）

设池内能力条目数 = **N**（当前尼古喵喵池 N=29）：

| 类 | 条数 | 约束 |
|---|---|---|
| **单工具题** | **N 条**（每个 `ref` ≥1 题） | 题面**自足**（无「它/这个」等先行词）；同一 `ref` 的题面不得与往期重复 |
| **多工具题** | **max(2, ceil(N/6))** 条（N=29 → 5 条） | 正确答案须是**可并存的多个 ref**（跨来源优先） |
| **噪声题** | **2 条**（上限 2，且 ≤ N/10） | 必须**池内确实无解**；**答案键要与工具能力相符**（大点 01 的 `city-climate` 教训） |
| 合计 | **N + max(2,⌈N/6⌉) + 2**（N=29 → **36 题**） | 与 v3.1 的 43 题**同量级** → 单轮耗时与额度可比 |

出题产物**先过你的人眼闸门**（可改题面、可改预期工具、可删题）→ 才允许执行。

### ① 应对什么问题

**方向一 · 文档架构本身缺设计约束。** v3.0 立《文件存放规则.md》整治的是「项目文件该放哪个目录」——它管的是**归属**；没管**架构**：一个版本目录内部如何编排、记录性质文档（规划 / 调研 / 裁定 / 实现记录 / 逐文件带读 / 交接 / 备份）各自扮演什么角色、谁是权威谁只读、彼此如何引用、哪些状态字段必须同步。这些此前靠惯例与助手记忆维持，已经出现事实性偏差（本次调研逐条核实）。

**方向二 · 外接配置没有完整条目。** 一批需要外部 key / 认证的配置散落在代码与数据库里，没有进 `.env.example` 的条目表。后果：一台全新电脑拿到项目、`.venv` 配好后，某些功能会因为缺外部认证直接报错，而用户无法从条目表看出该补什么。第一手事实：`.env` 现有 **36** 个键，`.env.example` 只有 **19** 个，**17 个键未进示例文件**。

### ② 功能（意向）

1. **文档架构**：全面清点项目下所有文件夹与子文件的作用，验证《文件存放规则.md》《版本文档规范.md》是否与实际一致，查缺补漏，产出一份可执行的文档架构口径（每个目录的判据 + 记录性质文档的角色表 + 状态字段的同步清单）。

## 05 网络搜索子Agent升级

> 状态：**已记录（2026-10-15）** —— 六阶段全部走完（占位 → 调研 → 定方案 → 实现 → 修 bug 与优化 → 记录）。实现记录见 `Done/05-网络搜索子Agent升级·实现记录.md`、逐文件带读见 `Done/05-网络搜索子Agent升级·逐文件带读.md`，逐条裁定见 `Verdict/05-网络搜索子Agent升级.md`（裁定 1~9），调研事实见 `research/05-网络搜索子Agent升级.md`。

### ① 应对什么问题

**现状（2026-10-14 只读实测，路径级证据）**：

| 事实 | 位置 |
|---|---|
| 子 Agent 只挂**一个**工具 `internet_search`；命名/描述/系统提示都来自提示词配置 | `agent/subagents/network_search_agent.py:9` · `prompt/prompts.yml` 的子 Agent 段 |
| 全网检索**只有 Tavily 一个通道**（228 行工具本体全部围绕它展开，未接入第二个引擎） | `tools/tavily_tool.py` |
| 已有能力参数：`topic`(news/finance/general) · `max_results` · `include_raw_content` · `days` · `strict_days`（代码层按 `published_date` 剔除超窗旧闻） | `tools/tavily_tool.py` |

**问题**：产品的「外部信息入口」集中在一个工具、一个厂商、一个额度池上 —— 检索的**通道可替换性**、**额度可见性与可控性**、**单次调用可中断性**都没有着落；且上面那些能力参数目前只能靠模型临场想起来传，缺一层「按场景固定策略」。

**真机暴露的两个具体痛点（2026-10-14 用户需求）**：① Tavily 属**词法匹配检索**，取不到**特定网址的一手资料**（站内要点击/切换才能看到的内容拿不到）；② 竞品官网这类**已知地址**的信息，v1.0 曾靠「每轮把竞品官网喂进检索」，结果是检索与参数面互相干扰、价格取不准，该可填项最终被置空。

### ② 功能（意向）

把网络搜索子 Agent 从**单一工具**升级为**可按场景配置、可观测、可扩展**的检索能力。意向轴：

- **通道**：是否从「一个厂商一个工具」变成「可配置的检索来源」（新增第二引擎 / 复用既有 HTTP 抓取 / 允许用户自配来源——须与本项目「配置导向、不写死厂商」的偏好一致）；
- **额度与成本**：是否给搜索调用加本地计量与闸门（现只有归类、不设闸），额度紧张时能否自动降级到零消耗通道；
- **可控性**：单次检索能否被打断、能否设更细的超时预算；
- **质量**：时效 / 双语 / 正文抓取这些既有能力是否要「策略化」（按问答 / 周报 / 专项场景固定一套参数，而不是靠模型临场发挥）。

> **本大点的取舍（用户 2026-10-14 定）**：只做「**通道**」这一轴的第二条腿 ——用 **browser-use** 解决「取不到特定网址一手资料 / 无法在站内交互」；不做「多厂商可配置检索来源」（留待后续需求），不做 `competitor_sites` 每轮注入（见 D.3）。

### ③ 实现功能的技术方案（**已实现** · 2026-10-15 定稿版，与代码一致）

> **与 2026-10-14 草案的差异（三处，均有依据）**：① 草案让 `browser-use` 装进**主 venv** —— 实现期实测**装不进**（要替换被运行中的后端占用的 `pydantic_core.cp311-win_amd64.pyd`，并会卸掉 14 个包），改为**独立 venv + 子进程**（`Verdict/05` 裁定 3）；② 草案把它做成**第二个 `@tool`**、由开关追加挂载 —— 用户 2026-10-14 定稿改为**三个工作流工具**、取法由**签名**钉死（裁定 6/7）；③ 草案的 `competitor_sites` 每轮注入**取消**，改为靠 Agent 自觉路由 + 三处描述面（裁定 1/2）。其余差异（按 0.13.11 实际 API 写、设置项默认值、接入点清单）见下。

#### A. 一句话

把 **browser-use 开源库 tool 化**成网络搜索子 Agent 的取法之一，与既有 Tavily 全网检索组成**三种取法**：① 没有来源导向 → **只全网检索**（＝升级前行为）；② 有明确地址（用户给的 / 库里存的 / 上一轮挑出的）→ **只进这个网址**（零 Tavily 消耗）；③ 需要来源导向但两者都没有 → **先检索定位、再进站深抓**。三种取法做成**三个工作流工具**，子 Agent 只调主 Agent 点名的那一个。

#### B. 依赖与隔离（实现期第一道闸，按实际结论落地）

| 项 | 结论 |
|---|---|
| 装在哪 | **独立 venv `browser_venv/`**（Python 3.11.15，107 包）：主 venv **不能**装 —— 实测会卸掉 14 个包并要求替换正在被运行中后端占用的 `pydantic_core`（`WinError 5 拒绝访问`）。装包一律 `uv pip install`（**禁 `uv add` / `uv sync`**），装前先冻结依赖清单、装后 `uv pip check` |
| 怎么调 | **子进程**：`scripts/browser_runner.py` —— stdin 收 JSON、stdout 末行回 JSON；**密钥走 stdin，不进命令行、不进日志** |
| 版本 | `browser-use 0.13.11`（PyPI 发布版）；接入按其**实际 API** 写：`BrowserProfile` 承载 `headless/channel/user_data_dir/accept_downloads/proxy/allowed_domains`；`Agent(task, llm, browser, tools, use_vision, max_actions_per_step, max_failures)`；`max_steps` 是 `agent.run(max_steps=…)` 的参数；`Agent.run(on_step_start/on_step_end)` 提供步级回调（中断检查接在这里） |
| 本机三条硬约束（**不可删**） | ① `--headless=new`（Chrome 155 已移除旧式 `--headless`，否则 0.2s 静默崩溃）② `--no-sandbox`（受限令牌下建不了子进程）③ `NO_PROXY=127.0.0.1,localhost,::1`（否则 CDP 被系统代理劫持） |
| 配置与遥测 | `BROWSER_USE_CONFIG_DIR` 重定向到 `user_data/_runtime/browseruse/`（默认落在 C 盘用户目录）；`.env` 新增 `ANONYMIZED_TELEMETRY=false` |

#### C. 工具与跑手

- **`tools/browser_tool.py`（util，**不是** `@tool`）**：`browse_pages(task, urls=None, max_steps=None)` —— 已撤下 `@tool`、**不再挂载**，只被工作流调用；模型解析走**聊天侧同一处**判定（`api.customize.get_active_provider`，可按引用取 `get_provider_by_ref`）。
- **`scripts/browser_runner.py`（独立进程）**：编排一次浏览 —— profile 归位与清理、`Agent` 构造、步级回调、结果整形（`ok / urls_visited / steps / seconds / results / errors`）；`flash_mode` + 模型调用超时 120s，把单次浏览从 265s 压到约 100s。
- **失败降级**：站点打不开 / 超时 / 模型不支持视觉 / 无可用浏览器 → 返回**中文人话** + 回退已有 Tavily 结果，**不抛异常打断整轮**。
- **异步边界**：项目里 agent 调用是同步阻塞的（`api/server.py` 用 `asyncio.to_thread` 丢线程池），而 browser-use 只有 `await agent.run()` —— 故用**子进程**隔开，顺带解决依赖隔离。

#### D. 三种取法的工作流落地（用户 2026-10-14 定稿，见裁定 6/7）—— 已实现

1. **按「有没有明确来源」分三种取法**（不再一律"先搜后进"）：

   | 情况 | 取法 | 说明 |
   |---|---|---|
   | 要公开信息、**没有明确来源导向** | **只做全网检索** | 与升级前一致；Tavily 结果**自带网址**，所以"要一批网站的清单"用这一种就够 |
   | 要公开信息、**已有明确地址**（用户消息里的网址 / 数据库里的官网 / 上一轮挑出的关键页） | **只进这个网址** | **不先检索** → 零 Tavily 消耗、少一轮往返 |
   | 需要有来源导向、但用户与库里都没有 | **先检索定位、再进站深抓** | 检索定出 **1~2 个**最相关站点，再进站取一手资料 |

2. **取法做成三个「工作流工具」，由签名钉住**（裁定 7）：
   - **底层两工具降级为 util**：`tools/tavily_tool.internet_search` / `tools/browser_tool.browse_pages` 撤下 `@tool`、**不再挂载**，只被工作流调用。
   - **`tools/web_workflows.py`** 暴露三个工作流：`web_search_only`（只全网检索，签名**无 urls**）／`browse_only`（只进指定网址，签名**无查询词**）／`search_then_browse`（先检索定位 → 去重域名、跳过聚合/问答/电商站 → 按序取前 `max_sites` 个 → 进站深抓）。
   - **子 Agent 的工具面 = 这三个**（`web_search_only` 常挂；另两个随 `BROWSER_USE_ENABLED` 开关）；子 Agent 的提示词只剩一条铁律：**只调主 Agent 点名的那一个工作流**。
   - **主 Agent** 的任务描述里点名三种说法之一 + 对应工作流名；**判别口径**（2026-10-15 真机实测后写实）：**按"用户要什么"判，不是按"问题里有没有出现网址"猜** —— 要一批网站的清单 → ①；要某个具体站的网址**且**要它站内的内容 → ③；已给地址 / 库里有的 / 上一轮挑出的 → ②。另加一条硬规矩：**涉及具体网址、网站现状、价格与时效信息，必须经助手取证，禁止凭记忆作答**。
   - **记账不被遮蔽**：中间件把工作流记一条（分类表里映射为**内部工具**），底层真正花额度的调用由工作流**显式** `record(...)`（M4 口径：要能回答"这次为什么烧了额度"）。

3. **"网址信息"从哪来 —— 靠 Agent 自觉路由，不做每轮硬编码注入**（裁定 1/2）：
   - **不新增**每轮上下文注入（原设想的 `competitor_sites` 源**取消**）。设计思想：**用户在对话里提到后，由 Agent 自己**从数据库把竞品官网取出来、再交给网络搜索子 Agent 去动用浏览器。
   - 链路靠**三处描述面**（都是提示词/工具说明，不是硬注入）：主 Agent 读到的两个子 Agent `description`（数据库子 Agent 写明能给竞品官网网址；网络搜索子 Agent 写明能接收网址进站）＋ 子 Agent 的系统提示（按点名的取法行事）＋ `browse_only` 的工具说明（传 `urls` 即直接打开）。
   - **风险与预案**：最先看到消息的是**主 Agent**（它没有浏览器工具），是否会把网址转交属**必须实测的行为**。真机实测结论：**能转交**（见 `Done/05-…` §三），故预案未启用。

4. **两道纪律进代码（2026-10-15 真机实测驱动，见裁定 8 前的审计结论）**：
   - **同轮查询词去重**：同一轮里同一查询词（大小写/空格归一后相同）**直接挡回**；
   - **每轮检索次数上限**：设置项 `WEB_SEARCH_MAX_PER_TURN`（默认 **15**，0=不限），超出返回中文说明；
   - 被挡回时**不发起任何外部调用**。为什么进代码：提示词里的次数纪律**被实测无视**（审计见一轮 2 分钟约 30 次、含字面重复）。

5. **中断回执补强（2026-10-15，见裁定 8）**：`agent/turn_ledger.py` 记在跑轮次台账，后端启动时扫残留补落「本轮回答已被重启 / 停止打断（未完成）」。原来的占位只覆盖「用户点中断」（`AgentCancelled` 路径），进程被强杀时走不到。

6. **开关**：`BROWSER_USE_ENABLED`（`utils/settings.py::SPECS` 登记 → 设置页自动出现，标 `restart=True`）；**关掉时两个进站工作流不挂载**，子 Agent 只剩全网检索，行为与升级前等价（可安全回滚）。

#### E. 设置项与阈值（照 `SPECS` 登记，设置页「🌐 浏览器抓取」组）

| 键 | 默认 | 作用 |
|---|---|---|
| `BROWSER_USE_ENABLED` | 1 | 浏览器取法总开关（关＝两个进站工作流不挂载，行为回到现状；**改动需重启后端**） |

#### F. 模型与成本

- **浏览器侧模型**：新增独立设置项 `BROWSER_MODEL_REF`（留空＝跟随聊天侧当前生效配置）。**实测三款模型**（同站点同任务）：GLM-5.3-Flash 干净可用（真点击、零结构化输出报错）＞ agnes-3.0-flash 真点进但会丢步（兼容模式可用）＞ deepseek-flash **不可用**（用自家 `<｜｜DSML｜｜ calls>` 方言，`response_format` 亦不支持）。结论：**浏览器侧要求结构化输出能力**；`.env.example` 已注明默认模型须有多模态能力。
- **视觉**：本大点**不启用视觉模式**（`EXP_VISION=1` 实测打坏 browser-use 的输出解析）。默认模型按 `supports_vision` 判定仍保留在代码里。
- **成本可见**：工作流返回 `steps/seconds` 等；`agent/usage_counter.py` 把三个工作流名映射为**内部工具**，底层调用记 `retrieval_external`。
- **量级预期（如实写明）**：浏览器侧是**多步 LLM 循环**，单次 token 消耗显著高于一次 Tavily 检索 —— 因此才有 E 的三个闸（步数/超时/URL 数）与"先检索筛选、只让浏览进 1~2 个最相关站点"的设计。

#### H. 验收判据（可复跑 · 实际执行版）

1. **无网址场景等价**：`BROWSER_USE_ENABLED=0` 时子 Agent 工具面只剩 `web_search_only`（单测断言工具列表），一轮问答走 Tavily，行为与升级前等价。

5. **中断回执**：进程被杀后重启，未跑完的轮次补落占位且**幂等**（单测 6 项）。
6. **回归**：全量单测 + 启动冒烟 + 设置页出现全部新项。
7. **对话实验（真机，2026-10-14/15 用户执行）**：① 竞品官网链（主 Agent 经数据库子 Agent 取官网 → 交网搜子 Agent 进站）**成立**；② 纯网址进站点击互动**成立**（同页弹层的交互能被识别并点击）；③ 先检索定位再进站（sakuracat 官网）**成立**，且如实报告候选站不可用。

**C2 保护名单**（每个工作目录根 `_保护名单.md`）

- **格式**：一行一条，`#` 注释；支持三类写法——纯文件名（该目录下同名文件）· 以 `/` 结尾的目录前缀（**递归保护其下全部**）· 含 `*` / `?` 的 glob；

## 07 资源嗅探与抓取

> 状态：**方案已定（2026-10-18）** —— 调研期产物见 `research/07-资源嗅探与抓取.md`（§二 只读取证 · §三 成本最低方案的三组对照实测）。

### ① 应对什么问题

**起因**：06 收尾后的一问——`use_browser` 能在网站里点击，那点「下载」按钮是否真的把文件下到了本地、且落点能被 Agent 与用户使用？只读取证得到的现状（2026-10-18）：

| 事实 | 证据 |
|---|---|
| 浏览器侧**下载被关**：`BrowserProfile.accept_downloads=False` | `scripts/browser_runner.py:146` |
| **点击动作是允许的**（排除列表只有 search / write_file / read_file / replace_file / upload_file） | `scripts/browser_runner.py:48` |
| 即便打开下载，库默认落盘目录是**系统临时目录**下的独立子目录，与账号工作目录无关 | `browser_venv/Lib/site-packages/browser_use/browser/profile.py:475-490` |
| 浏览器临时 profile 在 `finally` 里整体删除 | `scripts/browser_runner.py:139-141` |
| 现行唯一能把远程文件弄到本地的路是 `run_shell_command` 的 `curl`：URL 必须已知、无站点会话、不执行 JS | `tools/_runtime/shell_runtime.py` 的 `ALLOWED_COMMANDS` |

**问题**：Agent 在站点里「看得见资源、点得动按钮，却拿不到文件」；而按已知地址用 `curl` 又覆盖不了「点击后才出现」「需要站点会话」「JS 生成签名地址」这三类真实情况。缺的是：**在页面里嗅出资源 → 带着当前会话去取 → 落进账号工作目录 → 留元数据（来源页、体积、类型、去重）**。

### ② 功能（意向）

- **嗅探**：从当前页面与相邻页面里识别可下载资源（直链、图片、附件、音视频分片等），并区分「需登录/需点击才生成」的类别；
- **抓取**：带着当前浏览器会话（Cookie/UA）取资源；体积、类型、数量设闸；重名与重复内容去重；
- **落点**：资源进入该账号的工作目录，前端文件面板可见；图片类直接能在气泡里显示（沿用 06 的收口）；
- **留痕**：每条资源记来源页、请求地址、体积、MIME，写入该轮证据；
- **形态**：独立工具，或专用资源抓取子 Agent —— 两者能约束的范围不同，留待调研比较。

### ③ 方案（意向取舍与实现清单）

> **来源标注**：本节结论来自 2026-10-18 的只读取证与实测 —— ① `browser_venv` 里直接起 `Browser`（不经过 LLM、零额度），对同一套 profile/env 做三组对照；② 库源码行号；③ 项目现有调用链（`tools/browser_tool.py` → `scripts/browser_runner.py`）。

#### ③.1 意向取舍

| 意向轴 | 本次取舍 | 依据 |
|---|---|---|
| 形态 | **不新增工具、不新增子 Agent**；只修 browser-use 的下载落点 | 对照实测：`accept_downloads=False` 挡不住下载（该开关在 0.13.11 里基本未被使用），真正起作用的是 `downloads_path` |
| 落点 | 账号**当前启用工作目录**下的 `_downloads/browser_<时间戳>/` | 现状默认落到 `%TEMP%/browser-use-downloads-<id>`，与工作目录无关，前端看不见 |
| 回执 | 运行结束把下载清单（文件名 / 体积 / 相对路径）写进工具返回文本 | 全库检索无「把本次下载回给模型」的通道，模型只能笼统说"点了按钮" |
| 清理 | 本次运行目录若为空则删除；不保留空气泡 | 实测 `tmp/` 下已堆积 138 个空目录（本轮已清） |
| 安全 | 下载目录必须落在当前启用工作目录内（沿用工作目录那套路径校验）；站点给的文件名先清洗再去重 | 工作目录边界是 06 已立的硬约束，下载不能成为绕过口 |
| 体积 | 单文件上限 100 MB；超限**不删源文件**，只在回执里标「超限未收」并给出体积 | 浏览器侧没有字节闸，只能在落盘后判定 |
| 批量嗅探 | **本次不做** | 用户裁定按成本最低路线走；超出部分列为边界 |

#### ③.2 实现清单（三处小改 + 一次收尾）

| # | 文件 | 改什么 |
|---|---|---|
| 1 | `tools/browser_tool.py` | 起子进程前解析当前启用工作目录，建 `_downloads/browser_<时间戳>/`，通过请求体把 `download_dir` 传给 runner（不传则沿用库默认，行为与今天一致） |
| 2 | `scripts/browser_runner.py` | `BrowserProfile` 增加 `downloads_path=<download_dir>`；跑完扫该目录，结果里加 `downloads: [{name, bytes, rel}]`；`finally` 里目录为空则删除 |
| 3 | `tools/browser_tool.py`（返回） | 正文追加一行「本次下载 N 个文件：…（位于工作目录 `_downloads/browser_<时间戳>/`）」；其中图片另附 `[[img:<相对路径>]]`，沿用 06 的前端渲染 |
| 4 | 收尾 | 清空 `user_data/_runtime/browseruse/tmp/` 下的历史空目录（本轮已完成 138 个）；另有一批非空的 `browser-use-user-data-dir-*` 残留，需另行确认后再清 |

> **实现期修正（2026-10-18）**：真机发现把 `downloads_path` 直接指到 `<工作目录>/_downloads/browser_<时间戳>/` 时，watchdog 报「Download did not complete within 20 seconds」、文件始终不落盘；同一次任务改指项目内 `user_data/_runtime/browser_dl/run_<时间戳>/` 即正常。故实际实现为「**暂存 + 搬移**」：Chrome 先落暂存目录，跑完由 `_move_downloads()` 搬进工作目录（重名加后缀 `a-2.pdf`，搬完删暂存）。根因尚未查清（疑与本机受限令牌下该子树的 ACL 有关），已如实写进代码注释与 `Done/07` 记录。

#### ③.3 验收判据

1. 在带下载按钮的站点上点下载后，文件出现在 `<当前启用工作目录>/_downloads/browser_<时间戳>/` 下，前端「📁 工作目录」能逐级点到；
2. 工具返回文本里能读到文件名与体积（模型据此向用户交代"下载了什么"）；
3. 下载目录为空时不残留；
4. 下载目录无法越出当前启用工作目录（路径校验拒绝时不落盘并说明原因）；
5. 不新增任何外部调用额度（浏览器子进程本就在跑）。

#### ③.4 明确不做（本点边界）

- 不做「一次嗅探页面全部资源并批量下载」；
- 不做下载队列、断点续传、并发限速；
- 不改 `allowed_domains` 的推导口径（仍按传入网址推导）；
- 不为下载单独开一个 Agent 工具入口。
