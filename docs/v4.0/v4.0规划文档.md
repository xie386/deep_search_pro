## 01 度量口径收口工程

### ① 应对什么问题

路由质量的度量体系本身有三类**结构性缺陷**，导致「该不该上更强的机制（Jev 仲裁层）」这类判断建立在一个错误的读数上：

1. **目标不可达**：`precision@3 ≥ 0.7` 这条立项/软判据在现题库上**结构上限只有 0.536**——24 道非噪声题里 13 道只有 1 个可接受工具，而 top3 恒 3 条 → 这些题单题封顶 1/3。这条线**恒真**，等于没有触发条件（「只要去看就一定有问题」）。
2. **指标把正确行为算进坏账**：灰区比例把「噪声题的正确回退」也计入（7/30 道噪声题本该回退、实测也确实全部正确回退），于是灰区**天然 ≥ 0.233**；读数 0.267 看起来像 26.7% 的路由失败，实为「6 道噪声正确回退 + 2 道真没把握」。
3. **答案键与工具能力不符**：唯一未命中题 `city-climate`（气候知识问答）期望的 `mcp:city/search_city` 只返回地名/行政区/经纬度/人口/地点类型，**答不了气候问题**；这既拿错期望扣路由的分，又掩盖了「它其实是被自信路由到了错工具（z = 3.22）」这个真问题。

**证据（本机可复现，2026-10-09 实跑）**：`.venv/Scripts/python.exe tests/live/m5c_router_bench.py` 复现交接基线 `0.292 / 0.674 / 0.792 / 0.500 / 0.000` 与 `router_bench_baseline.json` **逐项一致**；三类缺陷的推导、逐题拆解与阈值扫描原始数据见 `research/01-度量口径收口工程.md` §二 / §四。

### ② 功能

把尺子先校准，让后续所有路由工作有**可达**的判据：

- 新增 **`precision@1`**（top1 是否可接受；**可达**，作为主力信号）与 **`precision@3_ceiling`**（结构上限，**脚本自算**，改题库自动跟着变，不会再漂）；
- 灰区**分两栏**：`gray_ratio`（全题，含正确的噪声回退）+ `gray_ratio_nonnoise`（非噪声题里的灰区，真信号）；
- 注入量按**实际注入形态**统计（完整卡数 + 注入字符，整池全量为参考）；
- 判据与 **Jev 立项线**重写为可触发的两条：软判据 = `precision@1 ≥ 0.7` ｜ `hit@3 ≥ 0.9` ｜ 噪声假阳性 ≤ 0.1 ｜ 非噪声灰区 ≤ 0.2；立项线 = **非噪声灰区题 ≥ 5 道 或 噪声假阳性 > 0.1**（原 `precision@3 < 0.7` 作废）；
- 题库 `city-climate` 按工具实际能力改判；阈值 `Z_STRONG` 依扫描重标定 2.4 → 3.3（噪声假阳性归零，四个质量指标不变）。

## 02 决策模型仲裁层（旧称 Jev 仲裁层）

> **状态：已完成(2026-10-13)

### ① 应对什么问题

素材层落地后，路由的**召回**这一侧已经打通（top3 含正解 **23/23**），但**「从候选里定下第一个」这一步仍是短板**：同一次运行里 23 道非噪声题有 **4 道 top1 选错**（`pdd-search`、`trip-route`、`compare-price`、`city-basic`），而现有机制**没有任何纠错手段**——快路的 `confident` 衡量的是"有没有明确目标"（z / 词法分数），**不是"第一个选得对不对"**，所以选错的 4 道里有 3 道是"自信题"，连灰区回退都拦不到。

同一批候选上，**决策模型（不吃文本、只给概率的一类新模型）的精排能力足够用**：第一期在"候选含正解"的 18 道上**全对**（18/18）；第二期召回已覆盖 23/23，它仍有 **2 道失手，且都是多步链题**（见下）——两轨实测把 `precision@1` 从 **19/23（0.826）抬到 21/23（0.913）**，噪声假阳性保持 **0.000**，单次决策调用的 state 只有 420~470 字符。另有一类失分**本批不治**：多步链题的单选退化（`trip-tickets` / `trip-transfer` 等失败姿势一致——都选了链条第一步 `get-current-date`），留作第二批。

**证据（可复现）**：
- 指标与逐题：`research/02-Jev仲裁层-demo/jev_track_metrics.json`（同仪器基线）· `jev_ag2_result.json`（两轨方案指标）· `jev_ag_items.jsonl` / `jev_ag2_items.jsonl`（逐题原始）
- 复跑：`unset PYTHONPATH && .venv/Scripts/python.exe docs/v4.0/research/02-Jev仲裁层-demo/jev_tracks_baseline.py`（三轨基线对账）、`…/jev_ag2_tracks.py`（两轨 B/C/D 复测）
- 分析与复盘：`research/02-Jev仲裁层.md` §十八（第一期 A~G 对比）· §二十（第二期两轨实测，含链题清单 §20.3）· §二十二（主路三条决定与噪声假阳性的单变量实验）
- 口径警示：素材层会漂移，`Done/01` §7.5 记的 0.870 属 10-09 那版素材、今日不可复现（§十九 / §二十一）；故本大点验收一律用**同仪器同期基线**（见 `Verdict/02-决策模型仲裁层.md` 裁定 5）

### ② 功能

**一句话**：当路由给回的两个候选咬得很近时，系统会请决策模型**复核一次**再定夺——做完之后，**在候选互相咬住的那些题上，Agent 第一次就选对工具的概率提高**（同口径实测 19/23 → 21/23），而现有能力与失败行为**一字不改**。

具体多了三样东西：

1. **一次「第二意见」**：只在触发条件下发生（近并列；默认关），选中结果被当作新的候选顺序；不改变 prompt 的注入量，也不改变「要不要用工具」的判定（噪声仍由路由器负责）。
2. **一条可配、可回退的生产接口**：不可用（超时 / 无额度 / 形状错 / 限流）时行为**逐字等于现状**；配置项全开（模型、门限、top-k、state 模板、预算、缓存开关）。
3. **一套可观测与可复算的工程件**：决策缓存（同池版本 + 同问题直接复用）、计量（token 走 `usage_events`、失败分类走 `failure_events`、缓存命中单独计数）、审计（每次精排的选择、概率、间距、耗时），为第二批链题专项留好位置。

### ③ 实现功能的技术方案

**形态：两段式决策精排**（主路；裁定 1）。不替换任何现有环节，只在"选"这一步加一层。

```text
用户消息
 └─ 现有快路（词法 + 向量 + 阈值；本地毫秒级，不动它）
 → 候选 top-k + fused / z / lexical 分数 + confident
 ├─ 触发条件命中（融合分间距 fused[top1] − fused[top2] < 门限）
 │ → 决策精排：候选卡片 + 用户消息 → 决策模型 choice → 采用其选择
 │ └─ 失败（超时 / 402 / 400 形状 / 限流）→ 逐字回退现状
 └─ 未命中 → 现状直通
```

1. **触发**：`decision_trigger = near_tie | always | gray`（默认 `near_tie`）；`decision_tie_threshold` 起点 **0.0005**；每次触发把间距写进审计日志，供后续在更大题集上复标。来源：`Verdict/02-决策模型仲裁层.md` 裁定 2 · `research/02-Jev仲裁层.md` §22.1 · 标定数据 `research/02-Jev仲裁层-demo/jev_near_tie_calibration.json`。
2. **state 构造**：`候选工具卡片（名称 / 关键词 / 能力说明，取**素材层之后**的字段）+ 本轮用户消息`；**选项键用 `e.ref`（显示键，与题库/实测同形）**，回填时映射回路由器内部键 `source:ref`；模板版本 `decision_state_template = v2` 计入缓存键（改 state 构造必须 +1）；**默认不含**对话历史、人格、画像（留开关）。来源：§十八（state 与选项粒度决定成败）· §二十（卡片必须用素材层之后的文本）。
3. **问法**：`choice`；`instructions = 从候选里选出最合适的一个工具`；`criteria = {候选 ref: 该工具的能力说明}`。**首批不把"要不要用工具"交给决策模型**（噪声归路由器）。来源：§二十（模板实测）· 裁定 3。
4. **候选集**：`decision_top_k = 3`（可配 3~8），取快路 `order` 的前 k 条；**决策调用的 state 约 420~470 字符**——这是发给决策模型的上下文大小，**不是**给主模型的 prompt 注入；本层不改变 prompt 注入量。来源：§二十。
5. **模型与凭据**：读项目 `.env` 的 `DECISION_MODEL_BASE_URL` / `DECISION_MODEL_NAME` / `DECISION_MODEL_API_KEY`；请求地址 = `base_url` 去掉 `/api/v1` 后接 `/api/alpha/decisions`。**总开关**（2026-10-13 用户裁定）：**账号级字段 `accounts.decision_router`，由前端 AI 对话区的开关切换**——开不开**不写进 `.env`**（`.env` 只留模型与凭据），默认关。**不硬编码厂商**。来源：§十七 Q5 / Q6 · §十一 · 2026-10-13 用户裁定。
6. **缓存**：键 = `账号 + 归一化问题文本 + pool_version + 素材指纹（source/ref/name/keywords/abilities/abilities_user —— 素材层改措辞即失效）+ state 模板版本 + 模型 ref`；**时效 24 小时**（`decision_cache_ttl_h`，2026-10-13 用户裁定：过期作废**并从缓存文件里删掉**）；命中直接复用上次选择与概率。来源：§十七 Q8 · §九·F · 2026-10-13 用户裁定。
7. **计量**：模型 token → `usage_events`（输出 token 免费）；失败按类型（超时 / 402 / 400 形状 / 限流）→ `failure_events`；缓存命中单独计数；每次精排落一条审计（选择、概率、间距、耗时、是否命中缓存）。来源：§九·F · §十二。
8. **fail-safe**：任何异常**逐字回退**现状（现有全量注入）；本层只影响"工具怎么被想起"，**不参与能不能执行**。来源：§十二。
9. **代码落点**：启用 `tools/tool_router.py` 的 `_route_provider()` 缝隙；新增模块（决策客户端 + 精排判定）的**位置按 `docs/文件存放规则.md` 第三节判据定，新增文件前先查该文件**。来源：预研 §3.4 · §九。
10. **配置项清单**（全部可配、默认关）：**开关 = `accounts.decision_router`（前端按钮，不走 `.env`）** · `decision_base_url` · `decision_model` · `decision_api_key` · `decision_trigger` · `decision_tie_threshold` · `decision_top_k` · `decision_state_template` · `decision_timeout_s` · `decision_max_retries` · `decision_cache_enabled` · `decision_cache_ttl_h`（**默认 24 小时，过期作废并从缓存文件里删除**） · `decision_budget_per_day` · `decision_budget_per_session`。
11. **明确不做**：不替换词法/向量快路；不做关键词黑名单式补丁；不在没有基准的情况下调阈值；不改 `card_text` 结构；不把"要不要用工具"交给决策模型；首批**不做**链题选项粒度改造（第二批）。
12. **验收判据**（裁定 5）：① `precision@1` ≥ 同一次运行路由器基线的 90%；② 噪声假阳性不得高于路由器；③ 附报 `hit@3` / 平均注入字符 / 调用次数 / 延迟。参考读数：第二期两轨基线 0.826 → 目标 ≥ 0.743，精排实测 0.913。跑基准时**连素材快照一起记录**（`pool_version` + 草稿文件哈希）。
13. **验证方式**：离线（同一次运行跑"路由器基线 / 精排"两遍比指标）+ 专项（4 道链题单列）+ 真机（网页端，含链题与噪声题的会话）；脚本自测与客户端测试**两步都不跳**。来源：§二十 · 项目「bug 修复」阶段纪律。
14. **测评期间强制关闭**（2026-10-13 用户裁定 6）：03 路由质量测评走 `/api/chat?probe=1` → 后端 `route_tools(allow_decision=False)` → **无论开关状态一律不参与，且不读不写缓存**，并落一条 `seen + eval_off` 审计。理由：03 测评量的是「路由器 + 素材层」的水平，带上决策层就换了仪器，数字与 01/03 历史基线**不可比**。另：01 的基准（`tests/live/m5c_router_bench.py`）直接调 `router.decide()`，本来就不经过本层，无需改动。来源：Verdict 02 裁定 6。

### ① 应对什么问题

- **测评面太窄**：路由质量的测评与修复（尤其**真机**测评）目前只覆盖「尼古喵喵」**一个账号当前的工具池**——换账号、或同一账号增减工具后，结论**不可迁移、也没有可比基线**。
- **词法经验没有落点**：往期改「工具的应用场景 + 方法介绍词段」（`keywords` / `abilities_user` / `name`）的经验散在文档与本机脚本里；用户自己改完**无从验证「到底变好了没有」**。
- **两条腿性质不同、此前混着走**：算法侧的经验（阈值、表征、判据）属**项目代码**（一次改到位、全账号受益）；词法侧属**账号数据**（每账号不同，只能由用户维护）。混着走的结果是两头都没沉淀。

**证据**：现状盘点见 `research/03-….md` §二（离线路由基准是项目级尺子、真机探针是脚本且题集绑账号）；三类波动见 §三；试点与既往可复用资产见 §七。

### ② 功能

分两条腿给出**明确归属**：

1. **算法侧（项目级）**：把往期在「尼古喵喵」池上验证出的算法/判据经验**直接改进项目路由代码**——全账号受益，不由用户端碰。
2. **词法侧（账号级，用户自维护）**：在「🧩 技能与工具」里**平级于 CLI 面板 / 第三方 CLI / MCP / API** 新增一个**工具池测评**模块：
 - 列出**本账号全部工具**与其**路由质量数据大屏**；
 - 动作流程：**生成真机题目**（覆盖全部工具的单工具题 + 适量多工具题 + 少量噪声题）→ **测评**（**提前声明网络搜索额度消耗**；只产出「工具调用记录表单」，不判对错）→ **判分**（Agent 判分 + **人类二次打分**）→ **词法改进建议**（Agent 带既往词法经验）+ 静态体检的硬规则结论 → **写入大屏**，并给出下一轮要改哪几条的排序；
 - 后端配一个**针对当前账号工具池的独立测评 Agent**（**不纳入主 Agent 体系**），职责与按钮一一对应（出题 / 执行 / 判分 / 建议 / 归档）。

#### D. 出题规则（题量公式定稿）

设池内能力条目数 = **N**（当前尼古喵喵池 N=29）：

| 类 | 条数 | 约束 |
|---|---|---|
| **单工具题** | **N 条**（每个 `ref` ≥1 题） | 题面**自足**（无「它/这个」等先行词）；同一 `ref` 的题面不得与往期重复 |
| **多工具题** | **max(2, ceil(N/6))** 条（N=29 → 5 条） | 正确答案须是**可并存的多个 ref**（跨来源优先） |
| **噪声题** | **2 条**（上限 2，且 ≤ N/10） | 必须**池内确实无解**；**答案键要与工具能力相符**（大点 01 的 `city-climate` 教训） |
| 合计 | **N + max(2,⌈N/6⌉) + 2**（N=29 → **36 题**） | 与 v3.1 的 43 题**同量级** → 单轮耗时与额度可比 |

出题产物**先过你的人眼闸门**（可改题面、可改预期工具、可删题）→ 才允许执行。

### ① 应对什么问题

**方向一 · 文档架构本身缺设计约束。** v3.0 立《文件存放规则.md》整治的是「项目文件该放哪个目录」——它管的是**归属**；没管**架构**：一个版本目录内部如何编排、记录性质文档（规划 / 调研 / 裁定 / 实现记录 / 逐文件带读 / 交接 / 备份）各自扮演什么角色、谁是权威谁只读、彼此如何引用、哪些状态字段必须同步。这些此前靠惯例与助手记忆维持，已经出现事实性偏差（本次调研逐条核实）。

## 05 网络搜索子Agent升级

**问题**：产品的「外部信息入口」集中在一个工具、一个厂商、一个额度池上 —— 检索的**通道可替换性**、**额度可见性与可控性**、**单次调用可中断性**都没有着落；且上面那些能力参数目前只能靠模型临场想起来传，缺一层「按场景固定策略」。

### ② 功能（意向）

把网络搜索子 Agent 从**单一工具**升级为**可按场景配置、可观测、可扩展**的检索能力。意向轴（**具体取舍留调研**）：

- **通道**：是否从「一个厂商一个工具」变成「可配置的检索来源」（新增第二引擎 / 复用既有 HTTP 抓取 / 允许用户自配来源——须与本项目「配置导向、不写死厂商」的偏好一致）；
- **额度与成本**：是否给搜索调用加本地计量与闸门（现只有归类、不设闸），额度紧张时能否自动降级到零消耗通道；
- **可控性**：单次检索能否被打断、能否设更细的超时预算；
- **质量**：时效 / 双语 / 正文抓取这些既有能力是否要「策略化」（按问答 / 周报 / 专项场景固定一套参数，而不是靠模型临场发挥）。

### ③ 实现功能的技术方案

> **来源标注**：`research/05-网络搜索子Agent升级.md` §一（用户需求与目的，逐字）· §二 1.1/1.3（Tavily 端点与计费）· §三 2.3/2.5/2.6（browser-use 用法与接入面）· §六（实现级事实与本项目接入面）。

#### A. 一句话

把 **browser-use 开源库 tool 化**成网络搜索子 Agent 的第二个工具，与既有的 `internet_search`（Tavily）组成**两段式检索**：**没有网址 → 只用 Tavily（＝现状）**；**有网址 → 先用 Tavily 快速定位与筛选 → 再用浏览器工具打开关键页面做交互或深度抓取**。

#### C. 新工具：`tools/browser_tool.py`

- **形态**：与 `tools/tavily_tool.py` 同构的 `@tool`，每次调用先 `monitor.report_tool(tool_name="浏览器抓取工具", args=…)`（前端靠它推进度）。
- **签名**（草案的「网址操作」落到参数上）：

```python
@tool
def browse_pages(task: str, urls: list[str] | None = None,
                 max_steps: int = 15, allowed_domains: list[str] | None = None) -> dict
```

- `task`：用自然语言写清"要在这些页面拿什么"（价格 / 参数 / 公告 / 日期 …）。
- `urls`：目标页；**browser-use 的 `directly_open_url` 默认为 True**（官方：「任务里带 URL 会直接打开」）—— 因此把 URL 拼进 task 即可直达，不必让模型先"决定去访问"。
- `allowed_domains`：只允许在给定域名内活动（官方参数，TLD 通配符被禁）；未传时**由 `urls` 的域名推导**，避免跑偏到无关站点。
- **内部构造**（全部为官方参数）：

```python
browser = Browser(headless=True, user_data_dir=<临时 profile>,
                  proxy=ProxySettings(server=…, bypass="localhost,127.0.0.1"))
tools = Tools(exclude_actions=["search", "write_file", "read_file",
                               "replace_file", "upload_file"])   # 搜索走 Tavily；不给文件写权限
agent = Agent(task=task, llm=<本项目模型>, browser=browser, tools=tools,
              use_vision=<按该配置的 supports_vision 决定>,
              page_extraction_llm=<小模型>,
              max_steps=max_steps, calculate_cost=True,
              allowed_domains=allowed_domains or 推导值)
history = asyncio.run(agent.run())        # 见「异步边界」
```

  理由：`exclude_actions` 去掉内置 `search`（**搜索只走 Tavily**，与草案一致）、去掉全部文件写/上传动作（本项目对"Agent 写能力"另有 06 大点，本大点不开口子）。
- **返回结构（给模型看的东西）**——只回它用得上的，不回原始 HTML：

```python
{"ok": True, "urls_visited": [...], "steps": history.number_of_steps(),
 "seconds": round(history.total_duration_seconds(), 1),
 "cost_usd": history.cost if calculate_cost else None,
 "results": [{"url":…, "title":…, "content":…}],       # 来自 history.extracted_content() / final_result()
 "errors": history.errors()[-3:]}                       # 失败也如实回传
```

- **异步边界（本项目的硬约束）**：项目里 agent 调用是**同步阻塞**的（`api/server.py` 用 `asyncio.to_thread` 丢线程池），而 browser-use 只有 `await agent.run()`。因此工具内部用 `asyncio.run(...)`：它运行在**工作线程**里（那里没有事件循环）→ 安全；并加一道守卫：若检测到当前线程已有运行中的事件循环，则改在**新线程**里跑，避免 `RuntimeError: asyncio.run() cannot be called from a running event loop`。
- **取消与超时**：`max_steps`（默认 15，设置页可调）+ 总超时双闸；步间若 browser-use 暴露步级回调则接 `agent/cancel.py::check()`（**该回调是否存在未验证**，见 `research/05` §六 6.3-4；未暴露则以 max_steps/超时兜底，并在记录里写明）。
- **失败降级**：站点打不开 / 超时 / 模型不支持视觉 / 无可用浏览器 → 返回 `{"ok": False, "error": <中文人话>, "fallback": <已有 Tavily 结果>}`，**不抛异常打断整轮**（与 `tavily_tool` 的代理降级同款风格）。

#### D. 三种取法的工作流落地（2026-10-14 用户定稿，见 `Verdict/05-…md` 裁定 6）

1. **按「有没有明确来源」分三种取法**（不再一律"先搜后进"）：

   | 情况 | 子 Agent 的取法 | 说明 |
   |---|---|---|
   | 要公开信息、**没有明确来源导向** | **只做全网检索**（只 `internet_search`） | 与升级前一致 |
   | 要公开信息、**已有明确地址**（用户消息里的网址 / 数据库里的官网） | **只进这个网址**（只 `browse_pages`） | **不先检索** → 零 Tavily 消耗、少一轮往返 |
   | 需要有来源导向、但用户与库里都没有 | **先检索定位、再进站深抓** | 检索定出 **1~2 个**最相关站点，再进站取一手资料 |

2. **模式怎么做 —— 做成三个「取法工作流工具」，取法由签名钉住**（2026-10-14 用户提出、评估后采纳，见裁定 7）：
   - **底层两工具降级为 util**：`tools/tavily_tool.internet_search` / `tools/browser_tool.browse_pages` 撤下 `@tool`、**不再挂载**，只被工作流调用。
   - **新文件 `tools/web_workflows.py`** 暴露三个工作流：`web_search_only`（只全网检索，签名无 urls）／`browse_only`（只进指定网址，签名**无查询词**）／`search_then_browse`（检索定位 → 去重域名、跳过聚合/问答/电商站、取前 `max_sites` 个 → 进站深抓）。
   - **子 Agent 的工具面 = 这三个**（`web_search_only` 常挂；另两个随 `BROWSER_USE_ENABLED` 开关）；子 Agent 的提示词只剩一条铁律：**只调主 Agent 点名的那一个工作流**。
   - **主 Agent** 的任务描述里点名三种说法之一 + 对应工作流名；其余口径不变（库里有的先取网址再原样转交；可按信息需求拆多次调度；②失败由主 Agent 决定是否另发 ①/③；③进站 ≤1~2 个站点由工作流内部限制）。
   - **记账不被遮蔽**：中间件会把工作流记一条（分类表里映射为**内部工具**），底层真正花额度的 Tavily/浏览器调用由工作流**显式** `record(...)`（M4 口径：要能回答"这次为什么烧了额度"）。
   - 残余软肋（如实记录）：**"选哪个工作流"仍是主 Agent 传话 → 子 Agent 挑工具**，仍是模型判断；若实测仍不听话，可把三个工作流直接拆成三个严格子 Agent（工具集强制），那时是十几行的改动。

3. **"网址信息"从哪来 —— 靠 Agent 自觉路由，不做每轮硬编码注入**（2026-10-14 用户拍板，见 `Verdict/05-…md` 裁定 1）：
   - **不新增**每轮上下文注入（原设想的 `competitor_sites` 源**取消**）。设计思想：**用户在对话里提到后，由 Agent 自己**从数据库把竞品官网取出来、再交给网络搜索子 Agent 去动用浏览器；同时保持 browser-use 的 **`directly_open_url=True`**（任务串里带 URL 即直达）。
   - 因此链路要"顺得通"，靠**三处描述面**（都是提示词/工具说明，不是硬注入）：
     - 主 Agent 读到的两个子 Agent `description`：① 数据库子 Agent 里写明它能给出**竞品官网网址**（`company_competitors.website`）；② 网络搜索子 Agent 里写明它能**接收网址并进入该页**做交互/深抓（否则主 Agent 想不到把网址转给它）；
     - 网络搜索子 Agent 的 `system_prompt` 第 6 条纪律（**按主 Agent 声明的三种取法**行事，规则见本段第 1~2 条）；
     - `browse_pages` 的工具说明里写明"传入 `urls` 即直接打开该页"。
   - **风险（用户明确指出）**：最先看到消息的是**主 Agent**，而它**没有** browser_tool —— 它是否会把网址转交给子 Agent，属**必须实测的行为**（见 H 的两轮对话实验）。
   - **预案**（实现期分叉，届时按 `Verdict/05` 追加裁定再动）：实验不通过时，在**主 Agent 的提示词**里加一条"消息含网址 → 交给网络搜索子 Agent"的路由图（仍属提示词层，不违反"不硬编码注入"）。
4. **开关**：`BROWSER_USE_ENABLED`（`utils/settings.py::SPECS` 登记 → 设置页自动出现）；**关掉时该工具不挂进子 Agent**，行为与升级前逐字等价（可安全回滚）。

#### E. 设置项与阈值（照 `SPECS` 登记，设置页即显示）

| 键 | 默认 | 作用 |
|---|---|---|
| `BROWSER_USE_ENABLED` | 1 | 浏览器工具总开关（关＝工具不挂载，行为回到现状） |
| `BROWSER_MAX_STEPS` | 15 | 单次浏览任务最大步数（官方默认 100，本项目按"取一页要点"的用途收紧） |
| `BROWSER_TASK_TIMEOUT_S` | 180 | 单次任务总超时 |
| `BROWSER_MAX_URLS` | 3 | 单次任务最多打开几个页面 |
| `BROWSER_HEADLESS` | 1 | 无头/有头（排查时可开有头） |

#### F. 模型与成本

- **浏览器侧模型**：沿用本项目既有的「定制助手 · 模型选型」（`llm_providers`）当前生效那条配置 —— 与"配置导向、不写死厂商"的既有偏好一致，不新增一套模型配置；`page_extraction_llm` 用同配置（官方建议"它只负责抽文本，可用小模型"）。
- **视觉**：按该配置的 `llm_providers.supports_vision` 决定 `use_vision`（True → `"auto"`；False → `False`），避免把截图喂给不支持视觉的模型。
- **成本可见**：`calculate_cost=True` + 返回 `steps/seconds/cost_usd`；`agent/usage_counter.py` 里登记新工具名（kind 归 `retrieval_external`）。
- **量级预期（如实写明）**：浏览器侧是**多步 LLM 循环**，单次 token 消耗显著高于一次 Tavily 检索 —— 因此才有 E 的 `BROWSER_MAX_STEPS`/超时/URL 数三闸；这也是"先用 Tavily 筛选、只让浏览器打开关键页"这条工作流的成本理由。

#### H. 验收判据（可复跑）

1. **无网址场景逐字等价**：`BROWSER_USE_ENABLED=0` 时子 Agent 工具面与今天一致（单测断言工具列表）+ 一轮问答走 Tavily。
2. **有网址场景**：给 `https://www.zhiben.cn/?products_1/`（库里已存的竞品官网）提"当前主要产品的价格"→ 工具返回含 `url/content/steps/seconds` 的结构化结果，且**逐条带来源 URL**。
3. **降级**：站点不可达 / 超时 / 模型无视觉 → 返回中文人话 + 回退 Tavily 结果，整轮不崩。
4. **上限生效**：故意给 5 个 URL → 实际打开 ≤ `BROWSER_MAX_URLS`；步数 ≤ `BROWSER_MAX_STEPS`。
5. **回归**：全量单测 + 真机客户端点检（设置页出现 5 个新项、开关可保存、无 JS 异常）。
6. **依赖与启动**：`uv pip check` 干净 + 启动冒烟通过（新闸 `tests/testclient/test_app_startup_smoke.py`）。
7. **对话实验 1（路由链，用户 2026-10-14 指定）**：问「查看我收藏的 xx 品牌竞品的官网并获取一下他们 xx 商品的最新价格」→ 观察：主 Agent 是否**先经数据库子 Agent** 取到该竞品官网 → 再把网址交给**网络搜索子 Agent** → 子 Agent 是否调用 `browse_pages`、并因 `directly_open_url=True` 直接打开该页。留痕：`data/audit/` 工具调用日志 + 前端右栏工具调用序列 + 落地截图。
8. **对话实验 2（纯网址，同上指定）**：问「看一下 <某网址> 里面有什么」→ 观察主 Agent 是否把该网址转给网络搜索子 Agent 并触发 `browse_pages`。**不通过的典型形态**：主 Agent 自己硬答、或把网址当 query/topic 丢给 Tavily 返回无关条目。
