## 〇、前置改造：用户数据自主管理（必须先做）

### 0.1 问题诊断

| 现象 | 根因 |
| --- | --- |
| 新注册的个人账号能看到「显卡/咖啡机」等样例兴趣 | `personal_tools.py` 三个工具查询**不过滤 `owner_id`**，任何用户都读到 alice 的样例行 |
| 新注册的公司账号直接关联「云协科技」竞品数据 | MySQL `competitors` 等表是**全局共享**的，无账号归属概念 |
| 用户无法增删改自己的兴趣/关注/产品/竞品 | 只有 Agent 只读工具，没有任何写入口 |

结论：这不是「换一份初始数据」的问题，而是**数据归属权（ownership）缺失**。

### 0.2 设计原则

1. **空置起步**：新账号（无论角色）业务数据为空，样例数据只属于 demo 账号 alice。
2. **谁的数据谁可见**：所有业务查询强制按当前登录账号过滤。
3. **读写分离**：Agent 工具保持只读（情报分析用）；**增删改走 REST API**（前端左栏/设置页操作），人主动维护数据，AI 只消费。

### 0.3 数据层改造

统一收归 **SQLite 个人库**（延续「本地单文件应用」哲学与 M1.5 泛用化方案；MySQL 降级为可选演示数据源）：

```sql
-- 已有：accounts
-- 公司侧新增（按账号隔离）
CREATE TABLE IF NOT EXISTS company_profile (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    owner_id INTEGER NOT NULL UNIQUE REFERENCES accounts(id),
    company_name TEXT,          -- 我的公司名（如「云协科技」，可空待填）
    note TEXT
);
CREATE TABLE IF NOT EXISTS company_products (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    owner_id INTEGER NOT NULL REFERENCES accounts(id),
    product_name TEXT NOT NULL,
    category TEXT, price REAL, currency TEXT DEFAULT 'CNY',
    attributes TEXT,            -- JSON 扩展列（泛用化，同 M1.5 方案）
    status TEXT DEFAULT 'active'
);
CREATE TABLE IF NOT EXISTS company_competitors (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    owner_id INTEGER NOT NULL REFERENCES accounts(id),
    comp_name TEXT NOT NULL,
    category TEXT, website TEXT,
    is_competitor INTEGER DEFAULT 1,
    note TEXT, mapped_product_ids TEXT   -- JSON 数组文本
);
-- 个人侧已有 products/interests/watchlist（含 owner_id），补 CRUD 即可
```

迁移策略：现有 MySQL 三表数据转为**一次性导入脚本**（导入到指定账号名下）；`docs/sql/company_schema.sql` 与 MySQL 连接保留但标记 legacy，`db_agent` 工具改为优先读 SQLite、`.env` 配 `DATA_BACKEND=sqlite|mysql` 可切。

### 0.4 归属权传递机制（关键）

复用现有 `api/context.py` 的 ContextVar：
- `/api/chat` 已设 `thread_id=username` → 新增 `set_owner_context(account_id)`；
- `personal_tools.py` / 新的公司侧只读工具在每个 SQL 加 `WHERE owner_id = ?`（从 ContextVar 取）；
- REST 写接口从 token session 取 `account_id`，天然隔离。

### 0.5 新增 REST 接口（读写分离的「写」侧）

```
GET/POST/PUT/DELETE  /api/me/profile        # 公司名称等信息（公司）
GET/POST/PUT/DELETE  /api/me/products       # 我司产品（公司，可选填）
GET/POST/DELETE      /api/me/competitors    # 关注竞品（公司）
GET/POST/DELETE      /api/me/interests      # 兴趣标签（个人）
GET/POST/PUT/DELETE  /api/me/watchlist      # 关注品牌商品（个人）
GET                  /api/me/overview       # 左栏一次性拉全（含完成度提示）
```
前端配套：公司工作台左栏改为「我的竞品」真实增删 UI + 首次登录引导弹窗（填公司名→选填产品→添加竞品）；个人工作台左栏兴趣/关注可增删。

### 0.6 验收标准

- 新注册公司账号：看不到任何云协/飞书数据；引导填写公司名后才有个性行为；可自由增删产品与竞品。
- 新注册个人账号：兴趣/关注为空；自行添加「无线耳机」后，快讯与性价比分析立即围绕它工作。
- alice 样例账号行为不变（回归验证）。

## 一、skill → 项目能力映射（ai-weekly-digest 移植）

| ai-weekly-digest 环节 | 项目内对应实现 | 说明 |
| --- | --- | --- |
| 信源扫描（浏览器抓搜索/HN API） | **Tavily 批量检索**（已有工具）为主；HN Algolia API 为公司侧科技类的免费补充通道 | 不引入浏览器抓取（服务端无人值守不适合）；查询词批次来自 **0.5 节用户自有的** interests / competitors / products |
| 三关筛选（P1实用>P2方法论>P3思维） | LLM 筛选节点：prompts.yml 新增 `digest` 提示词段 | 「立刻能用测试」领域化：公司侧=对竞品情报决策有用；个人侧=影响购买决策。排除融资软文/跑分对比规则照搬 skill |
| 固定模板周报 | 复用主 Agent 简报结构 ①摘要②动态③对比④风险机会⑤来源；个人侧用快讯流模板（条目+类型徽章+为什么值得看+来源） | 模板写进 prompts.yml，与代码解耦 |
| .md 文件交付 | **复用 M3 导出链路**：落盘 output/{user}/ + Word 转 PDF | api_export 抽成可复用函数 |
| 手动运行（cronjob 另配） | APScheduler 内嵌 FastAPI 进程内调度 | Windows 本地应用，不依赖外部 cron |
| skill 纪律继承 | 检索批次数硬上限 ≤8；统计口径诚实（覆盖不足在报告头注明实际扫描范围）；每条时间窗校验（近7天）防旧闻混入；绝不编造来源 URL | 写入 digest 提示词 + 引擎代码双重约束 |

## 二、架构总览（三阶段实施）

```
┌─ M4-a 订阅与报告存储 ────────────────────────────────┐
│ SQLite 新增两表：                                     │
│   digest_subs(id, owner_id, scope company|personal,  │
│              keywords TEXT/*JSON*/, schedule,        │
│              enabled, last_run_at)                   │
│   digest_reports(id, owner_id, title, md_path,       │
│              pdf_path, item_count, status,           │
│              coverage_note, created_at)              │
│ 默认订阅自动生成：公司←我的竞品清单；个人←我的兴趣标签。  │
│ 用户可在前端调整关键词与周期。                          │
└──────────────────────────────────────────────────────┘
┌─ M4-b Digest 引擎（核心，纯函数可独立调试）────────────┐
│ services/digest_engine.py                            │
│  1. 读订阅 → 展开查询词批次（≤8批纪律）                 │
│  2. Tavily 并发检索（topic=news + 时间窗过滤）          │
│  3. LLM 筛选：候选≥15条 → 保留5–10条（三关+排除项）      │
│  4. LLM 按模板生成周报 markdown                       │
│  5. 复用导出链路存档 + 写 digest_reports               │
│ 入口：run_digest(sub_id) 同步函数；tests/ 下脚本可单跑。 │
└──────────────────────────────────────────────────────┘
┌─ M4-c 调度与站内推送 ────────────────────────────────┐
│ APScheduler(CronTrigger)：每日9点 / 每周一9点          │
│ 推送定义（本地 Web 应用）：                            │
│  ① WS monitor_event(type=report_ready) 实时提醒       │
│  ② 顶栏红点 + 报告列表页（读 digest_reports，可下载/重跑）│
│ REST：GET /api/reports、POST /api/digest/run（手动触发，│
│ 便于测试）、PUT /api/digest/subs（调订阅）              │
└──────────────────────────────────────────────────────┘
```

依赖增量：仅 `apscheduler` 一个（uv add）。模型复用现有 `LLM_MODEL_MAX`，筛选与写作均为轻任务，不引入第二模型配置。
