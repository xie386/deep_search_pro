## 一、v3.0 的定位与边界

`IDEA.md` 第一行写着这个项目的出身： **"初学者框架型项目，后续改造成成熟应用项目"**。
v1.0 把它从框架变成 **能用**的东西（多智能体 + 前端 + 周报），v2.0 把它变成 **结构清楚**的东西
（上下文工程化 → 装配管线 → RAG → 技能与工具 → 工具智能路由），v2.5 是把 **用户摸到的每个坑**补平。

**v3.0 = 把它推到"成熟应用"**，具体是三条主线：

| 主线 | 一句话 | 为什么是现在 |
| --- | --- | --- |
| **① 工具生态闭环** | 把"能力目录 + 路由器"从 **只有 CLI** 扩到**API / MCP** | 这是 v2.0 唯一被**拍板推迟 **的功能（M5b-3/4），目录层与路由器**已按来源无关写好 **，只差适配器 |
| **② 情报质量闭环** | 让"给谁看、看什么、记不记得住"形成回路：用户画像沉淀 + 检索会话级计数器 + 价格监控告警 | 现有链路是"每次从零问"，画像与计数器是把 **已有数据**用起来的最短路径 |
| **③ 工程与交付** | 成本可视 / 测试可信 / 打得包发得出去 | 已经吃过两次"隐性成本"的亏（Tavily 额度被探针吃掉、前端改动被 WebView2 缓存吃掉） |

**v3.0 不做的事（先划边界）**：多用户 / 云端 SaaS、模型微调或本地大模型替换、多模态主链路（见 §7）。

## 五、里程碑草案（建议顺序，每项都有可测判据）

> 节奏沿用项目纪律： **每段端到端验证通过再进下一段**；每段收工更新 README 的阅读指南与 `docs/v2.5`（或 v3.0 内对应文档）。

### M1 · API 工具接入（M5b-3 实装）

- **目标**：把 REST 型工具接进统一能力目录，路由器对 **混合来源池**同样有效
- **关键交付物**： `tools/capability_pool.py` 的 `api_entry()` + `_entries_from_apis()`（打开已预留的注册表槽位）； `api_apis` 表（账号隔离）+ 表单（配置导向：base_url / 方法 / 路径 / 参数 / **默认只放行 GET**）；通用调用工具（与 `run_shell_command` 同级）+ 只读闸语义
- **验收判据**：
 1. 混合池（CLI 3 + API 3）上跑 `tests/live/_m5b_route_calib.py`： **命中判定 10/10、0 条路由到错的工具、无关问句 100% 回退**
 2. 注入量报告：命中形态 ≤ 1500 字（与 v2.0 同口径）
 3. 写方法（POST/PUT/PATCH/DELETE） **未勾选时必须被拒**，且拒因可读（回归用例≥6 例）
 4. 账号隔离：A 账号的 API 工具不出现在 B 账号的池里
- **风险**：混合池的条目文本长度差异大 → 标定可能要重新选 `Z_STRONG` / `LEX_MIN`

### M2 · MCP 工具接入（M5b-4 实装）

- **目标**：MCP server 的工具能被发现、按 `readOnlyHint` 预勾选、由 **人确认**后进入池
- **验收判据**：① 至少接 1 个真实 MCP server（本地 stdio 优先）跑通"发现 → 人工确认 → 调用 → 审计"；② 未确认的工具 **不可被 Agent 调用**；③ 断线/server 消失时池自动降级且不误报"工具可用"；④ MCP 工具的命中与注入量并入 M1 的同一张基准表
- **风险**：MCP server 的稳定性与权限语义差异大 → 建议 **只做只读默认**，写工具一律不默认勾

### M3 · 用户画像沉淀

- **定位（2026-09-25 修正）**： **不新建 `PROFILE.md`** —— `agents_docs/{user}/MEMORY.md` 的 `## USER PROFILE` 段**已经是 **唯一事实源（三处消费：对话注入 / 周报权重 / 前端编辑）。本里程碑 = 把"初始化一次的快照"改造成"**持续沉淀**"。
- **目标**：① **覆盖面**——数据库事实（收藏/关注/竞品/订阅）与 **周报主题**能进画像；② **更新语义**——同一维度 **就地更新**而非重复追加；③ **可治理**——每行带来源/时间、 **禁止占位行**、注入有硬预算；④ `memory_initializer` 从"一次性生成"升级为 **增量建议器**（首次「初始化」、之后「提建议」）
- **三个根因（取证）**：R1 触发源错配（提示词只认"**用户表达**"，而收藏/周报/订阅在对话里永不被表达）；R2 工具形态鼓励追加（`write_agent_doc` 只有覆盖/追加，无"按维度就地更新"）；R3 提示词 **要求**写占位（`memory_initializer` 明写"缺失的维度如实说明「暂无」"）
- **交付物**： `MEMORY.md` 行格式规范 + 维度白名单； `memory_suggester` 段落； `/api/memory/suggest|apply`；结构化写入入口；注入分层与预算；前端「AI 提建议」diff 面板 + 来源可点开
- **验收判据**：① 一个"只有结构化数据、不聊偏好"的账号跑一次建议 → 画像出现 ≥2 条 **来自收藏/竞品**的行且 **带来源**；② 连续 3 次更新同一维度 → 该维度 **恰好 1 行**；③ 画像段匹配不到 `暂无|待补充 `，且周报侧 **删掉字符串过滤后**仍能取到画像；④ 注入 ≤（画像 500 字 + 笔记 300 字），超长文件不线性膨胀
- **风险**：建议器"编造事实" → 只依据证据 + 每条带来源 + **人工勾选后才落盘**；模型改写弄丢人工行 → 人工行 **永不动**（用例覆盖）
- **详见**： `M3-用户画像沉淀方案.md`（§二 根因取证 / §五 契约 / §六 实施步骤）

### M4 · 检索计数器 + 装配入口收口

- **目标**： `build_request_context` 成为唯一装配入口；按会话统计检索/工具调用次数并支持预算告警
- **验收判据**：① 人格/记忆/画像/预算 **只有一处装配**（静态断言： `api/server.py` 不再直接拼装这些片段）；② `GET /api/usage?thread_id=` 返回本轮/本会话计数；③ 超预算时的行为有明确定义（拒绝 / 提示用户）且可测
- **风险**：改装配入口影响面大 → 必须有一层"老路径 = 新路径"的等价性回归（同输入比对注入结果）

### M5 · 价格监控（情报闭环的最后一块）

- **定位（2026-09-25 修正）**： **不先找数据源**。范围＝**三样都做**（① 个人收藏目标价提醒 ② 公司产品与竞品价格对比 ③ 周报价格情报结构化）； **阶段 1 零外部依赖**（手动 + 对话记价 + 阈值提醒）， **阶段 2** 再接**用户自配 **价格 API（复用 M1 适配器）
- **目标**：把静态参考价变成 **有历史、有阈值、会提醒、能写进周报**的价格闭环
- **交付物**：三张新表（`price_history` / `price_mentions` / `price_alerts`）+ 加列（url / 目标价 / 监控开关）+ `record_price` 工具 + 前端（跌幅 / 目标价 / 更新价格 / 资讯价折叠）+ **桌面通知与周报附录** + 阶段 2 的接口与桩
- **验收判据**：① 两条记录即可算出涨跌幅；② **首次跌破目标价**触发提醒、 **未创新低不重复**；③ **资讯价与当前价分表**，UI 明确标注来源（**禁止把资讯价当现价**）；④ 周报结构化价格块 **不额外增加模型调用**；⑤ 价格源配置 **不写死厂商**（阶段 2）；⑥ 失败/限流明确提示、不静默
- **风险**： **外部依赖最重**（仅阶段 2）→ 阶段 1 先落地、把源的选择推后； **最大的误导风险是"把资讯价当现价"** → 分表 + 来源标注为闸
- **明确不做**：爬虫/反爬对抗、把 Tavily 当价格源、任何 **下单链路**（含 CLISHOP —— 看过、取证过， **不引入依赖**）
- **详见**： `M5-价格监控方案.md`

### M6 · 工程与交付收尾

- **目标**：把 §3-B / §3-C 的债还清，让项目"能给别人看、能装、能信"
- **交付物（可分批）**：
 1. **测试可信**（B1/B2/S3）：探针基线快照 + 漂移阈值；10/1 后补跑 `m5b_pressure_probe`
 2. ~~**桌面版**：窗口位置记忆（A8）→ 拖文件入库（A9）→ 热键（A10）→ **打包方案拍板**（A11）~~ → ❄️ **2026-09-29 用户拍板：整块不做**（个人自用、无分发需求；以 `docs/v3.0/README.md` 的进度表为准）

## 七、明确不做（v3.0 scope out）

1. **多用户 / 云端 SaaS / 权限体系**：本项目定位是"本地个人应用"，加多租户会把每一处账号隔离逻辑变成安全边界
2. **模型微调 / 自训**：与"用现成模型把情报做对"的目标正交
3. **多模态主链路**（C6）：接视觉模型会同时改 provider 层、消息层、前端；先把文本链路做到"成熟"
4. **RAGFlow 接入**：v1.0 曾登记，现已被自建 Chroma 方案取代（`docs/v1.0/M4_Digest实现记录.md` 的遗留项可判废）
5. **微信版本降级**（C3）：为兼容 CLI 而牺牲日常使用不划算
6. **段落级消息合并**（B10）：收益不足、风险偏高
7. **自动放宽 `--wait`**（B7）：会牺牲"快速失败"，宁可留人工旋钮

> **用户已确认（2026-09-25，议题 X3）**：以上 7 条 **全部维持"不做"**。定位是**个人自用 **项目（最多在实习同事 / 同班同学 / 游戏好友的小圈子里传播），不需要为多用户、分发或云端做设计取舍。
