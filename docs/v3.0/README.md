| 文档 | 回答什么 | 粒度 | 什么时候定稿 |

## 三、每篇方案文档的固定骨架（保证可直接执行 + 可汇编）

```
# M<n> · <议题> 方案

> 状态：🔍 研讨中 / ✅ 定稿 ｜ 依赖：<前置议题> ｜ 对应规划书：§…

## 一、目标与验收判据        ← 判据必须可测（命令 / 断言 / 数字）
## 二、现状与证据            ← 带 file:line、实测数字；不写"应该没问题"
## 三、设计选型与取舍        ← 至少 2 个备选 + 为什么不选另一个
## 四、契约与数据模型        ← 表结构 / 接口签名 / 配置字段（照抄即可开工）
## 五、实施步骤              ← 可执行粒度（按"每步能独立验证"切分）
## 六、测试与回归清单        ← 新增用例 + 必须重跑的既有用例（含账号/配额纪律）
## 七、风险、回退与遗留
```

**三条硬要求**（沿用项目既有纪律）：
1. **凡结论必有出处**：文件路径 + 行号 + 实测数字，或明确标注"待实测"。
2. **凡改动必说影响面**：这条改动会不会波及既有功能（本项目历史上多次栽在"改 A 坏 B"）。
3. **凡安全相关必写口径**：只读闸 / 越权 / 账号隔离 / 审计日志，不给"以后再说"。

## 四、研讨期的纪律（先讲清楚，省得返工）

- **不动代码、不动数据**：研讨期只写文档；需要现场取证的只做**只读**探测（读文件、查库、探端口），
  不启动服务、不跑真机用例（**Tavily 额度紧张，10/1 前尤其**）。
- **不擅自扩议题**：一个议题一个方案文件；研讨中发现的**新问题**记进方案末尾的「遗留」并**回填规划书 §3**，
  不当场顺手做掉（本项目已被范围蔓延伤过一次）。
- **有分歧先摆证据再拍板**：涉及设计分叉的，我给 2~3 个备选 + 取舍理由，**等你拍板**再落进方案（不替你定）。
- **每篇定稿即回填进度表**：本文件 §2 的状态列 + `docs/README.md` 的 v3.0 行同步更新。
