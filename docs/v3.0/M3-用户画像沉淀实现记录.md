## 二、与原方案的偏差（**逐条给理由，均已在代码注释里写明**）

① **待更新信号：时间戳 → 计数水位**（方案 §3.3 说"比较 `memory_meta.refreshed` 与各表/周报的时间"）
 - 实测 `PRAGMA table_info`：用户域那 **6 张表没有 `created_at`**（只有 `digest_reports` 有），
 临时加列也补不回历史数据 → 方案原样**做不出来**。
 - 改为：`memory_meta` 多写一个 `counts=a,b,…` 水位向量（各来源条数），下次刷新与当前条数相减 →
 "自上次刷新以来新增了 2 条兴趣、1 篇周报"。**无需改表、对老账号立刻可用**，且老 `memory_meta`
 没有这个字段时静默不出信号（向后兼容）。
 - 位置：`tools/profile_evidence.py::count_vector / refresh_meta / staleness`；五条写路径统一走 `refresh_meta`。

② **笔记相关度：v1 只用词法**（方案 §4.3 已留口子："若复用成本高，v1 只用词法"）
 - 复用 `tool_router.lexical_scores` 会把能力池一起拉进来，且本机 embedding 冷启动实测 ~33s（`D:\LLM\model\bge-large-zh`）→
 为一次"笔记排序"不值得。
 - 实现：`_lexical_overlap` 用中文**二元字组**交集打分（零依赖）＋ 最近 3 条无条件保留（时效兜底，方案原话）。

③ **裁剪优先维度加了「身份与领域 / 身份变化」**（方案括号里只举了消费偏好/情报关注点/竞品）
 - 理由：身份是最稳定、最有用的上下文，超预算时**丢身份比丢"关注渠道"更糟**。
 - 位置：`agent/build_context.py::_PRIORITY_DIMS`（注释写明这是对方案举例的refinement）。

⑤ **来源不再写进画像文件**（2026-09-27 用户实测后定，**覆盖方案 §5.2/G5**）
 - 方案要求每条写 `（来源：关注#4 · 日期）`；实测反馈：那串 `表名#id` 是**给人溯源用的**，
 写进文件后会被原样注入模型上下文，而 agent 没有跨会话的表引用知识 → 纯噪声（用户原话"会造成污染"）。
 - 改为：文件里只写 `- 维度：事实`；来源/日期**保留在结构化层**（API 响应、建议面板、快照）；
 **只有人工行**保留短标记 `（人工）` —— 这是 `upsert(protect_manual=True)` 识别"用户手写行"的唯一依据，
 去掉就等于丢掉 D8 的人工行保护（用例 `test_source_out_of_file_but_manual_marker_roundtrips` 钉住往返）。
 - 顺带：建议器输出里的 markdown 星号（`**喜欢调酒**`）在解析时剥掉。

⑥ **`split_sections` 按 H1 切块 + 多块合并**（2026-09-27 用户实测报障"一份文件两份画像"）
 - 根因：`notes` 段原来一路取到**文件尾**，把 agent 早先用 `write_agent_doc` 追加进来的第二份整块
 也吞进笔记段 → 写回时"新画像在上、旧整块垫在笔记里"。
 - 改为：按文档级 H1 切块；后续块的**画像合并**（按维度去重、先出现者为准）、**笔记去重**，写回永远单份。
 - 同批修掉：`parse_rows(dedupe=True)` 供**写路径**用（读取默认忠实、不并变体）。

⑦ **快照端点补 `snapshots` 兼容键**（2026-09-27 实测"历史版本恒为 0"）
 - 后端返回的是 `items`，前端与方案文档读的是 `snapshots` → 界面永远空。已两键并存（同一份）+ 补
 `created_at_text`；用例断言两键必须相等。**教训**：那次前端 harness 是照我**以为**的响应形状写的 mock，
 所以它过了、真机却 0 —— 契约测试要对着**后端真实返回**写。

**已按 A 方案完成归一（2026-09-27）**：`尼古喵喵/MEMORY.md` 归一前 H1 块 2 个、含来源字样；归一后
**1 个块 / 1 个画像段 / 12 个维度（合并去重）/ 6 条笔记 / 无来源字样**，改前已留快照（现共 2 份）；
坏文件原样备份在 `docs/v3.0/backups/MEMORY.尼古喵喵.before_M3_repair.md`。

④ **「来源可点开」本轮只做到"可读可溯源"**（方案 §5.6 写的是"来源可点开 → 原始条目"）
 - 现状：差异行显示 `（来源：关注#7）`，且证据行本身带 `关注#7` 这种 **`表名#行id`** 引用（M3-2 为此专门补了 id）——
 溯源信息**是完整的**，但点击跳转到对应页面还没做（需要前端 tab/路由与列表锚点，属下一轮前端收口）。
 - 不谎报：这一条**没做完**，见 §五。

## 四、M3-8 真机抽样（覆盖度数字）

> 方案要求：跑「初始化 → 几轮对话 → 建议 → 一键导入 → 还原」，产出**画像 diff 与覆盖度数字**
> （来自 DB 的行数、来自对话的行数）。

**状态**：⏳ 待你的账号上跑（这一步会**改真实画像**，按你的习惯给手动步骤而不是我直接跑）。

我的只读部分（`/api/memory/suggest` **绝不落盘**，有 12 条用例钉住）已完成，数字见下：

**手动步骤（每一步都可停、可回头看，不会一步就把画像改花）**：

1. **重启后端**（当前跑着的服务是旧进程，新列/新端点还没生效）：
 `uv run python -m uvicorn api.server:app --host 127.0.0.1 --port 8123`
 —— 启动时会把缺的列/表补上（`abilities_user` / `tool_sources.intro` / `memory_snapshots`），**已有数据不动**。
2. 登录后进「⚙️ 定制助手 → 🧠 记忆画像」，先点 **🔍 AI 建议更新**（这一步**只读**：`/api/memory/suggest`
 绝不落盘，界面上会显示"依据：系统资料 N 条 · 周报 N 篇 · 对话 N 条"和逐条差异）。
3. **先看差异再决定**：`～` 是改现有维度（显示"旧 → 新"）、`＋` 是新维度、`−` 是老文件里的占位行（默认不勾）。
 人工行（来源=人工）与你画像里没有的**新维度**默认不勾 —— 想采纳就自己勾上。
4. 勾好后点 ** 应用勾选**（只落勾中的），或点 **⚡ 一键导入全部**（整份 + 覆盖确认）；
 两者都会**先存一份快照**。
5. 点 **🕘 历史版本** 看效果，点任意一条的 **↺ 还原** 可来回切（还原前也会先把当前版存一份）。
6. 想验对话侧的沉淀：聊两轮说出一个稳定事实（如"我预算最多 100 块"）→ 刷新画像，看它是不是**就地更新了
 `预算范围` 那一行**（而不是新加一行）。这就是 R2 被修掉的样子。

## 四·五、被既有回归挡下来的两个真问题（都出在我自己新写的注入裁剪上）

这两个都**不是方案里的设计缺陷，而是我落地 M3-6 时引入的回归**，靠"必须重跑"的那批用例抓出来的：

| # | 现象 | 根因 | 修法与防线 |
|---|---|---|---|
| ① | 注入给模型的记忆**整段消失**（只剩一行「（记忆文件：…）」提示） | `_split_memory` 只认标准排版：拿 `## USER PROFILE` / `## MEMORY` 分两段，**老文件或用户自己排版的文本两边都空 → 返回空** → 等于"悄悄把用户的记忆删了" | 两个段都空且原文非空 → **整段当画像原样注入**；新增用例 `test_split_memory_falls_back_for_nonstandard_text` 钉住 |
| ② | 没超预算的画像也被"重排"（`## USER PROFILE（用户画像）` 标题被吃掉） | `_trim_profile` 一律按"条目行"重建文本，把标题/空行当成可丢的东西 | **放得下就原样返回**（含标题、顺序、空行），只有真超预算才裁；新增用例 `test_untouched_when_within_budget` + `test_notes_heading_survives_trimming`（裁剪后也必须留 `## MEMORY（助手笔记）`，否则模型分不清"画像事实"与"助手流水笔记"） |

**为什么值得写进来**：这两条都是"功能看起来正常、只是少了一段内容"的静默失效 —— 而它们恰好被
**M2 期就存在的** `tests/test_assembly.py::test_compose_dynamic_prompt_combined` 挡住（那条用例断言"没超预算时注入逐字一致"）。
结论：改注入层一定要跑 `test_assembly.py`，它是这条链路最老也最灵的哨兵。
