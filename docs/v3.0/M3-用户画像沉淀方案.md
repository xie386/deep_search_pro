## 一、目标与验收判据

| # | 目标 | 验收判据（可测） |
| --- | --- | --- |
| G1 | **覆盖面**：数据库事实（收藏/关注/竞品/订阅）与 **周报主题**能进画像 | 造一个"只有结构化数据、不聊偏好"的账号 → 跑一次 AI 建议 → 画像里出现 ≥2 条 **来自收藏/竞争对手**的行，且 **带来源标注** |
| G2 | **不追加成瘾**：同一维度重复更新应 **就地更新**而非新增行 | 连续 3 次让 agent 更新同一维度（如预算）→ 断言该维度 **恰好 1 行**，且值 = 最新值；文件 **无重复维度行** |
| G3 | **不写占位**：画像里不出现"暂无/暂无资料/待补充"式占位 | 静态断言：画像段匹配不到 `暂无 | 待补充 | 待完善 `； `digest_engine` 侧 **删掉** `"暂无资料" not in seg` 的字符串过滤后仍能正确取到画像 |
| G4 | **有预算**：注入有硬上限，且画像优先于笔记 | 记忆纳入 `context_budget`：画像段 ≤ **500 字**、笔记段 ≤ **300 字**；构造超长记忆文件 → 注入结果不超上限，且画像段完整、笔记段按相关性取前 N |
| G5 | **可溯源**：每行能指回来源 | 画像行含 `（来源：<表> #<id> · <日期>） ` 或 `（来源：人工 · <日期>） `；前端可点开显示原始条目 |
| G6 | **周报消费不再靠字符串过滤** | `digest_engine` 读画像时 **不再判断 `"暂无资料"`**；无画像时按"画像为空"走既有回退路径（有用例） |

### 2.2 三个结构性根因（为什么"有设计却效果差"）

| 根因 | 证据 | 后果（与用户实测现象对应） |
| --- | --- | --- |
| **R1 触发源错配**（主因） | `prompts.yml:60` 的触发条件全是"**用户表达**"：品牌好恶、价格敏感、常用渠道、身份变化 | 收藏 / 周报 / 订阅 / 竞品来自 **数据库**，在对话里 **永远不会被"表达"** → 触发条件永不满足 → 画像只剩"对话里说过的关注/兴趣" |
| **R2 工具形态鼓励追加** | `write_agent_doc` 只有覆盖/追加；要实现"局部更新"得先读全文再整份重写 | 重写 1724 字只改一行， **成本高、怕覆盖丢内容** → 模型理性地选追加 → "只喜欢追加式编写" |
| **R3 提示词要求写占位** | `memory_initializer`：「明确缺失的维度（如「预算范围：暂无」）」「缺的维度如实说明「暂无」」 | 占位是 **被要求的**；下游只能 `"暂无资料" not in seg` 字符串过滤 → **一条占位废掉整段画像**（用户那份文件里就有 3 行占位） |

### 2.3 缺口小结（M3 要修的正是这些）

- **覆盖**：只有"对话表达"一路触发；DB 事实与周报主题没有入口（D3 的改造补这一路）。
- **更新语义**：没有"就地更新/去重"的机制与工具支持（D2-③ 要修 R2）。
- **可治理性**：无来源、无时间、有占位；注入无预算分层；下游靠字符串过滤（D6 全修）。
- **激励**：写了没反馈、不写没后果（提升积极性要落到"**可见信号 + 可测指标**"，见 §3.3）。

## 三、设计（三件套 + 三个根因的对应修复）

### 3.1 三种写入通道（D2）

```
① 人工编辑（已有） 定制助手 → 🧠 记忆画像 → textarea（保留）
 ↑ 人的行 = 最高权威，任何自动流程都不覆盖
② AI 建议（本次新增） 按钮：未初始化 →「✨ 初始化用户画像」
 已初始化 →「🤖 让 AI 给画像提建议」
 输入证据 = 7 张结构化表 + 最新 3 篇周报 + 最新 N 条会话
 输出 = **建议画像（逐行 + 来源）**
 两种落地：ⓐ 逐条勾选（默认可见）ⓑ **一键导入整份建议**（D8）
 应用前 **自动快照**当前画像（保留最近 3 份，D9）
 ↑ 补的就是 R1 缺的那一路（DB/周报）
③ agent 自主维护（保留） 对话中判断是否更新 → 走 **结构化写入口**（修 R2）+ 收到 **待更新信号**（修 R1）
```

### 3.2 AI 建议器的数据流（D3 落地）

```
[证据收集] db_interests / watchlist / products / company_* / competitors / digest_subs（沿用 _collect 逻辑）
 + 最新 3 篇周报：digest_reports 的 title/created_at/item_count + 对应 output/*.md 的 **标题与要点行**（纯字符串抽取，不再调模型）
 + 最新 N 条会话：conversations/messages 里最近的人类消息（去空白、截断，形成"用户最近在关心什么"）
 ↓
[memory_suggester] 输入=证据 + 现有画像正文；输出=**建议画像（逐行 + 来源）**； **不直接落盘**（落盘须经人工：逐条勾选或一键导入，D8）
 ↓
[前端 diff 展示] 每条形如： ＋新增维度 / ～更新维度（旧值→新值）/ −建议移除（默认不勾）
 每条带来源；人工可勾选、可编辑文案
 ↓
[应用（服务端）] 两种模式：逐条勾选 / **一键导入整份（D8）**
 按维度 **就地更新**（不新增重复行）； **人工行优先保留**（开关可覆盖）；写入 `（来源：… · 日期） `；更新 memory_meta
 ↓
[快照（D9）] 应用 / 人工保存 / agent 更新 **之前**先快照当前画像 → `memory_snapshots`（保留最近 3 份）
 → 前端「🕘 历史画像」可 **一键还原**（还原前对当前版本再快照一次，可来回）
```

**建议器与初始化器共用的硬约束**（写进两段提示词，并用契约测试钉住一致性）：
只依据给定证据、绝不编造；每条一行 `- 维度：事实 `； **缺失维度不写占位**；总字数 150~400；
输出 **不得**包含 `##` 级标题（段落正文由服务端拼装）。

### 3.3 agent 自主维护的"恰到好处"（修 R1 + R2，不改触发时机）

不靠"喊得更响"，靠 **把看不见的判断变成看得见的信号**（与 v2.5 CLI 能力描述改造同一手法）：

| 手段 | 做法 |
| --- | --- |
| **可见信号**（修 R1） | 注入块里加一行 **待更新提示**： `【画像待更新】检测到 3 条新收藏、2 篇新周报在你上次刷新（2026-09-20）之后产生；若与用户本轮问题相关，请用 update_user_profile 更新对应维度。 ` —— 由服务端比较 `memory_meta.refreshed` 与各表/周报的时间算出， **模型只做判断，不做统计** |
| **降低写入成本**（修 R2） | 用 **结构化写入口**（§4.1 的 F4 选型）替代"整份重写"：模型只给 `维度/新值/来源 `，服务端负责就地更新、去重、加来源 |
| **明确"更新"而非"追加"** | 现有规则里"追加或局部更新，避免覆盖已有条目" → 改成**"同一维度已存在就地更新该行；只有新维度才追加"**，并给一条格式示例（放 `@tool` docstring，遵守"机械细节只写一处"） |
| **可测指标** | G2 的用例（连续 3 次更新同一维度 → 恰好 1 行）把"积极性/正确性"变成回归断言；另在方案落地后跑一次"10 轮真实对话"的抽样，统计画像新增/更新行数（作为基线，不设死阈值） |
| **反馈闭环** | agent 写完仍要"告知用户已记录"（保留现有要求）；前端在画像卡片上显示 **每行来源与时间**，人一眼能看出"这行是哪来的、什么时候的" |

### 3.4 行格式规范（唯一事实源的"契约"）

```markdown
## USER PROFILE（用户画像）

- 身份与领域：Agent 应用开发实习生（来源：人工 · 2026-09-13）
- 消费偏好：对降价敏感，米诺地尔预算 ≤100 元/瓶（来源：关注#7 · 2026-09-24）
- 情报关注点：AI Agent 生态、低度蒸馏酒、戒烟辅助（来源：兴趣#3 · 2026-09-24）
```

规则：
1. 每行 `- 维度：事实（来源：… · 日期） `； **维度名**从白名单里选（见 §5.1），避免维度漂移；
2. **禁止占位行**（缺失就不写）；"哪些维度还没填"由前端单独提示，不进文件正文；
3. **人工行**在来源处标 `人工 ` → 自动流程 **永不改动/删除**该行；
4. 文件顶部保留可解析元数据（替换现有 `memory_init` 标记，向后兼容）：
 `<!-- memory_meta: init=2026-09-13 refreshed=2026-09-24 sources=12 -->`

## 四、设计选型与取舍

### 4.1 F4：agent 的 **写入入口形态**（✅ **已定 A**，见 §零 D7）

| 备选 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A. 新增专用工具 `update_user_profile(op, field, value, source)` | 语义单一、 **框架负责读改写/去重/加来源**（模型不可能写坏文件）；可测 | 多一个模型可见工具（+ 一段 docstring） | ✅ **已定（D7）**：与 M1M2 的"单一职责工具"取向一致 |
| B. 维持 `write_agent_doc` 整文件写，只改提示词 | 零工具面变化 | 模型仍要"读全文→整份重写"，R2 没修掉；覆盖丢内容的真实风险还在 | ❌ 不解决根因 |
| C. 给 `write_agent_doc` 加 `mode='upsert_profile'` | 不新增工具名 | 一个工具承担两种职责（写文档 / 更新结构化画像），docstring 与测试都要分叉 | 次选 |

### 4.2 提示词：拆两段还是一条带 mode？

| 备选 | 结论 |
| --- | --- |
| A. `memory_initializer`（首次）+ `memory_suggester`（增量） **两段** | ✅ **推荐**：职责单一、可分别测试与审计；两段的 **共有硬约束**用契约测试钉一致（防漂移） |
| B. 一段 + `mode: init\| suggest` | 少一份重复，但一段里两种输出格式容易让模型混用 |

### 4.3 笔记段的"相关性取前 N"

复用 M5b 现成栈： `tools/tool_router.lexical_scores`（词法）优先、必要时 `capability_pool.route_scores`（向量）。
**规则**：笔记条目 ≤ N（N=5）且总长 ≤ 300 字； **时效兜底**：最近 3 条无论相关性都保留（防"刚记的事看不到"）。
不引入新依赖、不新建向量集合（复用 `tool_route_{account_id}` 之外的 **现成 embedding 入口**即可；若复用成本高，v1 只用词法）。

### 4.4 元数据与标记的兼容

现有 `<!-- memory_init: done -->` 与 `_memory_initialized()`（`customize.py:780-808`）是既有契约 → 新 `memory_meta` 行 **并存**（首次写入时补上），旧代码路径不破坏； `_memory_initialized()` 保持不变。

## 五、契约与数据模型（照抄可开工）

### 5.1 维度白名单（防"维度漂移"）

```
身份与领域 / 消费偏好 / 预算范围 / 价格敏感度 / 情报关注点 / 竞品关注 /
关注渠道 / 品类偏好 / 身份变化 / 其他稳定事实
```
- 白名单外的维度 **允许但需人工确认**（建议器输出时标 `⚠️新维度 `，默认不勾选）。
- **不做**"缺失维度"条目（D6/R3）。

### 5.2 后端接口

| 端点 | 用途 | 变化 |
| --- | --- | --- |
| `GET /api/memory` | 读画像 + `initialized` | 已有； **加返回** `meta`（init/refreshed/sources 计数）与 `profile_lines`（解析后的结构化行） |

CREATE TABLE IF NOT EXISTS memory_snapshots (
 id INTEGER PRIMARY KEY AUTOINCREMENT,
 account_id INTEGER NOT NULL,
 content TEXT NOT NULL, -- 画像段全文（不含笔记段）
 reason TEXT NOT NULL, -- init | suggest_import | manual_edit | agent_update | restore

| 风险 | 缓解 |
