# 桌面版后端起不来时只能干等 180 秒

> **版本** v2.5（十进制：bug 修补）　**日期** 2026-09-22～23　**体例** 问题 → 方案 → 结果
> **报障形态** 用户双击 `desktop.cmd` → 窗口停在「正在启动本地后端」→ 等满约 3 分钟 → 失败退出，**没有任何可用的死因信息**
> **触及文件** `static/desktop/app.py`（`wait_ready_monitored` / `_log_has` / `_install_crash_logger`）· `static/desktop/desktop.cmd` · `agent/prompts.py`（import 期调试 print）
> **守住它的用例** `tests/desktop_shell_e2e.py`（含「后端起不来必须快速失败」三条 + GBK 崩溃回归）

---

## 一、问题

| 现象 | 用户侧感受 |
|---|---|
| 双击后窗口一直显示「正在启动本地后端…」 | 不知道是慢还是死了 |
| 约 180 秒后外壳报「后端未就绪，请检查 .env」 | 这句提示**指不到任何真实原因**（端口被占、缺依赖、编码崩溃全长得一样） |
| `desktop.log` / 控制台里**没有后端进程的任何输出** | 无法自查、也无法把现场发给别人 |

同类二次报障：**「桌面上次卡了 180 秒」**（后端明明没起，外壳却只能等满超时）。

---

## 二、排查

| \# | 动作 | 发现 |
|---|---|---|
| 1 | 看外壳里子进程的 `stdout/stderr` 归到哪 | **`DEVNULL`** —— 后端的全部输出被丢掉了，难怪「无据可查」 |
| 2 | 看轮询逻辑 | 只轮询「HTTP 就绪」，**从不看子进程还活着没有** → 「起不来」与「起得慢」在代码里没有区分 |
| 3 | 手工在控制台跑同一份 `app.py` | **能起**（控制台有输出）→ 说明不是配置错，是「起法」不同 |
| 4 | 把输出改成写文件再跑 | 复现出 `UnicodeEncodeError`（见根因②） |

---

## 三、根因（三条叠加）

### ① 输出进 `DEVNULL`，失败无现场

子进程的 stdout/stderr 全部丢弃。后端起不来时，外壳手里唯一的信号是「HTTP 没通」，于是只能编一句「请检查 .env」。

### ② 输出重定向到文件 → 中文 Windows 上按 **GBK** 编码 → import 阶段就崩

后端的 `sys.stdout` 变成非控制台（文件/管道）时，Python 按**系统 locale** 选编码（中文机 = GBK）。而项目 `import` 阶段有一条**调试用的 print 会把整份提示词 dump 出来**（含 `🔍` 等 emoji）→ `UnicodeEncodeError` → **进程在 import 阶段直接死**。

> 这条极具欺骗性：**手工在终端跑没事**（终端环境带 `PYTHONUTF8`/`PYTHONIOENCODING`，或控制台码页是 65001），**双击/计划任务/CI 就崩**。

### ③ 不监控子进程 → 「慢」和「死」分不开

轮询里没有 `proc.poll()`：子进程早就退出了，外壳还在那儿一秒一次地探 HTTP，直到超时。

---

## 四、方案

| # | 改动 | 效果 |
|---|---|---|
| 1 | 子进程 stdout/stderr **全部写 `static/desktop/backend.log`**（每次启动覆盖） | 失败有现场 |
| 2 | 轮询里同时看 `proc.poll()`：**子进程一退出立刻返回**（带退出码），并从日志认出死因 —— `10048` → 「端口被占用」+ 换端口命令；`ModuleNotFoundError` → 「依赖缺失」 | 从「等满 180 秒」变成**数秒内给结论** |
| 3 | **全文搜**日志里的关键字（`_log_has`），展示尾部时**过滤超长行**（单行几万字符的提示词转储会把真正的报错挤出窗口） | 人眼能看到重点 |
| 4 | 每 10 秒打印一次等待进度，**带存活性**（`已等待 Ns…（后端进程存活）`） | 区分「慢慢起」与「已经死了」 |
| 5 | 起子进程时**显式注入** `PYTHONUTF8=1` + `PYTHONIOENCODING=utf-8`（不依赖用户环境）；`.cmd` 里也 set 一遍 | 免疫 GBK 崩溃 |
| 6 | **根因治理**：`agent/prompts.py` 里两条 import 期调试 print 注释掉（既刷屏又是编码地雷） | 不在 import 路径上留地雷 |
| 7 | 留 `--wait N` 上限旋钮 | 机器慢时用户自己能调大，不用改代码 |
| 8 | `_install_crash_logger()`：无控制台时 stderr 可能为 `None` → 未捕获异常写 `desktop.log` | 「双击没反应又没线索」的情况消失 |

---

## 五、结果

`tests/desktop_shell_e2e.py` 里三条专门钉这件事（原注释：*这两条对应「用户双击后傻等 180 秒、什么线索都没有」的实测故障*）：

| 用例 | 断言 | 实测 |
|---|---|---|
| 子进程秒退 → 立刻返回（不等满超时） | 返回 `child_exit:<code>`，耗时 **< 10s** | ✅ |
| 端口被占 → 快速报死因 | 耗时 **< 60s**（旧实现会等满 180s） | ✅ |
| GBK 崩溃回归 | **剥掉自己的 UTF-8 变量**后 import 不崩；且断言 `agent/prompts.py` 的调试 print **仍处于注释态** | ✅ |

> ⚠️ 写这类回归必须带**对照组**：环境里本来就带 `PYTHONUTF8` 时断言恒真。复现用户环境要 `env -u PYTHONUTF8 -u PYTHONIOENCODING <命令>`；但**跑项目自带套件时要带着这两个变量**（套件自己会 `print('✅ …')`，剥掉后反而在打印处崩，看起来像「一整批失败」）。两个目的别混在同一条命令里。

外壳套件整体：**108/108**。

## 六、遗留

- 失败时的**退出码语义**只区分了「子进程退出」与「超时」，还没有细分到「bind 失败 / import 失败 / 依赖缺失」的机器可读分类（现在靠日志关键字匹配）。
- `--wait` 仍是人工旋钮；机器差异极大时可以考虑自动阶梯放宽，但会牺牲「快速失败」的收益，暂不做。

---

## 七、复盘思考题

1. 为什么「把子进程输出丢进 `DEVNULL`」是一个**交付缺陷**，而不是「日志没地方放」的小事？（提示：失败时外壳手里还剩哪些信号）
2. 同一个 `app.py`，手工在终端跑正常、被外壳当子进程起就崩 —— 环境差异在哪一层？为什么它只在**中文 Windows + 输出重定向**这个组合下出现？
3. 为什么「端口被占」要在**子进程自己 bind 失败**时才下结论，而不靠启动前的端口预检？（提示：预检既不可靠也不安全，见 `桌面版进程与端口归属判错.md`）
