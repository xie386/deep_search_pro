> **版本** v2.5（十进制：bug 修补）　**日期** 2026-09-24　**体例** 问题 → 方案 → 结果

> **触及文件** `agent/answer_text.py`(新) `api/server.py` `agent/digest_engine.py` `static/index.html` `tools/backfill_reasoning_answer.py`(新) `tests/test_answer_text.py`(新)

## 一、问题（用户报障原文）

1. **约 5 次出现 1 次**：Agent 把**回复正文**打在「思考」面板里；气泡里只剩标题、**没有正文**。
2. 刷新后**正文依然不出现**。
3. 刷新后出现**多个空白回复段**（一屏「情报简报 / 内容：空」的卡片）。

用户侧证据补强：他把「模型思考过程」复制到了桌面文本文件——而那份文本的内容**就是正文本身**（`没有找到相关视频。让我看看这个UP主的更多视频信息…你正在读的是白井智之的《我是异类，你是怪物》…`）。

---

## 二、排查（先取证，再猜因）

| \# | 动作 | 得到的硬证据 |
|---|---|---|
| 1 | 读用户提供的「思考」文本 | 文本**混着两条系统通知**（`（已注入可用 CLI 清单 3 条）`、`（历史过长，已自动压缩旧对话摘要）`）——说明思考面板是「`monitor.report_thinking` 的通知 + 模型 reasoning_content」**混渲染**，不是纯粹的模型思考 |

| 4 | 查 `additional_kwargs` 列 | `#2539` 的 `additional_kwargs.reasoning_content` **就是正文**（228 字）→ 证明「正文被写进了思考字段」，也证明历史行**可回填** |

## 三、根因（两条链，各自独立）

### 链一：正文落进「思考」字段，气泡拿不到

推理模型（`deepseek-flash` 系）**偶发把可见正文写进 `reasoning_content`、`content` 留空**（或仅一个换行），实测概率 ≈ 1/5。代码侧两处「想当然」同时踩雷：

```
模型：content=''  /  reasoning_content='没有找到相关视频。…（正文）'
  ├─ agent/thinking_capture.py  → 把 reasoning 原样推给思考面板 ⇒ 用户看到「正文在思考里」
  └─ api/server.py:285          → return messages[-1].content  ⇒ 空串 ⇒ 气泡没正文
```

### 链二：工具轮的空消息被当成「回复」渲染

一轮里每个工具轮次都会产生一条 assistant：`content="\n"`、真正内容在 `tool_calls` 里。这是 **OpenAI 协议要求**（tool 消息必须紧跟带 `tool_calls` 的 assistant），**服务端必须保留**。问题出在渲染侧：前端对每条 assistant 都出一张卡 → **7 个工具轮 + 1 条空答案 = 刷新后 8 张空白卡**。

> 一句话：**服务端的「协议消息」与「用户可见回复」是两个集合，前端把后者当前者用了。**

## 四、方案（四层，缺一层就留尾巴）

| 层 | 改动 | 为什么不能省 |
|---|---|---|
| **A 取答案** | 新增 `agent/answer_text.py`：`content → reasoning 回填 → 本轮更早的**非工具调用**回答 → 显式提示`；聊天与周报**共用**这个实现 | 只改聊天会漏掉周报（那里会误报「主 Agent 未产出有效周报内容」） |
| **B 边界** | 回溯**限定在本轮内**（上一条 HumanMessage 之后，且能匹配被技能前缀改写过的用户文本） | 不限边界会把**上一轮的旧答案**当成这一轮的答案 |
| **C 落库** | ① 回填/回溯时**把文本写回消息对象**（`m.content = answer`）；② 落库前过滤「空内容**且**无 `tool_calls`」的 assistant | ① 落库走同一批对象，只改返回值 → DB 仍空 → 刷新又变空卡；② 带 `tool_calls` 的**绝不能丢**（否则 tool 消息成孤儿，下一轮请求被上游 400） |
| **D 渲染** | 前端历史渲染：`if (!_txt.trim()) continue;` | 顺带把**历史遗留**的空白卡也隐藏掉，不用清库；且这是应对「服务端又漏了」的最后一道防线 |

**为什么不在前端做「合并连续 assistant」之类的大改**：前端展示需求（一条问答一张卡）没变，坏的是**输入数据**里混进了协议消息；在渲染侧只做「空则跳过」这一条最小规则，风险最低。

| 刷新路径 | 2 条 assistant → **1 张卡** | 3 条 assistant → **1 张卡**（修前会是 3 张，其中 2 张空白） |

## 六、遗留与后续

- **上游行为不可控**：仍有 1/5 概率把正文放错字段。现在的应对是**自动回填 + 思考面板留痕**（`（模型未返回正文，已用其思考内容回填答案）`），不再出现空白气泡。若日后换模型/换端点，这条概率需要重新观察。
- **历史数据回填**：`tools/backfill_reasoning_answer.py`（**默认 dry-run**）可把 `reasoning_content` 补回 `content`；dry-run 实测精确命中 1 条（`#2539`，228 字）。**是否执行由用户决定**，脚本 `--apply` 时自动备份受影响行。
- **未做**：把「段落级」的 assistant 消息真正合并成一条（需改动落库语义与历史兼容），当前判断收益不足、风险偏高。

## 七、复盘思考题

1. 为什么「刷新后空白卡」在**修好链一之后依然会出现**？（提示：把服务端的消息集合分成「协议消息」与「用户可见回复」两类来看）
2. 回填 `reasoning_content` 时必须**把文本写回消息对象**，而不是只改函数返回值——这个坑的本质是什么？（提示：落库和返回是不是同一份数据）
3. 为什么「往前找一条更早的 assistant 正文」这条兜底**必须限定在本轮内**？不限会发生什么？
4. 为什么带 `tool_calls` 的空消息**必须**落库，而空答案的空消息**必须**过滤？两者的区别在哪一层（协议 / 展示）？
