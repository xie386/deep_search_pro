# 桌面版进程与端口归属判错（误杀用户实例 / 把「别人的服务」当成自己的）

> **版本** v2.5（十进制：bug 修补）　**日期** 2026-09-22～23　**体例** 问题 → 方案 → 结果
> **报障形态** ① 外壳报「后端进程启动后立即退出」，而 `backend.log` 里明明写着 `Uvicorn running`；② 自测时外壳**「0 秒就绪」**（其实复用了用户已开着的实例）；③ **发生过一次误杀**：助手把用户 23:45 起的桌面实例所在端口上的进程强杀了
> **触及文件** `static/desktop/app.py`（`can_bind` / `port_in_use` / `wait_ready_monitored` / `_kill_tree` / `_OWN_BACKEND`）
> **守住它的用例** `tests/desktop_shell_e2e.py`（进程归属 / 复用别人服务后退出不关它 / 端口探测互补）

---

## 一、问题（三种表现，同一个根因）

| 现象 | 表面看像 | 真实原因 |
|---|---|---|
| 报「子进程启动后立即退出」但日志写着 `Uvicorn running` | 「后端起不来」 | **venv 的 `python.exe` 是 launcher**：它再起一个真解释器跑 uvicorn，端口归「孙子进程」，launcher 自己先退（码 1）→ 外壳按「子进程退出」判死 |
| 外壳「0 秒就绪」 | 「启动很快」 | 端口上**已经有用户开着的服务** → 按约定复用它（这一步本身是对的，但让人误以为新代码生效了） |
| **误杀用户实例** | —— | 助手用 `netstat` 找到「端口持有者 pid」并 `taskkill`，而那个 pid 不是自己启动的进程树 |

> 事故交代：当时读 8123 的 LISTENING 持有者是 pid 19168 并强杀；事后核对 `desktop.log` —— 用户 23:45 的实例（pid 12444）段**没有任何退出/看护记录**，据此判定它是被强制结束的。同时自测实例已清理、无遗留监听端口。**根因是「按 pid 归属」而不是「按端口归属」判断进程。**

---

## 二、排查

| \# | 动作 | 发现 |
|---|---|---|
| 1 | `tasklist` / 进程树看 venv 启动链 | `.venv\Scripts\python.exe` → 再起一个真解释器 → **端口由孙进程持有** |
| 2 | 看就绪轮询的判据 | `proc.poll() is not None` 被当成「服务没了」→ launcher 退出即误判 |
| 3 | 看退出清理 | `if proc.poll() is not None: return` → **直接把 handle 丢掉，把真服务留成孤儿**（端口一直占着） |
| 4 | 用「连接探测」判端口是否空闲 | 对「只 listen 不 accept」的端口，探测请求把 backlog（默认 1）填满 → 紧接着的 `connect_ex` 被**拒绝** → 误判为空闲 → 在占用端口上硬起，报 10048 |

---

## 三、根因

**判据错了：代码把「进程还活着吗」当成「服务还在吗」，把「pid 是谁的」当成「端口能不能动」。**

- 进程层真相：venv 的 `python.exe` 只是启动器，**真正的服务在孙子进程**；父子进程退出 ≠ 服务消失。
- 端口层真相：**「服务可用」才是唯一判据**（端口有没有人在听 + HTTP 通不通）。
- 所有权真相：`_OWN_BACKEND` —— **只有外壳自己起的后端才归它管**；复用别人的服务时，退出**绝不动它**。

---

## 四、方案

| # | 改动 | 要点 |
|---|---|---|
| 1 | 就绪判定改为「**服务可用**」：`held = port_in_use(p) or (p >= 1024 and not can_bind(p))`；子进程退出后**不立刻判死**，而是看端口上还有没有人在服务，给宽限（上限 ~90s） | `held` 假 → 立刻 `child_exit:<code>`；`held` 真且日志出现 `10048` / `attempting to bind` → 说明端口是**别人的**程序占着（我们 bind 失败才退）→ 立刻失败并报死因（实测 105s → 14s） |
| 2 | 启动就绪后用 `netstat -ano` **记下端口持有者 pid**；退出时两个 pid 都 `taskkill /F /T` | 不再把真服务留成孤儿 |
| 3 | 端口探测**双条件互补**：`can_bind(p) and not port_in_use(p)` 才算空闲 | `bind` 探测与连接队列无关（避开 backlog 陷阱）；配 `port_in_use` 是因为 Windows 上对方设了 `SO_REUSEADDR` 时 bind 会「抢占成功」 |
| 4 | 端口冲突**自动往后试**（8123→8127，`--port-attempts` 可调）；若端口上**能响应 HTTP 的服务**则按约定**复用**它 | 不误判、也不打扰用户 |
| 5 | 看护/重启**只对 `_OWN_BACKEND` 生效**，判据是「连续 N 次探测不通」（约 3 次 / 9s）再退避重启 | 复用/用户的服务**绝不重启、绝不 kill** |
| 6 | 单实例锁 socket 兼作 IPC：第二实例 `connect` 后发一行 `SHOW` → 第一实例 `show()+restore()` | 双击第二次不会开出第二个窗口 |
| 7 | **单实例锁绝不能设 `SO_REUSEADDR`** | 设了会让第二次 bind 成功 → 锁形同虚设 |

## 五、结果

`tests/desktop_shell_e2e.py`（**108/108**）里与本文相关的断言：

| 用例 | 断言 |
|---|---|
| 进程归属 | 只关自己起的后端；**复用别人服务后退出不关它** |
| 第二实例唤起已存窗口 | 真起 listener，发 `SHOW` 断言第一实例收到并会唤出窗口 |
| 端口自动换 | 空端口→new / 被占→换下一个 / 只剩一个且被占→none / **有 HTTP 服务→reuse** |
| 端口探测的 backlog 陷阱 | `bind` 探测与 `connect` 探测**互补**（`port_in_use(空端口) is False`） |
| 后端崩溃自动重启 | 判定逻辑 6 例 + **真机：认出端口持有者 → 杀掉 → 断言服务被自动拉回** |
| 快速失败 | 子进程秒退 → 数秒内返回 `child_exit`；端口被占 → < 60s 报死因 |

**纪律（写进 README 与 skill）**：`netstat` 的 LISTENING PID **≠ 你启动的 PID** = 那是**用户的服务**（可能是旧代码）→ 要么直接用、要么**换端口验证**（`--port 8124`），**绝不 kill**，也别因此断言「我的代码没生效」。

## 六、遗留

- 「端口持有者」在 Windows 上靠 `netstat -ano` 反查，多网卡/多栈（IPv6 vs IPv4）时偶有歧义；目前用「HTTP 探通 + 端口监听」双判据兜住。
- 崩溃自动重启最多 3 次（退避 2s/5s/15s），更多次没有意义（一般是环境性问题）。
