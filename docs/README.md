# docs/ 文档体系（版本规则 + 索引）

## 写作约定（2026-10-04 立）

**符号只作数据，不作标点。** `✓` / `✗` / `△` 仅允许出现在三种地方：

1. **评分与判据的表格单元格**（如终判分布、验收判据列）；
2. **行内代码里**（如符号归一规则 `` `√/v/对 → ✓` ``、契约串 `` `verdict:{✓36,△5,✗2}` ``）；
3. **紧邻数字的统计串**（如 `✓37 · △5 · ✗0`）。

正文叙述一律用中文把话写清（「已修」「未实现」「别这么写」），**不要**用符号当逗号、句号或语气词。
理由：这些符号高频出现在正文里会被后续会话（含 v4/v5）当成文风样板反复放大；2026-10-04 已对 v3.0/v3.1 全部文档做过一次清理
（2455 → 152，且正文与表格里的装饰性用法已归零，只余评分/判据/契约数据），清理前的原件备份在 `docs/v3.1/backups/symbol_cleanup_20261004/`。

> 本目录存放**设计文档与里程碑记录**，按版本分子目录。**新增文档前先读本页的版本规则**——放错目录比不写文档更麻烦（找不回、也对不上版本号）。

## 一、版本与文档规则（2026-09-24 用户定）

| 版本号形态 | 含义 | 放什么文档 |
|---|---|---|
| **整数**（v1.0 / v2.0 / v3.0 …） | **大规模变化**：新功能开发、现有功能的颠覆性优化、架构改进 | **技术调研、大型方案文件、工程计划书**（即使该版本收官之后才写的也归这里）；里程碑实现设计 |
| **小数**（v2.5 / v2.6 …） | **现有功能的用户观感优化、bug 修补、小功能添加** | **只放「问题 → 方案 → 结果」性质的文件**（一次修复/一个小优化一篇） |

⚠️ 两条容易搞错的边界：

1. **收官后补写的调研 / 大型方案 / 计划书，仍然进对应整数版目录**——不因为它「写晚了」就挪进小数版。判断依据是**文档性质**（调研/方案/计划），不是**写作时间**。
2. **小数版目录不允许出现长文档**：技术调研、架构方案、工程计划书一律不进小数目录，哪怕它是在 v2.5 期间写的。

### 新文档放哪？一句话决策

```
这份文档是「某个问题的排查+修复记录」或「某个小优化的前后对比」？
 ├─ 是 → docs/v<当前小数版>/（问题-方案-结果体例）
 └─ 否 → 是调研/方案/计划/里程碑设计？
 └─ 是 → docs/v<它归属的整数版>/（按「它服务于哪个大版本的目标」判断）
```

## 四、维护纪律

- **做完一个里程碑/一次修复就补文档**，别攒着（攒完就写不出「当时为什么这么定」）。
- 小数版文档**必须写清四件事**：现象（可复现的表述）、证据（库/日志/代码位置）、根因（链式，不是一句「模型抽风」）、验证（跑了什么、多少条、什么数字）。
- 文档里的**实测数字要能对上测试输出**（如「15/15」「109/109」）；写了数字就要能被复跑验证。
- 相对链接用相对路径（`../README.md`），别写绝对路径。
