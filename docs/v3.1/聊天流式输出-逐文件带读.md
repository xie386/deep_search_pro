## 〇、一眼看懂：四段链路 + 一轮问答的 12 步

| 阶段 | 什么时候发生 | 谁在跑 | 产物 |
|---|---|---|---|
| **① 调用期** | 用户点发送（`/api/chat`） | `api/server.py::_run_agent` → `_invoke_or_stream`（`_stream_enabled()` 判开关） | 一个 `DeltaSink` 实例 |
| **② 增量期** | 模型每吐一段 token | `agent.stream(...)` 的 `messages` 流 → `is_main_graph` → `iter_deltas` → `sink.feed` → `monitor.report_delta` | WS `delta` 事件（`kind`/`text`/`seq`） |
| **③ 渲染期** | 前端收到 `delta` | `front/index.html::applyStreamDelta` + `schedScroll` | 气泡增量文本 / 右栏思考文本 |
| **④ 收尾期** | 一轮结束或中断 | `sink.flush()` → `_run_agent` 返回 → `api_chat` 回 JSON | `finishStreaming` **覆盖**为完整文本（落库同源） |

```
用户点发送
 └─ POST /api/chat?token&thread_id&question
 └─ api/server.py::api_chat ── asyncio.to_thread(_run_agent)
 ├─ 建 agent（含工具路由注入）+ agent_cancel.begin(thread_id)
 ├─ _invoke_or_stream(agent, payload, cfg, thread_id) ← ★ 本文主角
 │ ├─ ZX_STREAM=0 ? → agent.invoke(...) 返回 (state, False) ← 回退路径（行为同改造前）
 │ └─ 默认：for mode, item in agent.stream(stream_mode=['messages','values'])：
 │ ├─ mode=='messages' → is_main_graph(meta)? 否 → 丢弃（子 Agent 的 token 不进气泡）
 │ │ 是 → iter_deltas(chunk) → [('answer',txt)|('reasoning',txt)]
 │ │ → agent_cancel.check(thread_id) ← ★ 中断粒度到"每段"
 │ │ → sink.feed(kind, text)
 │ │ └─ 攒够 80 字 / 距上次 ≥60ms → _send()
 │ │ └─ monitor.report_delta → _emit('delta', ...)
 │ │ └─ 按 thread_id 定向 → WS 推送
 │ └─ mode=='values' → final_state = item ← 取最后一个 == invoke 的返回值 
 │ （中断：AgentCancelled → exc.partial = sink.text；finally: sink.flush()）
 ├─ answer_text 提取 / thinking 回填 / 落库 / 统计 token ← 与改造前同一套，未改一行 
 └─ 返回 {answer, thread_id, cancelled, last_msg_id, ...} ← 契约未变 
```

**一轮问答里 WS 上能看到的三类事件（时间线）**：

| 顺序 | 事件 | 承载 | 前端落点 |
|---|---|---|---|
| 1 | `delta` (`kind='reasoning'`) | 思考逐段（若模型吐 reasoning） | 右栏思考折叠区（`thinkingText`） |
| 2 | `tool_start` / `assistant_call` / `task_result` | 工具与子 Agent 的**事件级**进度（非 token） | 监控列表 / 用量刷新 |
| 3 | `delta` (`kind='answer'`) | 正文逐段 | 聊天气泡（`messages` 末尾那条 `streaming`） |
| 4 | `thinking`（旧路径） | 与 `delta.reasoning` **并存**：旧路径是 invoke 后**一次性**回填 | 同右栏（`server.py:445` 的 `if not _streamed:` 已挡住重复 见 L3-7） |
| 5 | HTTP 返回 | 完整 answer（= 增量的**逐字**拼接） | `finishStreaming` 覆盖气泡 |

★ **注意第 3、4 步会交替出现多次**（工具轮 = 模型段 + 工具段交替）→ 观感就是「想/说一段 → 做一段 → 又想/说一段」

### 为什么是这套方案（选型留痕）

| 方案 | 做法 | 结论 |
|---|---|---|
| **①图级流式 + 复用既有 WS**（**采用**） | `agent.stream(stream_mode=['messages','values'])` + `delta` 事件走 `/ws/{thread}` | 内网单机自用、改动最小、**聚合形态不变**（`thinking_capture`/`answer_text`/成本表都不用改）、spike 已实测可用 |
| ②内部 `_stream` 直连模型 | 绕过 langgraph，自己拿 model 的 token 流 | 等于**另起一套**执行路径 工具循环/子图/中断检查点都要重做 否决 |
| ③真 SSE（新端点） | `text/event-stream` + EventSource | 要多一套传输/鉴权/重连 而项目已有 WS 且按 thread 定向 否决 |

★ 支撑①的**实测**（`tests/debug/_spike_stream_probe.py`，不靠推理）：`stream_mode='messages'` 能拿到 token、
`usage_metadata` 完整（成本表不受影响）、首块 ~5ms、甚至**原本担心的** `langchain/agents/factory.py` 里
`_execute_model_sync` 是 `model_.invoke(messages)`（未显式传 config）也**靠 contextvar 透传成功**。

## 二、逐文件带读

### L0-1 `.env` 的 `ZX_STREAM`（开关）

- **它是什么**：唯一的用户可见开关 默认**开**（`os.getenv("ZX_STREAM", "1")`）。
- **为什么放调用侧**：子 Agent / digest / CLI / 探针与前台**共用同一个 model 对象**，
 若做成"模块级开关"就会把它们一起带进流式（子 Agent 的中间 token 一旦漏出就是事故）。
- **逐行检查要点**：
 1. 只有 `api/server.py::_stream_enabled` 读这个变量（`grep -rn ZX_STREAM` 应只有一处逻辑）；
 2. 取值兼容 `0/false/off/no/空` → 关（别写出 `== "0"` 这种半吊子判断）。
- **思考题**：如果哪天要"按账号灰度"，应该改这里还是改 `_run_agent` 的 `stream` 形参（提示：答案在形参 —— 因为开关必须跟着**调用方**走）。

### L0-2 `front/index.html` 的思考折叠区（`:2561` / `:3881`）

- **它是什么**：右栏 `<details class="think-box" v-if="thinkingText">`（`:2561`）+ `const thinkingText = ref('')`（`:3881`）。
- **链路位置**：`delta(kind='reasoning')` **和** 旧的 `thinking` 事件**都**写进它。
- **逐行检查要点**：
 1. `v-if` 意味着**有思考才出现** → 没有思考的模型/问题下，右栏不占位；
 2. 清空时机：新一轮 `thinkingText.value = ''`（`:6878`）、切会话/重置（`:4498`/`:5843`/`:5854`）—— 检查是否有**漏清**导致上轮思考串到下一轮。
- **思考题**：思考区为什么不放在气泡里（提示：正文与思考**语义不同**、落库只有正文；且思考区可折叠，不干扰阅读）。

### L1-3 `agent/stream_sink.py`（144 行 · 本功能核心）

- **它是什么**：增量侧的**纯函数 + 一个节流汇聚器** 不碰 DB、不碰网络、不判对错（推送失败也吞掉）。
- **关键定义**：

| 行 | 符号 | 作用 |
|---|---|---|
| `:31`-`:33` | `MAIN_NODE='model'` / `DELTA_MIN_INTERVAL=0.06` / `DELTA_MIN_CHARS=80` | 三个可调常量（改这里就是调观感 vs 负载） |
| `:36`-`:48` | `is_main_graph(meta)` | ★ **只推主图**：`langgraph_node=='model'` **且** `checkpoint_ns` 不含 `\|`（竖线是子图嵌套分隔符） |
| `:51`-`:63` | `iter_deltas(chunk)` | 从 chunk 拆 `('answer', content)` / `('reasoning', additional_kwargs.reasoning_content)`；**多模态 content（list）不进增量 ** |
| `:66`-`:94` | `DeltaSink.__init__` | `emit` 默认注入 `monitor.report_delta`；`_buf`/`_acc`/`_counts`/`_seq`/`_emitted` |
| `:97`-`:106` | `feed(kind, text)` | 入缓冲 + 累计；**攒够 80 字或距上次 ≥60ms 就发** |
| `:108`-`:112` | `flush()` | 把剩下的推完；**思考先于正文**（保证时间顺序）；结束与中断都会走 |
| `:114`-`:126` | `_send()` | 取空即返回、`seq += 1`、**`try/except` 吞异常**（推送失败不能影响这一轮回答） |
| `:129`-`:144` | `.text` / `.reasoning` / `.counts` / `.emitted` | 聚合全文（**逐字比对的依据**）与节流是否生效的计数 |

- **逐行检查要点**：
 1. **`is_main_graph` 的两道条件缺一不可**—— 抽掉 `checkpoint_ns` 判断，子 Agent 的 token 就会串进气泡（`tests/unit/test_stream_sink.py::test_subgraph_meta_is_filtered` 盯着它）；
 2. `feed` 里 `kind` 不认识时归 `answer`（防御性）；
 3. **首块立即推**：`self._last = 0.0` 初值 → 第一次 `now - _last` 必然 ≥60ms 这是**设计行为**（第一眼就要看到字）—— 写断言时别假设"首块不推"（我自己踩过）；
 4. `flush()` 的 `finally` 调用位置在 **server** 侧（`:328`-`:329`）不在本文件—— 检查时顺链看过去。
- **思考题**：为什么"聚合"要放在 sink 里，而不是"前端把收到的 `text` 拼起来就行" 
（提示：① 中断时后端要拿**半截**落库；② 验证要能**逐字比对**；③ 前端拼错/丢块无法自证）。

### L2-4 `api/monitor.py`（增量怎么搭上既有 WS）

- **它是什么**：全局单例 `monitor` 既有事件（工具/子 Agent/报告）都走它 本次只**加了一个事件类型**。
- **关键行**：
 - `:63` `set_current_thread(thread_id)`—— 增量**按线程定向**，靠它（什么时候被设？→ `_run_agent` 一开始 这点也是"增量的 thread_id 从哪来"的答案）；
 - `:72`-`:125` `_emit` —— 三分支：① 有 WS 就推（`:89`-`:111`，**同循环直接 await / 跨循环 `run_coroutine_threadsafe`**）② 控制台 sink ③ `print` 保底；
 - `:129`-`:131` ★ **`delta` 直接 `return`**—— 增量块又密又多 控制台/CLI 不逐块打（正文由最终回答给出）;
 - `:148`-`:155` `report_delta(kind, text, seq)`；
 - `:200`-`:210` `ConnectionManager.send_to_thread`—— `active_connections[thread_id]` 里没有就**静默丢弃**（这是踩过的坑：没进 lifespan → `manager.loop` 未绑定 → 一条都收不到 见 L5-10d）。
- **逐行检查要点**：
 1. 增量的**并发安全**：`_emit` 在**工作线程**里跑（`asyncio.to_thread`）→ 必须走 `run_coroutine_threadsafe` 不能直接 `await`；
 2. ★ **推送失败由谁兜住**：`send_to_thread`（`:200`-`:203`）**本身没有 try/except**——兜底在**调用它的** `_emit`（`:117`-`:125` 的 `except Exception: pass` 推送失败绝不影响这一轮回答）；另外 `active_connections` 里**没有对应 thread 就静默丢弃**（这是「WS 连上了却零事件」的常见成因 见 L5-10d）；
 3. **别把 `delta` 也发给控制台**（`:129` 拦了 改这里要重跑 `m4_usage_frontend` 之类的事件面 harness）。
- **思考题**：为什么增量的 `thread_id` 用 `set_current_thread` 的隐式上下文，而不是每个 delta 都带一遍参数（提示：`DeltaSink` 的 `emit` 签名 `(kind, text, seq)` 少一层参数穿透；但代价是**依赖调用侧设对** → 检查点：`_run_agent` 必须在建 sink **之前**设好）。

### L3-5 `api/server.py::_stream_enabled`（`:280`）

- **它是什么**：唯一的开关判定（见 L0-1 的"为什么放调用侧"）。
- **逐行检查要点**：默认值 `"1"` 别改成 `""`/`None` 导致默认关（那就退回改造前了）；注释里写明"子 Agent 走形参、不经过本函数"。

### L3-6 `api/server.py::_invoke_or_stream`（`:290`-`:333`）★ 唯一的执行分叉点

- **它是什么**：跑一轮 agent 的**两种方式**，返回**同一形状**的 `(final_state, streamed)`。
- **逐段**：
| 行 | 代码 | 为什么 |
 |---|---|---|
| `:304`-`:305` | 关开关 → `agent.invoke(payload, cfg), False` | 回退路径**逐字**等同改造前 |
| `:306` | 函数内导入 `stream_sink` | 避免 `api.server` 加载期多拉依赖 |
| `:308` | `sink = DeltaSink(thread_id)` | `emit` 默认就是 `monitor.report_delta` |
| `:311`-`:318` | `messages` 分支：`is_main_graph` 过滤 → `iter_deltas` → **`agent_cancel.check(thread_id)`** → `sink.feed` | ★ 中断粒度从"每次模型调用前"**加密到每个增量段之间** 真省剩余 token |
| `:319`-`:320` | `values` 分支：`final_state = item`（覆盖式的最后一个） | 取**最后一个**才等于 `invoke` 的返回值 |
| `:321`-`:327` | `AgentCancelled` → `exc.partial = sink.text` → `raise` | 半截随异常上传 落库与前端一致（否则刷新后只剩占位语） |
| `:328`-`:329` | `finally: sink.flush()` | ★ 不 flush 就丢最后一句 |
| `:330`-`:332` | `final_state is None` → `RuntimeError`（附"请设 ZX_STREAM=0 回退"） | 失败要**可回退** 不能静默降级 |
- **逐行检查要点**：
 1. **两条路径的返回值形状必须一致**（`streamed` 只用于告知/回退判断 不参与下游语义）；
 2. `check()` 的**位置**：放在 `feed` **之前**—— 放之后就会多推出一段"本不该出"的内容；
 3. `flush()` 必须在 `finally`（异常/中断都要）；

### 4.1 ✅ 收尾不退出 —— **已定位并修复**（2026-10-02 二次核查）

- **现象**（当时）：断言全过 → 进程一直不返回 被 `timeout` 杀掉。
- **★ 真根因**：**不是** taskkill、不是库锁、不是日志句柄——
 是 **`TestClient.__exit__` 关闭 portal/lifespan 时在等 reader 线程那条仍挂着的 WS 会话**。
 更早排查绕了三圈的原因：那几轮「改成真 uvicorn 版」的写入**实际没有落盘**，
 盘上一直是 **TestClient 版**（`finally` 里是 `_cm.__exit__()`）→ 于是看着"改了还是卡"。
- **证伪过程**（`tests/debug/_spike_teardown_order.py` 隔离实验：起 uvicorn → 杀 → 回收，各自计时）：
 `taskkill /T` **0.2s** · `child.wait` **0.0s** · `purge_account` **0.0s**—— 三个怀疑**全部不成立**。
- **修法**：重写为**真 uvicorn 版**（不再有 TestClient portal）+ `os._exit` 强制退出 + 端口兜底清理 
 （`taskkill /T` 连 launcher 的**孙子进程**一起清—— 这个坑本身是真的 只是它不是卡点）。
- **复验**：**7/7 全过 · python `exit=0` · 8124 无残留 · 临时账号已回收** 
- **留了一手**：`faulthandler.dump_traceback_later(120, exit=True)`—— 收尾再出意外会**打印所有线程的栈**再退出 
（不再只看到「被 timeout 杀掉」这种无信息量的结局）；可用 `STREAM_E2E_FAULT` 调秒数。

### 4.2 ✅ 思考流 —— **已证实经 WS 到达右栏**（同日二次核查）

- **当时的误判**：用「用一句话说明你是谁」跑了 5 次 → 思考恒为 0 条 → 差点归因成**传输/供应商**问题。
- **★ 真相**：思考出不出现**首先取决于问题是否激发推理**——
 换成「用两步推理算一下 17 × 23」后：**增量 5 条 = 正文 1 + 思考 4（274 字）**；
 另一条直接捕获路径 `stream_delta_verify.py` 此前也已拿到 **270 字**。
- **判据已写进脚本**：默认问题就是「逼出推理」的那句，思考为 0 时**先换问题再怀疑传输**；
 可用 `STREAM_E2E_Q` 覆盖。
- **剩下的变量**：不同**供应商/模型**对 reasoning 的表达不同（本项目 `ReasoningChatOpenAI` 已把
 OpenRouter 的 `reasoning` 与原生 `reasoning_content` 归一）—— 换供应商时按 §四 4.4 复核。

### 4.3 中断省下多少 token —— 已决不做量化（2026-10-07）

- 原验收口径那条（`usage_events`：**不中断 vs 第 3 秒中断**对比）**不做**：各厂商对「中断后已产生 token 的额度返还」政策不一致（全额返还 / 部分返还 / 按实际计费 / 不返还都有），**不是纯数学计算**，量化结果没有跨模型可比性，跑两组真实对话也只能得出"这一个模型这一个口径下"的数。
- 中断设计的价值已改为**及时发现思考错误而中断**——省时间，并且**防止错误结论进入画像**（比"省多少 token"更贴合本项目定位）。

### 4.4 ⚠️ 换供应商要复核两件事

1. **`usage_metadata` 是否仍返回**（本模型实测有）→ 没有就会影响成本表；
2. **`reasoning_content` 字段名/位置**（OpenRouter 的 `reasoning` 已由 `ReasoningChatOpenAI` 归一）→ 别家可能要补映射。

### 4.5 ⚠️ 工具轮是"分段流"，中间仍会停顿

- 每次模型调用**一段** 中间工具执行期无 token → 那段时间靠既有 `monitor` 事件（`tool_start` 等）填 
—— 观感上就是「说一段 → 做一段 → 说一段」（这**正是**设计意图 不是缺陷）。
- 未做：中断后的"**继续生成**"入口（本轮范围外）。
