> 性质：**新能力落地 + 一组真机 bug 修复**（问题-方案-结果）→ 按 docs 规则归**小数版本** `v3.1/`

## 一、起因
用户：「现在 agent 的能力，文字处理和语音克隆和合成，现在我想增加 agent 的**视觉工作能力**，即用户可以在聊天框贴入图片，
agent 根据图片识别结果和用户文本提示词工作。目前 agent 的默认模型 **agnes 本身就是多模态模型**，只是从来没有使用过它的视觉能力。」

## 二、拍板口径（用户 2026-09-30 逐条定，**实现必须照此**）
| 分叉 | 决策 |
|---|---|
| 图片怎么送后端 | **A：独立上传接口**（multipart → 落盘 → `image_id`），不把 `/api/chat` 改成 JSON body |
| 哪些模型能用 | **配置导向**：`llm_providers` 加 `supports_vision`，「模型选型」里用户自己勾；**名字带 agnes 的默认置 1**；**未勾选却带图 → 明确报错，绝不静默丢图** |
| 图片作用域 | **只跟本轮**（不进历史）；落盘按账号隔离；**做压缩**；**每次提问最多 3 张** |
| 前端入口 | **粘贴 / 拖拽 / 点选 三入口都做** |
| 语音链路 | **不验证、不碰**（用户正在策划语音改造，是下一个优化目标） |

## 三、实现（六步，全部落地）
| 步 | 落点 | 关键点 |
|---|---|---|
| 1 基座 | `tools/chat_images.py`（新，约 11KB） | **只看 magic bytes** 不信扩展名；压缩（长边 ≤ 1568 质量阶梯 ↓）；**内容 sha256 当 id** 天然去重；`image_id` 只允许 `[0-9a-f]{16}\.(jpg | png | webp)` **防目录穿越**；`prune()` 默认 14 天 |
| 2 上传接口 | `api/server.py` → `POST /api/chat/upload` | 单张一次（前端累计上限 3）；`token` 走 query + `file` 走 multipart（照既有 `bg_upload` 写法）；`ChatImageError` → **400 人话** |
| 3 装配带图 | `agent/build_context.py` · `api/server.py#_run_agent` · `/api/chat` | 全链路**只有一处**把提问变 `HumanMessage` 单点挂钩；`images=` 仍走 **query 参数**（与 `skills` 同款 **零契约破坏**）；**无图时零变化**；块顺序「**文字在前、图在后**」 |
| 4 配置开关 | `tools/schema_personal.py` · `api/customize.py` | `supports_vision INTEGER DEFAULT 0`（**ALTER 与 CREATE TABLE 两条路径都加** 且 ALTER 也带 `DEFAULT 0`）；请求模型/出参/INSERT/**两条 UPDATE 分支**全带；一次性幂等默认：agnes → 1、其余 NULL → 0、**用户手动设过的不许覆盖** |
| 4b 视觉闸 | `api/server.py` | 生效配置未勾 → **400「未开启『支持图片』…」**；无自定义配置（走 .env 默认 agnes）**放行**；判定**只算一次** `_vision_ok` 与能力声明共用 |
| 5 前端 | `front/index.html` | 三入口 + 预览条（缩略图/单张 ✕/上限提示）+ **用户气泡显示本轮图片** + 微信式输入框 |
| 6 用例 | `tests/unit/test_vision_flag.py`（15 项） | 见第七节 |

## 四、关键口径（改代码前先读这段）
- **只跟本轮**：图片只注入**当前** `HumanMessage` 的 blocks；落库仍只存**文字** → 后续轮次的历史里没有图 不会重复收费；
- **子 agent 不带图**（只有主会话装配处注入）；
- **连续两个"能收图"判断**：`supports_vision` 为 `0/NULL` **都算不能**（NULL 与 0 不许被当成"能"）；
- **成本记账**：图片 token 计入上游返回的 input（M6c 记账链路无需改动）；
- 语音链路**一行未碰**。

## 五、真机问题与修复（全是实测踩出来的）
| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 贴图后 `TypeError: unhashable type: 'list'`（前端显示为"模型调用失败" 误导） | 提问 content 现在是**块列表**，而两处代码写的是 `m.content in 集合` | 抽 `agent/answer_text.message_text(m)` 统一取文字**一处实现**；两处（消段匹配 + 落库边界）改用它；加静态防线：全仓禁裸比较 |
| 2 | 老库新行 `supports_vision` 是 **NULL** 而非 0 | `ALTER TABLE … ADD COLUMN` **不带 DEFAULT**（只有 CREATE TABLE 的 `DEFAULT 0` 对新库生效） | ALTER 补 `DEFAULT 0`；代码侧把 NULL 也当"不能收图"；用例写明该陷阱 |
| 3 | 模型**看得见**却自称「我目前没有视觉识别的能力」「图片是通过您描述的方式呈现给我的」 | 注入块长期**只有工具视角**（人格/记忆/CLI 能力卡）→ 模型推理出"我的工具都是文字类的 → 没有视觉"；`prompts.yml` 一个字没提视觉 | 两段**条件化**声明：① **能力事实**（当前模型支持图片 纯文字轮也注入）② **本轮真有图**的强指令（图片已随消息送达 别否认 别找图像工具）；不支持视觉时两段都不出现（免得凭空虚报） |
| 4 | 发送后气泡里的缩略图会变空 | 我在发送处 `clearChatImages()` 里 **revoke 了对象 URL** | 改 `clearChatImages(true)`（图已归气泡所有 只在手动 ✕ 移除时释放） |
| 5 | 贴图**前**没有任何可见入口 | 预览条 `v-if` 只在有图/出错时才出现 | 微信用「＋ 展开面板」解决（相册 = 真上传） |

## 八、踩坑与教训（给下次的自己）
1. **补丁插进 `try:` 与 `except` 之间**—— 两次（`api/server.py`、`tools/schema_personal.py` 后者直接让全项目 import 崩）；根因是**省了编译** → **改完每个碰过的文件都要 `py_compile`**，一条不许省；
2. **中文串里混 ASCII 双引号**—— 本项目惯犯，本轮又中（用例里）→ 统一「」；写完必扫；
3. **锚点撞车**—— `if image_ids:` 有两处 → 断言拦住；**教训：写盘一律放最后**（本轮靠这个多次保住文件）；
4. **harness 循环统计假失败** ✗ —— 循环报 0/11 ✓ 逐个单跑全绿 ✓；另一次是漏 `< /dev/null` → 结论：**满屏红先怀疑跑法**，别急着改代码；
5. **`execute_code` 内核不是项目 venv**—— 涉及项目模块的活（迁移/真机冒烟）一律走 `terminal`；
6. **`utils.paths` 是我臆测的模块**（根本不存在）→ 改成"探测 + 从项目根兜底"；**不许凭想象 import**。
