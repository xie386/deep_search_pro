## 〇、一眼看懂：一次「长按说话」的 12 步

| 步 | 谁在跑 | 做什么 | 失败时的表现 |
|---|---|---|---|
| 1 | 前端 | `mousedown/touchstart` 在话筒上 → `recStart()` | 浏览器不支持录音 → 提示需 localhost/https |
| 2 | 浏览器 | `getUserMedia({audio})` 取麦克风 | 拒绝 → 「麦克风权限被拒绝…」 其它 → 「打不开麦克风…」 |
| 3 | 前端 | `MediaRecorder.start(100)` 每 100ms 落一片 | 初始化失败 → 人话提示 + 复位 |
| 4 | 前端 | 浮窗 `rec-pop` 现身（红点 + 计时 + **电平条**） | 电平失败不影响录音 |
| 5 | 用户 | 说话（可移出话筒 → 浮窗转红「松开取消」） | — |
| 6 | 前端 | `mouseup`（含**文档级兜底** 松手在话筒外也收得到）→ `recStop()` | — |
| 7 | 前端 | 判时长：<500ms → 「太短」；取消态 → 「已取消」 | **都不上传** |
| 8 | 浏览器 | `decodeAudioData` 解码 webm/opus → 混单声道 | 解码失败 → 人话提示（麦照样关） |
| 9 | 浏览器 | `OfflineAudioContext(1, N, 16000)` 重采样 → `_wavBlob()` 拼 WAV 头 | — |
| 10 | 后端 | `POST /api/asr`（token 校验 与 `/api/chat` 同一套）→ 转发给引擎 | 401 / 400（人话 detail 直接显示） |
| 11 | 引擎 | 若引擎不在 → **自动拉起**（首次 ~9s）→ 常驻推理**≈0.25-0.36s** | 引擎起不来 → 「语音引擎不可用」+ 日志路径 |
| 12 | 前端 | `recAppend(text)` **追加**到 draft 末尾 + 聚焦 + 光标到末尾；`_recReset()` 关麦/关上下文/清缓冲 | 空文本 → 「没听清，请再说一次」 |

**为什么是"两个进程"（本功能最反直觉、也最该检查的一点）**：

| 方案 | 结论 | 依据（都是实测） |
|---|---|---|
| 项目进程内直接 `import sherpa_onnx` | **否决** | 项目 venv 里 chromadb 依赖的 **onnxruntime 1.29** 与 `sherpa-onnx-core` **自带的 ORT 撞名** → 一 import 就**段错误**（整后端崩）；而 chromadb 是知识库在用的 动不得 |
| 每次调用起一个 CLI 进程 | **否决** | 模型**冷加载 8.5s**（`asr models` 只 import 只要 0.12s 差值全在加载）→ 长按一次等 9 秒 不可接受 |
| **独立引擎进程常驻（采用）** | ✓ | 引擎跑在**它自己的干净 venv**（与 `voice_test` 同形：本地模型能力 = 独立小项目）；加载一次 之后**0.25s**；**空闲 600s 自退** 不白占内存；自动拉起 用户无感 |

★ 另两条硬约束（用户 2026-10-04 拍板）：**音频不落盘**（全程内存 转完即弃）、**文字追加不替换**。

## 二、逐文件带读

### L0-1 `.env.example` 的语音小节（`:32`-`:39`）

- **它是什么**：六个开关**不写也能跑**（默认值就是生产值 这一节是给"要改的人"看的）。
- **逐行检查要点**：
 1. `ASR_ENABLED` 默认 `1`—— 关掉它则 `/api/asr` 返回 400 + 人话（`tools/voice_asr.py:42`） 前端话筒**照旧显示**（只是按了会提示 这是刻意的：不做灰度发现）；
 2. `ASR_MODEL_DIR` 默认 `D:/LLM/model`—— 本机统一模型目录（与 `EMBEDDING_MODEL_PATH` 同根 好检查）；
 3. `ASR_PORT` 默认 **8126** 别用 8123（那是后端自己的端口）。
- **思考题**：为什么这些开关**没有**做成"定制助手页里的配置项"？（提示：与 `ZX_STREAM` 同款——MVP 阶段用环境变量最省事；真要进 UI，落点应该是账号级设置 但那要连带做权限与迁移）

### L0-2 `front/index.html` 的样式与模板（`:1061`-`:1076` / `:2411`）

- **它是什么**：`.rec-pop`（浮窗）四种态：默认 / `.cancel`（红底）/ 计时 / 电平条；模板里 `v-if="recOn || recBusy"`——**识别中也保持浮窗**（显示「正在识别…」）。
- **逐行检查要点**：
 1. `.input-bar.wx { position: relative }`—— 浮窗靠它定位；去掉它浮窗会飞到页面左上；
 2. 浮窗 `pointer-events: none`—— 不然会挡住话筒自身的 `mouseleave`（移出取消就失灵）；
 3. `:disabled="recBusy"`—— 识别中不许再按（避免并发录两段）。
- **思考题**：为什么"识别中"还要占着浮窗？（提示：本地推理 0.25s 一闪而过 但**首次**可能等引擎拉起 9s 没有这个态用户会以为没反应）

- **它是什么**：把"一段音频字节"变成"文字"的**客户端**—— 外加**进程管家**（健康检查 / 拉起 / 预热）。**不 import api**（与 `tools/chat_images.py` 同层）。
- **关键行**：

| 行 | 符号 | 作用 |
|---|---|---|
| `:26`-`:31` | `LOG_PATH` / `DEFAULT_PORT=8126` / `DEFAULT_IDLE=600` / `HEALTH_WAIT_S=45` / `REQ_TIMEOUT_S=120` | 全部集中可调 |
| `:37` | `VoiceAsrError` | 给 API 层的人话错误 前端直接展示 |
| `:42`-`:64` | `_enabled` / `_port` / `_base` / `_bin` | 四项配置；`_bin` 依次试 **环境变量 → `~/.local/bin/asr[.exe]` → PATH** |
| `:68`-`:72` | `_client()` | **`trust_env=False`** 本机请求不走系统代理（项目通例） |
| `:75`-`:84` | `_health()` | `GET /health`（3s 超时）→ 引擎是否活着 |
| `:86`-`:115` | `_spawn()` | ★ 拉起引擎：`subprocess.Popen([asr, serve, ...])` + `CREATE_NO_WINDOW` + 输出进 `data/asr_serve.log` + 轮询 `/health` 最多 45s |
| `:117`-`:127` | `ensure_engine()` | 双检锁（并发下只拉一个） |
| `:129`-`:134` | `warmup()` | 启动预热（`api/server.py:523` 调） |

| `:145`-`167` | `transcribe(data)` | ★ 唯一的转写出口：置空/未启用 → 人话；`ensure_engine` → `POST /asr`（**裸字节** `application/octet-stream`）→ 400/500 都翻成人话 |

- **逐行检查要点**：
 1. ★ **本模块不得出现任何写音频的代码**—— `tests/unit/test_voice_asr.py::test_module_never_writes_audio` 用**源码级断言**钉住（允许的唯一落盘是引擎日志 追加写）；
 2. `_spawn` 的**幂等性**：`ensure_engine` 先 `_health()` 再进锁再 `_health()`—— 少了第二道就会在并发下起两个引擎；
 3. `HEALTH_WAIT_S=45` 与引擎"冷加载 ~9s"留了余量 改小会在慢机器上误报"启动超时"；
 4. 错误**永不静默**：每个失败分支都带人话 + 可操作线索（日志路径）。
- **思考题**：为什么这里**不做**"音频时长/格式校验"（提示：校验交给**引擎侧**做一次就够 两处都做会出现"两边规则不一致"的经典 bug 而引擎是本功能的事实源）

| `:146`-`:170` | `build_recognizer()` | ★ **识别器懒加载 + 缓存**（key = 模型目录+语言+线程）—— 常驻的关键 |

 1. `cmd_serve` 的 **`os._exit(0)`**（看门狗） 是刻意的：不给自己留"关不干净"的余地；
 2. `ThreadingHTTPServer` 但**推理串行**（单识别器实例）—— 并发长按不会并行推理（单用户场景够用 要并发得做实例池）；
 3. `samples_from_bytes` 的 16k 假设—— 与前端 `_recToWav16k` 是**一对**契约 改一边必改另一边（L4-7 有对应行号）；

- **思考题**：为什么 `serve` 不做成"复用主项目 venv 的 uvicorn 起一个子应用"（提示：那样又把 sherpa 拉回主项目的依赖图——**隔离是为了不打架** 见 §〇 选型表）

### L3-5 `api/server.py` 的两个路由 + 启动预热（`:1345` / `:1351` / `:523`）

- **它是什么**：把 `tools/voice_asr.py` 的能力暴露成两个 HTTP 端点 形状与 `chat_image_upload`（`:1329`）**逐行对得上**。
- **逐行检查要点**：
 1. `get_session(token)` 先做 → 无效 token 401（与 `/api/chat` 同一套 边界一致）；
 2. `await file.read()` 后**直接**交给 `transcribe`—— 中间**没有**任何 `open()`/临时文件（"不落盘"在装配层也要成立）；
 3. `except _va.VoiceAsrError` → **400 + 人话 detail**（前端直接展示 与贴图通道同款）；
 4. 预热在 `_startup` 里用**守护线程**（不阻塞启动 与天气预热并列）。
- **思考题**：为什么 `POST /api/asr` 收 **multipart 文件**，而客户端到引擎用的是**裸字节**（提示：前端发 multipart 最省事（`FormData` + `Blob`）；后端到引擎是本机进程间 裸字节最省开销——**两个边界两套格式，各有理由**）

- **逐行检查要点**：
 1. ★★ **`_recReset()` 与分片的顺序**—— `done()` 里必须**先 `_recChunks.slice()`** 再 `_recReset()`（后者会清空缓冲 ✗）。**这条是 harness 抓到的真 bug** ✓ 见 §四 4.0 ✓；
 2. `recCancel.value = false` 的下标位置—— 放在 `_recReset()` 里（浮窗与状态一起归零）；
 3. 关麦与关上下文都在 `_recReset()` 的 `try` 里—— 释放失败不该让状态机卡住；
 4. `_recToWav16k` 里 `tmp.close()` 用 `finally`—— 不关会攒 AudioContext（浏览器有上限 反复长按会失灵）。
- **思考题**：为什么不用 `AudioWorklet` 直接录 PCM（省掉解码+重采样两段）
（提示：手写编码这条路代码量与兼容性都更差 而 `decodeAudioData` + `OfflineAudioContext` 是**浏览器原生** 顺带把任意麦克风采样率都归一）

## 四、已知缺陷与未决清单

### 4.0 本次逐行核对**发现并已修**的三处（2026-10-04）

| # | 现象 | 根因 | 修法 |

| 1 | ★★ 上传的音频**恒为空** → 每次都是「没有录到声音」 | `done()` 里**先** `_recReset()`（它清空 `_recChunks`）**后**才 `new Blob(_recChunks…)` → 顺序反了 | 先 `const chunks = _recChunks.slice()` 再 reset（**harness 抓到的真 bug** 用户还没看见就修掉了） |

### 4.6 ★★ 环境事故复盘：`uv add` / `uv sync` 不可在这个项目上跑（2026-10-04）
