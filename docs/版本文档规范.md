# 版本文档规范（项目宪法·第二份）

> **为什么有这份文件**：往期版本反复栽在三件事上，它们都不是能力问题、而是**编排问题**：
>
> | 事故形态 | 具体长什么样 | 代价 |
> |---|---|---|
> | **文档编排与职责先后混乱** | 调研、方案、裁决、实现记录、带读混在同一份文档里；读者分不清「哪一句是当时在讨论」和「哪一句是定论」 | 实现期照着一句被否掉的试探结论去做，返工 |
> | **裁决记录未计或延迟** | 裁定散落在对话、各版本文档、甚至任务书正文里（「待拍板」「未决」「等你确认」到处是） | 同一件事被重复裁定、重复验证；事后说不清「当时为什么这么定」 |
> | **规划与实现脱节** | 规划文档没写清「这个议题来自哪份调研的哪个方案」 | 实现时无据可依，只能回头翻信息堆砌的调研文件 → 越翻越乱 |
>
> **本文件把这些定成规矩**：新增 / 整理任一版本文档前先读本文件。
> **与 [`文件存放规则.md`](文件存放规则.md) 的分工**：那份管「**文件放哪**」（目录职责、不入库清单），本份管「**同一版本内的文档怎么编排、谁先谁后、谁是权威**」。两者不重叠，冲突时各管各自那一段。

---

## 〇、三条硬规矩

1. **四类分家**：每个版本目录下的文档按 **规划文档 / `research` / `Verdict` / `Done`** 四类存放，**一份文档只承担一类职责**，不许一份文档里既有调研又有定论。
2. **决策字眼只有一处**（2026-10-14 批注扩写）：实现分叉的裁定**只写在 `Verdict/`** 里；**任何其他文档不得出现「待裁决 / 待拍板 / 未决」字样**。扩写口径：**凡是「选型 / 取舍 / 为何这么定」这类决策性表述，都只在 `Verdict/` 写**——规划文档只写**详细方案规划**（不记裁决结论、不记实现过程），实现记录只记**实现过程**。
3. **实现期只读两份**：`规划文档`的对应大点 + `Verdict/`。**调研文件不许在实现期通读**（见 §六）。

## 一、目录结构（以 v4.0 为例）

```text
docs/v4.0/
├── v4.0规划文档.md              # ★ 唯一权威：目录 + 每个大点四段式
├── research/                    # 调研期产物（信息堆砌，可天马行空）
│   └── 01-度量口径收口工程.md
├── Verdict/                     # 实现分叉的裁定记录（唯一裁决落点）
│   └── 01-度量口径收口工程.md
├── Done/                        # 实现后沉淀（每大点两篇）
│   ├── 01-度量口径收口工程·实现记录.md
│   └── 01-度量口径收口工程·逐文件带读.md
├── backups/                     # 改用户数据前的只读快照（不入库）
└── 交接文档.md                  # 版本冷启动入口（**例外**：不分进四类，见 §八）
```

- **编号 `<NN>`** = 该大点在规划文档里的序号（`01` / `02` / …）。**四类文件共用同一编号与同名** → 「规划里的一大点 ↔ 四个文件」一眼对上，不需要另建对照表。
- 四类目录**只在整数版本目录下建**（`docs/v4.0/`）；小数版本（`v2.5` 这类）不建，仍按「问题 → 方案 → 结果」单篇办。
- 版本目录本身仍按 [`文件存放规则.md`](文件存放规则.md)：**整数版 = 大改/调研/方案/计划，小数版 = bug 与小优化**。

## 二、`vn.0规划文档.md`（每个版本的唯一权威）

**内容 = 目录 + 每个「已经过讨论、敲定实现方案」的议题，一个新功能点（或一项工程改造）一大点。**
v4.0 的第一个大点就是「度量口径收口工程」——**工程类议题同样是大点**，不因为它不改产品行为就降格。

两条准入：
- **方案没敲定的不进规划文档**（它还在 `research/` 里躺着）；
- **网络 / 外部来源**（文档、接口说明、参考实现）要**指到出处**（URL 或项目内路径），别只写「据调研」。

### 每个大点的四段式（缺一段都不算完整）

| 段 | 写什么 | 判据（写好没有） |
|---|---|---|
| **① 应对什么问题** | 现象 + **证据** | 证据可复现：数字、日志、库/代码位置（`path:line`）。写不出证据的，说明它还在调研阶段 |
| **② 功能** | 做成什么样（用户视角） | 能一句话说清「做完之后，用户/系统多了什么」 |
| **③ 实现功能的技术方案** | 怎么落 + **来源标注** | 来源 = 「`research/NN-xxx.md` 的 §X」；有外部来源补 URL。要写到「换个会话照着能开工」的粒度 |
| **④ 实际实现的文档索引** | 指向 `Done/` 的两篇 | 未开工就写「未开始」；开工后填 `Done/NN-····实现记录.md` 与 `·逐文件带读.md` |

### 拷贝用骨架

```markdown
# v4.0 规划文档

> 目录
> - [01 度量口径收口工程](#01-度量口径收口工程)
> - [02 …](#02-…)
>
> 起点：调研文件在 `research/`；裁定在 `Verdict/`；实现记录与带读在 `Done/`。

---

## 01 度量口径收口工程

### ① 应对什么问题
<现象 + 证据：数字 / 路径 / 复现命令>

### ② 功能
<做完之后多了什么>

### ③ 实现功能的技术方案
<怎么落；来源：research/01-度量口径收口工程.md §三；外部来源：<URL>>

### ④ 实际实现的文档索引
- 实现记录：`Done/01-度量口径收口工程·实现记录.md`（未开始 / 已完成，实测 <N/N>）
- 逐文件带读：`Done/01-度量口径收口工程·逐文件带读.md`
```

> **为什么规划文档要详尽**：它是实现期**唯一**的入口文档。实现期不许回头翻 `research/` 找依据（§六），所以凡是实现时需要的（口径、来源、判据、边界、明确不做），都必须已经落在这一大点里。

### 「占位段」（已立项但方案未敲定）

允许为**已立项、但方案仍在调研**的大点在本文占一段（用户 2026-10-09 裁定）。格式要求：

- 段落标题下**立刻**写一行状态：`> 状态：方案未敲定（调研中，见 research/NN-xxx.md）`；
- **只写 ① 应对什么问题 与 ② 功能（意向）**；③ ④ 两段一律写「未开始」，**不得**编造方案或文档索引；
- 该大点**不得**进 `Done/`；方案敲定后，先把 ③ 段按 §二 补齐（含来源标注）再开工。

理由：占位段让「这一版还有哪些已立项的事」一眼可见，同时**不许**在规划文档里留悬空状态（「待裁决」类字样仍按 §四 禁止）。

## 二补、记录性质文档的角色表（2026-10-14 新增：D2 成文）

> 口径来源：用户 2026-10-14 批注（逐字见 `research/04` §3.1(a)）——「保持严格口径，决策相关字眼永远只在 Verdict 里面写；规划文件的实现过程不再记录裁决记录，只记录详细方案规划；实现记录只严格记录实现过程；README.md 其实不应该是作为索引表，而是留在整个版本做完以后，写用于面向用户式的（不从事开发的用户视角）新版本功能介绍。」

| 记录类型 | 角色（成文口径） | 不许写什么 |
|---|---|---|
| `Verdict/NN-*.md` | **决策类字眼的唯一出口**：所有「选型 / 取舍 / 为何这么定」 | —（它就是权威） |
| `vn.0规划文档.md` | **方案唯一权威**：只写**详细方案规划**（四段式③要写到换会话能开工） | 裁决结论、实现过程 |
| `Done/NN-*·实现记录.md` | **只记实现过程**：问题 → 做法 → 结果 + 可复跑数字 + 偏差/事故 | 决策口径 |
| `Done/NN-*·逐文件带读.md` | 逐行检查：文件清单 + 关键行号 + 链路位置 + 思考题 | 决策口径 |
| `docs/<版本>/README.md` | **整个版本做完之后**写的、**面向非开发用户**的「新版本功能介绍」 | 进度表 / 索引表 / 决策 |
| `交接文档.md` | 版本**冷启动入口**：当下状态 + 下一步 + 纪律与指向 | 进度真值（见下）、决策正文 |
| `research/NN-*.md` | 调研期信息（多方向、含废案）；实现期只许定点查（§六） | 定论口吻 |
| `docs/README.md` | **文档体系索引 + 全树导航**（职责不变） | — |
| `backups/` | 改用户数据前只读快照；**该大版本 git 提交完成后即删除** | — |

**进度 / 状态的唯一真值落点**（2026-10-14 批注）：**`v4.0规划文档.md` 的目录表**（一行摘要 + 指向 `Done/`）。README 与交接文档都**不再承载进度**，只留指向。

### 引用计数同步清单（D3：直治「同一条数被抄成三个数字」）

凡在文档里写了**条数 / 个数 / 计数**（"裁定 5 条"「修掉 6 个 bug」「共 32 项测试」），必须：

1. 只写在**该数的权威处**（裁定条数 → `Verdict/`；测试项数 → `Done/` 实现记录 + 可复跑命令）；他处一律**不重复数字**、改写成「见 `Verdict/NN-….md`」；
2. 若确需引用，**引用前重新数一遍**（`grep -c` 或跑一遍命令），不许凭记忆抄；
3. 收官巡检时列为检查项（`文件存放规则.md` §二末 巡检表）。

## 二补之二、大点的生命周期（五个阶段，2026-10-09 用户定）

每个大点都走同一条路，**阶段决定该写哪类文档**：

| 阶段 | 状态写法 | 产物 | 硬约束 |
|---|---|---|---|
| **1. 占位（待调研）** | 目录表「**待调研**」 | 规划文档**占位段**（只写 ①②）+ `research/NN-*.md`（可只建骨架） | ③④ 写「未开始」；不得进 `Done/` |
| **2. 调研** | 「调研中」 | **只在 `research/NN-*.md` 里写**（信息堆砌、多方向、含废案） | 不动代码、不改数据；取证只做只读探测 |
| **3. 定方案** | 「方案已定」 | 规划文档对应大点的 **③ 段补齐**（含来源标注）+ **`Verdict/NN-*.md` 里记下方案级裁定** | ③ 段不补齐 = 不许开工 |
| **4. 实现** | 「实现中」 | 代码/夹具/数据；**中途的实现分叉逐条落 `Verdict/NN-*.md`**（当场问、当场记） | 裁定不进任何其他文档 |
| **5. bug 修复** | 「修 bug 中」 | 先**脚本自测**（单测 / harness / 离线自检），再**实际客户端测试**（网页端真机点一遍）；发现的 bug 按需回阶段 4 改 | ★ **两步都不许跳**：只跑脚本 = 没验过 UI；只在客户端点 = 没回归。两者结果都记进阶段的记录 |
| **6. 记录** | 「已完成」 | **`Done/NN-*.md` 两篇**（实现记录 + 逐文件带读）+ 规划文档 ④ 段指向它们 | 实测数字要能复跑；偏差与事故如实写（含 bug 修复那一环的发现） |

- **阶段只前进不跳跃**：调研期写方案 = 越级（结论会带着没验证的假设）；实现期回头翻 `research/` 通读 = 污染（§六）。
- ★ **阶段推进由用户口令决定**（用户 2026-10-09 定）：「**只有我说到下一个阶段才能到下一个阶段**」。助手不得以「调研已充分」为由自行补 ③ 段或开工；调研期若发现下一步该做什么，写在 `research/` 里**建议**，等用户发话。
- **调研期的结论也要留档**：用户在调研期做出的选择（如「Q1 选 A」）**当场逐字记进 `research/NN-*.md`**（防「裁决未计」），到阶段 3 再转正为 `Verdict/NN-*.md` 的裁定。
- **状态写在哪**：`README.md` 进度表的「状态」列（一行摘要）+ 规划文档大点标题下的状态行；**裁定正文永远只在 `Verdict/`**。
- **回退**：实现中发现方案不成立 → 回阶段 3 改 ③ 段，并在 `Verdict/` 追加一条「推翻/修订第 n 条」及理由。

## 三、`research/`（调研期产物）

- **每个大点一个 md**，命名 `NN-<大点名>.md`（与规划文档的大点编号一致）。
- **可以天马行空**：信息堆砌、多方向畅意考察、试错记录、被否掉的路线、外部资料摘录，全都可以写进来——它不追求可读，追求**信息不丢**。
- **最终只有一个结果**写进规划文档对应大点的文段里（§二）。research 里可以有十个方向，规划文档里只有那一个。
- **读者是调研期与方案决定期的你**，不是实现期（§六）。

## 四、`Verdict/`（裁决的唯一落点）

**每个大点一个 md**：`Verdict/NN-<大点名>.md`，按时间**追加**条目；**旧条目不删、不改语义**（要改就在下面追加一条「修订 + 理由」）。

每条裁定至少写全六项：

| 项 | 内容 |
|---|---|
| 日期 | `YYYY-MM-DD` |
| 分叉点 | 一句话说清「在纠结什么」（含被否掉的那条路） |
| 可选方案 | A / B / C 各自代价 |
| **裁定结果** | 定了哪个 |
| **依据** | 实测数字、代码事实、或用户口径（他原话里的取舍原则） |
| 影响面 | 改了哪些文件、影响了哪些指标/行为 |

### 三条纪律

1. **当场问、当场记**：一旦判定为「实现分叉」就停下来问，拿到裁定立刻落 `Verdict/`，**不留「待裁决」**。
2. **别处置疑**：任何其他文档（含规划文档、实现记录、带读、任务书）**不得出现「待裁决 / 待拍板 / 未决」字样**；要引用裁定就写「见 `Verdict/NN-….md` 第 n 条」。
3. **同一条不重复裁定**：下次遇到同类分叉，先翻 `Verdict/` 引历史条目；确需推翻，就新追加一条并写明「推翻第 n 条」及理由。

> **为什么必须集中**：裁定散在多处 → ① 漏记（事后没人知道定过）；② 延迟（实现到一半才发现没人定）；③ 重复裁定（同一件事被问两遍，用户还得记着上次怎么定的）。集中到一处后，「这个版本一共拍了哪些板」翻一个目录就有答案。

## 五、`Done/`（实现记录 + 逐文件带读）

每个大点**两篇**，别揉成一篇：

| 文件 | 写什么 | 读者 |
|---|---|---|
| `NN-<大点名>·实现记录.md` | **问题 → 方案 → 结果**：改了什么、关键落点、踩坑、与方案的偏差（含偏差理由）、**实测数字（可复跑）**、待跑清单 | 想知道「改了什么、为什么」的人 |
| `NN-<大点名>·逐文件带读.md` | **逐文件带读**：文件清单 + **关键定义行号** + 在链路里的位置 + 逐行检查要点 + 思考题 | 想**逐行检查实现**的人 |

- 体例照既有范例：`docs/v3.1/工具路由设计-逐文件带读.md`（带读）、`docs/v3.1/` 下各篇问题-方案-结果（实现记录）。
- **文档里的实测数字要能对上测试输出**（写了「43/43」就要能复跑出 43/43）；写了数字却不给复跑命令 = 没写。
- 实现记录里**如实记偏差与事故**：方案说 A、实际做 B 的，写明为什么；踩过的坑写清「现象 / 证据 / 根因 / 验证」，别只写「已修复」。

## 六、阅读纪律（防上下文污染）

> 这一条是规范里**最容易被违反**的一条，单独立许。

- `research/` **只在调研期与方案决定期读**。
- **实现期不要通读 `research/`**：只在需要核对「这个方案的依据 / 数据来源」时**定点看一眼**（带着具体问题去查那一节）。
- 理由：research 是信息堆砌，里面混着**被否掉的路线**与试探性结论。通读会把它当现行方案，污染判断——比不读更危险。
- 实现期的权威只有两份：**规划文档的对应大点** + **`Verdict/`**。两者没写到的，才回去查 research，并顺手把缺的那条补进规划文档。

## 八、例外与存量口径

| 文件 / 目录 | 口径 |
