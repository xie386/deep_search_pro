## 三、踩坑记录（关键）

### Bug：mysql-connector 连接报 `RuntimeError: Failed raising error`
- **现象**：Agent 调用 DB 工具时连接失败，错误信息被 C 扩展吞掉，只显示 `Failed raising error`。
- **定位**：用最小化 `connect()` 参数仍报错；`mysql` 命令行客户端能正常连，说明 MySQL 服务本身没问题 → 是 **mysql-connector 的 C 扩展（CMySQLConnection）在本 Windows 环境损坏/被拦截**。
- **修复**：强制纯 Python 驱动 `use_pure=True`，实测可连并正常查询（读到 our_products 5 行）。
- **影响面**：所有 DB 工具函数（list_sql_tables/get_table_data/execute_sql_query）共用 `get_db_config()`，一处修复全局生效。

> 备注：若后续换环境 C 扩展恢复正常，可在 `.env` 设 `MYSQL_USE_PURE=False` 切回（性能更好）。

## 六、泛用性讨论与 C 折中方案落地（用户建议归档）

> 用户在 M1 评审中提出《改进建议：关于 M1 阶段数据库设计泛用性升级的方案》（原文附于本文件历史版本 / 讨论记录），核心论点：当前 `our_products`/`our_sales` 的 B 端硬编码字段（billing_unit、seats_sold、target_scale）无法适配 C 端实体商品（耳机/显卡/咖啡机），建议抽象化 + JSON 扩展列。
>
> 经讨论，采纳 **C 折中方案**：公司侧保持原表名与 B 端结构化字段不动（保护 M1 已验证成果、避免破坏 DB 子 Agent 的 SQL 习惯）；仅给 `competitors` 加一个轻量 `mapped_product_ids` JSON 列（记录竞品对标本司哪些产品，多对多映射）；重度的 attributes/dimensions 泛化设计**留到 M1.5 个人侧**（个人侧才需通吃各种消费品类，且个人库为独立 SQLite，不影响公司侧）。

### 6.1 实际改动（C 方案范围）
- `docs/sql/company_schema.sql`：`competitors` 新增 `mapped_product_ids JSON` 列；样例数据补全映射：
  - 飞书 → [1,2,4]（云协IM/文档/OA）
  - 钉钉 → [1,4]（云协IM/OA）
  - 企业微信 → [1]（云协IM）
  - Slack → [1]（云协IM）
  - Notion → [2]（云协文档）

### 6.2 验证（2026-08）
- 测试问题：「飞书主要对标我们公司的哪些产品？」
- ✅ Agent 正确读出 `competitors` 飞书 `mapped_product_ids=[1,2,4]`，关联 `our_products` 得云协IM/文档/OA，并反向识别「未对标」的云协会议、免费版。
- ✅ 来源标注 🗄️数据库(competitors + our_products) 正确。
- 结论：轻量扩展列被 Agent 真实利用，零返工、零破坏。

### 6.3 用户《改进建议》全文去向
