## 一 本地现状（只读取证，2026-10-30）

### 1.1 项目已有一条成熟的「图片进模型」通路

`tools/chat_images.py`（文件头注释写明职责边界：只做「用户图 → 校验 → 压缩 → 按账号落盘 → 返回 image_id」以及「把 image_id 还原成多模态 content blocks，**只喂本轮**、不进历史」）：

| 常量 | 值 | 口径 |
|---|---|---|
| `MAX_IMAGES` | 3 | 每次提问最多 3 张 |
| `MAX_UPLOAD_MB` | 12 | 单张上传体积上限（压缩前） |
| `MAX_EDGE` | 1568 | 长边上限（视觉模型常用上限） |
| `TARGET_KB` | 800 | 压缩目标体积 |
| `ID_RE` | `^[0-9a-f]{16}\.(jpg\|png\|webp)$` | image_id 的唯一合法形状（防目录穿越） |

其他已核实的口径：

- 格式判定**只看 magic bytes**（`sniff()`），不信任文件名/扩展名；
- 压缩时**有透明通道的 PNG 保留 PNG**（否则透明变黑），其余转 JPEG；
- **账号隔离靠路径由 `account_id` 决定**，绝不接受外部传入路径；
- `build_content()` 只给本轮用，历史里只存 `image_id` 引用。

### 1.2 接口侧的装配点

- `api/server.py:902-934`：本轮贴图装配（`image_ids` 解析、超过 `MAX_IMAGES` 拦在装配处）；
- `api/server.py:1814` 注释口径：单张一次，校验/压缩/账号隔离都在 `tools/chat_images.py`；
- `api/server.py:437` `_run_agent(...)` 签名里带 `image_ids` 与 `vision_capable` —— 说明「带图提问」本来就是一等公民，屏幕截图接进来不需要新概念。

### 1.3 用户图片来源与渲染

- 聊天里发出的图落在 `user_data/pic/{账号}/chat_images/*.png`（`docs/文件存放规则.md` §二）；
- 工具返回的图片有**既有渲染标记** `[[img:…]]`：`tools/capability_invoke.py` 的 `_save_tool_image()` 把图片字节/图片 URL 落进工作目录 `_tool_images/`，前端 `renderRich` 负责渲染（走 `/api/workdir/download` 鉴权通道）。→ 屏幕截图可以沿用同一个标记，前端不必新增分支。

### 1.4 模型侧的前置条件（已在文档里写死）

根 `README.md` 的配置说明里明确：`LLM_MODEL_MAX` **必须选支持视觉/多模态的模型**（进站抓取看截图取字段就靠它）。→ 屏幕共享复用的正是同一个能力，**不引入新模型要求**。

### 1.5 全仓没有任何屏幕捕获代码

装机依赖逐个查过：**未装** mss · dxcam · pyautogui · pywinauto · opencv-python；**已在** pywin32 312（可走 `PrintWindow` / `BitBlt`）、pillow 12.3.0（`ImageGrab` 属于它）、numpy 2.4.6。

### 1.6 既有先例：browser-use 走的是网页 DOM，不是像素

项目现有的「看」是 browser-use（网页），拿的是 DOM 与无障碍树；桌面像素捕获是**从零开始的一条新路**（本条用于说明为何本步不能照抄 07 资源嗅探的实现）。

## 二 意向形态

1. 球上多一个**「看屏幕」**开关，按下才截，不按不截；
2. 默认可选三种取景：**当前前台窗口**（先做）→ **用户框选**（其次）→ **整屏**（最后）；
3. 截图进入**现有图片链路**：校验、压缩到既有上限、按账号隔离落盘、只喂本轮、历史只留引用；
4. 球面板上能把截图作为本轮提问的附图（与文字一起发出）；
5. 不做后台定时截屏、不做录屏、不把截图送往外部服务（除模型本身）。

## 三 候选路线与代价

### 3.1 捕获方式

| 方式 | 原理 | 速度 | 能否拿到被遮挡的窗口 | 代价 / 坑 |
|---|---|---|---|---|
| `PIL.ImageGrab`（pillow 已在） | GDI `BitBlt` | 慢 | 否（截到的是屏幕上可见像素） | 零新依赖；多屏要显式 `all_screens=True`；高 DPI 需进程先声明感知 |
| `mss` | 仍是 GDI 语义，但实现更薄 | 快（30~60 FPS 量级） | 否 | 新增一个纯 Python 依赖；跨平台；多屏一次拿 |
| `PrintWindow`（pywin32 已在） | 让窗口自己把内容画到内存 DC | 中 | **能**（遮挡、无焦点也行） | 对 Chromium/GPU 合成窗口有**黑帧**风险，需回退方案；不需要抢焦点是它的最大优点 |
| Desktop Duplication（`dxcam` / `BetterCam`） | DXGI 桌面复制 | 最快（BetterCam 自述 240Hz+） | 否 | 依赖 GPU 与驱动；多适配器、独占全屏、部分受保护内容场景有坑；依赖体积最大 |

**外部印证**：`BetterCam` 自述用 Desktop Duplication API 做到 240Hz+（https://github.com/RootKit-Org/BetterCam）；参考实现 `windows-computer-use-mcp` 的取舍是「**PrintWindow 原地截、不抢焦点**」，并强调「能读文字就不截图（`ui_tree` / OCR 优先）」、截图**长边压到 1568**（https://github.com/sshh12/windows-computer-use-mcp/blob/main/CLAUDE.md）。

→ **1568 这个数字与本项目 `tools/chat_images.py` 的 `MAX_EDGE = 1568` 完全一致**，说明这条压缩口径是行业共识，本步直接复用既有链路即可，不需要另立标准。

### 3.2 取景与触发策略

| 策略 | 说明 | 代价 |
|---|---|---|
| 前台窗口截图 | 拿窗口句柄 → `PrintWindow`（必要时回退 GDI 裁剪） | 需要窗口枚举与 DPI 口径 |
| 用户框选区域 | 球上进入框选态，用户拉一个矩形 | 前端交互成本；跨屏框选要处理负坐标 |
| 整屏 | 一次拿全部显示器 | 隐私面最大，建议放最后 |

### 3.3 与现有链路的接法（两个候选，取舍留待定方案期）

- **候选甲**：截图 → 直接交给 `tools/chat_images.py` 的落盘/压缩（复用 `MAX_EDGE` / `TARGET_KB` / 账号隔离）→ 得到 `image_id` → 与本轮提问一起进 `_run_agent(image_ids=…)`；
- **候选乙**：截图先落当前工作目录 `_tool_images/`、以既有 `[[img:…]]` 标记回气泡（适合「截图只是为了给用户看」的场景），再按需转成 `image_id` 供下一轮提问。

差异：甲是「图进模型」，乙是「图给人看」；两条都走既有渲染与鉴权，不动前端大结构。

## 四 未知项与实测清单（必须真机跑）

1. **多屏与缩放**：150% / 200% 缩放下截图分辨率与后续点击坐标是否一致（需进程早期设 per-monitor DPI 感知；不一致会导致「看见的落点」与「点下去的落点」错开）。
2. **PrintWindow 对 QQ / 微信这类 GPU 合成窗口是否黑帧**：黑帧就得回退到「先置顶该窗口再 GDI 截」的路子。
3. **成本**：1568 长边的一屏图，进模型的 token 成本与时延（要实测一轮问答的整体耗时，避免「点一下等半分钟」）。
4. **预览通路**：球面板上截图预览走 `[[img:…]]` 还是 chat_images 的回显地址，需在实现期定一个并核对鉴权。
5. **是否需要多图**：一屏 + 用户框选局部（两张）是否比单张更有效，受 `MAX_IMAGES = 3` 约束。
