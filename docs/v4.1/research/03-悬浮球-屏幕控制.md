1. **确认制**：每一步动作先给预览、由用户确认后才执行；
2. **draft 模式**：消息类操作只把文字写进输入框，**发送由用户按**；
3. **窗口白名单**：只允许在用户勾选的窗口范围内动作；
   并明确不做：后台静默操作、锁屏下运行、批量加好友或群发陌生触达。

## 一 本地现状（只读取证，2026-10-30）

### 1.1 项目目前**没有任何**桌面输入能力

装机依赖逐个查过：**未装** pyautogui · pydirectinput · pywinauto · comtypes · uiautomation · keyboard · mouse · opencv-python；**已在** pywin32 312（`SendInput`、`SetCursorPos`、窗口枚举都能直接用）、pillow、numpy、pythonnet 3.2.0。

全仓搜过：`tools/` 与 `tools/_runtime/` 现有工具里没有桌面输入类；现有「动手」能力只有两处 —— 工作目录内置写工具、自配来源（CLI/API/MCP）的写能力。

### 1.2 项目已有一套**写能力授权**先例，可直接沿用语义

| 事实 | 落点 |
|---|---|
| 写工具集授权靠 ContextVar 传「本轮选中」 | `utils/write_auth.py`（`selected` / `set_selected()`） |
| 自配来源的写操作要在输入框用「/」显式选中 | 前端「/」三组索引（技能 / 写工具集 / workflow）+ `api/write_pool.py` 的授权说明书 |
| 内置写工具（工作目录 create/edit/delete）**纯文字可用**，不过运行期闸 | v4.0 `Verdict/06` 裁定 11 |

→ 屏幕控制属**破坏性外部动作**，性质与「写工具集」同源：可复用同一套「/」授权语义，而不必新造一套。

### 1.3 工具与执行器的既有分层（实现期落点）

| 层 | 目录 | 口径 |
|---|---|---|
| 挂载给 agent 的工具 | `tools/`（`@tool` 封装） | 与「用户自配工具」区分 |
| 执行器（面板与 agent 共用） | `tools/_runtime/` | 除 `api/`（面板层）与 `agent/` 外不许直接 import |
| 提示词里的工具文档串 | `prompt/prompts.yml` | 只写工具文档串与注入块 |
| 测试 | `tests/unit`（静态契约）· `tests/live`（真窗口） | 真窗口类先例：`tests/live/desktop_window_e2e.py` |

### 1.4 本步与「网页自动化」的差别（说明为什么不能照抄 browser-use）

现有 `browser-use` 走的是网页 DOM 与无障碍树，元素可寻址、可等待、可重试；桌面应用没有 DOM，只能靠**无障碍树（UIA）**或**像素**两条路，可靠性天然更差（详见 §三）。

## 二 意向形态

1. 球上多一个**「帮我操作」**能力，**默认关闭**，需用户显式授权（「/」选中屏幕控制工具集）；
2. 动作面限于基础鼠标键盘：单击 / 双击 / 右键 / 滚轮 / 拖选 / 打字 / 组合键 / 粘贴；
3. **每步先预览再确认**：先截一张图，把要点的落点框出来，用户点确认才执行；
4. **消息类走 draft**：打开应用 → 找到会话 → 文字写进输入框 → 用户自己按发送；
5. 只允许在用户勾选的窗口内动作（白名单）；
6. 动作全过程留审计（谁、何时、对哪个窗口、做了什么动作）。

## 三 候选路线与代价

### 3.1 输入注入方式

| 方式 | 说明 | 代价 / 坑 |
|---|---|---|
| `SendInput`（ctypes 或 pydirectinput） | 现代 Win32 输入注入，扫描码级 | 新增依赖可选（pywin32 已在，ctypes 也能直接调）；对 DirectX 游戏兼容性优于老 API |
| `pyautogui` | 老 API（`mouse_event` / `keybd_event`）封装 | **`typewrite` 不支持非 ASCII** → 中文必须走剪贴板 + `Ctrl+V`；坐标受 DPI 影响 |
| UIA `ValuePattern`（若控件可达） | 直接给控件设值，不经键盘 | 最稳，但只对能被 UIA 找到的控件有效 |

**中文输入是硬要求**（本项目全中文场景）：无论选哪种注入，中文都建议走「写剪贴板 → `Ctrl+V`」这条路；外部印证见 https://tools.yiteai.com/en/books/python-automation/ch14 （注明 `typewrite` 不支持 Unicode）。

### 3.2 元素定位（三层，可靠性从高到低）

| 层 | 做法 | 适用范围 | 代价 / 未知 |
|---|---|---|---|
| ① UIA 元素树 | `pywinauto` / `uiautomation` 读控件树，按名字/类型定位 | Win32 / MFC / WPF / Qt 可靠 | Chromium / Electron 内容树**默认不进 UIA**：Chromium 的 UIA provider 需开启特性开关（https://chromium.googlesource.com/chromium/src.git/+/refs/heads/main/docs/accessibility/browser/uiautomation.md），Electron 在检测到辅助技术时会自动开启（https://www.electronjs.org/docs/latest/tutorial/accessibility/）；有 issue 记录「Chromium/Electron 内容树对 UIA 不可见」（https://github.com/trycua/cua/issues/1616）→ **QQ NT / 微信 4.x 属这一类，能否读到控件树必须真机实测** |
| ② 截图 + 视觉定位 | 多模态模型直接给坐标；或先过 OmniParser 把截图解析成带坐标的元素清单再让模型选 | 通吃（含自绘界面） | 稳定性依赖模型；OmniParser v2 在 ScreenSpot-Pro 上 39.5%（https://github.com/microsoft/OmniParser）；另可参考原生 GUI agent 模型 UI-TARS（https://arxiv.org/html/2501.12326） |
| ③ 固定坐标 / 模板匹配 | 记录落点坐标或做图像匹配 | 短期能用 | 最脆：目标应用一改版就废，且不同分辨率/缩放下全部失效（不建议作为主路线） |

### 3.3 动作词表与安全机制（可借鉴的产品化先例）

- OpenAI 的 `computer_use` 工具词表是 `left_click` / `type` / `key` / `scroll` / `drag` 这一套 —— 参考实现明确建议「**与原生词表对齐**，让模型第一次就懂」（https://github.com/sshh12/windows-computer-use-mcp/blob/main/CLAUDE.md）；
- 同一份 API 里有 `pending_safety_checks` 概念（把危险动作挂起等确认，https://platform.openai.com/docs/guides/tools-computer-use）—— 与本步的「确认制」同构，说明这不是本项目自创的约束，而是这类能力的产品化通行做法。

### 3.4 参考实现（同类系统的工程取舍）

| 项目 | 可借鉴的点 |
|---|---|
| `sshh12/windows-computer-use-mcp` | PrintWindow 原地截（不抢焦点）· SendInput 注入 · **`capture_id` 防旧帧误点**（截图与点击必须同一帧，否则报错而不是静默点错）· 工具面收窄到 7 个 · 「能读文字就不截图」 |
| `EVSkyFall/Windows-Computer-Use-MCP` | 列窗口/应用 → 截图 → 读 UIA 树 → 发键鼠，工具面划分 |
| `CursorTouch/Windows-MCP` | 其 issue #86 记录「高 DPI 下坐标错位（物理像素 vs 逻辑像素）」，是本步最该提前设防的坑（https://github.com/CursorTouch/Windows-MCP/issues/86） |

### 3.5 边界（必须写进方案的事实）

**UI 自动化不改变平台层面的约束**：用鼠标键盘模拟用户操作，可以被平台视为「自动化脚本」（用户协议通常禁止），只是平台检测难度大。这一点不影响技术可行性，但**决定了本能力只应面向「用户自己看得见、自己确认过的动作」**，不应扩到批量、定时、无人值守的对外触达。这条口径在定方案期需要写清楚。

## 四 未知项与实测清单（必须真机跑）

1. **QQ NT / 微信 4.x 的 UIA 可读性**（决定走「元素路线」还是「纯视觉路线」，是本步最大的分流点）；
2. **DPI 与坐标口径**：截图坐标、模型给回的坐标、注入用的坐标三者必须同一坐标系（物理像素）；进程需在最早期设 per-monitor DPI 感知，否则出现 issue #86 那类错位；
3. **中文输入**在 QQ / 微信输入框的粘贴可行性（含输入法激活态下的行为）；
4. **确认制下的动作时延**：每步一次用户确认，多步任务的体感（是否会「点一下等一次确认」到不耐烦）；
5. **误动作的可挽回性**：误点造成的后果往往不可撤销（消息发错人）→ 预览是否需要给出「即将点的元素文本」而不只是一个高亮框；
6. **多步任务的中断与恢复**：用户中途不确认时，任务如何收尾（报错退出还是挂起）。

## 八 补充调研（2026-11-09）：聚焦「点击 + 打字」两个工具

> 用户 2026-11-09 定的本步范围：**只做两个工具** —— (1) 鼠标点击；(2) 文字输入。
> 其余动作（拖拽、滚动、组合键、右键等）留到后续 4.x 补齐。本节围绕这两件事收口取证。

### 8.1 注入层：pywin32/ctypes 直调 `SendInput`，零新依赖

本机实测（2026-11-09）：

- 未装 pyautogui / pydirectinput / pywinauto / uiautomation / pyperclip —— 也就是说，**走元素路线必须引依赖，走 SendInput 路线零依赖**；
- `user32.SendInput` / `SetCursorPos` / `GetAsyncKeyState` 全部可用；
- `ctypes` 构造 `INPUT` 结构（含 `MOUSEINPUT` / `KEYBDINPUT` 联合体）实测可构造，`sizeof(INPUT)=40`；
- 本机 200% 缩放（DPI 192）已确认：进程已声明 system-aware，`SetCursorPos` 与 `SendInput` 的 `MOUSEEVENTF_ABSOLUTE` 用**物理像素**，与 02 截图返回的 `screen_rect`（物理像素）同一坐标系。

结论候选（待定方案期拍板）：鼠标点击用 `SendInput`（`MOUSEEVENTF_ABSOLUTE | MOVE | LEFTDOWN/UP`）；打字用「剪贴板 + Ctrl+V」承担中文、`SendInput` 的 `KEYBDINPUT` 承担 ASCII。不引 pyautogui/pydirectinput。

### 8.2 词表：与 OpenAI computer use 的动作集对齐

`openai-python` 的 `response_computer_tool_call.py` 里动作共 10 类（本轮取证）：

```
click(button: left/right/wheel/back/forward) · double_click · drag(path)
keypress(keys) · move(x, y) · screenshot · scroll(scroll_x, scroll_y)
type(text) · wait
```

本步「点击 + 打字」对应其中两类：

| 本步工具 | 对齐的动作 | 注入实现 |
|---|---|---|
| 鼠标点击 | `click`（本步只做 left）+ `double_click`（常用，成本为零，顺手带上） | `SetCursorPos` + `SendInput(MOUSEEVENTF_LEFTDOWN/UP)` ×2 |
| 文字输入 | `type(text)` | 中文/任意 Unicode：剪贴板写入 + `SendInput(Ctrl+V)`；纯 ASCII 可选逐键 `KEYBDINPUT` |

`wait`（动作间的短暂等待）建议作为**内部机制**而非工具：每步注入后固定小睡 + 可配置，避免「点完立刻截屏读到旧帧」。

### 8.3 坐标契约：三处坐标、一次换算

02 已经把口径立好（`tools/screen_tool.py`）：每帧返回 `capture_id`、`screen_rect`（物理像素）、`scale`（模型看到的图 ÷ 物理像素）。03 的点击换算规则：

```
模型给的 (x, y) 是「图上的像素」
→ 物理坐标 = 图上坐标 ÷ scale + screen_rect 左上角
→ SendInput 用物理坐标
```

**校验点**：工具入参必须带 `capture_id`；与 `cu_mode.current().last_cid` 不一致时直接拒绝（「屏幕已变化，请重新截图」），杜绝「看旧帧点新界面」（windows-computer-use-mcp 的 capture_id 防旧帧做法，本仓 02 已有同构的帧号机制）。

多显示器：`screen_rect` 的原点可能是负数（左侧屏）。`MOUSEEVENTF_ABSOLUTE` 的坐标要按目标显示器的原点与宽高归一化到 0~65535；单屏时原点为 0，退化为线性映射。本机单屏，此分支实现后只能静态审查，真机留待双屏环境。

### 8.4 中文输入的现实约束

- `pyautogui.typewrite` 不支持非 ASCII（外部印证 + 常识：键盘扫描码没有汉字）→ **中文一律走剪贴板**；
- 剪贴板写入需要 Windows API（`OpenClipboard` / `SetClipboardData`）或引 `pyperclip`（纯 Python、依赖小）——零依赖做法是用 ctypes 直调 user32 的剪贴板 API（约 30 行），实现期二选一；
- 粘贴依赖目标窗口的输入框支持 Ctrl+V —— 主流聊天/编辑框都支持；浏览器地址栏、部分游戏内嵌框不支持（要在文档串里写明）；
- **输入法激活态**：Ctrl+V 直接粘贴不经 IME，不受输入法影响；这是选这条路的核心原因（逐键注入中文会和 IME 打架）。

### 8.5 computer use 模式下的工作流程（03 扩展 02 的流程）

02 的开关语义是「本轮 agent 可看屏」；03 在其上叠加「本轮 agent 可动手」。两档开关、两个授权层级：

| 档 | 开关 | 能力 | 闸门 |
|---|---|---|---|
| 只看 | computer use（02 已实现） | `screen_capture` | 开关 + 轮内状态 |
| 看 + 动 | **本步新增**（如 `allow_control=1` 请求参数） | `screen_capture` + `mouse_click` + `type_text` | 前者全部 + 控制闸 |

控制闸建议比 02 的开关**更严**，候选（定方案期拍板）：

- 每轮动作上限（类似 `SCREEN_MAX_SHOTS_PER_TURN` 的 `CU_MAX_ACTIONS_PER_TURN`，防失控循环）；
- 动作前强制「重新截图」（不能用上一帧的坐标直接点，屏幕必须刚刚看过）；
- 白名单窗口（调研稿 §二已列；实现期决定是「请求参数带窗口标题」还是「设置页勾选」）；
- 破坏性动作（右键菜单里的删除/发送类）由模型在 `reason` 里自述风险，前端展示给用户——不做自动判定。

**工作流**（一轮之内）：

```
用户开「看 + 动」 → /api/chat?computer_use=1&allow_control=1
   → cu_mode.begin_turn(on=True, control=True)
   → 模型循环：screen_capture（拿 capture_id/坐标口径）
        → mouse_click(x, y, capture_id) 或 type_text(text, capture_id)
             → 闸门：control? / 次数? / capture_id 一致?
             → SendInput 注入 → 等待 → 返回「做了什么 + 之后的前台窗口标题」
        → 需要看结果再截（回到 screen_capture）
   → 轮末 end_turn（与 02 相同：状态全清、审计落 data/audit/）
```

**每步要不要用户确认**：调研稿 §二写的是「每步先预览再确认」，但这与「agent 自主多步」矛盾（点一下等一次确认，多步任务没法用）。参考 OpenAI 的 `pending_safety_checks`：**普通动作（点击空白处、输入文字到已获焦的框）自动执行；动作后的回执里写明做了什么**，用户看到不对可以立刻打断（`/api/chat/cancel` 已有）。真正的「确认制」收窄到：每轮开始前用户开了 allow_control、以及文档串要求模型对不可逆动作先复述再动手。取舍待定方案期拍板。

### 8.6 审计

每次注入写一行 JSONL：时间、thread_id、capture_id、动作、坐标/文本长度、注入后前台窗口标题。落 `data/audit/cu_actions.jsonl`（`data/audit/` 已有先例）。审计是**只追加**的，与「纯内存不留截图」不冲突（审计记的是动作元数据，不含屏幕内容）。

### 8.7 测试策略（真机可自动化）

- 单测：坐标换算（scale/screen_rect/多屏原点）、闸门（未开 control 拒绝、超次数拒绝、capture_id 不匹配拒绝）、词表映射（click/type 的参数校验）；
- 真机（`tests/live/`）：开一个记事本，让 agent「在记事本里输入 hello」→ 读记事本内容断言；点一个已知坐标的按钮 → 断言状态变化。不涉及聊天软件（避免误发消息）。

## 九 收官补记（2026-11-10）：小图标点不准的取证与行业做法

真机三轮里，注入本身没有偏（`SetCursorPos` 是物理像素级），偏的是**模型从缩略图里估出来的坐标**：
屏幕 2880×1620 压到 1456×819（scale 0.506）后，24 px 的图标在图里只有 12 px，而模型报点误差
常见 ±10~20 图像像素（折回屏幕 ±20~40 px），远大于图标半径。

外部取证（本轮检索，均只作口径参考）：

| 来源 | 可用的结论 |
|---|---|
| Anthropic《Best practices for computer and browser use》 | 点击精度是整条链路的地基；**坐标空间必须与模型真正看到的图一致**——图超限会被服务端二次降采样，模型是在降级图上点，harness 却按原图换算。建议先预缩放到限内（老模型长边 1568 / 总像素 1.15 MP，新模型 2576 / 3.75 MP），起点可用 1280×720 |
| GUI-Lens（arXiv 2608.03270，粗到细裁剪） | 用一个通用 VLM 先看全局、再**选区放大**逐级收敛，把局部坐标映射回屏幕；报告 grounding 精度最高提升 24.9 个百分点 |
| Agent-S issue #177 | 小元素坐标靠**多候选采样 + 投票**收敛，单点预测抖动大 |
| cua PR #936 | 接地模型给的坐标没有按设备分辨率换算回去 → 点击整体偏移（与我们 DPI 那次同型） |

据此定的本版口径（已实现）：

- **「小」= 截图上外接框长边 < 40 图像像素**（设置项 `SCREEN_SMALL_TARGET_PX`，范围 8~200）；
  取 40 是「模型误差 ±10~20 取两倍余量」，折合 0.5 缩放时约 80 物理像素；
- 小目标走 `screen_capture(region=[x, y, w, h])`：坐标仍按**当前帧图上像素**给，工具换算成物理像素，
  外壳裁剪后**按原生分辨率返回**（长边 <300 放大 3 倍、<900 放大 2 倍），不按长边压缩；
- 放大帧**不占**本轮截图额度，单独计数并封顶（2 × 截图额度，12~60）；
- 大按钮 / 整行卡片 / 输入框 / 菜单项不用放大，直接点（避免每步多花一次取图）。

暂未采用（留作后续评估）：多候选投票、截图上的坐标网格叠加、UIA/无障碍树取元素框。
