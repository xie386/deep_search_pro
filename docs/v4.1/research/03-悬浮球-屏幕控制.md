## 〇 身世（用户口径逐字）

> 「创建v4.1子文件,按照悬浮球外壳(对话入口)->悬浮球(屏幕共享)->悬浮球(屏幕控制)三大实现步骤做实现方案调研」（2026-10-30）

上游对话（2026-10-30，逐字，节选）：

> 「…并可以开启"共享电脑屏幕",Agent有"点击","打字","光标选中"等基础鼠标/键盘操作,这样理论上通过类似"打开QQ,给xx发消息'xxx'"的命令擦边实现账号操作,或者说上升为模拟window用户操作电脑」

上一轮对话中助手给出的三条约束（用户未反驳，本轮调研按此展开为设计约束）：

1. **确认制**：每一步动作先给预览、由用户确认后才执行；
2. **draft 模式**：消息类操作只把文字写进输入框，**发送由用户按**；
3. **窗口白名单**：只允许在用户勾选的窗口范围内动作；
   并明确不做：后台静默操作、锁屏下运行、批量加好友或群发陌生触达。

## 一 本地现状（只读取证，2026-10-30）

### 1.1 项目目前**没有任何**桌面输入能力

装机依赖逐个查过：**未装** pyautogui · pydirectinput · pywinauto · comtypes · uiautomation · keyboard · mouse · opencv-python；**已在** pywin32 312（`SendInput`、`SetCursorPos`、窗口枚举都能直接用）、pillow、numpy、pythonnet 3.2.0。

全仓搜过：`tools/` 与 `tools/_runtime/` 现有工具里没有桌面输入类；现有「动手」能力只有两处 —— 工作目录内置写工具、自配来源（CLI/API/MCP）的写能力。

### 1.2 项目已有一套**写能力授权**先例，可直接沿用语义

| 事实 | 落点 |
|---|---|
| 写工具集授权靠 ContextVar 传「本轮选中」 | `utils/write_auth.py`（`selected` / `set_selected()`） |
| 自配来源的写操作要在输入框用「/」显式选中 | 前端「/」三组索引（技能 / 写工具集 / workflow）+ `api/write_pool.py` 的授权说明书 |
| 内置写工具（工作目录 create/edit/delete）**纯文字可用**，不过运行期闸 | v4.0 `Verdict/06` 裁定 11 |

→ 屏幕控制属**破坏性外部动作**，性质与「写工具集」同源：可复用同一套「/」授权语义，而不必新造一套。

### 1.3 工具与执行器的既有分层（实现期落点）

| 层 | 目录 | 口径 |
|---|---|---|
| 挂载给 agent 的工具 | `tools/`（`@tool` 封装） | 与「用户自配工具」区分 |
| 执行器（面板与 agent 共用） | `tools/_runtime/` | 除 `api/`（面板层）与 `agent/` 外不许直接 import |
| 提示词里的工具文档串 | `prompt/prompts.yml` | 只写工具文档串与注入块 |
| 测试 | `tests/unit`（静态契约）· `tests/live`（真窗口） | 真窗口类先例：`tests/live/desktop_window_e2e.py` |

### 1.4 本步与「网页自动化」的差别（说明为什么不能照抄 browser-use）

现有 `browser-use` 走的是网页 DOM 与无障碍树，元素可寻址、可等待、可重试；桌面应用没有 DOM，只能靠**无障碍树（UIA）**或**像素**两条路，可靠性天然更差（详见 §三）。

## 二 意向形态

1. 球上多一个**「帮我操作」**能力，**默认关闭**，需用户显式授权（「/」选中屏幕控制工具集）；
2. 动作面限于基础鼠标键盘：单击 / 双击 / 右键 / 滚轮 / 拖选 / 打字 / 组合键 / 粘贴；
3. **每步先预览再确认**：先截一张图，把要点的落点框出来，用户点确认才执行；
4. **消息类走 draft**：打开应用 → 找到会话 → 文字写进输入框 → 用户自己按发送；
5. 只允许在用户勾选的窗口内动作（白名单）；
6. 动作全过程留审计（谁、何时、对哪个窗口、做了什么动作）。

## 三 候选路线与代价

### 3.1 输入注入方式

| 方式 | 说明 | 代价 / 坑 |
|---|---|---|
| `SendInput`（ctypes 或 pydirectinput） | 现代 Win32 输入注入，扫描码级 | 新增依赖可选（pywin32 已在，ctypes 也能直接调）；对 DirectX 游戏兼容性优于老 API |
| `pyautogui` | 老 API（`mouse_event` / `keybd_event`）封装 | **`typewrite` 不支持非 ASCII** → 中文必须走剪贴板 + `Ctrl+V`；坐标受 DPI 影响 |
| UIA `ValuePattern`（若控件可达） | 直接给控件设值，不经键盘 | 最稳，但只对能被 UIA 找到的控件有效 |

**中文输入是硬要求**（本项目全中文场景）：无论选哪种注入，中文都建议走「写剪贴板 → `Ctrl+V`」这条路；外部印证见 https://tools.yiteai.com/en/books/python-automation/ch14 （注明 `typewrite` 不支持 Unicode）。

### 3.2 元素定位（三层，可靠性从高到低）

| 层 | 做法 | 适用范围 | 代价 / 未知 |
|---|---|---|---|
| ① UIA 元素树 | `pywinauto` / `uiautomation` 读控件树，按名字/类型定位 | Win32 / MFC / WPF / Qt 可靠 | Chromium / Electron 内容树**默认不进 UIA**：Chromium 的 UIA provider 需开启特性开关（https://chromium.googlesource.com/chromium/src.git/+/refs/heads/main/docs/accessibility/browser/uiautomation.md），Electron 在检测到辅助技术时会自动开启（https://www.electronjs.org/docs/latest/tutorial/accessibility/）；有 issue 记录「Chromium/Electron 内容树对 UIA 不可见」（https://github.com/trycua/cua/issues/1616）→ **QQ NT / 微信 4.x 属这一类，能否读到控件树必须真机实测** |
| ② 截图 + 视觉定位 | 多模态模型直接给坐标；或先过 OmniParser 把截图解析成带坐标的元素清单再让模型选 | 通吃（含自绘界面） | 稳定性依赖模型；OmniParser v2 在 ScreenSpot-Pro 上 39.5%（https://github.com/microsoft/OmniParser）；另可参考原生 GUI agent 模型 UI-TARS（https://arxiv.org/html/2501.12326） |
| ③ 固定坐标 / 模板匹配 | 记录落点坐标或做图像匹配 | 短期能用 | 最脆：目标应用一改版就废，且不同分辨率/缩放下全部失效（不建议作为主路线） |

### 3.3 动作词表与安全机制（可借鉴的产品化先例）

- OpenAI 的 `computer_use` 工具词表是 `left_click` / `type` / `key` / `scroll` / `drag` 这一套 —— 参考实现明确建议「**与原生词表对齐**，让模型第一次就懂」（https://github.com/sshh12/windows-computer-use-mcp/blob/main/CLAUDE.md）；
- 同一份 API 里有 `pending_safety_checks` 概念（把危险动作挂起等确认，https://platform.openai.com/docs/guides/tools-computer-use）—— 与本步的「确认制」同构，说明这不是本项目自创的约束，而是这类能力的产品化通行做法。

### 3.4 参考实现（同类系统的工程取舍）

| 项目 | 可借鉴的点 |
|---|---|
| `sshh12/windows-computer-use-mcp` | PrintWindow 原地截（不抢焦点）· SendInput 注入 · **`capture_id` 防旧帧误点**（截图与点击必须同一帧，否则报错而不是静默点错）· 工具面收窄到 7 个 · 「能读文字就不截图」 |
| `EVSkyFall/Windows-Computer-Use-MCP` | 列窗口/应用 → 截图 → 读 UIA 树 → 发键鼠，工具面划分 |
| `CursorTouch/Windows-MCP` | 其 issue #86 记录「高 DPI 下坐标错位（物理像素 vs 逻辑像素）」，是本步最该提前设防的坑（https://github.com/CursorTouch/Windows-MCP/issues/86） |

### 3.5 边界（必须写进方案的事实）

**UI 自动化不改变平台层面的约束**：用鼠标键盘模拟用户操作，可以被平台视为「自动化脚本」（用户协议通常禁止），只是平台检测难度大。这一点不影响技术可行性，但**决定了本能力只应面向「用户自己看得见、自己确认过的动作」**，不应扩到批量、定时、无人值守的对外触达。这条口径在定方案期需要写清楚。

## 四 未知项与实测清单（必须真机跑）

1. **QQ NT / 微信 4.x 的 UIA 可读性**（决定走「元素路线」还是「纯视觉路线」，是本步最大的分流点）；
2. **DPI 与坐标口径**：截图坐标、模型给回的坐标、注入用的坐标三者必须同一坐标系（物理像素）；进程需在最早期设 per-monitor DPI 感知，否则出现 issue #86 那类错位；
3. **中文输入**在 QQ / 微信输入框的粘贴可行性（含输入法激活态下的行为）；
4. **确认制下的动作时延**：每步一次用户确认，多步任务的体感（是否会「点一下等一次确认」到不耐烦）；
5. **误动作的可挽回性**：误点造成的后果往往不可撤销（消息发错人）→ 预览是否需要给出「即将点的元素文本」而不只是一个高亮框；
6. **多步任务的中断与恢复**：用户中途不确认时，任务如何收尾（报错退出还是挂起）。
