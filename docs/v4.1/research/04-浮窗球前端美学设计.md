# 04 浮窗球前端美学设计 · 调研

> 性质：调研期产物（只取证、只列候选，不做裁决）。裁定在 `Verdict/04`；方案在规划文档 04 的 ③ 段。
> 取证日期：2026-11-10。检索 7 次（规范/启动器/面板尺寸/动效/无障碍/徽标/减弱动效）。
> 边界：本轮只读——读代码、量数值、静态渲染截图，未改任何项目文件。

## 一、这次要解决的不是「加装饰」

悬浮球与它的迷你面板在 01~03 里被三个功能需求推着长出来：球要能显示、能拖动、能贴 PNG；面板要能聊天、能切会话、能开两个能力开关。**没有一个环节是为「好看」做决策的**。所以现状的问题不是「缺一点美化」，而是四件事没有统一：

1. 球与面板是**两套视觉语言**（橙 vs 绿、拟物渐变 vs 扁平纸面）；
2. 面板与主窗是**两套设计 token**（面板自写一套 `--ink/--bg/--accent`，主窗另一套 `--form-base` 等）；
3. **状态没有视觉语言**（思考中/看屏中/等待确认/出错，只有文案和托盘标题）；
4. 尺寸与信息密度没有推导过（380×560 里塞了 6 个头部按钮）。

## 二、现状取证（数值与画面）

### 2.1 球（`front/desktop/ball_window.py` + `assets/ball_*.png`）

| 项 | 现状 |
|---|---|
| 尺寸 | 逻辑 32~96，默认 **64**（设置项 `BALL_SIZE`） |
| 不透明度 | 40~100%，默认 100（`BALL_OPACITY`） |
| 形态 | 128×128 PNG → 按目标尺寸 LANCZOS 缩放，`UpdateLayeredWindow` 贴图 |
| 状态 | 三张图：`idle` / `busy`（外圈白色弧）/ `alert`（右上红点） |
| 命中区 | `WM_NCHITTEST`：圆内 `HTCLIENT`、圆外 `HTTRANSPARENT`，拖动阈值 8 物理像素 |

画面观察（三态拼图 `tests/test_out/_ball_states.png`）：

- 三态是**同一颗橙色渐变球**加小配件：忙碌态加一圈约 1/4 的白弧，提醒态加一个红点；
- 白弧在浅色桌面上对比不足（白 + 白），远看只剩"球脏了一点"；
- 红点直径约是球的 1/10（64 逻辑像素下约 6 px），且红与橙同色系，色差不足；
- 球本身是**纯装饰性球体**，没有品牌符号、没有可点击的提示（悬停无变化、无光标变化）；
- 与项目主色（`--accent: #54aa69` 松绿）不同色系——球是橙，面板是绿，主窗是浅绿纸面。

### 2.2 面板（`front/desktop/ball.html`）

| 项 | 现状 |
|---|---|
| 尺寸 | 逻辑 380×560（物理 760×1120，倍率 2.0） |
| 头部 | 深色条 `#161d18`，40 px 高：握把 + 会话下拉 + ＋ ✎ 🗑 🖥 🖱 ×（**6 个 26 px 图标**） |
| 正文 | 浅绿底 `#f5f8f3`，气泡最大宽 86%，圆角 12 px，字号 13.5 px / 行高 1.55 |
| 输入区 | 白底输入框（圆角 10）+ 绿色发送键（圆角 10） |
| 空状态 | 一行灰字「请先登录桌面版，再用悬浮球对话」 |

画面观察（静态渲染 `tests/test_out/_panel_mock.png`，380×560）：

1. **硬切口**：深色头部与浅色正文之间没有过渡，读起来像「两个产品上下拼在一起」；主窗的纸面风是浅底 + 细描边 + 柔阴影，这里却是重色块。
2. **头部过载**：会话标题被压成「销售明细·整理…」；6 个 26 px 图标的视觉重量超过标题本身，而且 ＋ ✎ 🗑 是 emoji 字形，与 🖥 🖱 的线性图标不同族。
3. **空状态是洞**：没有数据时中间约 400 px 全是底色，既没有引导也没有"我在这里等你"的暗示。
4. **状态只剩一行灰字**：`本轮已用 3/20 次动作` 和错误提示都挤在消息流里，与真消息同级，读起来像系统日志。
5. **气泡与输入区不在一个层级**：气泡圆角 12、输入 10、发送 10，头部下拉 7——同一屏里出现了四种圆角尺度。
6. **像缩小版主窗的地方**：顶部一条工具条 + 下面一片消息流 + 底部输入框，这正是主窗的结构；而它只有 380 宽，功能却要少得多（没有侧栏、没有多视图、没有导出）。

## 三、外部规范与可借鉴的口径

| 来源 | 可用结论 |
|---|---|
| WinUI 3《Timing and easing》 | 标准时长：`ControlNormalAnimationDuration` **250 ms**、`Fast` **167 ms**、`Faster` **83 ms**；Fluent 缓动基线 `cubic-bezier(0,0,0,1)` 与 `cubic-bezier(1,0,1,1)` |
| Material 3《Easing and duration》 | 时长 token：short 50/100/150/200 ms，medium 250~400 ms；缓动 `emphasized.decelerate = cubic-bezier(0.05,0.7,0.1,1)`、`standard = cubic-bezier(0.2,0,0,1)` |
| 聊天组件形态（designpixil 等） | 桌面端窗口宽 **360~420 px**；启动器应「找得到但不显眼」，**脉冲、弹跳、自动展开会被当成广告**；首屏要在一眼之内说清「这个助手能干什么」 |
| WCAG 2.2 | 目标尺寸最小 **24×24 CSS px**；非文本 UI 组件与其状态需 **3:1** 对比；动效需支持 `prefers-reduced-motion` |
| Material Badges / MUI Badge | 徽标用于「补充状态」，计数徽标与纯点徽标是两种语义；点徽标必须在底色上有足够对比，不能靠色相区分 |

对照现状：

- 头部 26 px 图标刚好过 24 px 底线，但**间距只有 6 px**，误触概率高；
- 白弧与浅色桌面、红点与橙球，都达不到 3:1；
- 三态只有形状微差，没有引入"语义色 + 语义形态"的组合。

## 四、几个必须先想清楚的技术约束

这几条会直接否决某些"好看但做不到"的方向，先摆出来：

1. **球不能实时模糊背景**。分层窗口（`UpdateLayeredWindow`）只能贴一张位图，拿不到背后的桌面内容——所谓「毛玻璃球」只能做**伪玻璃**（半透明 + 噪点 + 高光），真模糊做不到。
2. **球与面板是两个窗口、两套渲染**（Win32 分层窗 vs WebView2）。**连续变形动画做不到**（球不能"长"成面板）；只能做**接力**：球在落点缩到 0.2 并淡出，同时面板从同一锚点以 0.85 缩放淡入。
3. **面板的圆角要靠 DWM**。无边框 pywebview 窗口本身是直角，Windows 11 可用 `DwmSetWindowAttribute(DWMWA_WINDOW_CORNER_PREFERENCE)` 拿系统圆角；想自定义半径（比如 14 px）只能自绘或接受系统值。
4. **动效帧率受分层窗口贴图限制**。球的状态动画目前是换 PNG，做逐帧动画要么预生成序列图（内存与体积代价），要么改成 Direct2D 自绘（工程量陡增）。
5. **380 宽的硬约束**：面板宽 380 是 01 定的，改宽会挤压桌面可用区域；所有信息设计必须在 380 内成立。

## 五、候选方向（三选一，或组合）

### 方向 A：「纸面贴片」——把球和面板拉回主窗的语言

- 球：与主窗同色系的松绿圆片（`--accent` 到 `--accent2` 的极浅渐变），细白描边 + 柔阴影，中间一个极简符号（例如一枚"目"或对话折角）；三态用**同一形状 + 语义色环**（忙碌：环旋转；提醒：右上角实心圆点用 `--warn`，加白描边保证 3:1）。
- 面板：头部改为**浅色纸面条**（白 + 1 px 松绿细线 + 会话标题为主），图标从 6 个减到 4 个（新建、会话、屏幕两档收进"⋯"），字号与主窗统一（13/12/11 三级）。
- 动效：面板从球锚点 0.9→1 缩放 + 透明度 0→1，**167 ms**，`cubic-bezier(0,0,0,1)`；球悬停亮度 +4%，按下 0.97。
- 代价：低（不引依赖、不动结构），主要工作是把 `ball.html` 的 CSS 变量换成主窗 token、重画三张 PNG。
- 风险：仍是"一个球 + 一个面板"，形态上没有新意，但**一致性最强**。

### 方向 B：「玻璃浮层」——球与面板都做半透明浮层

- 球：伪玻璃（半透明白/淡绿 + 噪点纹理 + 顶部高光），状态用**光晕**表达（忙碌时环形光晕旋转、提醒时外圈脉冲一次）。
- 面板：`backdrop-filter: blur()` 在 WebView2 里可用（**注意**：WebView2 的透明窗需要额外设置，且模糊的是窗口内部背景，不是桌面），配合 1 px 高光边。
- 代价：中。需要验证 WebView2 透明 + 无边框的渲染（02 期间已知 `background_color` 与 DWM 圆角有冲突）；球侧只能伪玻璃；噪点纹理要预生成。
- 风险：玻璃在浅色桌面上容易"糊成一片"，可读性下降，且与主窗的纸面风相冲。

### 方向 C：「一体化形态」——球展开即为面板

- 球缩小为一个"胶囊柄"贴在面板顶部，展开时胶囊柄留在原地、面板从它下方生长；收起时反向。
- 代价：高。需要面板窗口按动画尺寸逐帧 `resize`（pywebview 每次 resize 会触发重排，容易掉帧），且球与面板的坐标接力要非常准。
- 风险：收益（"变形"的惊艳感）与工程量不成比例；一旦掉帧，观感比现在的直接切换更差。

## 六、无论选哪个方向都该做的六件事

1. **统一 token**：把球/面板的颜色、圆角、阴影、字号抽成与主窗同源的一组变量（球侧用于生成 PNG 的脚本，面板侧用 CSS 变量）。
2. **三态语义化**：状态 = 颜色（松绿/琥珀/朱红）+ 形态（静/环/点）两个维度，不只靠配件。
3. **状态可见**：把「正在看屏 / 正在动手 / 等待确认」做成**常驻的一个小胶囊**（面板头部下方一行，或在球上加环形进度），不要混进消息流。
4. **头部减负**：6 个图标降到 3~4 个 + 一个「⋯」溢出菜单；会话标题至少保留 96 px 的可读宽度。
5. **空状态给方向**：一句能干什么 + 两三个示例问题（点击即填入输入框，不自动发送）。
6. **动效克制**：只用 83/167/250 三档时长与两条 Fluent 曲线；支持 `prefers-reduced-motion`（球不做旋转，面板不做缩放，只做透明度）。

## 七、明确不做（本大点）

- 不做实时模糊背景的球（分层窗口拿不到背后画面）；
- 不做球与面板的连续变形动画；
- 不改面板的逻辑尺寸（380×560）与两档开关的交互（03 已定）；
- 不引入前端框架或动效库（面板仍为零依赖单文件）。

## 八、留给 `Verdict/04` 的取舍

1. 走 A / B / C 哪个方向（或 A 的形态 + B 的局部质感）；
2. 球的品牌符号：项目图标（`assets/icon.png`）的缩微，还是另做一枚与「情报/观察」相关的符号；
3. 「状态胶囊」放面板头部，还是做成球的外环（球更显眼，但 64 px 上可读性差）;
4. 是否把三态从 PNG 换成自绘（关系到后续能否做逐帧动画）。
