## 二、逐文件

### 1. `tools/_runtime/cu_input.py`（358 行）—— 执行器

- **关键行**：`52 INPUT`（SendInput 的联合体）· `87 dpi_aware` + 导入期直接调用 · `106 process_name_of` · `127 whitelist` · `161 check_target`（双层判定）· `212 click` · `235-273` 剪贴板 · `293 scroll` · `314 press` · `326 type_text` · `348 audit`。
- **在链路里的落点**：`control_tool` 的每个动作最后都落到这里；面板或其他入口要做同样的动作，也应该调这里，不要另写一套。
- **检查要点**：
  - `dpi_aware()` 是**模块级调用**，不是函数内调用。理由是 `WindowFromPoint` / `SetCursorPos` 会按进程的 DPI 感知状态解释坐标；等到 `click()` 里再声明，前面已经算过一次坐标了（真机上就是这么被拒的）。
  - `GlobalAlloc` / `GlobalLock` 必须声明 `argtypes`/`restype`，否则 64 位下 HGLOBAL 会被当成 32 位整数，中文一个字都粘不进去。
  - `check_target` 判两层：前台窗口 + `WindowFromPoint` 落点的顶层属主。只判前台是不够的——对话框、弹层盖在上面时，点击会落到另一个进程。
  - `audit` 里 `try/except` 吞掉所有异常：审计失败不能影响动作本身。
- **思考题**：如果把剪贴板改成「先读原内容、粘贴后还原」，在目标应用特别慢（粘贴还没完成）时会出什么问题？现在的 `sleep(0.25)` 是经验值，你能想到更稳的判定方式吗？

### 2. `tools/control_tool.py`（231 行）—— 四个工具

- **关键行**：`24 _limit` · `32 _guard`（闸门 1~3）· `53 _to_physical` · `63 mouse_click` · `103 type_text` · `141 press_key` · `183 mouse_scroll` · `229 _thread_id`。
- **检查要点**：
  - 四个工具共用 `_guard`，顺序固定：**开关 → 次数 → 帧号**；白名单在 `_guard` 之后单独判（因为 `type_text`/`press_key` 只判前台，`mouse_click`/`mouse_scroll` 才判落点）。
  - 回执里必须带「落点所在窗口」和「前台进程」——这是模型判断「刚才那一下到底中没中」的唯一依据。真机上「点放大镜说成功、其实没中」正是靠它发现的。
  - 每次成功动作都 `bump_action()` 并写审计；被拒绝的动作**不计数**（否则模型试错几次就把额度耗光）。
- **思考题**：`mouse_scroll` 的坐标用来定位「滚哪」，但它不改变前台窗口；如果模型给了一个落在列表外面的点，滚动会作用到别的区域。有没有更稳的判定方式（例如先判落点窗口与上次点击的是否同一窗口）？

### 3. `utils/cu_mode.py`（82 行）—— 轮内状态

- **关键行**：`21 CuTurn` · `43 begin_turn(on, control, thread_id)` · `64 can_control` · `72 set_frame` · `80 bump_action`。
- **检查要点**：
  - 用 `ContextVar` 而不是全局变量：`_run_agent` 跑在工作线程里，并发请求之间不能串号。
  - `shots`（截图）与 `zooms`（放大）是两个独立计数：放大帧不进 `shots`，但也不能无限刷。
  - 帧号 `next_cid` 单调递增，放大时取 `max(next_cid, last_cid + 1)`，杜绝撞号。
- **思考题**：现在所有状态轮末丢弃。如果将来要做「跨轮继续同一个任务」，哪些状态必须保留、哪些必须丢？

### 4. `agent/cu_middleware.py`（118 行）—— 摘工具的闸

- **关键行**：`33 GATED_TOOLS` · `36 CONTROL_TOOLS` · `38 CU_TOOLS` · `51 _dropped` · `61 _keep_only_cu` · 同步/异步两个 `wrap_model_call`。
- **检查要点**：
  - 「关闭即不存在」靠的是**把工具从 `request.tools` 里摘掉**，不是让工具自己返回拒绝——后者模型仍能看到卡片，会反复尝试。
  - CU 模式打开时走 `_keep_only_cu`：只剩屏幕工具，业务工具一律不发。这既是安全面收敛，也是性能优化（真机上单步从十几秒降到几秒）。
  - 同步/异步两个入口必须同时改，历史上就漏过一处。
- **思考题**：如果将来要让 CU 模式和某个业务工具共存（比如「查资料后复制到网页」），摘工具的策略怎么设计才不会回到「工具表爆炸」？

### 5. `api/server.py` —— 参数、提示词、跳过路由

- **关键行**：`/api/chat` 的 `allow_control` 参数 · `_run_agent(computer_use, allow_control)` 里的 `begin_turn` · 提示词「屏幕控制·本轮已开启」段（第 4 条讲小图标阈值、第 5 条讲回车）· `if computer_use: route_mode = "cu"`。
- **检查要点**：
  - `allow_control` 只由前端按会话传，后端校验会话归属；**不读库、不读环境变量**，避免「偷偷一直开着」。
  - CU 模式跳过 `tool_router`：不调决策模型、不拼简报。这条同时修掉了「比价报告」类幻觉（简报里的能力卡是主要诱因）。
  - 提示词里的阈值 `%d` 取自设置，不要在代码里写死第二个数字。
- **思考题**：如果用户在同一会话里先做 CU 再问业务问题，工具表在下一轮会自动恢复吗？恢复的时机在哪一行？

### 6. `tools/screen_tool.py` + `front/desktop/app.py` —— 取图与放大

- **关键行**：`screen_tool`：`91 _max_shots` · `98 _max_zooms` · `103 _grab` · `118 _grab_via_shell` · `138 _grab_local`（region 分支）· `201 screen_capture`。`app.py`：`212 _capture_for_agent(monitor, region)`（裁剪 + 放大）· 抓图服务里解析 `region` 查询参数。
- **检查要点**：
  - 两条抓图路径（外壳端点 / 本进程）必须**同构**：同样的裁剪、同样的放大倍数、同样的 meta 字段。只改一边是最常见的漏洞。
  - 放大帧**不按 `SCREEN_SHOT_EDGE` 缩**，否则等于白放大。
  - 返回的 `screen_rect` 是**这一块**的物理矩形，`scale = 图宽 ÷ 物理宽`（放大后可能大于 1），后续点击直接用它换算。
- **思考题**：放大 3 倍时 JPEG 质量设到 95、体积会明显变大；对 200% 缩放的屏幕，2 倍和 3 倍的收益差多少？有没有必要做成自适应？

### 7. 前端两个开关

- **关键行**：`front/index.html` 的 `CTL_KEY = 'zx_cu_control'`、`ctlOn`、`toggleCtl`、请求拼 `allow_control=1`；`front/desktop/ball.html` 的 `ctlS` 按钮与 `syncCtlBtn`。
- **检查要点**：
  - 控制档是**派生状态**：`ctlOn = cuOn && ctlSessions[thread]`。关掉屏幕共享时，控制档自动失效，不需要额外的清理逻辑。
  - 两窗共享同一个 localStorage 键，靠 `storage` 事件同步；写入时更新 `_rev` 键触发对窗。
- **思考题**：如果用户在 A 窗开着控制，B 窗把共享关掉，A 窗下一次发消息会带 `allow_control=1` 而没有 `computer_use=1`——后端这时的行为是什么？

### 8. `tests/unit/` —— 钉住什么

- `test_control_tool.py`：四道闸的拒绝路径、坐标换算、回执字段、计数只加成功动作。
- `test_cu_tool_trim.py`：三态（全关 / 只看 / 看+动）下模型最终看到的工具表。
- `test_screen_tool.py`：放大帧的换算、不占截图额度、必须先有整屏、上限、过小区域拒绝。
- `test_frontend_payloads.py`：保存已有配置时字段必须取自本行（防「勾选被静默重置」）。
