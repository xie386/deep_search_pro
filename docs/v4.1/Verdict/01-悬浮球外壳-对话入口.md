## 第 1 条 · 球的实现形态

- **日期**：2026-10-30
- **分叉点**：球用「pywebview 无边框透明窗」还是「Win32 分层窗口贴 PNG」？
- **可选方案**：
  - A. pywebview `frameless + transparent`：代码最少，全部 HTML/CSS 渲染。
  - B. Win32 分层窗口（`WS_EX_LAYERED` + `UpdateLayeredWindow`）：窗口是方的，alpha 掩码是圆的。
  - C. 不透明圆角胶囊（纯 CSS）：成本最低，但视觉上不是球。
- **裁定结果**：**B，Win32 分层窗口贴 PNG**。
- **依据**：2026-10-30 实测（`tests/debug/_spike_ball_window.py`）四条路全部失败 ——
  1. `transparent=True`：窗内四角恒为实色 `(32,32,32)`，窗外是桌面 `(26,23,36)`，两者从不对上；
  2. `SetWindowRgn` 裁圆：对窗体与 5 个子窗口都执行成功，截图前后逐像素一致；
  3. 色键（`SetLayeredWindowAttributes` + 窗体 `TransparencyKey`）：方块底色仍在；
  4. 直接改 `CoreWebView2Controller.DefaultBackgroundColor`：后台线程被 COM 拒绝（`E_NOINTERFACE` + 「只能从 UI 线程访问」）。
  分层窗口是 Windows 上做「异形浮窗」的既有做法，能做到逐像素透明与圆外点击穿透，且不依赖 WebView2 的合成行为。
- **影响面**：新增 `front/desktop/ball_window.py`（Win32 窗口类）；球体视觉改为 PNG 资源（`front/desktop/assets/`）；球的动态效果改由位图切换承担。

## 第 2 条 · 面板的复用方式

- **日期**：2026-10-30
- **分叉点**：对话面板是「复制一套聊天 UI」还是「复用现有 SPA」？复用的话，走 iframe 还是直接加载？
- **可选方案**：
  - A. 新写 `ball.html` 独立实现聊天：球壳最轻，但流式、中断、workflow 步骤、`/` 选择、图片渲染都要再实现一遍，必然漂移。
  - B. 外层薄壳 + iframe 指向 `index.html?ball=1&embed=1`：CSS 隔离，但多一层 iframe。
  - C. **面板窗直接加载 `index.html?ball=1&embed=1`**：不做球壳页面，紧凑模式由同一份前端承担。
- **裁定结果**：**C**。球已改为原生窗口，不存在「球的 HTML 壳」，iframe 失去存在理由；面板直接把现有 SPA 以紧凑模式加载。
- **依据**：现有 URL 参数模式已存在（`app.py:1390` 的 `?desktop=1&_=<ts>`、`front/index.html:5040` 的 `IS_DESKTOP` 正则容忍附加参数）；对话链路（会话加载、`/api/chat`、SSE、`/` 选择、图片渲染、workflow 步骤卡）无需改动一行。
- **影响面**：`front/index.html` 只加一个模式开关与一段 `.ball-mode` 样式；不新增第二套聊天实现。

## 第 3 条 · 几何与尺寸口径

- **日期**：2026-10-30
- **分叉点**：坐标用逻辑像素还是物理像素？窗口尺寸在创建时给定还是创建后设定？
- **可选方案**：
  - A. 全流程物理像素：与 Win32 一致，但 pywebview 的 `x/y/width/height` 是逻辑像素，混用会错位。
  - B. **全流程逻辑像素**，需要物理值时用实测倍率反推。
  - C. 创建时给定尺寸：代码最直白。
- **裁定结果**：**B + 尺寸创建后设定**。
- **依据**：2026-10-30 实测 —— 进程 DPI 感知为 system-aware（值 1），本机倍率 2.0（逻辑 40 → 物理 80，逻辑 200 → 物理 400）；`win32_rect_w / win.width` 可直接反推倍率；创建时传 `68×68` 实际得到 `118×32`，创建后 `SetWindowPos(136,136)` 立刻回到 `68×68`；`resize()`、`move()` 运行时均生效。
- **影响面**：球窗与面板窗的坐标换算集中在 `ball_window.py` 一个函数里；配置与持久化只存逻辑坐标。

## 第 4 条 · 生命周期与关闭语义

- **日期**：2026-10-30
- **分叉点**：球是否要在主窗口关闭后继续常驻？是否要改现有「点 X 收进托盘」的行为？
- **可选方案**：
  - A. 主窗关闭 = 退出应用（球随之退出），保持最简单的生命周期。
  - B. 沿用现状：点 X 收进托盘，球继续常驻，托盘「退出」才真正结束。
  - C. 新增设置项让用户二选一。
- **裁定结果**：**B，沿用现状，不改行为**。
- **依据**：`front/desktop/app.py:54` `CLOSE_TO_TRAY = True`；`:1450-1466` 的 `on_closing` 已经实现「点 X → 收进托盘」，托盘不可用时自动放行关闭。球作为同进程窗口天然共享这套语义，不需要新增分支。
- **影响面**：`on_quit`（`:1436`）需要先关闭球线程再退出；`on_closing` 不改。

## 第 5 条 · 跨线程调用

- **日期**：2026-10-30
- **分叉点**：球在自己的 Win32 消息循环线程里运行，点击后要驱动的却是 pywebview 的面板窗 —— 直接调窗口方法，还是要自建队列？
- **可选方案**：
  - A. 球线程直接调用 `panel.show()/hide()/move()`。
  - B. 球线程投递命令到 `queue.Queue`，主线程轮询执行。
- **裁定结果**：**A**。
- **依据**：pywebview 的 WinForms 后端对窗口操作做了线程编组 —— `load_url`（`:489`）、`hide`（`:491-492`）、`show`（`:494-500`）、`toggle_fullscreen`（`:595-596`）都先 `self.Invoke(Func[Type](...))` 再执行，因此跨线程调用是安全的。
- **影响面**：球线程可直接开关面板、移动到球旁；若实现中发现个别方法未编组，再退回 B（加队列）而不改球窗结构。
