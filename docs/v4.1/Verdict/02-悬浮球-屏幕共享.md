# 02 悬浮球（屏幕共享）· 裁定记录

> 裁决的唯一落点。按时间追加；旧条目不删、不改语义，要改就在下面追加一条「修订 + 理由」。
> 裁定日期：2026-11-09（定方案期）。

---

## 第 1 条 · 能力形态与开关粒度

- **日期**：2026-11-09
- **分叉点**：屏幕共享做成「界面上一个截图按钮、用户按一次发一次」，还是「agent 手里的一个工具」？开关按账号全局还是按会话？
- **可选方案**：
  - A. 界面按钮：用户每次手动截、手动附到提问里。行为直观，但 agent 无法在推理中途「再看一眼」。
  - B. **内置工具 + 按会话开关**：开关打开后 agent 可在本轮自行决定何时截、截几张。
  - C. 工具 + 按账号全局开关：少一层状态，但一个会话开着，其它会话也被动获得看屏能力。
- **裁定结果**：**B**。
- **依据**：用户 2026-11-09 口径——「做模式分离，在两个窗口的聊天页面做一个 computer use 模式开关，只有开启时才有 computer use 能力」「1. 按会话开」。工具形态也是 03 的前提：屏幕控制必须能「看一眼再点」。
- **影响面**：新增上下文开关（`utils/cu_mode.py`，contextvar 形态，与 `utils/write_auth.py` 同构）；`api/server.py` 的 `/api/chat` 增 `computer_use` 参数并校验会话归属；`_run_agent` 增同名形参；前端两处开关按 `thread_id` 记忆（`localStorage` 键 `zx_cu_sessions`）。
- **关闭时的口径**：不注入提示词、工具自身拒绝、界面没有截图入口——能力在关闭状态下「不存在」，而不是「存在但被拦」。

## 第 2 条 · 捕获实现

- **日期**：2026-11-09
- **分叉点**：用零依赖的 `PIL.ImageGrab`，还是引入 `mss`？一帧按什么尺寸与格式交付？
- **可选方案**：
  - A. `ImageGrab`：零新依赖，实测整屏 62 ms，够用。
  - B. **`mss`**：多屏与逐屏抓取更直接，速度更快；新增一个纯 Python 包。
  - C. Desktop Duplication（`dxcam` / `BetterCam`）：最快，但依赖 GPU 与驱动，体积大。
- **裁定结果**：**B**，并在交付前压到长边 1456、JPEG q85。
- **依据**：
  - 用户 2026-11-09 决定「引入 mss」；`uv pip install --dry-run mss` 解析结果只有 `mss==10.2.0` 一个包，无连带升级。
  - 本机实测（2880×1620，DPI 192）：整屏 `ImageGrab` 62 ms、原图 13.3 MB；长边 1568 + JPEG q85 为 1567×881 / 210 KB / 131 ms；长边 1280 为 152 KB / 60 ms；同尺寸 PNG 894 KB / 476 ms。
  - 1568 长边在 16:9 屏上约 1792 个 28px tile，超过 1568 的 tile 上限会被服务端再降一次，导致坐标与模型看到的图不一致（Anthropic 官方最佳实践明确写了这条）。16:9 的安全档约 1456×812（52×29 = 1508 tile）。
- **影响面**：新增 `tools/screen_tool.py`；依赖 `mss` 进 `pyproject.toml`；压缩复用 `PIL`，不引入新图像库。

## 第 3 条 · 自身窗口不入镜

- **日期**：2026-11-09
- **分叉点**：主窗、面板、球需不需要从截图里排除？怎么排？
- **可选方案**：
  - A. 统一每帧隐藏再恢复：实现一致，但每帧闪一下。
  - B. **主窗/面板用窗口排除属性，球用会话级隐藏**：零闪烁 + 无球残留。
  - C. 截完按窗口矩形涂黑：实现简单，但把用户真正想看的内容也涂掉了。
- **裁定结果**：**B**。
- **依据**：2026-11-09 本机实测（`WDA_EXCLUDEFROMCAPTURE` + 整屏 GDI 截图，取窗口中心像素）：

  | 窗口类型 | API 返回 | 截图结果 |
  |---|---|---|
  | 普通 Win32 窗 | 成功 | 变白，露出下层窗口 |
  | WebView2 普通窗（主窗同款） | 成功 | 变桌面色 |
  | WebView2 无边框置顶（面板同款） | 成功 | 变桌面色 |
  | 分层窗（球同款） | 成功 | **仍是球本身**（假成功） |

  球隐藏对照：隐藏后球矩形内 8630/16384 像素发生变化，0.8 秒内完成；恢复显示会回到 `data/ball_state.json` 记录的落点。分层窗不支持该排除机制这条与社区结论一致（`robmikh/Win32CaptureSample` issue 51）。
- **影响面**：`front/desktop/app.py` 在主窗与面板创建后各设一次窗口排除属性；`BallWindow` 增 `set_hidden_for_capture()/restore_after_capture()`（内部即 `hide()/show()`），由 `screen_tool` 在会话首帧与末帧之间调用。

## 第 4 条 · 每轮张数与上下文治理

- **日期**：2026-11-09
- **分叉点**：每轮固定一张、按题固定几张，还是让 agent 自行决定？
- **可选方案**：
  - A. 每轮固定 1 张：成本可控，但翻页类任务（一页一张）做不了。
  - B. 固定 N 张：仍要预设，遇到长文档就卡住。
  - C. **agent 自行决定 + 硬上限 + 同屏去重 + 上下文降级**：张数随任务，成本有天花板。
- **裁定结果**：**C**。
- **依据**：用户 2026-11-09 口径——「会话截图数量不能确定，如果未来开发完需要拿它来做题，那翻页情况下就是一页一张，需要由 agent 自行判断或者用户在该轮直接指定」。
- **口径细节**：
  - 硬上限 `SCREEN_MAX_SHOTS_PER_TURN`，默认 6、范围 1~10；超限时工具直接回「本轮截图次数已用完」，不再抓屏。
  - 同屏去重：每帧记录屏幕内容的哈希，哈希相同直接复用上一帧，不重复消耗视觉 token。
  - 上下文降级：一轮内**只有最近一帧以图片形式留在上下文**，更早的帧降级为一行文字（帧号 + 前台窗口标题 + 时间），避免多图把上下文与成本撑爆。
  - 用户当轮用自然语言指定（「这轮最多截 5 张」「每页截一张」），不额外加数字输入框。
- **影响面**：`tools/screen_tool.py` 内部计数与去重；`utils/settings.py` 增 `SCREEN_MAX_SHOTS_PER_TURN`、`SCREEN_SHOT_EDGE`（默认 1456）、`SCREEN_SHOT_QUALITY`（默认 85）。

## 第 5 条 · 图片如何到达模型

- **日期**：2026-11-09
- **分叉点**：工具返回的截图，走「工具消息携带图片块」，还是回到「本轮图片通道」？
- **可选方案**：
  - 甲. `screen_capture` 返回带 `image_url` 块的 `ToolMessage`：最自然，agent 在同一轮内就能看图再决定。
  - 乙. 工具落盘并返回 id，由装配层在下一次模型调用时把图挂上：改动面落在 deepagents 之外，风险大。
  - 丙. 每轮开场由 harness 截一张、走现有 `images=` 通道：模型一定看得到，但「再看一眼」要等下一轮。
- **裁定结果**：**优先甲；实现第一步用 30 行验证，失败即退丙**。
- **依据**：现有工具返回全是文本，`[[img:…]]` 只用于界面渲染（`tools/capability_invoke.py` 的 `_save_tool_image()`），没有「工具把图交给模型」的先例；deepagents 是否透传 `ToolMessage` 的图片块未经实测，必须先证伪再定实现。
- **影响面**：`tools/screen_tool.py` 的返回类型；若走丙，`agent/build_context.py:336` 的 `_ci.build_content(...)` 会在本轮开场附带截图，工具退化为「触发下一轮截屏」的提示。

## 第 6 条 · 留存与隐私

- **日期**：2026-11-09
- **分叉点**：截图落盘留存，还是只活在内存？
- **可选方案**：
  - A. 落 `user_data/pic/<账号>/chat_images/`：与上传图同链路，历史可回看，但屏幕内容会被长期保存。
  - B. **纯内存**：轮内可用、轮末丢弃，聊天记录里不留缩略图。
  - C. 内存 + 轮末保留一张：历史可追溯，但与「纯内存」的选择冲突。
- **裁定结果**：**B**。
- **依据**：用户 2026-11-09 口径——「3. 纯内存不留」。
- **影响面**：
  - 帧只在进程内以 `bytes` 存在；视觉链路若必须有文件（`chat_images` 走路径），落 `user_data/_runtime/screens/<账号>/` 并在本轮结束、切会话、关开关、超时（单轮 10 分钟）四个时机删除。
  - 不使用 `chat_images.save()` 的长留存目录，避免与用户主动上传的图混在一起。
  - 轮内给用户可见反馈：面板显示「共享中」，每次截帧在气泡里留一行「已截取第 N 帧（capture #id）」，轮末不保留画面。

## 第 7 条 · 两窗开关的同步

- **日期**：2026-11-09
- **分叉点**：主窗与悬浮面板各存一份开关状态，还是共用一个状态？
- **可选方案**：
  - A. 各存各的：实现最简单，但同一会话在两个窗口里状态不一致。
  - B. **按 `thread_id` 存共享状态，storage 事件互相同步**：与会话列表同步同构。
- **裁定结果**：**B**。
- **依据**：两窗同源共用 WebView2 profile，`localStorage` 与 `storage` 事件已实测可用（2026-11-09 会话同步：主窗 3 条 → 面板删 1 条 → 主窗 2 条）。
- **影响面**：`front/index.html` 与 `front/desktop/ball.html` 各加一个开关与一个 `storage` 监听；键名 `zx_cu_sessions`（`{thread_id: true}`）；后端仍以请求参数为准，前端状态只是 UI。

## 第 8 条 · 修订第 3 条：排除只在抓图那一瞬间

- **日期**：2026-11-09
- **分叉点**：`WDA_EXCLUDEFROMCAPTURE` 是常驻开着，还是只在 agent 抓图的那一下开？
- **可选方案**：
  - A. 启动时给主窗与面板常驻设排除：实现最省事，但**用户自己的截图也会被屏蔽**。
  - B. **只在抓图瞬间设、抓完立刻清**：需要把抓图动作放回外壳进程（只有窗口的属主进程能改这个属性）。
- **裁定结果**：**B**。第 3 条的「主窗/面板常驻排除」按本条作废。
- **依据**：用户 2026-11-09 真机反馈——「由于当前设计了截图屏蔽，我现在用截图快捷键截不到窗口画面……请保证只是项目 Agent 截图时做屏蔽，用户直接用截图快捷键截图时不屏蔽」。
- **实现口径**：
  - 外壳起一个只绑 `127.0.0.1` 的随机端口 HTTP 抓图接口（令牌随进程生灭，退出即失效）；
  - 后端 `tools/screen_tool._grab()` 优先走该接口（`ZX_CU_ENDPOINT` 由外壳注入子进程环境）；
  - 外壳侧 `_capture_for_agent()`：设排除 → 藏球 → 等 120 ms → mss 抓 → 压缩 → **无论成败都还原**（清排除、显示球）；
  - 没有该环境变量时（纯 web 版、后端独立跑）退回本进程直接抓，此时没有自身窗口需要排除。
- **实测（2026-11-09，隔离实例 8139）**：抓图前与抓图后 `GetWindowDisplayAffinity` 均为 `0`（未排除），
  而模型对同一帧的回答是「没有标题含「智选情报官」的窗口」「没有橙色圆球」——说明排除只在抓图瞬间生效。
- **影响面**：`front/desktop/app.py` 新增 `_start_cu_server/_capture_for_agent/_set_capture_excluded`；
  `DesktopApi.cu_begin/cu_end` 退化为空操作（球不再整轮隐藏）；`tools/screen_tool.py` 增加外壳抓图分支。
- **连带修复**：面板是 `focus=False` 创建、由不激活的分层球点开的，主窗收进托盘时进程没有前台窗口，
  键盘与输入法留在上一个应用（现象：输入法条可见、回车录不进字）。`_toggle_panel(True)` 现在会在
  `show()` 之后调 `_activate_window()`（必要时用 `AttachThreadInput` 抢一次前台）；实测点球后面板即前台。
  浮窗输入框的 Enter 也补了输入法判定（`isComposing` / `compositionstart-end` / `keyCode 229`），
  避免把「上屏的回车」当成「发送」。
