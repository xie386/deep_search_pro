## 第 1 条 · 动作面与注入实现

- **日期**：2026-11-09
- **分叉点**：动作面多大？用什么方式注入？要不要引 GUI 自动化依赖？
- **可选方案**：
  - A. 全词表（单击/双击/右键/滚轮/拖选/组合键/粘贴）+ pyautogui：一步到位，依赖大、词表杂。
  - B. **本步只做鼠标点击（left click / double click）与文字输入（type）两类工具**，pywin32/ctypes 直调 `SendInput`，零新依赖；其余动作留后续 4.x。
  - C. 走 UIA 元素路线（pywinauto）：最稳，但 Chromium/Electron 类应用（QQ NT、微信 4.x）内容树默认不可见，且必须引依赖。
- **裁定结果**：**B**。词表与 OpenAI computer use 的动作定义对齐（`click` / `double_click` / `type`）；`wait` 不做成工具，作为注入后的内部等待机制。
- **依据**：用户 2026-11-09 口径——「目前先实现这两个简单和常用的操作，其他操作在后续某个 4.x 的版本中补齐」；本机实测 pyautogui / pywinauto / uiautomation 均未安装、`SendInput` 经 ctypes 可直调（`INPUT` 结构 `sizeof=40`）；中文输入的硬约束是键盘扫描码不含汉字，**打字走「剪贴板 + Ctrl+V」**（ctypes 直调 user32 剪贴板 API，约 30 行，零依赖），粘贴不经 IME，不受输入法激活态影响。
- **影响面**：新增 `tools/_runtime/cu_input.py`（SendInput 封装 + 剪贴板）与 `tools/control_tool.py`（`mouse_click` / `type_text` 两个 `@tool`）；不引任何新 pip 依赖。

## 第 2 条 · 坐标契约与防旧帧

- **日期**：2026-11-09
- **分叉点**：模型给的坐标按什么口径解释？如何防止「看着旧帧点新界面」？
- **可选方案**：
  - A. 信模型：模型说点哪就点哪，不校验。
  - B. **统一换算公式 + `capture_id` 校验**：模型给的是「图上坐标」，工具换算为物理坐标；入参必须带 `capture_id`，与最近一帧不一致直接拒绝。
  - C. 每次动作前由工具自己重新截图比对：最稳，但每次动作多一帧成本，且「比对」本身不可靠。
- **裁定结果**：**B**。换算公式：`物理坐标 = 图上坐标 ÷ scale + screen_rect 原点`（`scale` 与 `screen_rect` 来自 02 的帧元数据，存于 `cu_mode` 轮内状态）。
- **依据**：02 已立「模型看到的图 ÷ 物理像素 = scale」的口径（`tools/screen_tool.py` 帧信息）；windows-computer-use-mcp 的 `capture_id` 防旧帧是同类系统通行做法；Windows-MCP issue #86 记录高 DPI 坐标错位，本机 200% 缩放同款风险。
- **影响面**：`utils/cu_mode.py` 的 `CuTurn` 增 `last_scale` / `last_rect` 字段；两个控制工具入参含 `capture_id`；多显示器时 `MOUSEEVENTF_ABSOLUTE` 按 `screen_rect` 原点与宽高归一化（本机单屏，双屏分支静态审查 + 留双屏真机待验项）。

## 第 3 条 · 授权分级与控制闸

- **日期**：2026-11-09
- **分叉点**：「看」与「看+动」是一个开关还是两档？控制闸多严？
- **可选方案**：
  - A. 一个开关，开了就能动：省事，但「看屏」和「动手」的授权混在一起。
  - B. **两档**：`computer_use=1`（只看，02 已实现）→ `allow_control=1`（看+动）；控制闸 = 轮内状态 + 动作上限 + 白名单。
  - C. 每个动作都弹窗确认：最安全，但多步任务无法使用。
- **裁定结果**：**B**。
- **依据**：用户 2026-11-09 拍板——确认制走 `pending_safety_checks` 模式（普通动作自动执行、回执写明；不可逆动作模型先复述再动；用户随时可经 `/api/chat/cancel` 中断）、动作上限默认 20、白名单进设置页。
- **口径细节**：
  - `CU_MAX_ACTIONS_PER_TURN`：默认 20，可设 1~50；超限工具直接拒绝；
  - `allow_control` 由**前端按会话传递**（与 `computer_use` 同一机制，`localStorage` 键按 `thread_id` 记忆），后端校验会话归属；
  - 动作执行后回执必须包含：做了什么、落点坐标、注入后的前台窗口标题；
  - 不可逆动作（发送消息、删除等）：文档串要求模型**先用文字复述它将要做的事**，再执行；不做自动判定。
- **影响面**：`utils/cu_mode.py` 增 `control` / `actions` 字段与 `CU_MAX_ACTIONS_PER_TURN` 设置项；`api/server.py` 的 `/api/chat` 增 `allow_control` 参数；`agent/cu_middleware.py` 的 `GATED_TOOLS` 扩为按档位放行（只看时摘掉控制工具）。

## 第 4 条 · 白名单：按进程名，设置页勾选

- **日期**：2026-11-09
- **分叉点**：白名单按窗口标题、按进程名，还是别的形态？放请求参数还是设置页？
- **可选方案**：
  - A. 按窗口标题关键字（设置页填 `记事本`、`Chrome`）：直观，但标题随文档名变化（「未命名 - 记事本」→「文档1 - 记事本」），需模糊匹配，脆。
  - B. **按进程名**（`notepad.exe`、`chrome.exe`）：认「应用」而非「标题」，标题怎么变都不影响；同一进程的所有窗口放行（Chrome 各标签页/弹窗都算）——这正是用户直觉。
  - C. 请求参数带白名单：可被提示词注入引导模型构造，防线形同虚设。
- **裁定结果**：**B（按进程名）+ 设置页勾选**。
- **依据**：用户 2026-11-09 拍板「按照 B 写定方案」「设置页勾选」；请求参数形态在安全上不可接受（提示词注入可以诱导模型构造参数）。
- **口径细节**：
  - 设置页新增「屏幕控制白名单」文本项：每行一个进程名（不区分大小写，可带可不带 `.exe`）；
  - 执行前双重判定：① `GetForegroundWindow()` 的进程名在名单内；② `WindowFromPoint(落点)` 取真正接收点击的窗口（可能是子弹窗/对话框），其**顶层属主**的进程名也在名单内；
  - 名单为空 = 全部拒绝（默认最严）；判定失败工具返回「前台窗口（xxx.exe）不在屏幕控制白名单」；
  - 进程名通过 `QueryFullProcessImageNameW` 取，不做路径匹配，只取文件名小写比较。
- **影响面**：`utils/settings.py` 增 `CU_WHITELIST`（textarea）与 `CU_MAX_ACTIONS_PER_TURN`（number）；`tools/_runtime/cu_input.py` 承载双重判定；设置页（`front/index.html` 设置组）加对应表单项。

## 第 5 条 · 审计与边界

- **日期**：2026-11-09
- **分叉点**：动作记录记什么、记在哪？哪些事情明确不做？
- **可选方案**：
  - A. 不记录：出事无从追溯。
  - B. **只追加 JSONL，记动作元数据**（时间、thread_id、capture_id、动作、坐标/文本长度、注入后前台窗口），落 `data/audit/cu_actions.jsonl`。
  - C. 连屏幕内容一起存：审计完整，但与「截图纯内存不留」的 02 裁定冲突。
- **裁定结果**：**B**。
- **依据**：`data/audit/` 是既有审计目录；02 裁定第 6 条「截图纯内存」仍然有效——审计不含屏幕内容，两者不冲突。
- **边界（沿用调研稿 §三.5 与 §六，定方案期正式写入）**：UI 自动化不改平台约束，可能被平台视为自动化脚本；本能力只面向「用户自己看得见、自己确认过」的动作。明确不做：后台静默操作、锁屏运行、批量加好友/群发/对陌生人的自动触达、绕过平台审核的路径。
- **影响面**：`tools/_runtime/cu_input.py` 每次注入追加一行；测试用例断言行格式。
