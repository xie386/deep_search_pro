## 01 悬浮球外壳（对话入口）

> 状态：实现中（2026-10-30 开工；方案见本段 ③，裁定见 `Verdict/01-悬浮球外壳-对话入口.md`）

### ① 应对什么问题

提问入口只有「切窗口」一条路，用户一动手就被打断：

- 桌面壳是**单窗口 + 托盘**，且窗口是 1280×820 的普通大窗 —— `front/desktop/app.py` 全文只有一次窗口创建（`:1402-1405`），托盘只提供菜单与气泡通知（`:752`、`:844-880`）；
- 全局热键**没有**（`app.py` 全文只有 `:807-808` 用 `ctypes` 设 AppUserModelID，无 `RegisterHotKey`、无键盘钩子）；
- 于是用户正在写代码、看文档、翻网页时想问一句，只能切到壳或浏览器，问完再切回来；
- 页面没开时，提醒也收不到：页面内推送走 WS（`api/digest_scheduler.py:22` 的 `_notify_ws`），只有托盘气泡能漏出来一点。

后果是「随手可用」这件事在当前形态下做不到：入口有，但要用户主动去找它。

### ② 功能

做完之后，用户桌面上多一个**常驻小球**：

- 球浮在其它窗口之上、可拖到任意角落、不抢当前窗口焦点；
- 单击球展开一个**对话小面板**，直接提问，答案就在球上滚动显示（复用现有 AI 助手同一套会话与流式事件）；
- 托盘可切换球的显示与隐藏；球的外观（尺寸、透明度、是否置顶、初始角落）在设置页里调，不写进 `.env`；
- 球是**纯入口**：不新增模型能力，提问走的仍是现有主 Agent 链路。

### ③ 实现功能的技术方案

#### 3.1 进程与窗口模型

桌面壳进程内三个实体，职责单一：

| 实体 | 载体 | 生命周期 |
|---|---|---|
| 主窗口 | pywebview（现状：1280×820，URL 带 `?desktop=1`） | 常驻；点 X 收进托盘（`front/desktop/app.py:54`、`:1450-1466`） |
| 悬浮球 | 纯 Win32 分层窗口，独立线程 + 自己的消息循环 | 设置项开启时创建；托盘「退出」时销毁 |
| 对话面板 | pywebview 窗口（无边框、置顶、启动时 `hidden=True`） | 首次点球时 `show()`；面板关闭只是 `hide()`，不 destroy |

三者同进程、同 webview profile（`data/desktop_webview`）→ 登录态共享（2026-10-30 实测：一窗写入 localStorage，另一窗读到同一值），**不需要任何令牌传递**。

#### 3.2 球窗规格（新增 `front/desktop/ball_window.py`）

| 项 | 做法 |
|---|---|
| 窗口样式 | `WS_POPUP` + `WS_EX_LAYERED | WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE | WS_EX_TOPMOST` |
| 尺寸 | 48 / 64 / 80 三档（设置项），默认 64；**创建后**用 `SetWindowPos` 定尺寸 —— 创建参数在 200% 缩放下不可信（实测传 68×68 实际得到 118×32，创建后改回 68×68 成功） |
| 绘制 | Pillow 读 `front/desktop/assets/ball_{idle,busy,alert}.png`（64×64、带 alpha、阴影烘焙进图），转 `HBITMAP` 后 `UpdateLayeredWindow` 贴图；状态切换 = 换图重贴 |
| 命中 | `WM_NCHITTEST`：落在圆内（半径 = 尺寸/2 − 1）返回 `HTCAPTION`（拖动交给系统）；圆外返回 `HTTRANSPARENT`（点击穿透到下层窗口） |
| 单击 | `WM_LBUTTONUP` 且位移 < 4px → 切换面板显示/隐藏 |
| 右键 | `WM_RBUTTONUP` → 上下文菜单（打开主窗口 / 隐藏悬浮球 / 退出） |
| 拖动 | 由 `HTCAPTION` 交给 DefWindowProc；拖动结束后把**球心逻辑坐标**写回 `data/ball_state.json` |
| 状态 | `idle` / `busy`（回答中，球面进度环）/ `alert`（有未读回答，红点）；由面板经 `pywebview.api.ball_state(state)` 回调，球线程内部用线程安全的 setter 更新 |
| 消息循环 | 线程内 `RegisterClassW` + `CreateWindowExW` + `GetMessageW/DispatchMessageW`；线程退出时 `DestroyWindow` 并注销类 |

#### 3.3 面板窗规格

| 项 | 做法 |
|---|---|
| 创建 | `webview.create_window(title, url, width=380, height=560, min_size=(320, 420), frameless=True, on_top=True, hidden=True, focus=False, easy_drag=True, js_api=DesktopApi())` |
| 加载地址 | `http://127.0.0.1:<port>/front/desktop/ball.html`（与主窗同源，共用同一 webview profile → 直接读 localStorage 里的 `zx_token`/`zx_user`） |
| 页面内容 | **只做聊天与会话**：会话下拉 + 新建/重命名/删除 + 消息区 + 输入框/发送/中断；不加载主 SPA，不带侧栏、顶栏、工作台 |
| 展开落点 | 面板出现在球的**朝向屏幕内侧**一侧（球在左半屏→右侧展开，右半屏→左侧；上下同理），与球留 12px 间距；超出工作区则翻转到另一侧或夹紧；全部按逻辑坐标计算，夹紧算法是纯函数（便于单测） |
| 圆角与阴影 | `frameless` + CSS 圆角；Windows 11 可另用 `DwmSetWindowAttribute(DWMWA_WINDOW_CORNER_PREFERENCE)` 让系统画圆角与阴影 |
| 关闭 | 面板右上角 × 与 `Esc` 都只 `hide()`，不 destroy（下次展开秒开） |
| 拖拽 | 面板顶部 40px 为拖拽条，元素加 `pywebview-drag-region` 类（pywebview 默认的拖拽选择器就是它，`webview/js/customize.js:92-94`） |

#### 3.4 迷你聊天页（新增 `front/desktop/ball.html`）

一张独立页面，只调三个接口面（同一后端、同一 token）：

| 能力 | 接口 |
|---|---|
| 发问 / 中断 | `POST /api/chat?question=&token=&thread_id=`（返回 `answer`/`cancelled`）· `POST /api/chat/cancel?token=&thread_id=` |
| 会话列表 / 新建 / 重命名 / 删除 | `GET /api/chat/sessions` · `POST /api/chat/sessions?kind=chat` · `PATCH /api/chat/sessions/{id}?title=` · `DELETE /api/chat/sessions/{tid}`（`api/server.py:1028-1080`） |
| 读历史 | `GET /api/chat/sessions/{tid}?token=`（只渲染 `role=user/assistant`，跳过工具消息） |

口径：
- token 从 `localStorage.zx_token` 读（与主窗同源共享，不注入、不回传）；
- 版面用 `flex` 三段（头 40px / 消息区 `flex:1; min-height:0` / 输入条固定），**输入条永远在可视区内**（修 bug3 的根因就是旧方案把 100% 高度的 SPA 塞进矮窗）；
- 顶部 40px 头与关闭按钮：`pywebview-drag-region` 负责拖动，`×` 与 `Esc` 只 `ball_hide()`，不退出；
- 答案按纯文本渲染（`white-space: pre-wrap`），不做主 SPA 的富文本/图片/工作流卡片。

**不再改** `front/index.html` 的布局：首版为紧凑模式加的 `IS_BALL`、`.ball-mode`、拖拽条已回退；该文件只保留三处登录态回报（`doLogin` / `doLogout` / `onMounted`）。

#### 3.5 与主壳的集成（`front/desktop/app.py` 改动点）

| 行段 | 改动 |
|---|---|
| `:1384-1390` | 主窗 URL 不变；面板窗改为加载 `/front/desktop/ball.html` |
| `:1402-1405` 之后 | 追加 `panel = webview.create_window(... hidden=True ...)` |
| `webview.start(...)` 之前（`:1506`） | 启动球线程 `BallWindow(on_click=..., on_menu=...)`；单例；起不来只打日志 |
| 托盘菜单 `:855-867` | 追加 `显示/隐藏悬浮球`（带勾选态）；球窗不参与「显示主窗口」 |
| `on_quit` `:1436` | 先 `ball.close()`（投递 `WM_CLOSE` + `Join` 1s），再退出 |
| `on_closing` `:1450-1466` | 不改（现状即收进托盘） |
| `DesktopApi` | 新增 `ball_state(state)`：页面把 idle/busy/alert 回传给球线程；新增 `ball_toggle()` 供页面快捷键调用 |

跨线程依据：pywebview 的 WinForms 后端对窗口操作做了线程编组（`winforms.py:489-500` 的 `load_url` / `hide` / `show` 都先 `self.Invoke(...)`），球线程可直接调用面板的 `show()/hide()/move()`。

#### 3.6 配置与持久化

- `utils/settings.py` 的 `SPECS` 增五项：`BALL_ENABLED`（switch，默认 0）、`BALL_SIZE`（select 48/64/80，默认 64）、`BALL_OPACITY`（number 60-100，默认 100）、`BALL_HOTKEY`（text，默认 `Ctrl+Alt+Space`）、`BALL_ON_TOP`（switch，默认 1）。都是开关/参数 → 落 `app_settings`，不进 `.env`，改完即生效。
- 几何落 `data/ball_state.json`（运行时数据，不入库）：`{"monitor": 0, "x": <逻辑>, "y": <逻辑>, "visible": true}`；只由球线程读写。
- 热键：球线程内 `RegisterHotKey(NULL, 1, MOD_CONTROL|MOD_ALT, VK_SPACE)`，`WM_HOTKEY` → 切换面板；注册失败（组合键被占）只记日志，托盘入口仍可用。

#### 3.7 降级路径

| 情况 | 行为 |
|---|---|
| 托盘不可用（缺 pystray） | 球仍可开；主窗点 X 直接退出（现有逻辑同样放行） |
| 球线程起不来 | 打日志、托盘不出现球项，主窗功能不受影响 |
| 面板页加载失败 | 面板内显示极简错误页 + 重试按钮，不阻塞球 |
| 后端未就绪时点球 | 面板显示既有 loading 页，就绪后再导航（与主窗同一套流程） |

#### 3.8 测试与验收判据

- **单元（`tests/unit/test_ball_geometry.py`）**：圆内/圆外命中判定、面板方位与夹紧算法、倍率换算、`ball_state.json` 读写 —— 纯函数，零窗口。
- **真机（`tests/live/desktop_ball_e2e.py`）**：起壳 → 断言存在对应类名的顶层窗口、`WS_EX_TOPMOST` 置位、尺寸等于设置值、圆外 `WM_NCHITTEST` 返回 `HTTRANSPARENT`、单击后面板可见。
- **客户端实测（人工）**：球浮于所有窗口之上；拖动后落点被记住；点开/收起顺畅；球里完成一轮问答并看到流式；关主窗（收托盘）后球仍在；托盘「退出」后无残留进程。

## 02 悬浮球（屏幕共享）

> 状态：实现中（2026-11-09 开工；方案见本段 ③，裁定见 `Verdict/02-悬浮球-屏幕共享.md`）

### ① 应对什么问题

Agent 的「看」有边界，看不到用户自己的屏幕：

- 现有三条取信息的路是联网检索、进站抓取（browser-use）、账号资料与知识库，**没有一条能看本机屏幕**；
- 现有图片通路只接受用户手工上传/粘贴的图：`tools/chat_images.py`（magic bytes 校验 → 压缩 → 账号隔离落盘 → 本轮限定），`api/server.py:902-934` 是本轮贴图装配；
- 全仓无屏幕捕获代码：装机依赖里 mss / dxcam / pyautogui / pywinauto / opencv 均未安装（pywin32 312 已在）；
- 于是「屏幕上这个报错是什么意思」「这张表第三列怎么填」这类问题，用户只能打字描述，或手工截图存文件再上传，多步且易失真。

### ② 功能

做完之后，聊天页多一个**「computer use」模式开关**，**按会话**记忆：

- 只有开关打开，agent 才拥有「看屏幕」的能力：关闭时不注入提示词、工具直接拒绝、界面没有截图入口；
- 打开后由 agent 自行决定何时截、截几张（翻页类任务就是一页一张），用户也可以在该轮用自然语言限定张数；
- 每次截图是整屏一帧，物理像素交付，长边压到 1456、JPEG q85；
- 主窗与面板不入镜（窗口排除属性），悬浮球在共享期间隐藏；
- 截图只活在内存，本轮结束即丢弃，聊天记录里不留画面。

### ③ 实现功能的技术方案

**能力形态**：新增内置工具 `screen_capture`，与 `query_kb`、`invoke_tool` 同级注册进主 Agent；是否放行由**本轮开关**决定（contextvar 形态，与 `utils/write_auth.py` 同构），不让模型自己判断。

**开关与模式分离**

| 项 | 口径 |
|---|---|
| 存放 | 前端 `localStorage` 键 `zx_cu_sessions`，形如 `{"<thread_id>": true}` |
| 默认 | 新建会话为关闭；切回旧会话按该会话的记忆恢复 |
| 同步 | 两窗监听 `storage` 事件，与会话列表同步同一套机制 |
| 请求 | `/api/chat` 增 `computer_use=1`；后端校验 `thread_id` 属于当前账号后才认 |
| 关闭时 | 不注入提示词、工具拒绝、界面无入口——能力「不存在」 |

**进程内数据流**

```
前端开关（按会话） → POST /api/chat?computer_use=1
   → _run_agent(computer_use=True) → set_cu_mode(True)（contextvar，随本轮任务传播）
   → build_request_context 注入一段「本轮可看屏幕」的说明（未开启时这段不存在）
   → 模型调用 screen_capture(reason, monitor?)
        → 外壳：设窗口排除 + 藏球 → mss 抓屏 → 无论成败都还原
        → 压到长边 1456 / JPEG q85 → 返回图片块 + capture_id + 屏幕矩形 + 缩放比
   → 模型据图继续推理或给出回答
   → 本轮结束：set_cu_mode(False)、清理内存帧、球恢复可见
```

**工具契约**（机械细节只写在 `@tool` 文档串里）

- 入参：`reason`（一句话说明为什么截，落进气泡回执）、`monitor`（缺省为全部显示器合成一帧，多屏时给索引）；
- 出参：图片块 + `capture_id`（单调递增）、`screen_rect`（物理像素原点与宽高）、`scale`（模型看到的图 ÷ 物理像素）、`ts`；
- 闸门：未开启 → 直接返回「本轮未开启屏幕共享」；超过 `SCREEN_MAX_SHOTS_PER_TURN` → 返回「本轮次数已用完」；同屏哈希相同 → 复用上一帧；
- 失败：mss 缺失 / 抓屏异常 → 返回人话错误，不抛栈。

**采集与压缩**

- `mss` 10.2.0（`uv pip install`，解析只多一个包）；
- 物理像素采集，压缩长边 1456、JPEG q85（本机实测约 200 KB / 130 ms）；
- 单帧与压缩合计约 200 ms；不走 GPU 采集，避免多一个重依赖。

**自身窗口排除**

- 抓图走外壳的本地接口：**抓之前**给主窗与面板设 `WDA_EXCLUDEFROMCAPTURE`、把球藏起来，抓完立刻还原；
- 不能常驻开排除 —— 那会把用户自己的截图（Win+Shift+S、PrintScreen）也屏蔽掉（裁定第 8 条）；
- 悬浮球是分层窗，对该属性「假成功」（实测返回成功但截图里仍在），只能靠隐藏；隐藏同样只在抓图那 ~0.2 秒；
- 还原放在 `finally` 里，抓图失败也不会留一个被排除或被藏起来的窗口。

**图片如何到模型**

- 首选甲：`screen_capture` 返回带 `image_url` 块的 `ToolMessage`；
- 实现第一步先写 30 行验证 deepagents 是否透传图片块；
- 若不透传，退丙：本轮开场由 harness 截一张、走现有 `images=` 通道（`agent/build_context.py:336` 的 `_ci.build_content`），工具退化为「提示下一轮再截」。

**上下文治理**

- 一轮内只有**最近一帧**以图片形式留在上下文，更早的帧降级为一行文字（帧号 + 前台窗口标题 + 时间）；
- 图片本体不进历史（沿用现有「只喂本轮」口径）；
- 上限默认 6 张（1~10 可配），超过即拒绝抓屏。

**前端改动**

- `front/index.html`：聊天工具栏加「computer use」开关，按 `thread_id` 读写 `zx_cu_sessions`；开启时在输入框上方给一条常驻提示；

## 03 悬浮球（屏幕控制）

> 状态：已收官（2026-11-10，真机三轮通过）；裁定见 `Verdict/03-悬浮球-屏幕控制.md`，取证见 `research/03-悬浮球-屏幕控制.md`，实现记录与带读见 `Done/`

### ① 应对什么问题

Agent 的手只伸到自己的沙箱，碰不到桌面上其它应用：

- 现在能改的只有两处：自己工作目录（内置写工具 create/edit/delete）与自配来源的写能力（CLI/API/MCP，凭「/」授权，`utils/write_auth.py` 的 selected ContextVar）；
- 全仓无输入注入代码：装机依赖里 pyautogui / pydirectinput / pywinauto / comtypes / uiautomation 均未安装；
- 用户的实际诉求（2026-10-30 原话）是「打开QQ,给xx发消息'xxx'」这类**跨应用操作**，以及把它上升为「模拟 window 用户操作电脑」。

### ② 功能

做完之后，computer use 开关之上多一档**「屏幕控制」**（按会话开启）：

- 动作面本步只做两类：**鼠标点击**（左键单击/双击）与**文字输入**（中文走剪贴板粘贴）；其余动作（右键、滚轮、拖选、组合键）留后续 4.x；
- 确认制走 `pending_safety_checks` 模式：普通动作自动执行、回执写明做了什么；不可逆动作（发送、删除）模型先复述再动；用户随时可中断；
- 每轮动作有上限（默认 20），防止失控循环；
- 只允许对**设置页勾选的白名单进程**动作（双重判定：前台窗口 + 落点窗口），名单为空时全部拒绝；
- 动作全过程留审计（只追加 JSONL，记元数据不含屏幕内容）。

### ③ 实现功能的技术方案

**能力形态**：`screen_capture`（02 已有）之外新增两个内置工具——`mouse_click` 与 `type_text`；放行由两档开关决定：`computer_use`（只看）与 `allow_control`（看+动）。`agent/cu_middleware.py` 按档位摘工具：只开「看」时，控制工具从模型工具表里剥掉（与 02 的「能力不存在」口径一致）。

**开关与请求**

| 项 | 口径 |
|---|---|
| 只看 | `computer_use=1`（02 已实现） |
| 看 + 动 | `computer_use=1&allow_control=1`；前端按 `thread_id` 记忆（`zx_cu_control` 键），两窗 storage 事件同步 |
| 后端校验 | 会话归属（同 02）；`cu_mode.begin_turn(on, control)` |
| 关闭时 | 控制工具被中间件摘掉、工具自身拒绝、界面无入口 |

**工具契约**

```
mouse_click(x, y, capture_id, reason, double=False)
type_text(text, capture_id, reason)
```

- `x, y` 是**图上坐标**；换算 `物理坐标 = 图上坐标 ÷ scale + screen_rect 原点`，`scale`/`screen_rect`/`last_cid` 都在 `cu_mode` 轮内状态里；
- `capture_id` 必须等于最近一帧，否则拒绝（「屏幕已变化，请重新截图」）——防看旧帧点新界面；
- `reason` 落审计与回执；
- `type_text` 全量走「写剪贴板 → Ctrl+V」，不经 IME；注入前后保存/恢复剪贴板原内容。

**注入层**（`tools/_runtime/cu_input.py`，执行器与面板共用）

- 鼠标：`SetCursorPos`（物理像素）→ `SendInput(MOUSEEVENTF_LEFTDOWN/UP)`；双击连发两次、间隔 ≤ 500ms 系统阈值；
- 键盘：`SendInput(KEYBDINPUT)` 发 `Ctrl` down → `V` down/up → `Ctrl` up；
- 剪贴板：ctypes 直调 `OpenClipboard`/`EmptyClipboard`/`SetClipboardData(CF_UNICODETEXT)`/`CloseClipboard`（约 30 行，零依赖）；
- 每次注入后固定等待（内部机制，非工具），再取前台窗口标题做回执与审计。

**白名单（双重判定，默认最严）**

| 判定 | 实现 |
|---|---|
| ① 前台窗口 | `GetForegroundWindow()` → `QueryFullProcessImageNameW` 取进程文件名，小写后在名单内 |
| ② 落点窗口 | `WindowFromPoint(物理坐标)` → `GetAncestor(GA_ROOT)` 取顶层属主 → 同上判进程名 |

- 名单存设置项 `CU_WHITELIST`（textarea，每行一个进程名，不区分大小写、可带可不带 `.exe`）；
- **名单为空 = 全部拒绝**；两项判定任一失败即拒绝，返回「前台窗口（xxx.exe）不在屏幕控制白名单」；
- 设置页（`front/index.html` 设置组）加白名单 textarea 与 `CU_MAX_ACTIONS_PER_TURN` 数字项。

**动作闸门（顺序执行）**

1. 本轮 `control=True`？（中间件已摘工具，工具内再兜底一次）
2. `actions < CU_MAX_ACTIONS_PER_TURN`（默认 20，1~50）？
3. `capture_id == last_cid`？
4. 白名单双重判定通过？
5. 注入 → `actions += 1` → 审计 → 回执（做了什么 + 落点 + 注入后前台窗口标题）。

**审计**：`data/audit/cu_actions.jsonl` 只追加：`{ts, thread_id, capture_id, action, x, y, text_len, fg_process}`。不含屏幕内容（与 02「截图纯内存」不冲突）。

**前端改动**

- `front/index.html` 与 `front/desktop/ball.html`：computer use 开关旁加一档「屏幕控制」子开关（仅当上一档已开时可用）；请求带 `allow_control=1`；两窗 storage 同步；
- 设置页加白名单与上限两个表单项；
- 回执气泡里展示模型 `reason`（做了什么）与注入后前台窗口标题。

**后端改动**

| 文件 | 改动 |
|---|---|
| `tools/_runtime/cu_input.py` | 新增：SendInput 封装、剪贴板、白名单判定、审计 |
| `tools/control_tool.py` | 新增：`mouse_click` / `type_text` 两个 `@tool` |
| `utils/cu_mode.py` | `CuTurn` 增 `control/actions/last_scale/last_rect` |
| `utils/settings.py` | 增 `CU_WHITELIST`（textarea）、`CU_MAX_ACTIONS_PER_TURN`（number，默认 20） |
| `api/server.py` | `/api/chat` 增 `allow_control`；`_run_agent` 传入 |
| `agent/cu_middleware.py` | 按档位摘工具：只看时剥掉控制工具 |
| `agent/build_context.py` | `allow_control` 时注入一段控制能力说明（关闭时不出现） |

**降级与错误**

| 场景 | 行为 |
|---|---|
| 未开 allow_control | 工具不存在于工具表（中间件摘除）；若仍被调用（兜底）返回「本轮未开启屏幕控制」 |
| capture_id 过期 | 返回「屏幕已变化（当前帧 #N），请先重新截图」 |
| 超动作上限 | 返回「本轮动作次数已用完（上限 N）」 |
| 白名单不匹配 | 返回「前台窗口（xxx.exe）不在屏幕控制白名单，请在设置页添加或切换窗口」 |
| 白名单为空 | 同上，并提示「当前白名单为空，所有动作都会被拒绝」 |
| SendInput 失败 | 返回人话错误，不抛栈 |

**测试与验收**

- 单测：坐标换算（scale/原点/多屏负坐标）、闸门顺序（control→次数→capture_id→白名单）、白名单判定（前台与落点两道）、审计行格式、剪贴板保存/恢复；
- 真机（`tests/live/`，不碰聊天软件）：记事本输入 hello → 读回断言；点已知坐标按钮 → 断言状态变化；白名单不含 notepad.exe 时同一动作被拒；
- 真机（用户侧）：两档开关的组合行为、中断即时性、审计文件增长。

**明确不做**

- 右键、滚轮、拖选、组合键（后续 4.x）；
- 后台静默操作、锁屏运行、批量/定时/无人值守触达；
- 绕过平台审核的路径；
- 截图与屏幕内容入审计或历史。

## 04 浮窗球前端美学设计

> 状态：占位（待调研，等待口令进入调研期）

### ① 应对什么问题

悬浮球与它的迷你面板，功能已经跑通（01 建壳、02 给眼、03 给手），但**外观是工程实现顺手带出来的**：

- 球是三态 PNG + Win32 分层窗口，尺寸、圆角、描边、阴影都是为了「能显示、能拖动」定的，没有经过视觉设计；
- 迷你面板是**独立 HTML 页**（`front/desktop/ball.html`），配色与间距自成一套，和主窗（`front/index.html`）的设计语言并不统一；
- 状态表达弱：思考中 / 已完成 / 出错 / 需要确认，目前只在文案和托盘标题上有区别；
- 屏幕共享与控制两个开关，是两个贴着 tooltip 的图标，缺少「当前这一轮 agent 正在看/正在动手」的持续可见状态。

后果是：功能在，但用户不会觉得它「好看、想用」，也不会一眼看出 agent 此刻在干什么。

### ② 功能（意向，调研后细化）

- 球的形态、材质、动效（悬浮、悬停、拖拽、呼吸/脉冲）与状态可视化；
- 迷你面板的视觉体系：配色、字号层级、气泡、输入区、会话切换，与主窗统一又不喧宾夺主；
- agent 状态的可视化语言（看屏中、操作中、等待确认、完成、出错）；
- 与小尺寸约束的平衡：球只有 48~64 逻辑像素，面板宽 380，能承载多少信息。
