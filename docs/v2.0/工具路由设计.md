# 工具路由设计 · 智能体「该用哪个工具、怎么让它想起来」的完整链路

> **文档定位**：这是一份**跨里程碑的设计说明**（不是某一期的计划书）。
> `docs/v2.0/M5工具智能路由.md`（M5a 计划 + 实测）与 `docs/v2.0/M5b工具检索路由.md`（M5b 计划 + 实测）
> 记录的是「当时怎么规划、怎么验」；本文回答的是**「现在这套东西到底是怎么运转的」**——
> 从一张数据库表到模型眼前的那段提示词，每个文件负责哪一环、为什么这么切、改哪儿会牵动哪儿。
>
> **一句话概括**：内置工具靠 **schema 静态挂载**（模型天生看得见），用户自配的第三方 CLI 只能靠
> **提示词动态注入**（命令清单随账号变化，塞不进 schema）——工具一多提示词就爆，于是有了**能力池 + 路由器**：
> 问一句「我最近在读什么书」，只把 `weread` 的能力卡完整注入，其余工具各留一行名字。

**三条心法（读完再回看一遍）**

1. **路由只管「说不清的那一段」**。能用 schema 说清的工具（`query_kb`、`internet_search`…）根本不需要路由——它们的名字和参数是静态的，模型每次请求都看得见。只有**用户自己配的第三方 CLI** 是动态的：可执行名、子命令、只读清单都随账号变，无法进 schema，只能变成提示词里的一段文字 → 才有「工具一多，这段文字怎么办」的问题。
2. **不确定就回退全量，绝不猜**。整套设计是 fail-safe：任何一处（空池 / 向量挂了 / 置信不够 / 代码抛异常）都退回 M5a 的**全量简报**。回退的代价只是「没省 token」，猜错的代价是「模型拿着错工具的说明书去答用户的问题」。
3. **未命中的工具也留一行名字**。路由是概率判断，总会有没命中的时候；把工具从提示词里彻底藏掉，等于让「那一次没命中」的问题**永久无解**（用户配了也白配）。

## 二、问题定义：为什么需要「工具路由」

### 2.1 这个项目里其实有**两套**工具机制

| 机制 | 谁在用 | 模型怎么知道它存在 | 需要路由吗 |
| --- | --- | --- | --- |
| **静态挂载** | 内置工具与子智能体：`read_agent_doc` / `write_agent_doc` / `list_agent_docs` / `query_kb` / `run_shell_command`；子 Agent `network_search_agent`（`internet_search`）、`db_agent`（公司库 3 工具）、`personal_agent`（个人库 3 工具） | `create_deep_agent(tools=[...], subagents=[...])` 把工具 schema 交给框架，**每次请求都随请求发给模型** | **不需要**。工具名、参数、描述都是静态的，函数调用协议本身就是最强路由信号 |
| **动态注入** | 用户自配的第三方 CLI（`weread` / `lark-cli` / `wechat-cli` / `bili`…） | 只能写进**系统提示词的文本区块**（【可用命令行工具（用户自配的 CLI，只读）】），因为「这个账号装了哪些 CLI、放行了哪些子命令」是运行时才知道的 | **需要**，且这正是本文的主题 |

**关键推论**：路由不是「给所有工具做检索」，而是**「给那段塞不进 schema 的文本做预算管理」**。
所以 `run_shell_command` 这个工具本身是静态挂载的、永远可见；路由决定的是**它说明书里写哪些 CLI、写多细**。

### 2.2 三重压力（可复现，不是假想）

| 压力 | 实测/现象 | 后果 |
| --- | --- | --- |
| **预算被一条长描述吃光** | 3 个 CLI 时，某条 787 字的 `abilities` 把第 3 个工具整个挤出简报 | 排在后面的工具**从提示词里隐身** → 用户配了等于没配 |
| **弱模型不会自己去找** | free 模型下，用户问「我最近在读什么书」，模型不知道该调 `weread`；连「有没有这个工具」都不查 | 路由失败 = 用户拿不到自己账号里的私有数据，于是**编造**或**跑去网搜** |
| **规模一涨，平铺就崩** | M5a 的做法是「所有工具一律平铺，装不下就降级成一行」 | 工具越多每份额度越小，路由精度随规模**下降**——注解里的原话：这是**分配器**，不是**选择器** |

**M5a 已经证明了「描述写法」的收益**：同一批问句，命令名形态（`shelf recent` 这种）命中 **2/10**，
改写成用户语言的能力描述（`我最近在读什么书 → shelf recent`）后 **10 正例全中**。
M5b 要解决的是它的下一个瓶颈：**工具变多之后，这段「有用的文字」放不下了**。

### 2.3 演进三层（谁解决什么，别混）

| 层 | 里程碑 | 一句话 | 落点 |
| --- | --- | --- | --- |
| ① 让模型**知道有**这个工具 | M4c | 用户登记 CLI + 只读清单 → 简报注入 → 模型知道「本机有这个命令」 | `tools/cli_registry.py` `agent_brief()` |
| ② 让模型在你说**人话**时想起它 | M5a | 能力描述（触发词 + 说法→命令映射）+ few-shot 示例 | 同上 + `ability_examples()` |
| ③ 工具**多到放不下**时选对 | M5b | 能力池 + 相关性路由 + 分层注入 + 兜底 | `tools/capability_pool.py` + `tools/tool_router.py` |

## 三、总体架构与数据流

```
                          ┌───────────────────────── 用户侧（配置一次，长期有效）─────────────────────────┐
  前端「🧩 自定义 CLI」页  →  POST /api/cli/save|status|delete  →  tools/cli_registry.py::save_cli/set_state/delete_cli
  （static/index.html）                （api/server.py）                    │
                                                                          ├─→ user_clis 表（唯一事实源：可执行名/只读清单/能力描述/状态）
                                                                          └─→ capability_pool.sync_cli_entry()
                                                                                 ├─ 写 tool_capabilities 快照
                                                                                 └─ bump_pool_version()   ← 只打版本，不碰向量（否则界面冻住）

                          ┌──────────────────────── 提问侧（每一轮都跑）────────────────────────┐
  用户提问 ─→ api/server.py::_run_agent
                     │
                     ├─ tool_router.route_tools(account_id, question)
                     │        │
                     │        ├─ capability_pool.pool_entries(account_id)      ← 从来源适配器**派生**当前池
                     │        │        └─ 空/太短/无提问 → 快路径：直接 agent_brief（= M5a 行为，逐字一致）
                     │        │
                     │        ├─ capability_pool.route_scores(account_id, q)   ← 稠密信号
                     │        │        └─ ensure_vectors_fresh() 版本落后才重建 bge 向量（惰性）
                     │        │             └─ Chroma collection `tool_route_{account_id}`（账号隔离）
                     │        │
                     │        ├─ tool_router.decide()  词法信号 + RRF 融合 + z 分数 + 置信判定（纯函数）
                     │        │        不置信 → 回退全量简报
                     │        │
                     │        └─ _render_routed()  完整卡(≤3) / 紧凑行(≤2) / 仅名称(其余)
                     │
                     ├─ agent/build_context.py::build_request_context(cli_brief=…)
                     │        └─ compose_dynamic_prompt() → 动态 SystemMessage（人格 + 记忆 + 能力区块）
                     │
                     └─ agent.invoke(messages)  → 模型看到的工具清单 = 静态 schema + 这段文本
                              │
                              └─ 模型调 run_shell_command(command="weread", argv=[…])
                                       └─ tools/shell_executor.py → tools/_runtime/shell_runtime.py
                                              ├─ 七道闸（白名单/无 shell/路径/命令级/资源/审计/只读闸）
                                              └─ data/audit/commands.jsonl（**调用事实，验收的唯一凭据**）
```

**一次提问的生命周期（编号对应上图的环节）**

1. 用户在聊天框问「我最近在读什么书」→ `POST /api/chat` → `_run_agent(account_id, question, …)`。
2. `route_tools(account_id, question)`：先 `pool_entries()` 拿该账号当前池（只含「已接入 + 清单非空」的 CLI）。
3. 池 ≤ `FAST_PATH_MAX`(4) → 直接返回 `agent_brief()` 结果，`mode="full"`（**与 M5a 逐字一致**，叠加层不改变小规模行为）。
4. 池更大 → `route_scores()` 取稠密相似度（必要时按版本惰性重建向量）→ 词法分 → RRF 融合 → 置信判定。
5. 置信不够 → `mode="full"`（回退）；置信 → `_render_routed()` 分层出文本，`mode="routed"`，并记录 `hits`。
6. `_run_agent` 把 `brief + examples` 拼成 `cli_brief`，交给 `build_request_context()`。
7. 装配管线把「人格 / 记忆 / 能力区块」拼成一条动态 `SystemMessage` 放在 `messages[0]`（截断时被保护，永不丢）。
8. 模型据此决定是否调 `run_shell_command`；真调用进审计日志，同时 `monitor.report_tool()` 把进度推到前端右栏。
9. 前端思考区还能看到 `（工具路由：8 个工具中命中 1 个完整能力卡）`——**路由行为对用户可见**。

## 四、数据层：单一事实源 + 快照 + 版本号

### 4.1 三张表（`tools/schema_personal.py:271~320`）

| 表 | 谁写 | 谁读 | 作用 |
| --- | --- | --- | --- |
| `user_clis` | `/api/cli/save`、`/status`、`/delete` | `cli_registry.list_clis()` | **唯一事实源**：可执行名、只读命令清单（JSON）、能力描述 `abilities`、状态 `state`、备注、外键 `REFERENCES accounts(id)` |
| `tool_capabilities` | `sync_cli_entry()` / `rebuild_pool()` | 目前只有测试与审计 | 池的**快照**：`(account_id, source, ref)` 唯一，存 name/keywords/abilities/invoke_hint/enabled + `updated_at` |
| `tool_pool_meta` | `bump_pool_version()` | `current_pool_version()` | 每账号一个 `pool_version` 计数——**缓存失效的唯一依据**（不用 TTL） |

> M5 还给 `user_clis` 加了 `abilities TEXT DEFAULT ''` 列，用 `PRAGMA table_info` 判断后**幂等 ALTER**，
> 老库（M4c 时期建的）不会因为缺列而整体 500。

### 4.2 「派生而非迁移」——为什么读来源表而不读快照表

`pool_entries()` 每次都**直接调来源适配器**（现在只有 CLI 一个），完全不碰 `tool_capabilities`：

- **一致性**：用户在面板里改完能力描述，下一次提问的池**立刻**是新内容，不存在「两张表之间有个不同步窗口」。
- **零迁移**：CLI 的能力描述本来就在 `user_clis.abilities`，不搬家——M5b 对存量数据零改动。
- **快照表的定位**：将来 API/MCP 的来源表若读取昂贵（网络/鉴权），可以切成「读快照 + 版本号失效」，
  **`pool_entries()` 的签名不用变**（这是当初留的退路）。

### 4.3 版本号与惰性向量（这条是被实测逼出来的）

```
save_cli()  →  sync_cli_entry()  →  写 tool_capabilities 快照 + bump_pool_version()
                                   ↑ 到这里就结束，**不碰向量**
route 时刻  →  ensure_vectors_fresh()  →  比对 (池版本 vs chroma_route/_pool_version.json)
                                         不一致才 sync_vectors()（真正加载 bge）
```

**为什么必须惰性**：向量同步要加载 bge 模型，首次 **1~3 分钟**。原先写在配置写入路径上，
用户点一次「保存」界面就冻住 1~3 分钟（实测数字），体验上等于卡死。
改成「写入只落库 + 打版本，重建推迟到真正要路由的那一刻」后，保存耗时 **0.18s**。

**容错口径**：`sync_cli_entry()` 全函数包在 `try/except` 里、失败只打印——
**池坏了绝不允许影响 CLI 配置本身的写入**（配置是用户数据，池只是加速层）。

### 4.4 账号隔离

| 东西 | 隔离方式 | 说明 |
| --- | --- | --- |
| 池条目 | `user_clis` / `tool_capabilities` 都带 `account_id` | 每个账号只看得到自己配的 CLI |
| 池版本 | `tool_pool_meta(account_id)` | 每账号独立计数 |
| 向量 | Chroma collection **`tool_route_{account_id}`** + 目录 `rag_knowledge/db/{username}/chroma_route/` | 与 M3 知识库 `kb_user_*` 完全分离，互不污染；collection 名只用 account_id，因为 **chroma 只接受 `[a-zA-Z0-9._-]`，中文 username 会直接报 `InvalidArgumentError`** |
| 沙箱 | `data/sandbox/{username}/` | 由 `shell_executor._owner()` 从 `get_owner_context()` 取 |

## 五、能力池：`tools/capability_pool.py`（488 行）

### 5.1 `CapabilityEntry` —— 路由器唯一认得的形状

```python
@dataclass(frozen=True)
class CapabilityEntry:
    source: str        # 'cli' | 'api' | 'mcp'（SOURCES 元组）
    ref: str           # 来源内唯一标识：CLI 就是可执行名
    name: str          # 展示名
    keywords: str      # 路由信号（从 abilities 里解析出的「关键词：」那一行）
    abilities: str     # 用户语言的能力描述原文
    invoke_hint: str   # 调用形式提示
    enabled: bool      # 未接入 / 清单为空 → False（不进池，fail closed）
    rules: tuple       # CLI 专有：只读命令路径（渲染卡片用）
    invokable: bool    # 是否真的可被调用
```

**设计要点**

- `frozen=True`：条目是**值对象**，池每次从来源重算，不需要可变身份。
- `rules` / `invokable` 标注为「来源侧细节」：它们只服务渲染，**不进契约语义**——API/MCP 来源留空即可，
  路由器完全不需要知道「命令」这个概念（这就是接新来源时路由器一行不改的原因）。
- `ref` 是**来源内**唯一，跨来源靠 `source:ref` 组成主键（`"cli:weread"`）——日志、`hits`、Chroma id 全用它。

### 5.2 三种渲染形态（路由分层的「素材」）

同一个条目由路由器按相似度选择渲染深度，三种形态都是 `@property`（**纯函数、可单测**）：

| 形态 | 用在哪 | 真实文本（示意） |
| --- | --- | --- |
| `card_text` **完整能力卡** | 命中（前 3 名） | `- 微信读书（可执行名 \`weread\`）：用户问到下列任一场景时，**先用它取真实数据**（这是用户自己账号里的私有数据，网搜/知识库都拿不到）；不要改用别的工具顶替，也不要凭你自己的知识作答——\n  我在读/书评/书架…\n  共 12 条只读命令，例如 shelf recent / book progress / …` |
| `compact_text` **紧凑行** | 次要（第 4~5 名） | `- 微信读书（可执行名 \`weread\`）：共 12 条只读命令；关键词：我在读、书评、书架（截断 160 字）` |
| `nameonly_text` **仅名称** | 其余全部 | `- 微信读书（可执行名 \`weread\`）：共 12 条只读命令` |

卡片的措辞不是装饰，是**提示词工程**：明确写「先用它取真实数据 / 不要改用别的工具顶替 / 不要凭你自己的知识作答」——
指向的就是 §2.2 那两条失败模式（跑去网搜、凭知识编造）。

### 5.3 适配器：接新来源只加一行

```python
_ADAPTERS = {
    SOURCE_CLI: _entries_from_clis,
    # SOURCE_API: _entries_from_apis,   # M5b-3 实装后接入
    # SOURCE_MCP: _entries_from_mcps,   # M5b-4 实装后接入
}
```

- `cli_entry()` 是**纯函数**（吃 `list_clis()` 的一条 dict，吐一个条目），所以适配器逻辑可以脱离 DB 单测。

### 5.4 关键函数逐一带读

| 函数 | 干什么 | 读它时注意 |
| --- | --- | --- |
| `pool_entries(account_id, enabled_only=True)` | 从适配器派生当前池 | 去重（`source+ref`）、过滤 `enabled`、单来源容错 |
| `current_pool_version()` / `bump_pool_version()` | 读/递增池版本 | `ON CONFLICT DO UPDATE pool_version = pool_version + 1`（UPSERT，首次插入即 1） |
| `sync_vectors(entries)` | 把池条目向量化并写入 collection | **只对 content_hash 变过的条目重算**；来源里已消失的 id 会被删（stale 清理）；文本只含 name+keywords+abilities，**不含命令样例**（命令名会干扰语义匹配） |

| `route_scores(account_id, question)` | 稠密相似度 `{'source:ref': sim}` | cosine 空间 → `sim = max(0, 1 - distance)`；**任何异常返回 `{}`**（调用方退到词法路）；`col.count()` 为 0 也返回空 |

| `sync_cli_entry(account_id)` | CLI 写入口的增量同步钩子 | 只落库 + 打版本；完全容错 |
| `pool_summary(account_id)` | 条目数 / 各来源分布 / 版本 / refs 列表 | **目前只有测试与调试在用，还没接端点**（见 §11.5） |

## 六、路由器：`tools/tool_router.py`（262 行）

### 6.1 四级决策总览

```
route_tools(account_id, question)
   │
   ├─ ① 守卫：no_account / pool_error / empty_pool / 无提问 / force_full   → mode=full（原因写进 detail.reason）
   ├─ ② 快路径：len(pool) ≤ FAST_PATH_MAX(4)                              → mode=full（= M5a 逐字一致）
   ├─ ③ 路由器：route_scores（稠密）+ lexical_scores（词法）→ RRF 融合 → 置信判定
   │        └─ 不置信（z_top < 2.0 且 lex_top < 2）                        → mode=full（reason=low_confidence）
   └─ ④ 分层渲染：完整卡 ×3 → 紧凑行 ×2 → 仅名称 ×N（预算 1500 字逐级降级）
            └─ 任何异常                                                  → mode=full（reason=route_error:*）
```

**「快路径」为什么值得单独存在**：池只有 1~4 个工具时，全量简报本身就装得下，
再跑一次 embedding + 融合纯属浪费（延迟 + 一次模型加载）；而且那条路径与 M5a **逐字一致**，
意味着「M5b 是叠加层，不改小规模行为」这件事可以被断言钉死（`tests/m5b_router_e2e.py` 第 1 组）。

### 6.2 信号一：稠密向量

`capability_pool.route_scores()` 把问句 embed 后查 `tool_route_{account_id}`，
返回每个条目的余弦相似度（`n_results = min(col.count, 50)`，避免小池查询越界）。

### 6.3 信号二：词法（中文短问句的救命信号）

```python
lexical_scores(question, entries)
    # ① 短语命中：条目 keywords 行切出的短语（≥2 字）出现在问句里 → 每命中一条 +3 分
    # ② 字符 2-gram 重叠：问句与「名称 + 关键词」的二元组交集大小 → +1 分/个
```

- 中文没分词 → 用 2-gram 做粗粒度重叠；英文按词切（`_HAN` 负责切分）。
- 短语权重 3 倍：用户写的关键词本来就是短语（`我在读`、`书评`），命中一次就是强信号。

### 6.4 融合：RRF（**这里踩过一个真 bug**）

```python
_rrf(ranks)   # score += 1 / (RRF_K + rank)，RRF_K = 60（与 M3 检索栈同口径）
```

**必须剔除「无信号的排序器」**：词法全为 0 时，如果仍把「全是 0 的排序」当一路输入，
RRF 会给排在前面的条目（其实是插入顺序/字母序）加分，把向量路正确的 top1 顶掉。

> **实测现场**：问「我这个月读了多久」，向量 top1 明明是 `booky`，融合后却变成 `sched`。
> 现在 `decide()` 只在 `any(v > 0 for v in dense_vals)` / `any(v > 0 for v in lex_vals)` 时才把该路放进 `ranks`，
> 并且 `tests/m5b_router_e2e.py` 有一条单测专门固化这个场景。

### 6.5 置信判定：为什么是 z 分数 + 词法，而不是「相似度 > 0.5」

**阈值标定实测（`tests/_m5b_route_calib.py`，8 个异构工具池）**

| 量 | 实测值 | 含义 |
| --- | --- | --- |
| 中文短问句的余弦相似度绝对值 | 全落在 **0.53 ~ 0.70** | 与「命中与否」**无关**地都偏高 |
| top1 与 top2/top3 的差距 | 只有 **0.02 ~ 0.06** | 区分度极低 |
| 无关问句（「你是谁」）的 z 分数 | **1.57** | 噪声也能"看起来像" |
| 真命中的 z 分数 | **1.65 ~ 1.99** | 与噪声**重叠** |
| 词法命中 ≥ 2 的问句 | **100% 命中正确工具** | 最可靠的那一路 |

**结论与参数**

| 参数 | 值 | 依据 |
| --- | --- | --- |
| `Z_STRONG` | **2.0** | 取在噪声(1.57)与真命中(1.65~1.99)之上，让一切噪声回退全量 |
| `LEX_MIN` | **2** | 短语命中一次(3 分)即达标；2-gram 需两个重叠 |
| 判定式 | `confident = lex_top ≥ LEX_MIN or z_top ≥ Z_STRONG` | 或关系：**任一路给出明确信号就算置信** |

> ⚠️ **别改回绝对阈值**。设计初稿写的是 τ_high=0.50 / τ_low=0.35，实测直接证伪：
> 绝对阈值在中文短问句上会「全部命中」，分层形同虚设。
> 相对信号（z）的另一个好处是**随工具数增长自动放大**——池越大，均值和标准差越能拉开差距。

### 6.6 分层渲染与预算护栏

| 参数 | 值 | 作用 |
| --- | --- | --- |
| `MAX_FULL_CARDS` | 3 | 最多 3 张完整能力卡 |
| `COMPACT_TOP_N` | 2 | 第 4~5 名给紧凑行 |
| `TOTAL_BUDGET_CHARS` | 1500 | 注入总量上限（≈750 token） |

`_render_routed()` 逐条累加长度，`used + len(txt) > budget` 就往下退一档；
返回 `(文本, 完整卡 refs, 命中顺序)`——`full_refs` 既用于 §6.7 的示例过滤，也作为 `hits` 供审计/度量。

### 6.7 few-shot 示例过滤

M5a 的示例区块是「全量工具 × 全量映射」；路由模式下要**只保留命中工具的示例**——
非命中工具的示例既白占预算，又会**诱使模型乱调**。

> **又一个被测试逮住的真 bug**：`_filter_examples()` 原先按 `ln.startswith("- ")` 判断「这是示例行」，
> 而示例行的真实格式是 `用户问到「…」→ run_shell_command(command="…", argv=[…])`，**根本不以 `- ` 开头**
> → 过滤形同虚设（路由后仍会看到别的工具的命令）。现在按 `run_shell_command(` / `command=` 判断，
> 并且「过滤后只剩引导语、没有一条示例」时**整段丢掉**（空标题没意义）。

### 6.8 兜底矩阵（fail-safe 的全部触发点）

| 触发条件 | `mode` | `detail.reason` | 行为 |
| --- | --- | --- | --- |
| 没有 account_id | full | `no_account` | 全量简报（未登录场景） |
| 池读取抛异常 | full | `pool_error:<类型>` | 全量简报 |
| 池为空 | full | `empty_pool` | 空简报（没配 CLI 的用户零开销） |
| 提问为空 / `force_full=True` | full | `fast_path` | 全量简报 |
| 池 ≤ 4 | full | `fast_path` | 全量简报（= M5a 逐字一致） |
| 向量不可用（bge 挂了/collection 空） | 仍可 routed | — | 走词法路；两路都没信号 → `low_confidence` |
| 置信不足 | full | `low_confidence` | 全量简报（**保守：宁可多注入，不可猜错**） |
| 路由过程抛异常 | full | `route_error:<类型>` | 全量简报 + `detail.error` |

**`mode` 与 `hits` 是观测面**：`_run_agent` 据此在思考区打「（工具路由：N 个工具中命中 M 个完整能力卡）」。

**★ 改写纪律：机械细节可以搬走，「信念锚」必须留下（实测）**。重排时最容易犯的错，是把下面三句当成"啰嗦的重复说明"一起删掉——它们不是说明，是**让模型敢去调工具的条件性强度要求**：

| 信念锚 | 缺了它会怎样 |
| --- | --- |
| ① 「本区块出现 = 用户本机**确实装了**这些 CLI 并已放行只读命令」 | 模型怀疑工具是否真实存在，把清单当背景资料读 |
| ② 「问题落在能力描述覆盖的领域时**优先调用**它取真实数据」 | "优先"丢掉后退化成"需要时才用"，问句一模糊就不调 |
| ③ 「不要在没有任何工具返回的情况下声称该命令不可用／未登记」 | 模型用一句免责声明代替调用 |

**★ 同日 A/B（2026-09-24 完成）——这条经验值一个完整实验**：把三句话随机械细节一起搬走后，`tests/m5_probe_e2e.py`（10 条自然语言 → 期望命令）得 **5/10**，补回锚后重测 **4/10**，看着像真回归（两轮失败集合还不一样）。于是做了同日 A/B：把提示词与注入块**临时切回改写前版本**再跑一次 ——

| 臂 | 提示词 | 正例首调命中 | 反例 | 耗时 |
| --- | --- | --- | --- | --- |
| A | 改写前（`git show HEAD:`，已核对逐字旧版） | **5/10** | 3/3 | 476s |
| B | 改写后（当前版） | **6/10** | 3/3 | 417s |

两臂差 1 条（判据：差 ≥3 才算信号）→ **掉分与本次改写无关**；历史基线（另一天）9~10/10 与今天 5~6/10 的差距是**模型侧行为漂移**。两臂**失败的是同 4 条问句**（「帮我找几本讲降噪耳机的书」「《白夜行》这本书讲了什么」「《白夜行》的评价怎么样」「帮我搜一下《认知觉醒》这本书」），都是模型**先去委派网搜**（A 臂 15 次 / B 臂 26 次委派），审计日志里 CLI 调用（`notes notebooks`、`book info`）反而是**后补**的——即当天模型的动作顺序变了（web-first），不是"想不起工具"。**方法论结论**：自然语言探针是**随机**的，单轮或多轮低分都不构成回归证据，**必须同日 A/B** 才能归因；跑之前先确认外部搜索额度（本次两臂都用离线桩 `STUB_WEBSEARCH=1`，**零额度消耗**）。

**归属结论**：它们只在工具区块存在时才有意义（条件性强度要求）→ 归**注入块**（`agent/build_context.py`，已就地写明理由），不进静态提示词；静态提示词只保留跨工具的通则（一次一条、失败不重试、被拒如实转述）。**同时注意**：这类回归**单元测试全绿也照样发生**（本次 5 套单测 100% 通过、行为却塌了），所以提示词改写**只有真机探针能验收**。

### 8.3 动态工具 = 用户自配的 CLI（唯一被路由的对象）

- 只有 `state ∈ {installed, authed}`（即「本机确实装了」，`LIVE_STATES`）且**只读清单非空**的 CLI 才进池；
- 未登记 / 清单为空 → `enabled=False` → **不进池**（fail closed：不猜「能不能放行」）；
- 配置到执行的桥是 `cli_registry.allowed_for_agent(account_id)`：`shell_runtime.execute()` 用它组
  **动态白名单**（`{可执行名: {readonly, max_runtime, …}}`），命令名不在里面直接拒；
  在里面则再调 `readonly_verdict(args, dyn["readonly"])` 判子命令（`shell_runtime.py:419/440`）。
- **同一个 `readonly_verdict()` 也是 few-shot 示例的守门人**（`ability_examples()` 逐条校验）——
  一处判定、两处复用，所以「示例里出现的命令」与「运行时真能跑的命令」永远一致。

### 8.4 闸门：模型"调了"与"跑了"是两件事

`tools/_runtime/shell_runtime.py`（570 行）是 CLI 面板与 Agent **共用的同一套执行器**
（复用是关键，否则「Agent 能跑什么」和「用户在面板里能敲什么」会漂移）：

| # | 闸 | 内容 |
| --- | --- | --- |
| 1 | 白名单 | `ffmpeg/git/curl` 调外部程序；`ls/cat/grep/echo/pwd/mkdir` 用 Python 内建实现（Windows PATH 里缺这些命令）；**`python` 剔除** |
| 2 | 不开 shell | `subprocess` 参数永远是 list，不做字符串拼接（`; rm -rf /` 只是普通参数） |
| 3 | 参数级路径校验 | 所有像路径的参数 resolve 后必须在 `data/sandbox/{username}/` 内 |
| 4 | 命令级限制 | git 限安全子命令；curl 只 GET（禁 `-o/-d/-F/-T/-X/-H`）；ffmpeg 禁读文件协议与滤镜 |
| 5 | 资源上限 | 单命令超时（ffmpeg 300s / curl 30s / git 15s / 文件命令 5s）+ 输出 1MB 截断 |
| 6 | 审计 | 每次调用（**含被拒绝的**）追加 `data/audit/commands.jsonl` |
| 7 | **第三方 CLI 只读闸** | 已接入 CLI 进动态白名单，但**只有只读/查询子命令放行**；写操作与 `-o/--output/--download` 等落盘参数一律拒 |

`readonly_verdict(argv, rules)`（`tools/cli_registry.py:632`）是第 7 道闸的判定函数，
**被两处复用**：① 执行时放行判定；② `ability_examples()` 生成 few-shot 时逐条校验
（**示例里的命令必须真能跑**，否则等于教模型去撞墙）。

## 九、配置写入链路：用户怎么把一个工具「路由进来」

### 9.1 五个端点（`api/server.py`）

| 端点 | 作用 | 备注 |
| --- | --- | --- |
| `GET /api/cli/list` | 我的配置 + 预填示例（`TEMPLATES`）+ 本机检测结果 | 预填模板**不享受任何特权**：不进白名单、不参与判定 |
| `POST /api/cli/ability_draft` | 按「CLI 名称 + 只读清单」生成能力描述**草稿** | **只返回草稿、不落库**；清单为空直接 400（不调模型） |
| `POST /api/cli/save` | 新增/修改配置（局部更新「缺省即保留」） | 保存后触发 `sync_cli_entry()` |
| `POST /api/cli/status` | 登记/撤销「已接入」状态（含备注） | 状态决定 `enabled` → 决定进不进池 |
| `POST /api/cli/delete` | 删除配置（同时回收代跑权限） | 池里对应条目在下一次 `sync_cli_entry()` 被清掉 |

**还有一条迁移路径**：M4c 初版把「内置厂商」记在 `third_party_clis` 表里，M5 起改用 `user_clis`；
`cli_registry.migrate_legacy(account_id)` 把老表里 `state ∈ LIVE_STATES` 的记录搬过来（bin/名称/只读清单按模板补），
**幂等**且失败只返回 0（迁移不能影响主流程）。

### 9.2 保存一次配置的完整时序

```
用户在表单里填：可执行名 / 只读清单 / 能力描述（可点 ✨ 让 AI 起草）
   │
   ├─ 点「✨ 生成能力描述」→ /api/cli/ability_draft → customize.cli_ability_generate()
   │        └─ prompts.yml 的 ability_writer 小 Agent 生成「关键词 + 说法→命令」草稿
   │           （命令只能从用户给的只读清单里挑，原样不改）→ 回填表单，人可改
   │
   └─ 点「保存」→ /api/cli/save → cli_registry.save_cli()（字段校验：纯可执行名/清单条数/token 形状/长度上限）
            └─ capability_pool.sync_cli_entry(account_id)
                     ├─ 写 tool_capabilities 快照（增量 + 删多余）
                     └─ bump_pool_version()            ← 只打版本号
            （向量留到下一次路由时由 ensure_vectors_fresh() 重建：保存耗时 0.18s 而非 1~3 分钟）
```

### 9.3 校验规则（都在 `cli_registry.py`，安全底线）

- **可执行名只允许纯名字** `^[A-Za-z0-9][A-Za-z0-9._-]*$`——含 `/ \ :` 一律拒（否则等于把「执行任意程序」做成表单）；
- 只读清单：每行 ≤ `MAX_RULE_TOKENS`(8) 段、最多 `MAX_RULES`(40) 行，含 shell 元字符（`; | & > < \` $` 等）即拒；
- 能力描述 `MAX_ABILITIES`(2000) 默认上限（**超长 warn 而非截断**）+ `MAX_ABILITIES_HARD`(8000) 硬上限；
- 清单里的落盘类参数（`WRITE_FLAGS`：`-o/--output/--output-dir/--download/--out`）**即使写在清单里也不放行**（沙箱只读口径）。

## 十、扩展指引

### 10.1 加一个工具（用户侧，零代码）

目标：让 Agent 在你用人话提问时能想起用它。

1. 「技能与工具 → 🧩 自定义 CLI」里填：可执行名、安装/认证命令（照做一次）、只读命令清单；
2. 清单填完点「✨ 生成能力描述」拿草稿 → 改成人话（**关键词写你会怎么说**，映射写「说法→命令」）；
3. 状态点「已接入」→ 池里立刻出现该条目（版本号 +1）；
4. 首次提问时会触发一次向量重建（加载 bge，慢一次；之后走版本对齐，秒回）。

**写映射时最容易踩的坑**：需要前置 ID 的命令不能直调 → 映射写成**两步链**（`书评怎么样→book resolve 再 reviews list`），
示例取链上第一步。否则模型要么调报错命令、要么绕去网搜答你的私有数据。

### 10.2 加一种来源（API / MCP 适配器，v3.0 的事）

要动三个地方，**路由器一行不改**：

| # | 改哪 | 什么内容 |
| --- | --- | --- |
| 1 | `capability_pool._ADAPTERS` | 加一行 `SOURCE_API: _entries_from_apis` |
| 2 | 来源表 | 新增 `tool_api` / `tool_mcp`（带 `account_id`），存各自的可调用定义 |
| 3 | 适配器函数 | 把来源行转成 `CapabilityEntry`（`rules`/`invokable` 可留空） |

**顺带不用改的两处**：`purge_account()` 自省表结构（凡带 `account_id` 的表都清），
`SOURCES` 常量已预留 `api` / `mcp`。渲染形态若对 API 不适用（没有"命令数"），
应收敛到来源适配器内部（例如 `rules=()` 时 `card_text` 自动换成中性措辞），**别把来源分支写进路由器**。

### 10.3 加一个内置工具（静态路径）

在 `tools/` 里写 `@tool` 函数 → 加进 `api/server.py` 的 `create_deep_agent(tools=[...])`
（或某个子 Agent 的 `tools=[...]`）→ 在 `prompt/prompts.yml` 的主 Agent 段补一句使用纪律。
**这类工具不需要池、不需要路由**——如果它需要「随账号变化的说明书」，那才考虑纳入能力池。

### 10.4 调参纪律

**任何 `tool_router.py` 顶部的常量改动，都必须重跑 `tests/_m5b_route_calib.py` 标定 +
`tests/m5b_router_e2e.py` 回归**，并把新数字补回 §6.5/§6.6 的表。
理由：这套阈值是**实测标定**出来的（z=2.0 卡在噪声 1.57 与真命中 1.65~1.99 之间），
凭直觉改一个数，路由要么全回退（等于没做），要么开始猜错。

## 十一、验证与度量

### 11.1 判定铁律（沿 M4c 方法论，不采信模型自述）

| 铁律 | 防的是什么 |
| --- | --- |
| **只看第一次调用（首调）** | 装上命令桩后每条命令都能成功，模型会把清单挨个试；按「出现过即命中」判会虚高 |
| **真值配对取 `messages.tool_calls`** | 审计日志窗口会被**并发进程**写进同名调用污染（实测踩过），会话级真值才准 |
| **真桩工具** | 每个可执行名都装一个能跑通的 `.cmd`，避免「找不到二进制」引发重试风暴 |
| **反例必须存在** | 与任何工具都无关的问题，**不该调任何工具**——只有正例的探针会漏掉最致命的失效模式 |
| **题面自足** | 「那个视频讲了什么」无先行词时，模型澄清而非瞎猜是**合理行为**，不是路由失败；修题面而不是改算法 |

### 11.2 测试矩阵（当前实测数字，2026-09 复跑）

| 用例 | 覆盖 | 结果 | 耗模型 |
| --- | --- | --- | --- |
| `tests/m5_abilities_e2e.py`（269 行） | M5a：`abilities` 列与读写、`agent_brief` 两形态、示例过只读闸、装配链路、API、前端接线 | **43/43** | 否 |
| `tests/m5b_pool_e2e.py`（312 行） | M5b-1：两表结构、`cli_entry()` 纯函数（三种形态）、写入口联动、池版本、`rebuild_pool` 幂等、向量增量/清理、账号隔离 | **62/62** | 否 |
| `tests/m5b_router_e2e.py`（274 行） | M5b-2：快路径逐字一致、路由命中、反例回退、**兜底三分支**、预算护栏、未命中不隐身、示例过滤、RRF 单测 | **34/34** | 否 |
| `tests/m4c_cli_e2e.py`（473 行） | CLI 配置 CRUD / 只读闸 / 简报注入（**M5b 改动后回归**） | **109/109** | 部分 |

**8 工具加压的实测结论**：10 条问句中 8 条走路由（命中集都含正确工具、**0 条猜错**），
2 条无关问句**全部回退**；注入量 **1644 字 vs 全量 2499 字**。

### 11.3 为什么「降级=回退全量」必须被断言

路由的失败模式有两种：**猜错**（注入错工具的说明书）与**静默失效**（注入空内容）。
前者靠命中率探针守，后者靠 `m5b_router_e2e.py` 的兜底三分支守——
**「绝不让注入变空」是硬不变量**（空简报意味着模型眼里这个账号一个工具都没有）。

### 11.4 度量沉淀（写下一步要用）

- 每轮 `RouteResult.detail` 带 `z_top / lex_top / order / full / scores / z / lexical / pool`；
- 探针结果落 `data/m5b_pressure_result.json`（单条重跑落 `..._only.json`，不覆盖整轮）；
- **注入量对比**是最能说明收益的单一数字（1644 vs 2499 字）。

### 11.5 已知缺口（诚实记录）

| 缺口 | 影响 | 备注 |
| --- | --- | --- |
| `pool_summary()` 未接端点 | 前端看不到「池里现在有几个工具、向量的版本对齐没」 | 排查时只能进 Python 调 |
| 桩夹具只能验「路由是否发生」 | 验不了「回答是否忠实于工具返回」 | 所以另写了 `_m5_real_weread_check.py`（真实 CLI）补齐 |
| 向量首建慢（1~3 分钟） | 换工具后第一次提问会卡一下 | 已尽量推迟到路由时刻；彻底解法是常驻 embedding 服务（v3.0） |

## 十二、坑与教训（每条都有测试守着）

| # | 现象 | 根因 | 修法 | 守它的测试 |
| --- | --- | --- | --- | --- |
| 1 | 问「我这个月读了多久」，向量 top1 是 `booky`，融合后变成 `sched` | 词法全 0 时仍把「全 0 的排序」当一路输入 RRF → 给插入序加分 | `_rrf()` 剔除**无信号**的排序器 | `m5b_router_e2e.py` RRF 单测 |
| 2 | 路由后示例区仍出现非命中工具的命令 | `_filter_examples` 按 `- ` 前缀认示例行，而真实格式不以 `- ` 开头 | 改按 `run_shell_command(` / `command=` 判断；只剩引导语则整段丢 | 同上（示例过滤断言） |
| 3 | 点一次「保存 CLI」界面冻 1~3 分钟 | 写入口同步了向量（加载 bge） | 写入口只落库 + 打版本；`ensure_vectors_fresh()` 路由时刻按版本重建（0.18s） | `m5b_pool_e2e.py` 向量组 |
| 4 | 删账号报 `FOREIGN KEY constraint failed` | 新表带 `REFERENCES accounts(id)` + `PRAGMA foreign_keys=ON` | 加 `purge_account()`：自省 `sqlite_master`，凡带 `account_id`/`owner_id` 的表都清（加表不用再改） | 三套测试的清理段 |
| 5 | 模型调 `book info` 直接报错 | 需要前置 ID 的命令不能直调 | 能力描述写成**两步链**（示例取链上第一步） | `_m5_real_weread_check.py`；探针「备选首调」 |
| 6 | 备选首调判定恒为 False | argv 是 `list`、备选写成 `tuple`，`["search","x"][:2] in [("search",)]` 永远为假 | 比较前统一 `list(a)` | `m5b_pressure_probe.py` |
| 7 | 探针 4/5/7 三条"失败" | 题面写「这本书…」但全新会话里没有先行词 | 题面自足化（点名到具体书/视频） | 探针题面规范 |
| 8 | 用户以为「配了 CLI 但 AI 说没有」 | 简报没注入 / 工具从提示词隐身 | 未命中工具保一行名字 + `prompts.yml` 的使用纪律 | `m5_abilities_e2e.py` |

**两条高层教训**

1. **安全与路由分层治理**：只读清单（决定**能不能跑**）必须人给；能力描述（决定**想不想得起跑**）可以 AI 起草。
   错判代价量级不同——前者是安全问题，后者只是路由问题。
2. **加速层永远不许成为单点**：向量、池、路由全是**加速层**——任何一处失败都必须退化成「M5a 的全量简报」，
   而不是「注入为空」或「接口 500」。

## 十三、明确不做（范围边界）

- **不做「让模型自己发现工具」**：不给 Agent 一个 `list_tools()` 让它先查再调——
  免费模型不会主动查（M5a 实测），多一轮调用还多一次失败机会。
- **不做工具注册中心 / 远程目录**：单机自用，池就是本机账号配了什么。
- **不做语义检索「命令级」**：路由的粒度是**工具（CLI）级**，不是子命令级——
  子命令的选择交给模型看能力卡自己挑（卡里已经给了「说法→命令」映射）。
- **MCP / API 适配器**：按用户拍板推迟到 **v3.0**（池与路由器已为它们预留位置，见 §10.2）。

## 附：术语表

| 术语 | 含义 |
| --- | --- |
| **能力池 / 池**（capability pool） | 当前账号所有「可用于完成请求」的能力条目集合（当前只有 CLI 来源） |
| **能力条目**（`CapabilityEntry`） | 池里的一个元素，路由器唯一认得的形状 |
| **能力描述**（`abilities`） | 用户语言写的「什么场景该用这个工具 + 说法→命令映射」，是 M5a 的路由信号 |
| **能力路由卡**（card） | 能力描述的完整注入形态（含命令计数与样例） |
| **快路径**（fast path） | 池 ≤4 或无提问时直接走 M5a 全量简报 |
| **兜底 / 回退全量**（fallback） | 任何不确定/异常情形下退回全量简报，绝不让注入变空 |
| **命中集**（`hits`） | 被渲染成完整能力卡的条目 ref（`source:ref`） |
| **只读闸** | 第 7 道安全闸：已接入 CLI 只放行只读/查询子命令 |
