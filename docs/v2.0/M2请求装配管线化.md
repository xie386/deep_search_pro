# M2 请求装配管线化 · 实现设计 & 验证规划（智选情报官 v2.0）

> 里程碑：M2（承接 `docs/v2.0/AstrBot_v2.0对比借鉴.md` §3 借鉴点 5️⃣「请求装配函数 build_request_context」+ §三行动清单 5️⃣）
> 目标：把「动态内容（人格 SOUL / 记忆画像 MEMORY.md / 未来 KB 片段）在**每次 invoke 前拼装**」替代 v1.0「改人格/记忆就**重建整个 agent**」的机制——agent 静态化，请求上下文动态化。
> 状态：✅ 已完成并实测通过（2026-09-03）
> 前置依赖：M1 已完成（SQLite 历史 + token 预算 + 多会话），M1 的 `agent/build_context.py` 已提供 `compose_system_prompt()` 与 `build_request_context()` 骨架

## 〇、一句话目标 + 核心机制验证（Spike 结论）

**把 system_prompt 从「agent 构建时固死」变成「每次 invoke 前由装配管线动态拼装」——改人格/记忆/（未来）知识库片段都不再重建 agent，且每次请求带了什么可观测、可叠加。**

### 现状痛点（为什么 M2 值得做）

v1.0 `_get_agent_for`（api/server.py:138）：账号有自定义模型/人格/记忆画像时，把 **soul_text + memory_text 拼进 system_prompt 后 `create_deep_agent` 重建**，缓存 key 含 `hash((soul_text, memory_text))`：

```python
# v1.0：动态内容固化进 agent 构建 → 画像一变就重建（重 + 无法叠加 + 难以观测）
if provider or soul_text or memory_text:
    key = (account_id, hash((soul_text or "", memory_text or "")))
    if key not in _custom_agents:
        _custom_agents[key] = _build_custom_agent(provider, soul_text, memory_text, username)
    return _custom_agents[key]
```

后果：① 每次改人格/记忆都重建 agent（创建 deep agent 有固定开销，且缓存膨胀）；② 「定制助手 × 全局 AGENT」两套逻辑并存（`_get_agent_for` 分叉）；③ 无法叠加多个动态来源（记忆 + KB 片段 + 订阅偏好一起注入时没位置放）；④ 难以调试「这次请求到底带了什么」——system_prompt 藏在缓存的 agent 里。

### Spike 验证（2026-09 实测，决定架构可行性）

**问题**：deepagents（底层 `langchain.agents.create_agent`）构建时 system_prompt 已注入，invoke 时 messages 首条再塞 `SystemMessage` 会怎样——双 system？谁生效？

| 实验 | 设置 | 模型回答（关键句） |
| --- | --- | --- |
| 1 | 构建 system="静态助手" + invoke 塞 SystemMessage("动态注入的助手") | **"我是动态注入的助手，角色说明已被当前动态注入覆盖"** |
| 2 | 构建 system="" + invoke 塞 SystemMessage("动态助手") | 正常回答（动态生效） |
| 3 | 对照组：构建 system 有值，invoke 不带 system | 静态生效 |

**结论**：deepagents 的图在 invoke 时以传入 messages 为准——**首条 SystemMessage 可动态覆盖/补充构建时 system_prompt**。M2 架构成立：

```
构建时（静态，一次）：agent = create_deep_agent(system_prompt=main 基础提示词)
invoke 时（动态，每次）：messages[0] = SystemMessage(soul + 记忆画像)   ← 动态生效
```

> ⚠️ 实验 1 的"覆盖"是模型层面的行为（两个 system 都发了，模型按后文优先），非字面覆盖。M2 回归测试须覆盖「main 职责指令 + 人格 + 记忆三者同时在场且不互斥」的场景（见 §六 6.3 第 4 条）。

## 三、核心设计：agent 静态化 + 装配管线

### 3.1 分层职责（改造后）

```
┌─ 静态层（agent 构建一次，进程生命周期内不变）─────────────┐
│  agent = create_deep_agent(                               │
│      model = 该账号模型（无自定义→全局 model）,             │
│      system_prompt = main 基础提示词（稳定职能+记忆维护指令）,│
│      subagents / tools / middleware = 固定组合)            │
└───────────────────────────────────────────────────────────┘
              ▲ invoke 时传入 ctx.messages（含动态 SystemMessage）
┌─ 动态层（每次请求，build_request_context 管线）────────────┐
│  ctx.messages = [                                          │
│      SystemMessage(soul + 记忆画像)   ← _apply_persona/_apply_memory │
│      *SQLite 历史（M1）                                     │
│      HumanMessage(本次提问)                                 │
│  ]                                                         │
└───────────────────────────────────────────────────────────┘
```

### 3.2 缓存策略变化

| | v1.0 | M2 |
| --- | --- | --- |
| 缓存 key | `(account_id, hash(soul+memory))` | `(account_id, provider 配置哈希)` |
| 触发重建 | 改人格 / 改记忆 / 改模型 | **仅改模型**（换 base_url/api_key/model_name）|
| 缓存数量 | 每账号 × 每画像版本（膨胀）| 每账号至多 1 个（收敛）|
| 动态内容 | 固化在构建时 | 每次 invoke 现拼 |

### 3.3 system_prompt 的「静态 base」与「动态注入」分工

- **静态 base（构建时，一次）**：`prompts.yml main_agent.system_prompt`——职责路由、来源标注纪律、输出结构、记忆**维护指令**（教 Agent 何时调写文档工具）。这些是"怎么当情报官"的稳定部分。
- **动态注入（每次）**：
  - `_apply_persona`：激活人格 SOUL.md 全文（customize 的激活人格文件）
  - `_apply_memory`：MEMORY.md 的 USER PROFILE 段（记忆画像内容，Agent 每次对话都可能改它）
  - `_apply_kb`（预留）：RAGFlow 命中片段（v2.0 后续里程碑挂进来）
- **顺序**：`人格 → 记忆画像`（与 v1.0 拼接顺序一致，M1 `compose_system_prompt` 已实现）；main base 由构建时提供，不进 invoke system（避免重复）。

## 四、装配管线实现（`agent/build_context.py` 升级）

参考 AstrBot `astr_main_agent.py` 的 `_apply_*` 可插拔链，本项目管线段：

```python
# agent/build_context.py（M2 升级后）

def build_request_context(
    thread_id: str, account_id: int, new_user_msg: str,
    *,
    base_system_prompt: str,          # main 基础提示词（调用方从 prompts.yml 读）
    dynamic: dict | None = None,      # 装配输入：{"soul_text":…, "memory_text":…, "username":…}
    config=None, manager=None,
) -> ContextBundle:
    # 1. _apply_persona + _apply_memory：动态内容 → SystemMessage
    sys_prompt = base_system_prompt

> **M4c 补充（2026-09-11）**：动态 SystemMessage 现在承载 **三个** 动态块——人格(SOUL) → 记忆(MEMORY) → **可用命令行工具简报**
> （`compose_dynamic_prompt(..., cli_brief=…)`；由 server 层取 `tools/cli_registry.agent_brief(account_id)` 传入，本模块仍不 import api.*）。
> 装配结果用 `ContextBundle.cli_injected` 标记，方便观测「这轮到底注了没」。

    persona = SystemMessage(content=compose_dynamic_prompt(dynamic or {}))
    # 2. 历史（SQLite）+ 提问 + 预算（M1 不变）
    history = conversation_store.get_history(account_id, thread_id)
    processed = mgr.process([persona, *history, HumanMessage(content=new_user_msg)], cfg)
    ...
    return ContextBundle(messages=processed.messages, system_prompt=base_system_prompt, ...)
```

关键点：
1. **persona SystemMessage 放 messages 首条**（Spike 验证的注入位），历史紧随其后——被截断时 persona 永不丢（`ContextTruncator` 的 system 保护逻辑已覆盖，见 M1）。
2. `compose_system_prompt`（M1 已有，拼 soul+memory）改名为/复用为 `compose_dynamic_prompt`，只处理动态部分；base 由构建时承载 → **删除 server.py 旧拼接副本**（单一来源）。
3. 未来加动态段 = 在管线加一个 `_apply_xxx` 并往 `dynamic` dict 塞键——不动 agent、不动 invoke 主链路。

## 五、踩坑预判

| # | 风险 | 防御 |
| --- | --- | --- |
| 1 | **双 system 语义不清**（构建 base + invoke 动态都发，模型可能偏信后文）| 回归测试覆盖「职责+人格+记忆」同时在场（§六.3-4）；若实测互斥，改为构建时 system 传空、全部走 invoke |
| 2 | **历史截断误伤 persona SystemMessage** | ContextTruncator 保护所有 SystemMessage（M1 已实现），单测补一条「persona 在首条 + 25 轮历史截断后仍在」 |
| 3 | **无自定义模型的账号也走装配后行为漂移**（原来直接用全局 AGENT）| 装配对 account_id=None 与有值账号输出一致结构；§六端到端用默认账号回归 |
| 4 | **缓存 key 只按 provider，改人格后旧 agent 的 model 单例引用问题** | agent 静态化后人格不进构建，本就不存在"旧 agent 带旧人格"；确认 `customize.switch_soul` 后无需清缓存 |
| 5 | **记忆/人格文件读 IO 每次 invoke 一次**（v1.0 是缓存命中时零读）| 文件小（KB 级）+ 本地磁盘，读一次 <1ms；若在意可在 account 级加 5s 短缓存（M2 不做，留注释） |
| 6 | **main base 提示词里若有「画像已注入」占位文案**（提示词假设记忆在 system 里）| 审查 main_agent.system_prompt 的记忆维护指令段：改为「画像会在对话开头以 system 消息注入」的通用表述（⑥ 阶段确认） |

## 八、与 AstrBot 装配链的差异（避免照搬）

| 维度 | AstrBot `astr_main_agent.py` | 本项目 |
| --- | --- | --- |
| 链式形态 | `_apply_kb` / `_apply_prompt_prefix` / `_ensure_persona_and_skills` 等**方法链** | `build_request_context` 单函数内顺序段（当前动态源仅 2 个，方法链过度设计）|
| Provider 选择 | `_select_provider`（多平台多模型注册表）| `_get_agent_for` 按账号 llm_providers 表（已收敛）|
| Skills 注入 | `_ensure_persona_and_skills` 目录扫描 | 本项目无 Skills 体系（v2.0 C 级，暂不做）|
| 注入载体 | 拼进 system 消息 | 同样 messages[0] SystemMessage（与 AstrBot 同构）|
| KB | `_apply_kb` 每轮查向量库注入 | 预留 `_apply_kb`，实际走 RAGFlow 工具化（借鉴点 4️⃣，后续里程碑）|

> **抄 A 不抄 B**：借鉴"每次请求可观测地拼装动态内容"这一思想；不抄 AstrBot 的多平台 provider 注册表与 Skills 扫描（本项目账号体系已收敛、无 Skills 需求）。
