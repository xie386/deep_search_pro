# 智选情报官 · RAG 库内容设计讨论

> 讨论背景：v2.0 计划接入 RAGFlow，但在动代码前需要先回答"**RAG 库里到底要存什么**"。
> 本文不是实施承诺，而是 **决策依据文档**——通过"判据 → 候选 → 过筛"推理链，
> 回答"为什么是这三条，不是其他五条"。
>
> 讨论前提：
> 1. RAG 工具本身不是目的，**业务价值 + 检索必要性**才是
> 2. 现有手段能解决的需求（网络搜索、关系库、MEMORY.md）**不应重复造轮子**
> 3. 选 P0/P1/P2 严格遵循 RAG 适用性判据
>
> 关联文档：`docs/v2.0/v2.0方案.md` §一（RAGFlow 接入规划）、
> `docs/v2.0/AstrBot_v2.0对比借鉴.md`（工具化检索 vs 子 Agent 路线讨论）

## 〇、核心拷问（先复述本讨论的出发点）

- **产品信息咨询** → 现有 `tavily_tool` 网络搜索能解决，**且能拿到实时数据**——
  RAG 存了反而过期
- **用户信息** → 已有 `MEMORY.md` 账号画像 + `db_tools` 关系库，**不需要 RAG 重复**
- 那么 v2.0 这个"接入 RAGFlow"到底要存什么？——既不能"为技术而技术"，
  又得满足 **"RAG 比传统手段更合适"** 的判据

> 同意这种怀疑精神。先给**判据**，再**枚举候选**，再**过筛子**。

---

## 一、RAG 适用性判据（什么场景"非 RAG 不可"）

RAG 不是"高级数据库"，它是 **"自然语言 ↔ 向量近似匹配"** 的专用工具。
**只有当以下四条同时满足**，RAG 才是对的工具（而非"高级搜索"）：

| 判据 | 含义 | RAG 解决得好 | RAG 解决得差 |
|---|---|---|---|
| **① 数据是「自然语言段落」** | 半结构化/非结构化文本，有语义而无固定 schema | ✅ | ❌ 表格数字、严格 schema |
| **② 检索是「语义近似」而非「精确匹配」** | "GPU 显存" ≈ "显卡内存" ≈ "VRAM" | ✅ | ❌ "订单号=12345" |
| **③ 知识相对稳定（非强实时）** | 隔几天更新，不需要秒级 | ⚠️ 适合 | ❌ 股价/实时价格 |
| **④ 召回后要「拼回自然语言」喂给 LLM** | 答案要带来源、要引用、要可解释 | ✅ | ❌ 只为展示列表 |

**判据全过 = RAG 必选；过三条 = 值得用；过两条 = 可有可无；过一条 = 别用**。

## 二、deep_search_pro 业务场景的「候选 RAG 库」过筛

列了 8 个候选，按"判据契合度"排序。

### 候选 1：🏆 用户的「个人知识库」（周报原始素材库）

**是什么**：用户**主动上传**的资料——行业报告 PDF、产品白皮书、关注的竞品官网截图
OCR、内部规范、自己写的读书笔记……

**过筛**：

- ① 自然语言段落 ✅（PDF/笔记都是文本）
- ② 语义近似 ✅（"公司战略"和"业务方向"应该匹配同一段）
- ③ 相对稳定 ✅（上传的内容本来就是用户选择保留的"沉淀物"）
- ④ 拼回 LLM ✅（周报/简报场景天然要引用源）

**为什么非 RAG 不可**：

- 网络搜索拿到的是**公开信息**，**用户私有的"我看到过的、我想记住的"**这一类是
  搜索引擎抓不到的
- 关系库存不了（不是用户账号属性，而是**用户的「第二大脑」**）
- 比 SQL 模糊查询强——"我之前看过关于 XX 的报告"这种自然语言查询，SQL 做不到

**示例场景**：

- 用户问"我之前收藏的关于 RAG 的资料里，讲过哪些 Rerank 选型建议？"
- 周报自动写"📚 本周提到你的个人知识库里关于'智能体'的 3 个观点，关注度↑"

### 候选 2：🥈 多源情报的「本地索引镜像」

**是什么**：网络搜索结果（Tavily 返回）落地后的**摘要+元数据+原始链接**，存进 RAG。

**过筛**：

- ① 自然语言段落 ✅
- ② 语义近似 ✅
- ③ 相对稳定 ❌ **不满足**——网络信息会过期
- ④ 拼回 LLM ✅

**问题**：强实时场景下，RAG 里存的是"昨天的快照"，**反而会误导 LLM 给过期答案**。

**结论**：**❌ 别用 RAG**——RAG 适合"沉淀"，网络搜索适合"探索"。混着做会让 LLM
分不清"这是新鲜的还是陈旧的"。

**但有一个变体值得讨论**：

- 如果是"用户**长期关注**的某个领域/某个实体（如某家公司、某个人物、某个产品）
  的历史报道"——这是"用户沉淀的"而不是"工具主动索引的"，**仍然属于候选 1**。

### 候选 3：🥉 智能体配置/SOUL/记忆的「向量快照」

**是什么**：把 `SOUL.md`、`MEMORY.md` 自身的语义摘要存到向量库，便于跨人格/跨账号的
"相似度检索"。

**过筛**：

- ① 自然语言段落 ✅
- ② 语义近似 ✅（"二次元" ≈ "ACG"）
- ③ 相对稳定 ✅
- ④ 拼回 LLM ⚠️ 有点牵强（本来在 prompt 里就行）

**问题**：

- 现状是 SOUL/MEMORY 已经在 system_prompt 拼好了，直接给 LLM 全文就行
- RAG 价值在于"从很多份里挑最相关的"，但**一个账号只有一份 SOUL + 一份 MEMORY**，
  没有"挑"的需要

**结论**：**❌ 别用 RAG**——单份文档不需要相似度检索。

### 候选 4：多账号/多人格的「共享知识」

**是什么**：多账号之间**共享的公共知识**（如"智选情报官的使用教程"、"产品操作 FAQ"）。

**过筛**：

- ① 自然语言段落 ✅
- ② 语义近似 ✅
- ③ 相对稳定 ✅
- ④ 拼回 LLM ✅

**问题**：

- 项目是**单用户本地部署**，没有"多账号共享"需求
- 即使有，**直接放 system_prompt 末尾**也够用（因为是公共的、有限的、确定的）

**结论**：**❌ 现状别用**——除非未来走 SaaS，否则不必要。

### 候选 5：用户对话的「历史 QA 库」

**是什么**：把所有"用户问过 + Agent 答过"的高质量对话存进 RAG，新提问时先检索
"过去怎么答过类似问题"。

**过筛**：

- ① 自然语言段落 ✅
- ② 语义近似 ✅（"显卡价格"≈"GPU 报价"）
- ③ 相对稳定 ⚠️（只要对话不撤回，稳定）
- ④ 拼回 LLM ✅

**价值**：

- 个性化连续性——"上次我问过 A，这回 B 是 A 的后续"
- 减少重复检索——之前查过的信息复用

**问题**：

- 与 `MemorySaver`（对话历史）的边界**容易模糊**——对话历史已经在 LLM 上下文里了
- 真正的价值是"**跨会话的、长期沉淀的高质量答案**"，不是所有对话

**结论**：**⚠️ 部分用**——如果 v2.0 要做，**只存"用户★收藏的对话"或"系统判定
高价值的对话"**，**不是全部**。

### 候选 6：🆕 用户的「意图分解 / 任务模板库」

**是什么**：`prompts.yml` 里 `sub_agents` 那一坨"如何分解情报检索任务"的**领域经验**——
比如"做公司尽调时，应该问哪些维度（产品/财务/团队/竞争/风险）"。

**过筛**：

- ① 自然语言段落 ✅
- ② 语义近似 ✅（"做尽调"≈"调研公司"≈"公司分析"）
- ③ 相对稳定 ✅
- ④ 拼回 LLM ✅（任务类 prompt 直接拼进上下文）

**价值**：

- 这是 **"Agent 自己的工作经验"**——不是用户的私有知识，而是**系统的可复用经验**
- RAG 的好处：**按当前任务挑相关的经验拼进去**，而不是一股脑塞给所有任务

**结论**：**✅ 值得做**——属于"系统级知识库"，对情报助手的"任务分解质量"提升巨大。

### 候选 7：🆕 工具的「使用案例与失败案例」

**是什么**：工具调用时的"成功案例"和"失败案例"（包括修复方法）——比如
"上次 `tavily_tool` 返回 429 后我们等了 10 秒重试成功"。

**过筛**：

- ① 自然语言段落 ✅
- ② 语义近似 ✅（"网络工具不可用" ≈ "搜索超时"）
- ③ 相对稳定 ✅
- ④ 拼回 LLM ✅（错误处理流程可拼给模型参考）

**价值**：

- **工具护栏经验沉淀**——AstrBot 那种"工具调用超时 / 失败"的修复经验
- 让 Agent 在新场景下"借鉴历史怎么处理过的"

**结论**：**✅ 值得做**——但优先级低，等基础 RAG 跑通后再加。

### 候选 8：🆕 用户/Agent 共同标注的「周报素材库」

**是什么**：周报写完后，用户对每条新闻的反馈（👍/👎/💬 批注）沉淀到 RAG，
作为"下周写周报的偏好依据"。

**过筛**：

- ① 自然语言段落 ✅
- ② 语义近似 ✅（"用户不喜欢纯营销稿" ≈ "用户爱技术分析"）
- ③ 相对稳定 ✅
- ④ 拼回 LLM ✅

**价值**：

- **用户偏好沉淀**——比 MEMORY.md 的"显式画像"更细腻，体现"用户的隐性偏好"
- 周报/简报质量持续提升的**数据飞轮**

**结论**：**✅ 值得做**——可以和数据飞轮设计合并。

## 三、决策汇总：RAG 库内容的优先级与边界

| 优先级 | 候选 | 角色 | 触发条件 |
|---|---|---|---|
| 🥇 **P0** | **用户的「个人知识库」** | **「沉淀物」主库** | 用户主动上传（产品资料/报告/笔记） |
| 🥈 **P1** | **「任务模板/经验」库**（系统级） | Agent 的工作经验 | 与主 Agent 提示词解耦，按任务动态调取 |
| 🥉 **P2** | **「用户反馈偏好」库** | 提升周报/简报质量 | 用户对周报/简报条目的反馈沉淀 |
| ❌ 不做 | 网络搜索结果本地缓存 | — | 强实时，与 RAG 定位冲突 |
| ❌ 不做 | SOUL/MEMORY 自身的向量化 | — | 单份文档无检索必要 |
| ❌ 不做 | 多账号共享知识 | — | 单用户项目无需求 |
| ⚠️ 慎做 | 对话历史 QA 库 | 跨会话复用 | 只存★收藏或高价值对话，不存全部 |

## 四、判断逻辑（"为什么是这些"的判据 × 价值 × 成本）

按 **"判据 × 业务价值 × 实现成本"** 三维评分：

1. **个人知识库（P0）**：四个判据全过 + 业务价值最高（用户真正缺的"我的第二大脑"）
   + 实现成本可控（参考 AstrBot `kb_agentic_mode` 即可）
2. **任务模板/经验库（P1）**：四个判据全过 + 业务价值中（提升 Agent 自我能力）
   + 成本低（把 `prompts.yml` 里的 sub_agents 经验抽出来即可）
3. **用户反馈偏好库（P2）**：四个判据全过 + 业务价值高（数据飞轮）
   + 成本中（需要标注通路 + 反馈入口）

被否掉的 4 个，根本原因都是**"没满足判据"或"现状已有更好解"**：

- 网络缓存：不满足判据 ③
- SOUL/MEMORY 向量化：不满足判据 ② ④
- 多账号共享：现状无需求
- 对话历史：与 `MemorySaver` 重叠，边界不清

## 五、待 v2.0 实施时定的开放问题

> 以下问题不影响 P0/P1/P2 选型，但实施时必须先回答，否则会埋坑。

### 边界问题 1：「个人知识库」和"网络搜索结果"如何隔离？

- 用户上传的 PDF 里**有可能**包含他看过的过期文章（如"2024 年某公司财报"）
- LLM 检索时拿到的是"用户标注的"还是"网上搜的"——来源混淆会降低可解释性
- **建议方向**：**严格隔离，两套 collection**，prompt 里明确区分
  "📚 你的知识库" vs "🌐 网络"

### 边界问题 2：RAG 命中时，来源怎么展示？

- 现状（v1.0 周报）：来源标注清晰（🌐 网络 / 📰 特定订阅源）
- RAG 接入后，需要加 `📚 知识库` 这第三种来源
- **建议方向**：沿用 emoji 来源系统 + 引用片段预览（给链接或文件名）

### 边界问题 3：P0「个人知识库」与 P1「任务模板库」是否共享 RAG 实例？

- 共享：省运维、一套 SDK；但 prompt 路由复杂、检索噪声大
- 隔离：清晰、互不干扰；但运维成本翻倍
- **建议方向**：**共享 RAG 实例（一个 RAGFlow 服务），但用 collection 隔离**——
  集合命名 `kb_user_<account_id>` 与 `kb_system_tasks`

### 边界问题 4：P2「用户反馈偏好」是 RAG 还是结构化？

- 偏好评数据是**短文本 + 结构化标签**混合体（"👍 技术分析" / "👎 营销稿"）
- 如果只在 LLM 生成周报时**一次性**用，可以存结构化
- 如果要"语义近似"（"用户不喜欢煽动性语言" ≈ "用户不喜欢过度营销"），需要 RAG
- **建议方向**：**结构化为主 + 关键长文本进 RAG**（双轨）

### 边界问题 5：P1「任务模板库」从哪里来？

- 候选 A：人工整理（参考 `prompts.yml` sub_agents）
- 候选 B：Agent 在使用中**自己沉淀**（每次任务完，self-evaluate 后入库）
- 候选 C：用户对 Agent 工作的反馈反向沉淀
- **建议方向**：**A 起步，B 演进**——不要一上来就让 Agent 自管理经验库，
  否则容易污染。建议等 P0 跑通后，专门做一版 B 的方案评审

## 六、反向自查（确保没"为技术而技术"）

| 自查问题 | 答案 |
|---|---|
| 没有 P0「个人知识库」，v2.0 缺什么吗？ | 缺"用户的第二大脑"——这是用户**真正缺**的能力，不是 RAG 营销词 |
| 没有 P1「任务模板库」，Agent 表现会差吗？ | 略差——当前靠 `prompts.yml` 静态提示词能撑，但跨任务复用经验欠缺 |
| 没有 P2「用户反馈偏好」，周报质量会停滞吗？ | 不会立即停滞，但失去"持续进化"的数据飞轮——长期重要 |
| 做了这三条，会不会跟现有 MEMORY.md 重复？ | 不重复：MEMORY 是"显式账号画像"，RAG 是"自然语言素材库"——维度不同 |
| 做了这三条，会不会跟网络搜索重复？ | 不重复：网络搜索是"实时探索"，RAG 是"沉淀复用"——时机不同 |
| 不做"网络搜索结果本地缓存"会不会漏需求？ | 不会——过期信息比没信息更危险 |
