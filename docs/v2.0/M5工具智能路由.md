## 〇、一句话目标 + 问题定义

### 0.1 一句话目标

用户用**自然语言**提问（如「看看我最近在读什么书」），Agent 能**可靠地**选中正确的工具（`run_shell_command("weread", ["shelf","recent"])`）——而不是回答「该功能不可用」或凭知识编造。

### 0.2 问题的本质：工具路由（Tool Routing）

这不是「提示词写得不够强硬」的问题。当前链路存在三个**结构性断点**：

| # | 断点 | 现状 | 后果 |

|---|---|---|---|

| 1 | **命令名 ≠ 用户语言** | `agent_brief` 注入的是 `search / book progress / shelf recent / readdata summary` 等命令动词 | 用户问句「我最近在读什么」是**意图**，注入的是**CLI 动词**——两个语义空间对不上，模型做不了匹配 |

| 2 | **只有「名字」没有「何时该用」** | 一行简报给了「可代跑 15 条 + 6 个示例命令」，但没有一条说"`book progress` 能回答『正在读什么书』" | 模型不知道命令与用户意图之间的对应关系，只能靠猜 |

| 3 | **单工具 + 通用 description** | 所有 CLI 共用 `run_shell_command` 一个工具，其 docstring 讲的是白名单/沙箱/限制，不含任何 CLI 能力语义 | langchain 工具选择时唯一的语义信号就是系统提示词里那一行简报 |

### 0.3 为什么免费模型下更严重

免费/小参数模型的**工具路由能力天然偏弱**（长上下文注意力稀释，多工具清单会进一步稀释注意力）。M4c 实测已经踩过一次：配好了 weread、Agent 却回答「不在白名单」——事后查审计日志确认**它连工具都没调**（把工具说明书的通用描述当成了"查过白名单的事实"）。当时用「CLI 简报常驻注入」解决了"知不知道有"的问题；M5 要解决的是"**能不能想起来用、用对**"的问题——是同一条链路的第二级台阶。

## 一、调研佐证（业界共识 + 论文结论）

> 结论先行：这个问题的研究已经成熟，四条结论全部对得上我们的痛点；我们不是在发明新东西，而是在把已知最佳实践落到本项目。

| # | 来源 | 核心结论 | 对应我们的动作 |

|---|---|---|---|

| 1 | **Anthropic《Writing effective tools for agents》**（官方工程博客） | 工具描述必须写清**意图 / 输出语义 / 什么场景该用**；工具名要反映任务的**自然划分**（名字本身就是路由信号） | 第一层：`abilities` 能力描述字段 |

| 2 | **《Learning to Rewrite Tool Descriptions for Reliable LLM-Agent Tool Use》**（arXiv 2602.20426） | 核心动作就是**把"命令名"重写成"用户语言"**——描述质量直接决定路由可靠性 | 第一层：把 `book progress` 翻译成「我正在读的书」 |

| 3 | **Instruction-Tool Retrieval / ITR**（arXiv 2602.17046） | 工具一多，全量塞上下文反而**诱发乱调用**；每步只检索暴露最相关子集：routing 准确率 **+32%**、上下文 token **-95%**、整episode 成本 **-70%** | 第三层：检索式工具路由（命中才放大） |

| 4 | **Online-Optimized RAG for Tool Use**（arXiv 2509.20415） | 用 embedding 把「用户 query」与「工具能力描述」做相似度 top-k 匹配；描述有噪声时检索会失配 | 第三层的技术选型依据（embedding 检索足够，不必上微调） |

**反直觉但重要的一条**：工具每多接一个，不是"能力更强"，而是"路由更难"。现在只有三五条 CLI 简报还好；等 MCP + API 都接进来（v2.0 规划里已在列），全量注入会**先于功能**崩掉。所以 M5 不只是修 weread 唤不醒——是给即将到来的多工具时代打地基。

## 二、方案总览：四层递进

```

┌─────────────────────────────────────────────────────────────────┐

│ 第四层（规范层）  接入规范：任何新工具/MCP/API 接入必带能力描述        │ ← 现在定规矩

├─────────────────────────────────────────────────────────────────┤

│ 第三层（路由层）  检索式路由：问题 ↔ 能力描述 embedding 相似度命中放大   │ ← M5b（工具多时）

├─────────────────────────────────────────────────────────────────┤

│ 第二层（示例层）  few-shot 对照：自然语言 → 工具调用 示例 2~3 条        │ ← M5a

├─────────────────────────────────────────────────────────────────┤

│ 第一层（语义层）  abilities 字段：每个工具一句「用户语言的能力描述」      │ ← M5a（必做）

└─────────────────────────────────────────────────────────────────┘

        支撑：探针验证组（10 条自然语言探针 + 3 条反例，量化唤醒率）

```

**分层逻辑**：第一层给模型「意图→工具」的桥（信息）；第二层给「照着做」的示范（格式）；第三层解决「工具多了塞不下、塞多了乱」（规模）；第四层保证「以后每接一个新工具自动进这个体系」（演进）。前两层是纯注入内容改动，成本低、见效快；第三层复用 M3 的 Chroma + bge 检索栈，不是从零造。

## 三、M5a：能力语义注入（第一层 + 第二层）

> ⚠️ 本节为**实施后口径**（2026-09-13）。规划初版与实现有若干偏差（示例条数、映射形态、命令参数要求），
> 逐项差异与原因见 §9.1 与 §9.5 的迭代记录——**以本节为准**，避免照旧版设计实现。

### 3.1 数据模型：`user_clis.abilities`

```sql
-- tools/schema_personal.py：CREATE TABLE 同步加列 + 老库幂等 ALTER（沿用 M3 迁移模式）
abilities TEXT DEFAULT '',   -- 用户语言的能力描述（关键词 + 「用户说法→命令路径」映射）；空 = 回退 M4c 形态
```

**内容约定**（前端 placeholder 与教程同款）：

- **两段式**：第一行 `关键词：<8~15 个用户可能说到的词，用 / 分隔>`；其后写「**用户的口语说法 → 命令路径**」，
  多条用 `；` 或换行分隔，箭头支持 `→ / -> / =>`；
- 长度 ≤ **400 字**、**允许换行**（表单是 textarea；注入简报时压平成一行）；
- **「缺省即保留」**：表单只改名称/清单时，`abilities` 不会被清空（显式空串才清空）；
- **★ 需 ID 的命令必须写两步链**（实施期最关键的一条）：

  ```text
  关键词：读书/阅读/看书/书架/我在读/读书进度/笔记/划线/书评/找书/想看的书。
  我正在读什么书→shelf recent；读到哪了→shelf recent 再 book progress；帮我找书→search；
  这本书讲什么→book resolve 再 book info；书评怎么样→book resolve 再 reviews list；
  我的笔记与划线→notes notebooks；找相似的书→discover recommend；
  读书数据统计→readdata summary；我的书架→shelf list
  ```

  原因：`weread book info` / `reviews list` / `book progress` / `discover similar` 都**必须带数字 bookId**
  （`--help` 实测），而口语提问只有书名。直调 → 参数报错或绕去网搜；写成两步链后，系统抽示例取**链上第一步**
  （`book resolve`，可直接执行），模型先解析 ID 再调目标命令。分隔符支持 `再 / 然后 / 接着 / 或`。
- 生成方式（决策 2）：表单「✨ 按只读清单生成草稿」→ AI 起草（`ability_writer` 段）+ **人工确认后保存**
  （接口只返回草稿不落库）。`ability_writer` 里同样写明了「详情类命令要写两步链」这条规则。

### 3.2 `agent_brief()`：从「命令名清单」到「能力路由卡」

`tools/cli_registry.py::agent_brief()` **双形态**（函数签名不变，`api/server.py` 零改动）：

```text
- 微信读书（可执行名 `weread`）：用户问到下列任一场景时，**先用它取真实数据**（这是用户自己账号里的私有数据，
  网搜/知识库都拿不到）；不要改用别的工具顶替，也不要凭你自己的知识作答——
  关键词：读书/阅读/看书/书架/我在读/读书进度/笔记/划线/书评/找书/想看的书。 我正在读什么书→shelf recent；…
  共 15 条只读命令，例如 search / book info / book resolve / book progress / reviews list / discover recommend / …
```

- **回退规则**：`abilities` 为空 → 退回 M4c 的「可代跑 N 条只读命令，例如 …」形态——**存量配置零影响**；
- **私有数据优先指令**（实施期新增，二轮实测加入）：开头写明「先用它取真实数据、不要改用别的工具顶替」，
  针对「模型拿网搜/知识库答用户私有数据」（如用公开书评回答「我的书评」）这一失败模式；
- 预算沿用 M4c：`max_clis=8 / max_cmds=6 / max_chars=1400`（本轮**未调整**——规模问题交给 M5b）。

### 3.3 few-shot 对照示例（第二层）

由 `ability_examples()` 从能力描述里**动态生成**，`ability_examples_block()` 组装成区块，`_run_agent` 拼在简报之后：

```text
【怎么把用户的话对应到工具调用（照这个格式）】
用户问到「我正在读什么书」→ run_shell_command(command="weread", argv=["shelf", "recent"])
用户问到「书评怎么样」→ run_shell_command(command="weread", argv=["book", "resolve"])
…
**先在你的能力描述里找到与用户问题最贴近的那一条场景，再按该条给出的命令调用**；不要总用同一条命令应付
不同的问题。以上只是格式示范，实际能用的命令以本区块列出的为准，没有对应能力就直说，不要编造。
```

三条实现口径（都与规划初版不同，理由见 §9.5）：

| 口径 | 规划初版 | 实施版 | 原因 |
|---|---|---|---|
| 示例条数 | 抽 2~3 条 | **覆盖该 CLI 的全部映射**（上限 10 条） | 只给 3 条时，弱模型把示例里的头两条认成「万能命令」，问什么都调它们 |
| 安全校验 | 未提 | **每条 argv 逐条过只读闸**（`readonly_verdict`），未放行的映射直接丢弃 | 示范一条会被拒绝的命令 = 反向教学 |
| 承载位置 | 写死在 `prompts.yml` | 动态生成、拼进 `cli_brief`（`prompts.yml` 只放「格式示范 + 以区块为准」的纪律） | 示例必须来自用户真实配置，写死会与配置漂移 |

## 四、M5b：检索式工具路由（第三层，最小闭环）

### 4.1 触发条件（不满足就不做）

- 已接入的工具类能力（CLI + MCP + API）**合计 > 6 个**，或单条能力简报超过 ~1500 字；

- M5a 探针在「工具清单变长后」出现明显回退（探针通过率 < 9/10）。

### 4.2 设计：路由库 + 命中放大 + 兜底

```

用户问题 ──embedding──▶ 与「能力描述池」比对（bge，M3 现成栈）

                          │

              相似度 ≥ 阈值（如 0.45）

                          ▼

        命中的 1~2 个工具：完整能力卡（触发词 + 全部映射 + 示例）

        未命中工具：只保留一行名字（「有 weread，可查读书数据」）

        全部未命中：维持 M5a 全量简报（confidence-gated fallback，ITR 同款思路）

```

| 组件 | 实现 | 复用 |

|---|---|---|

| 能力描述池 | SQLite 新表 `tool_abilities(account_id, source[cli/mcp/api], ref_id, text, keywords)`，落库时机 = 工具接入/编辑时 | 新增，小 |

| embedding | bge-large-zh（M3 已加载，`rag_knowledge/kb_service.embedding_model()` 直接 import——注意该模块按用户分库，路由库是**独立 collection** `tool_route_{account_id}`，不与知识库混） | ✅ 复用 |

| 相似度比对 | 每次组装上下文时，对池内 ≤ 20 条做暴力余弦（不必建 ANN 索引，规模小） | 新增，小 |

| 命中放大 | 命中工具的简报块替换为完整能力卡；其余降为一行 | 新增，小 |

| 兜底 | 相似度全低于阈值 → 全量简报（宁可多给信息，不可漏工具）；`run_shell_command` 的 docstring 与白名单逻辑零改动 | 设计约束 |

**为什么不直接上 MCP 的动态工具暴露**：MCP 接入本身还没做；先把「能力描述池 + 命中放大」在自有 CLI 上跑通，MCP 接入时把它的工具描述往池子里灌即可——接口已经留好（`source` 字段）。

### 4.3 M5b 改动清单

| 文件 | 改动 | 量级 |

|---|---|---|

| `tools/schema_personal.py` | 新表 `tool_abilities` | 小 |

| `tools/tool_router.py`（新建） | `route_tools(account_id, question) -> {hit: [...], brief: str}`：embedding 比对 + 阈值 + 放大/降级；embedding 加载失败/池空 → 返回 None（调用方回退 M5a 全量简报） | 中 |

| `api/server.py` | `_run_agent` 组装 cli_brief 前先过 `route_tools`（question 就是本轮用户提问，现成参数） | 小 |

| `tools/schema_personal.py`(同步) | CLI 保存/删除/状态变更时同步路由池（增/删/改） | 小 |

| `tests/m5_router_e2e.py` | 路由命中/未命中/池空降级/阈值边界；真机探针在「模拟 8 个工具」压力下复测（构造多条假 CLI 记录） | 中 |

### 4.4 M5b 验证

- 单测：路由函数的命中/未命中/降级三分支 + 阈值边界；

- **压力探针**（关键）：构造 8~10 个假工具记录（模拟 MCP 接入后），复跑 §5.3 探针组——目标：**加压后通过率不比 M5a 基线低**（证明检索路由真的在"多工具"场景下起作用，而不是摆设）；

## 五、验收与度量

### 5.1 验收 = 探针组 + 调用事实，不采信模型自述

M4c 的教训直接沿用：模型说「我调用了」不算数。**主判据是会话真值 `messages.tool_calls`**（按 `thread_id` 取模型实际发出的调用，天然不受并发进程污染），`data/audit/commands.jsonl` 作交叉验证（证明调用真的到了执行器）。

### 5.2 探针组设计（10 正 + 3 反）——实施后口径

> 规划初版的探针表（含 `notes underlines` / `book chapters` / `profile summary` 等）与实施版不同：
> 那些命令**不在只读清单里**或**需要额外参数**，按下表为准（逐条明细与判定见 §3.5 与 §9.7）。

| 类型 | 提问 | 期望（可执行的**第一步**） |
|---|---|---|
| 正例 ×10 | 看看我最近在读什么书 | `shelf recent` |
| | 我上次读到哪一章了 | `shelf recent`（→再 `book progress <id>`） |
| | 帮我找几本讲降噪耳机的书 | `search 降噪耳机` |
| | 《白夜行》这本书讲了什么 | `book resolve 白夜行`（备选 `search`） |
| | 《白夜行》的评价怎么样 | `book resolve 白夜行`（→再 `reviews list <id>`） |
| | 我的笔记和划线都有哪些 | `notes notebooks`（**两词整体传**） |
| | 有没有和《白夜行》相似的书推荐我 | `discover recommend`（备选 `book resolve`） |
| | 帮我看看我的读书数据统计 | `readdata summary` |
| | 我的书架里都有什么 | `shelf list` |
| | 帮我搜一下《认知觉醒》这本书 | `search 认知觉醒` |
| 反例 ×3 | 今天成都天气怎么样 / 帮我写一首关于秋天的五言诗 / 用几句话解释什么是量子纠缠 | **无**本 CLI 调用 |

设计要点（都是实测踩出来的）：

- **题面必须无歧义**：初版写「**这本书**的评价怎么样」而每条探针跑在**全新会话**里、没有先行词 → 那是题面缺陷不是路由失败，改为指名道姓（`《白夜行》…`）；
- **需 ID 的命令要允许「两步走」**：期望写成可执行的**第一步**，备选里保留「命令对但缺 ID」的映射目标；
- **反例要覆盖三类**（应走别的工具 / 无需工具 / 应走子 Agent），防止过拟合。

### 5.3 通过标准（实施后）

- **M5a**：正例（**首调**命中）≥ 9/10、反例 3/3、首调可执行 = 10/10；断言只看调用事实（会话真值 + 审计交叉验证），**不看回答措辞**；
  实测 **10/10 + 3/3 + 可执行 10/10**（复跑 9/10），对照组（M4c 命令名形态）**2/10** —— 见 §9.7；
- **M5b**（未实施）：加压（≥8 工具）后通过率 ≥ M5a 基线，且命中形态 token 消耗 ≤ 全量形态；
- **回归**：M4c 自定义 CLI **105/105**、M4b CLI 面板 51/51、M5a 单测 43/43、M4a 前端 56/56、
  教程 35/35 + 31/31、天气 55/55 + 前端 51/51、dspro CLI 36/36（`agent_brief` 签名未变，仍须复跑）。

### 5.4 度量沉淀（已落地）

- 每次跑探针把明细写进 `data/m5_probe_result*.json`（逐条 `expect / got / tag / ok / exec_ok / self_fixed`），
  对照组写 `data/m5_probe_result_control.json`，历史轮次另存 `*_run1.json` 等；运行日志 `data/m5_probe_run*.log` 留档；
- 在本文档 §9.3 / §9.7 记「配置 → 分数」对照表，形成项目的**路由回归基线**：后续每接一个新工具跑一遍，防止能力回退。

### 9.2 实现期新增的三个设计判断

1. **能力描述允许换行、注入时压平成一行**——textarea 里分行更好写（关键词一行、映射若干行），但注入简报时用 `" ".join(text.split())` 压平，避免多行块把「- 」开头的 CLI 简报条数统计打乱。解析映射时仍按 `；/;/换行` 切段。
2. **few-shot 示例必须逐条过只读闸**——示例里的 `argv` 用 `readonly_verdict()` 复核，**指向未放行命令的映射直接丢弃**（实测：描述里写「我的划线→notes underlines」而清单只有 `notes notebooks` 时，该条被丢、同段里放行的那条照常生成）。理由：示例是「教模型怎么调」的强信号，示范一条会被拒绝的命令，等于主动把模型往拒绝上引。
3. **无 abilities = 零开销回退**——`ability_examples_block()` 返回空串、`agent_brief()` 走 M4c 形态。存量用户（如只填了清单没写描述）行为完全不变，M5 是纯增量。

> **夹具说明（B 组最终采用）**：探针可执行名改用**能真正跑通的桩**（PATH 前置一个同名 `.cmd`，输出固定 JSON）。
> 原因是实测发现「未安装」会诱发模型**重试风暴**——它会去 `ls /usr/local/bin/` 找二进制、把命令名当无参再调一次、
> 把目录名当 argv 传，单个探针被拖到 5+ 分钟且噪声调用干扰判定。装桩后单探针降到 1-2 分钟。

> 避免「挨个试一遍总能蒙对」造成指标虚高。

> **结论（可归因）**：M4c 的「命令名清单」只能让模型在**最直白的问法**（「看看我最近在读什么书」→ `shelf recent`）上想起工具；

### 9.6 关键核实：第三方 CLI 的命令**不是都能直接调用**（用户提示后核实，2026-09-13）

第三轮第 4、5 条（`book info` / `reviews list`）连续失败，用户提示「那个命令集里好像确实没有获取书本详情和书评的命令」。
直接问 CLI（`weread <cmd> --help`）核实结果：

| 命令 | 是否存在 | 参数要求（实测） |
|---|---|---|
| `search <keyword>` | ✅ | 关键词 |
| `book resolve <title>` | ✅ | 书名 → 返回候选 bookId |
| `book info <bookId>` | ✅ 存在 | **必须数字 bookId** |
| `book progress <bookId>` | ✅ 存在 | **必须数字 bookId** |
| `reviews list <bookId>` | ✅ 存在 | **必须数字 bookId** |
| `discover recommend` | ✅ | 无参（可直接调） |
| `discover similar <bookId>` | ✅ 存在 | **必须数字 bookId** |
| `shelf list` / `shelf recent` / `readdata summary` / `notes notebooks` / `doctor` | ✅ | 无参（可直接调） |

**结论：命令都存在（我们的只读清单没写错），但 4 条需要 `bookId`，而自然语言提问里只有书名**——
正确的调用是**两步**：先 `book resolve <书名>`（或从 `shelf recent` 挑一本）拿到 id，再调目标命令。
按「一次调用必须命中目标命令」判，等于要求模型在缺参数的情况下硬调一条必报错的命令，**口径错了**。

由此产生的三处修正（都影响真实使用，不只是测试）：

1. **能力描述必须写成「可执行的第一步」**：`user_clis.abilities` 里把这类场景写成两步链——
   `这本书讲什么→book resolve 再 book info`；`书评怎么样→book resolve 再 reviews list`。
   示例生成器（`_parse_ability_pairs`）取**链上第一步**作为示例命令（`book resolve`），保证示例本身可执行；
   `_PATH_SPLIT` 相应加入 `再 / 然后 / 接着` 分隔符。
2. **真实账号（微信读书，id 43）的能力描述已按此改写**，9 条映射全部通过只读闸校验（见 §9.2 第 2 条的同一机制）。
3. **探针判据改为「可执行的首选 + 备选」**，并新增**可执行性维度**（`_exec_ok`）：按命令的真实参数要求
   （需数字 bookId / 需参数 / 无参）判断这次调用**在真机上能不能跑通**，与「命令选得对不对」分开记。

**AI 草稿同样会踩这个坑（实测）**：真机跑 `POST /api/cli/ability_draft` 生成的草稿把 `book info` / `reviews list` /
`discover similar` 全写成了直调（和我最初的错一模一样——模型只看清单、不知道哪些命令需要 ID）。
已在 `ability_writer` 提示词里加规则：清单里同时存在「查找/解析类」与「详情类」命令时，详情类要写成两步链；
补规则后复验，草稿已生成 `查一本书的详情→book resolve 再 book info`（命令全部在清单内）。
即便如此，**草稿按设计只是草稿**——表单提示与教程都写明了「需要 ID 的命令要写两步链」，由人最终确认。

> 方法论收获（已写入 skill）：给第三方 CLI 写能力描述前，**先 `--help` 核实每条命令的参数要求**；
> 需要前置参数的命令，映射必须写成两步链，否则模型要么调用报错、要么绕去网搜——后者正是本次观察到的现象。

**结论**：

1. **达标**：M5a 在修正后的严格口径下正例 10/10（复现 9/10）、反例 3/3、首调 100% 可执行；
2. **可归因**：同题对照组只有 2/10，差异来自**能力描述 + few-shot 示例**（模型从「想不起来用」变成「首调就选对」）；
3. **口径修正本身也是成果**：`book resolve 先解析 ID` 这条两步式映射让「书评 / 相似推荐」从连续失败变为首调命中，
   且这条修正对**真实使用**同样生效（用户账号的 weread 能力描述已按此改写）；
4. **诚实标注两点局限**：① 桩的输出是固定 JSON，模型有时会为找「更像样的数据」多调几轮（首调判定不受影响，
   但耗时被拉长）；② 免费模型存在跑批间波动：修正口径后两次测量为 9/10 与 10/10（见上方复现性小节），
   可作为「稳定在 9~10/10」的证据，但不宜宣称「稳定 100%」。
