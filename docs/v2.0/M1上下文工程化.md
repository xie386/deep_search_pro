## 〇、本期一句话目标

**把"上下文管理"从隐式（靠 MemorySaver 内存+运气）变成显式（计数→压缩→截断 + 持久化），保证：(1) 进程重启对话不丢；(2) 永远不超模型上下文窗口；(3) 工具调用后的中间消息也能被合理管理。**

**并支持类似主流 AI 聊天应用的会话管理**：同一账号可新建多个会话、列表切换、删除，历史持久化到 SQLite（重启不丢）。

实现后 `_run_agent` 的一次调用链路会从

```python
cfg = {"configurable": {"thread_id": thread_id}}
result = agent.invoke({"messages": [HumanMessage(content=question)]}, cfg)
```

变成

```python
ctx = build_request_context(thread_id, new_user_msg)     # 装配：取历史+压缩+截断
config = {"configurable": {"thread_id": thread_id},
          "messages": ctx.messages}                       # 注入处理后的 messages
result = agent.invoke({"messages": ctx.new_turn}, config)
save_conversation_turn(thread_id, ctx, result)           # 持久化本轮
```

## 三、上下文工程化设计（核心组件）

参考 AstrBot `astrbot/core/agent/context/` 的 5 文件拆分（共 818 行），本项目按 v1.0 风格精简为单文件 `agent/context_budget.py`（预计 250-350 行）。

### 3.1 数据类（`ContextConfig`）

```python
@dataclass
class ContextConfig:
    max_context_tokens: int = 6000     # 免费模型 deepseek-v4-flash 窗口约 8K，留余量
    enforce_max_turns: int = 20       # 最多保留 20 轮用户-助手对话
    truncate_turns: int = 4           # 超限时一次性丢弃最早的 N 轮
    llm_compress_provider = None      # None=只用截断；非 None=先用 LLM 摘要再截断
    llm_compress_keep_recent_ratio: float = 0.3  # 摘要时保留 30% 最新消息原文
    llm_compress_instruction: str = "请把以下对话历史压缩成结构化摘要，保留关键事实/偏好/结论："
```

> 策略选型依据：v1.0实际是「**单用户短会话**」（平均 3-5 轮），但 v2.0 引入多会话后会出现「资深用户 50+ 轮长会话」场景——A 级默认值在「中度使用不触发任何机制」/「重度使用能优雅降级」之间取平衡。

### 3.2 四大组件

| 组件 | 责任 | API |
| --- | --- | --- |
| `TokenCounter` | 估算消息列表 token 数 | `count(messages: list[BaseMessage]) -> int`（默认 `EstimateTokenCounter`：中文 1.5 字/token、英文 0.75 词/token、含 tool_calls 字段加 50 token 保险） |
| `Truncator` | 按轮/按 token 丢弃 | `truncate_by_turns(messages, keep_recent_n) -> list` |
| `Compressor` | LLM 摘要压缩（可选） | `compress(messages, keep_recent_ratio, provider) -> list`（Protocol 接口 + `LLMSummaryCompressor` 默认实现 + `TruncateByTurnsCompressor` 兜底） |
| `ContextManager` | 编排三组件 | `async process(messages, config) -> ProcessedContext{messages, dropped_count, compressed_count}` |

### 3.3 与 LangGraph checkpointer 协同

**`MemorySaver()` 不再承载消息历史**——AstrBot 走自己的 `ConversationV2` 持久化（content JSON 存消息列表），我们 SQLite 同样存。我们的做法：

```
build_context()  装配 messages    agent.invoke(...)    save_turn()
       │                                    │                │
       ▼                                    ▼                ▼
  SQLite messages                       LangGraph 内部     SQLite messages
  （历史+N 条）                          （不存消息，         （追加本轮）
                                         只存中间 state
                                         用于断点恢复）
```

> `MemorySaver()` 保留：LangGraph 内部状态机需要它来"知道现在到图里哪个节点了"，但**消息本身走 SQLite**（v1.0 把所有东西塞进 MemorySaver 是错的，MemSaver 的 checkpoint 序列化整张图 state 极重）。
> 首次迁移的兼容期：双写（同时往 MemorySaver 和 SQLite 写），跑两周后切单写。

## 四、请求装配（`build_request_context`）

承接 v2.0 借鉴文档 §三·5️⃣ 的设计——抽独立函数，把"该账号的 SOUL + MEMORY 摘要 + 历史"在每次 invoke 前拼装，**不再靠"重建 agent"传递动态内容**。

```python
# agent/build_context.py
def build_request_context(
    thread_id: str,
    account_id: int,
    new_user_msg: str,
    base_system_prompt: str,
) -> ContextBundle:
    """请求级装配：取历史 → 压缩/截断 → 拼 system_prompt → 返回 messages。"""
    history = conversation_store.get_history(thread_id)         # 读 SQLite
    soul_text = customize.get_soul_content(account_id)          # 现成 API
    memory_text, _ = _get_memory_text(account_id)               # 现成 API
    sys_prompt = _compose_system_prompt(base_system_prompt, soul_text, memory_text)
    new_messages = [HumanMessage(content=new_user_msg)]
    processed = context_manager.process(history + new_messages, config)  # 压缩/截断
    return ContextBundle(
        messages=processed.messages,
        system_prompt=sys_prompt,
        dropped_count=processed.dropped_count,
        compressed_count=processed.compressed_count,
    )
```

`_compose_system_prompt` 直接复用 v1.0 `_get_agent_for` 里的拼接逻辑（`{soul}\n\n——\n\n{main}\n\n——\n\n【你的用户记忆画像】{memory}`）。

### 收益
- 移除 `_get_agent_for` 的"重建 agent 缓存"逻辑（v1.0 改人格/记忆就重建整个 agent，浪费）
- 动态内容（SOUL/MEMORY）和静态内容（系统提示词 base）解耦
- 自然支持多会话（每个 thread_id 独立的历史）
- `MemorySaver` 不再承担消息存储，压力骤降

### 4.5 会话管理设计（AI 聊天应用体验）

> 用户 2026-09 拍板：参照主流 AI 聊天应用「新建/列表/切换/删除会话」，全采用默认建议。

**设计决策（已确认）**：

| 决策点 | 方案 |
| --- | --- |
| `thread_id` 生成 | **UUID**（`uuid4().hex`，重启不冲突） |
| 会话标题 | 首问前 20 字自动取（`title = question[:20]`），可手动重命名 |
| 删除 | **硬删**（DELETE 级联删 messages，不可恢复） |
| 新建会话后首次发问 | 前端先 `POST /api/chat/sessions` 拿 thread_id，再带 thread_id 发问（两步） |
| 历史共享 | 按 `account_id` 共享（同账号多端登录可见同一批会话） |

**后端 API 形态**：

| 路由 | 用途 | 返回 |
| --- | --- | --- |
| `GET /api/chat/sessions?token=` | 当前账号会话列表（按 updated_at DESC） | `[{id, thread_id, title, message_count, updated_at}]` |
| `POST /api/chat/sessions?token=` | 新建空会话 | `{id, thread_id, title, created_at}` |
| `GET /api/chat/sessions/{thread_id}?token=` | 读某会话全部消息（按 turn_index ASC） | `[{role, content, ...}]` |
| `PATCH /api/chat/sessions/{thread_id}?token=` | 重命名标题 | `{ok: true}` |
| `DELETE /api/chat/sessions/{thread_id}?token=` | 删除会话（级联删 messages） | `{ok: true}` |
| `POST /api/chat`（改造） | 带 `thread_id` 参数发问（兼容旧：缺省时用「default」= v1.0 单会话行为） | 回答 + 会话已持久化 |

> 安全：所有路由按 session token 解析 `account_id`，SQLite 查询强制 `WHERE account_id=? AND thread_id=?` 防越权。

**前端交互**：

```
┌─ 左栏 ────────────────┬─ 右栏聊天区 ──────┐
│ [＋ 新对话]           │   ...messages...   │
│ ─────────────         │                    │
│ 📄 首问标题... (当前)  │   [输入框] [发送]  │
│ 📄 另一个会话...       │                    │
│ 📄 第三个...           │                    │
└───────────────────────┴────────────────────┘
```

- 「+ 新对话」→ POST 建空会话 → 自动切换（清空右栏）
- 列表项点击切换（调 GET 拉历史渲染）；当前项高亮（左边框/加粗）
- hover 列表项出「⋯」菜单：重命名（PATCH）/ 删除（confirm 弹窗后 DELETE）
- 列表项显示：title + 消息数 + updated_at（2 小时前 之类，前端格式化）
- 首屏无会话时显示「开始新对话」引导

## 五、踩坑预判（v1.0 经验 + AstrBot 设计借鉴）

| # | 风险 | 防御 |
| --- | --- | --- |
| 1 | **首次迁移丢对话历史**（MemorySaver 内存 → SQLite 持久化） | 兼容期双写两周 + 提供"导出当前会话"工具给老用户；migration 跑日志统计存量用户 |
| 2 | **token 估算偏差大**（EstimateTokenCounter 启发式 vs tiktoken 精确） | 默认走启发式（零依赖），但预留 `custom_token_counter` 钩子（v2.0 借鉴 AstrBot `ContextConfig.custom_token_counter`），后续可换 tiktoken |
| 3 | **LLM 摘要慢/超时**（Compressor 用 LLM 时阻塞 invoke） | ① 设置硬超时 15s；② 失败回退 `TruncateByTurnsCompressor`（AstrBot 同款降级）；③ 进度经 `monitor.report_thinking` 推前端（"压缩中…"） |
| 4 | **多 session 间数据混淆**（前端误传 thread_id 给另一账号） | SQLite 查询强制带 `account_id` 过滤（防越权读他人对话历史）；FK 设计上 conversations.account_id NOT NULL |
| 5 | **消息 JSON 体积膨胀**（tool_calls 数组很大） | ① SQLite 用 TEXT 存 JSON；② Compressor 优先压缩 tool 结果（AstrBot `ContextTruncator.fix_messages` 处理）；③ 定期清理 30 天前历史 |
| 6 | **LangGraph invoke 不再自动追加消息**（消息显式传入而非由 checkpointer 管理） | `save_turn` 必须在 invoke 成功后同步落库；失败重试时用 idempotency_key（turn_index 唯一） |
| 7 | **前端切换 session 时旧 WS 还在流式** | 切换/清空时主动关 WS（`/api/chat/sessions/{id}/active` POST 触发服务端通知断开） |
| 8 | **删会话后 LangGraph checkpointer 残留该 thread 状态** | DELETE 时同时清 MemorySaver 的 checkpoint（`checkpointer.delete_thread(thread_id)`）；兜底：checkpointer 只存中间态不存消息，残留仅浪费内存，不泄漏数据 |
| 9 | **多会话并发写同一账号 SQLite** | SQLite 写锁：`save_turn` 用 `INSERT OR REPLACE` + `BEGIN IMMEDIATE`；个人场景单任务串行，冲突概率极低 |

## 八、与 AstrBot 设计的具体差异（避免照搬）

| 维度 | AstrBot | 本项目 |
| --- | --- | --- |
| 用户态 | 多用户/多平台/多会话 | 单机个人/多账号/多会话 |
| 消息落库 ORM | SQLModel (Pydantic+SQLAlchemy) | 裸 sqlite3（v1.0 沿用，简单可控） |
| 压缩 Provider | 必须 LLM（默认走 LLM 摘要） | 默认 truncate，LLM 摘要可启用（个人场景 truncate 已够用） |
| 上下文管理器组件数 | 5 文件（配置/计数/截断/压缩/管理） | 1 文件（按需展开，v1.0 风格） |
| Skill 注入 | astr_main_agent 装配链 | 本项目不走 Skills（v2.0 借鉴文档 C 级，按需再加） |
| 多模态附件 | modalities 体系加工 | v1.0 不涉及，v2.0 不引入（除非业务需要） |

> **抄 A 不抄 B**：借鉴的"上下文工程化机制"是要解决你真实痛点；AstrBot 的多 IM 平台、Provider 注册制、Dashboard 都不需要。
