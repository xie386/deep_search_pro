# CLI 工具接入教程 —— 以「微信读书」为例

> **目标**：把一个装在你本机的第三方 CLI 接入「智选情报官」，让 AI 助手能**代跑其中的只读命令**（查书架、搜书、导出划线……）。
> **适用范围**：任意厂商 / 任意自研 CLI。系统**不预设厂商**——像配置模型填 base_url 一样，你填什么，它就认什么。
> **耗时**：约 5 分钟。跟着做一遍即可复现本文全部截图。

---

## 0. 三条必须先知道的规则

| # | 规则 | 为什么 |
| --- | --- | --- |
| 1 | 安装与认证命令**由你在自己的终端执行** | 项目不代跑 `npm install -g`、不代理 OAuth、不托管凭证 |
| 2 | **只读命令清单必须你给** | 哪些子命令是只读无法自动推断（`search` 是读、`config set-key` 是写、`im +messages-send` 是写），系统不猜；**清单留空 = 不放行 AI 代跑** |
| 3 | 只读清单就是**安全边界** | 这类 CLI 会读你主目录下的凭证（如 `C:\Users\<你>\.weread-cli\config.json`）。放行整个可执行文件等于把边界让给它；只放行查询命令，才能把「AI 能做什么」压到最小可用面 |

## 3.5 补上「能力描述」——让 AI 在你说人话时想起它（M5）

上面的「只读命令清单」解决的是**能不能跑**；这一步的「能力描述」解决的是**想不想得起跑**。

问题很直白：清单里写的是 `shelf recent`、`book progress` 这种**命令名**，而你提问时说「我最近在读什么书」——两个说法不在同一个语义空间，AI（尤其是免费模型）经常匹配不上，于是要么答「该功能不可用」，要么干脆凭自己的知识编。

**填法很简单**：在「🧩 自定义 CLI」表单里点 **「✨ 按只读清单生成草稿」**，AI 会按你的 CLI 名称 + 已放行命令生成一段描述；核对右侧命令是否都在清单里，改完保存即可。手写也行，格式是两行：

### 3.5.1 先选「依据从哪来」——三选一（★ 2026-10-07 新增）

草稿是 AI 写的，它得先有依据。表单里 **「能力描述的依据（三选一）」** 让你指定唯一的信息源：

| 选哪个 | 什么时候选 | 你要填 |
| --- | --- | --- |
| 🌐 **网址** | 工具有公开的 GitHub README / 文档站（最常见） | README 的网址 |
| 📁 **本机文件** | 工具是**自研的、还没上传 GitHub / 不想开源**，但仓库里有 README.md | 该文件的**绝对路径**（如 `D:\code\my-cli\README.md`） |
| 🖥 **跑一遍 `--help`** | 工具是**闭源的、公测期**，官网只有一句介绍——**`--help` 是唯一的方法信息源** | 什么都不用填，连接时项目自己跑 |

选「🖥 跑一遍 `--help`」后，点「✨ 按只读清单生成草稿」时项目会**真在本机执行**：

```text
<可执行名> --help                  ← 命令总览：子命令清单 + 一句话说明 + 用法示例
<可执行名> <只读清单里的命令> --help   ← 每条命令的参数形态（例：book info <bookId>）
```

两份输出拼成一份证据交给 AI。**这也是唯一会让你在表单里看不到"文档链接"这一栏的模式**——那时它没有意义（依据在本机，不在网上）。

> ⚠️ **它安全吗？** 这是**只读取证**：只跑 `--help`（外加 `--version`），其余命令一概不放行；`--help --output x` 这种"夹带落盘参数"的写法照旧被拒。取证走的是与 Agent 调用**完全相同**的执行器（超时、输出截断、沙箱目录、审计日志一个不少）。
>
> 💡 **这也顺带解释了 §3.5 下面那条建议**：以前要你自己去终端跑 `weread book --help` 再把输出粘进「帮助文本」；现在选「跑一遍 `--help`」就不用粘了——项目自己跑。手粘的「帮助文本」在网址 / 本机文件两种模式下仍然有用（文档没覆盖的命令以它为准）。

> 💡 **兜底**：万一某个模式取不到证据（网址打不开 / 路径写错 / CLI 没装），草稿照样会生成，只是退化成"更保守"，并在按钮下方**明确告诉你它没拿到什么**——不会假装读过。

```text
关键词：读书/阅读/看书/书架/我在读/读书进度/笔记/划线/书评/找书/想看的书。
我正在读什么书→shelf recent；读到哪了→shelf recent 再 book progress；帮我找书→search；这本书讲什么→book resolve 再 book info；书评怎么样→book resolve 再 reviews list；我的笔记与划线→notes notebooks；找相似的书→discover recommend；读书数据统计→readdata summary；我的书架→shelf list
```

> ⚠️ **关键细节：有些命令必须先解析 ID 才能调**。实测 `weread book info` / `reviews list` / `book progress` / `discover similar`
> 都**必须带一个数字 bookId**，而你提问时通常只说书名（「《白夜行》的评价怎么样」）。
> 如果映射直接写 `书评怎么样→reviews list`，AI 会拿着书名去调一条必报参数错的命令，**然后绕去网搜**——
> 看起来像“AI 不听话”，其实是映射没给可执行的路径。
>
> 正确写法是**两步链**：`书评怎么样→book resolve 再 reviews list`（`book resolve <书名>` 先拿到 ID 再调目标命令）。
> 系统抽 few-shot 示例时会取**链上第一步**（即 `book resolve`），保证示例本身是能跑通的。分隔符支持 `再 / 然后 / 接着 / 或`。
> 想知道每条命令的参数要求，在你自己的终端跑一句即可：`weread book --help`、`weread reviews --help`。

- 第一行 `关键词：` 后面写**用户可能说到的词**（路由匹配用）；
- 后面每段写「**你的口语说法 → 清单里的命令路径**」，中间用 `→` 或 `->`，多条用 `；` 分隔；
- **右侧命令必须逐字来自上面的只读清单**——写了清单外的命令，那一条示例会被系统丢弃（它不会去教 AI 调一条注定被拒绝的命令）。

保存后，卡片上会显示这段描述。它的效果是双重的：

1. AI 的上下文里，原来的「命令名清单」变成**「能力路由卡」**（用户语言 + 命令映射）；
2. 系统会从你的描述里抽出「触发语 → 命令」生成 **few-shot 对照示例**一起注入，让模型照着格式把口语翻译成调用。


> 💡 **留空会怎样？** 完全不影响使用——系统会回退成 M4c 的「命令名清单」形态，只是自然语言唤醒率偏低。M5 是**纯增量**：填了就更容易被想起，不填也不会坏。
>
> 💡 **为什么描述可以交给 AI 起草，只读清单却必须你自己填？** 两者错了的代价不同：只读清单是**安全边界**（写错了 AI 就能多跑一条你没放行的命令），能力描述只是**路由信号**（写错了最多是没被唤醒、或唤醒到别的能力上）。一个决定「能不能跑」、一个决定「想不想得起跑」——所以前者必须人给、后者可以 AI 起草 + 人确认。

## 6. 什么会被拒绝（安全边界）

| 动作 | 例子 | 结果 |
| --- | --- | --- |
| 写操作 / 未列入的子命令 | `weread config set-key HACKED` | ⛔ 不在只读清单内，拒绝 |
| 落盘参数 | `weread notes export 123 --output x.md` | ⛔ 沙箱只读，禁止落盘 |
| 清单外子命令 | `weread calendar xxx`（未登记） | ⛔ 不在只读清单内 |
| 逃生口 | `weread api call /store/search ...` | ⛔ 路径越界（不建议把 `api call` 加进清单） |
| 未登记状态 | 状态为「未接入」时 | ⛔ 命令不在白名单（放行需登记为已安装 / 已接入） |

被拒绝时，AI 会**如实转述工具返回的错误原文**（形如 `⛔ 第三方 CLI ...`），不会凭空说「我没有这个工具」。

## 7. 常见问题（FAQ）

| 现象 | 原因与处理 |
| --- | --- |
| 卡片显示「⚠ 本机未检测到」 | 可执行名写错（最常见：写成了 npm 包名 `weread-agent-cli`，应为 `weread`）；或该目录不在 PATH（装完请**重开终端**再试） |
| 清单里写了带参数的命令 | 可以整条粘贴，系统会裁成子命令路径：`weread notes export 123 --output n.md` → 存成 `notes export` |
| 想让 AI 用别的方式调用 | 一次只让它跑一条命令，并要求「必须实际执行、把输出原文贴出来」 |
| 想换 / 想撤销 | 「✏️ 编辑」改字段；「🗑 删除」立即回收 AI 的代跑权限（CLI 本身不受影响） |
| 多账号 | 配置与登记**按账号隔离**，各账号独立维护 |
| 想加别的 CLI | 重复第 2–3 步即可：任何 CLI 都是「可执行名 + 安装/认证命令 + 只读命令清单」这三件事 |

## 8. 沙箱机制与常见问题（接入必读）

CLI 面板在**沙箱**里跑命令：cwd 固定为 `data/sandbox/{用户名}/`，所有**看起来像路径的参数**都要落在沙箱内。
但**你的登录态与 CLI 配置仍然读真实用户目录**——所以「在自己终端配置一次，面板直接复用」是成立的。

> ✅ 一句话口径：**鉴权只做一次**（在你自己的 cmd / PowerShell 里），面板不需要、也不应该重新登录。

### 8.1 「路径逃逸沙箱」——命令参数指向了沙箱外的目录

**现象**：报错 `⛔ 路径逃逸沙箱：D:\appdata\...`

**原因**：沙箱 cwd 是 `data/sandbox/{用户名}/`，**参数里**出现的绝对路径会被校验，沙箱外一律拦截
（防止 `cat ../../.env`、`curl file:///C:/Users/...` 这类越界读取）。

**解法**：**初始化类命令在自己终端跑，别在面板跑**：

1. **在你自己的终端**执行初始化，例如 `wechat-cli init --db-dir D:\appdate\xwechat_files\...`——
   它会把配置写进你的**用户目录**（如 `~/.wechat-cli/config.json`）；
2. 回到面板，**直接跑查询命令**（`sessions`、`search`…）。CLI 会自动读到刚才那份配置，**无需复制、无需重新鉴权**。

> 注意：面板里不要再跑 `init`（它要写的路径在沙箱外，会被拦——这是设计使然，不是 bug）。

### 8.2 「UnicodeEncodeError / 乱码」——输出含中文或 emoji

**现象**：输出是乱码 `δ�ҵ�΢������Ŀ¼` 或报 `UnicodeEncodeError: 'gbk' codec can't encode character`

**原因**：中文 Windows 子进程默认用 GBK 写 stdout，遇到 emoji 就溢出。

**已内置修复，无需手动处理**：
- 沙箱子进程强制 `PYTHONIOENCODING=utf-8`（Python CLI 用 UTF-8 写 stdout）
- 输出解码优先 GBK、回退 UTF-8（兼容中文 Windows CLI）

**如果仍乱码**：换一种输出格式试试（很多 CLI 支持 `--format text` / `--json`），并把现象反馈给我。

### 8.3 「命令在 cmd 里能跑，面板里不行」

按这个顺序排查：

| # | 检查项 | 说明 |
|---|---|---|
| 1 | **可执行名对不对** | 面板卡片会显示「本机检测」结果；写错名字 → 「本机未检测到」。注意：**面板进程的 PATH 取自启动服务的那个终端**，若 CLI 装在刚加的目录里，请重启服务 |
| 2 | **登录态在不在用户目录** | 沙箱**继承**你的真实用户目录（`USERPROFILE` / `APPDATA` / `LOCALAPPDATA`），CLI 的凭据（如 `~/.bilibili-cli/credential.json`）会被正常读到。若面板报「未登录」而终端正常，请把 CLI 名字告诉我 |
| 3 | **是不是要写文件** | 沙箱 cwd 在项目内、且只读口径不放行落盘参数；`--output` / 下载类命令会被拒 |
| 4 | **是不是要读沙箱外的数据** | 见 8.1：初始化在自己终端做，面板只跑查询 |

### 8.4 判断命令是否适合接入

| 命令类型 | 能否接入 | 示例 |
| --- | --- | --- |
| 纯查询（读数据、返回结果） | ✅ 适合 | `sessions`、`search`、`contacts`、`bili whoami` |
| 需要一次性初始化 | ⚠️ **在自己终端做一次**，面板直接复用 | `wechat-cli init --db-dir ...`、`bili login` |
| 需要写文件（导出、下载） | ❌ 不适合（只读口径会拦落盘参数） | `export --output xxx.md` |
| 需要网络（只读 API） | ✅ 可以 | 只读接口类命令；带写操作的会被拦 |

### 8.5 接入多个 CLI 时（简报预算）

每个 CLI 的能力描述都会进 Agent 的系统提示词。项目按 **CLI 数量公平分配**展示额度：

- 3~4 个 CLI：每个都能拿到完整能力卡；
- 更多 CLI 时：靠后的会**降级成紧凑行**（仍保留名称 + 可执行名 + 命令数 + 关键词），
  **不会出现「某个 CLI 整块消失」**的情况。

> 若某个 CLI 只想让它能被路由、不需要详细说明，把「能力描述」写短一些（保留「关键词：」那一行即可）。
